# Agent edge — the public door for outside agents

## Purpose

This unit serves outside agents on `https://mcp.metorite.com` (WS-55). The spec is `project-docs/specs/external_agent_access.md`. EA-2a built the public half of the authorization server. EA-3 adds the MCP endpoint `/mcp`.

## Start

- `app._lifespan` calls `acb_auth.secret_check.check_startup_secrets("agent_edge")` (task 574, `docs/secrets_drop.md` §6). The edge needs `database_url`, and `agent_edge_signing_key` while `agent_access_enabled` is on. The check uses the rule of `agent_signing.signing_key`: 32 bytes or more, and not equal to the internal token or the LLM key. It needs no gateway secret. `SECRET_STARTUP_CHECK` in the env file of this unit sets the mode, and the default `shadow` only logs. Fence: `tests/unit/test_secret_startup_check.py`.

## Routes (EA-2a)

- `GET /.well-known/oauth-authorization-server` is the RFC 8414 document.
- `GET /.well-known/oauth-protected-resource` is the RFC 9728 document. The same document also answers at the path of the resource, `/.well-known/oauth-protected-resource/mcp`.
- `POST /oauth/token` serves `authorization_code` with PKCE S256 and `refresh_token`.
- `POST /oauth/revoke` answers 200 for an unknown token (RFC 7009).

## The MCP endpoint (EA-3b-1 and EA-3b-2)

- `POST /mcp` is the stateless MCP endpoint. `mcp.py` holds the transport and the order of the checks of spec §9.6.
- `bearer.py` reads the bearer token, looks it up, checks the audience and computes the effective scopes with `agent_oauth.effective_scopes`. ⚠️ Since EA-17c-3 a token carries every scope that the agent asked for, so no edge module reads the token scope alone. The token endpoint reads `agent_oauth.granted_scope` for its answer and for the scope check of a refresh.
- `gateway_client.py` is the only client of the gateway. It sends the four signed headers of `acb_auth.agent_signing` and no other header that it sets.
- `cursor.py` signs and reads the page cursor of a list tool. The cursor binds the tool name, so a cursor of one tool never pages another.
- `tools.py` holds the tool records and is the ONE module that maps a gateway response to a tool result (EA3-9). It holds the seven read tools of spec §9.1: `whoami`, `list_projects`, `get_project`, `list_tasks`, `get_task`, `get_task_timeline` and `search_tasks`. EA-6a adds the two write tools of spec §9.2, `set_task_status` and `add_task_reference`. Each needs `projects:write`, and branch 0 of the gateway checks the nonce, the scope, the writes flag and the cap. EA-12b adds the six agent-run tools of spec §12.1 and `agent_runs` in `get_task`. They show only while `agent_runs_enabled` is on, and the edge reads that flag through `agent_oauth.runs_enabled`. So the edge and the gateway need the same value.

## Local contract

1. **The flag.** While `agent_access_enabled` is false, every request answers 404 and does nothing else. That covers every path and every method, `OPTIONS` and `HEAD` too. The ASGI middleware `EdgeGate` in `app.py` answers first, before the router. A wrong method then cannot leak a 405 with an `Allow` header.
   **The organization allowlist (EA-10p, spec §10.6).** `agent_access_orgs` limits the flag to the organizations that it names, and the default names none. The token endpoint answers `invalid_grant` for an organization off the list, because the store refuses the issue. The bearer check of `/mcp` answers 401 with `invalid_token`. Take the rule from `agent_oauth.org_allowed`, and take the organization from the token row. `/oauth/revoke` does not check the list.
2. **No import of the gateway.** This package never imports `gateway`, and never imports `gateway.outbound_guard`. The gateway half fetches a client's metadata. The edge reads the cache in `agent_client` only.
3. **The rules live in `acb_auth`.** Take the scopes, the addresses, the PKCE check and the flag from `acb_auth.agent_oauth`. Take every token act from `acb_auth.agent_tokens`. Do not copy a rule here.
4. **The tenant comes from a token row.** No route reads an organization or a member from a header, a query or a form field. The store binds the tenant from the row it finds.
5. **No token in a URL.** `token` and `revoke` refuse any query string. Every route refuses `access_token` in the query.
6. **One error for a bad grant.** Every refused code or refresh token answers `invalid_grant`. The log names the reason, and the response does not. The code spend matches four values: the client, the redirect URI, the S256 of the verifier and the resource. A wrong presentation spends nothing.
7. **No token, code or hash goes into a log line.** Log ids and reasons only.
8. **No rate limit yet.** EA-7 owns the limits. Do not add a limiter here before EA-7. The body cap of `token` and `revoke` is `agent_oauth_max_body_bytes`. The body cap of `/mcp` is `mcp.MAX_BODY_BYTES`, which is 1 MiB. CIV-14b: one `tools/call` of `upload_task_image` may reach `mcp.MAX_UPLOAD_BODY_BYTES` (6 MiB). Such a body must declare its `Content-Length`, and any other body over 1 MiB gets 413. The token check of a large body runs before the read. Fix round 2: a large body of an organization off `MCP_IMAGE_UPLOAD_ORGS` then gets the 413 of the cap before CIV-14b, with no slot and no read. Then the body takes a slot: 4 for the edge (`mcp.LARGE_BODIES_AT_ONCE`) and 2 for each connection (`mcp.LARGE_BODIES_PER_CONNECTION`). One more gets 503. The read has `mcp.LARGE_BODY_READ_TIMEOUT_S` (408), and a count of the shape bytes runs before the parse (413). The `max_size` of `mcp.metorite.com` in the Caddyfile equals the 6 MiB cap (`test_agent_edge_deploy.py`).
9. **No control character.** A C0 control character or DEL in a form field is `invalid_request`. Postgres refuses a NUL in text, so the edge must refuse it first.
10. **The edge holds no bearer.** A gateway request carries the four signed headers and nothing else that the edge sets. In an MCP session (SW-7) it also carries the signed `X-Agent-Session`. A write (EA-6a) also carries the signed `X-Agent-Nonce`, a JSON `Content-Type` and `If-Match` when the tool sends a version. Only `gateway_client.write` sends a write, and only for a pair of `agent_oauth.MCP_WRITE_ROUTES`. There are two exceptions. `gateway_client.send_call` sends a door write of the manifests (MCP-P1a). `gateway_client.write_file` sends the one multipart write, an image to `POST /projects/tasks/{task_id}/attachments` (CIV-14b), with a form `Content-Type`. An approved door write also carries the signed `X-Agent-Approval` (MCP-P1b-2), and only `send_call` sends it. Never send an `Authorization` header or a member header to the gateway. Never copy a header of the client request into a gateway request.
11. **Keep the order of the checks.** The order of spec §9.6 is the flag, the key, the method, the origin, the body, the token, the version and the scope. Do not move a check.
   CIV-14b: a body that declares more than 1 MiB runs the token check before the read. Spec §9.6 "The body size" holds that order.
12. **An outage is a 503, never a 401.** A 401 makes a client drop a good token. `acb_common.db_busy.is_db_outage` decides.
13. **Only check 8 sends `insufficient_scope`.** A gateway 403 is a tool error with a fixed text. Never send a gateway error text to an agent.
14. **Free text is untrusted.** Each free-text value goes out as `{"untrusted_text": ...}`. A tool returns only the keys that spec §9.1 names. A value that a member writes and the gateway does not shape-check leaves as a plain string only in its shape (spec §9.1, mark (S)). Today these are `task_prefix`, `timezone`, each assignee and the `slug` of `get_company_context` (EA-5).
15. **One mapping module (EA3-9).** Only `tools.py` may hold an identity literal such as `"email"`, and only as a `.get()` argument, a subscript index or a dict-display key. `tools.py` reads no request header, query, form, cookie or path parameter, and imports nothing from `fastapi` or `starlette`. Every other edge module holds no identity literal at all. One position is exempt (EA-6e). In `prompts.py`, `"user"` may be the value of the `"role"` key of a prompt message. That value is the MCP role, not an identity. ⚠️ The AST tests of this rule are a heuristic that catches the common shapes. They miss a literal that reaches a read through a variable, such as a value from a dict key, and an attribute name that the code computes without `getattr`. The real guards are that `tools.py` receives no `Request` object and that coverage rule 4 holds.
16. **An edge input needs a spec amendment.** An input that the edge applies itself, because the route takes no such parameter, goes in the tool record's `edge_inputs`. Spec §9.5 rule 4 names each one, and `NAMED_EDGE_INPUTS` of `test_mcp_edge_coverage.py` holds the list. Four are of `list_projects`. Three more are the `idempotency_key` of `create_task` (EA-6d) and of `add_comment` (EA-6c), and the `limit` of `my_work` (EA-15b). MCP-G1 adds the `level` and the `idempotency_key` of `create_project`, and the `preview_id` of `move_tasks`. MCP-G9 adds the `idempotency_key` of `update_comment` and of `delete_comment`. WS-39 LP-1a adds the `idempotency_key` of `post_project_update`, in the slot of `add_comment`. CIV-14b adds the `idempotency_key` of `upload_task_image`, in the same slot.
17. **Redis through the tenant wrapper only (EA-6d, R5).** Only `idempotency.py` reaches Redis. It uses `acb_common.tenant_redis` and binds the organization of the token row, never a request input. A slot key holds the tool name and the SHA-256 of the agent's key (EA3-35), and no log line holds the raw key. `Slot` takes the tool as a keyword with no default. A store outage at the claim gives the busy text and no write. A call with no key touches no store. PB-4 adds one more caller, `idempotency.first_time`, for the tips of `claim_task` and `my_work`. It is a hint: a store failure shows no tip and raises no error.
18. **A write body holds only the named keys (EA-6d).** Each write tool builds its body from a fixed tuple of names (`CREATE_BODY_KEYS`, `UPDATE_BODY_KEYS`, `COMMENT_BODY_KEYS`, `COMMENT_EDIT_BODY_KEYS`), never from the whole input. The move of `update_task` sends `{parent_task_id}` only, and `set_assignees` sends `{assignees}` only (MCP-G2). The gateway refuses any other key of a signed create, PATCH or move too (`routes/projects/tasks.py`). The body model of the PUT, `AssigneesIn`, holds `assignees` only, and it ignores any other key. MCP-G1: the node writes use `PROJECT_CREATE_BODY_KEYS` and `PROJECT_UPDATE_BODY_KEYS`, and `tree.py` refuses any other key of a signed node write. WS-39 LP-1a: `post_project_update` uses `UPDATE_POST_BODY_KEYS` (`health` and `body`), and the gateway body model forbids any other key.

## Deploy

Spec §15.3 pins the deploy (EA-10). The unit is `deploy/hostinger/acb-agent-edge.service` on `127.0.0.1:8091`. It runs as a systemd `DynamicUser`, never as `acb`, so the edge cannot read a 0600 file of `acb`. systemd loads `apps/services/agent_edge/.env` as root. The process starts in the empty `/run/acb-agent-edge`, so `Settings` opens no `.env`. Never set `WorkingDirectory` to the checkout root or to this directory.
