# Apps

## Purpose
Three distinct kinds of unit, grouped by lifecycle into subfolders. The split
is load-bearing: **services** are deployed processes; **agents** and **skills**
are *loaded by* a service at runtime and are never deployed on their own.

## `services/` — deployed FastAPI processes
- gateway/ -- FastAPI entry point, AG-UI chat, agent routes, OAuth, integration credential management (DB-backed, encrypted at rest), MCP server registry, plugin registry
- orchestrator/ -- Agent execution engine, mutation layer, MAF integration
- ingestion/ -- Zoho/Gmail webhook receivers, MCP servers, the Redis-Streams producer (`queue.py`), the drain loop (`consumer.py`), and the sink registry (`event_hooks.py`). Rules below; the design record is `FOUNDATION_BUILDOUT_CHECKLIST.md` §BO-20.
  - ⚠️ **`sources/zoho/writer.py` is the only outward-WRITE client in this package, and the only Zoho write surface in the repo** (WS-26b, spec `crm_app.md` §7.1/D-CRM-7). Its sibling `client.py` stays read-only — **ten reads**: the six module readers (Accounts, Contacts, Leads, Deals, Notes, Tasks), `list_deleted`, `list_users`, and the two WS-26f settings readers (`list_deal_layouts` / `list_deal_pipelines`). The one POST is the OAuth refresh. ⚠️ **The two settings readers are the one place this module does NOT use `/crm/v2`**: `settings/pipeline` does not exist on v2, so `SETTINGS_API_VERSION` names the version ONCE and a tenant that refuses it raises `ZohoApiVersionError` — a reported outcome, never a retry ladder down the version list, because the endpoint that answers on an older version is a different endpoint with different fields. `ZohoScopeError` carries the exact scope string (`ZohoCRM.settings.{layouts,pipeline}.READ`) an owner would have to re-mint the token with; "no scope" and "no data" are different sentences and the caller prints them as such. The writer has **exactly one caller**, `gateway/routes/crm/sync_zoho.py::execute_push`, grep-asserted in `tests/unit/test_crm_zoho_sync.py`; it is deliberately dumb about authority because the Action-Broker gate lives gateway-side (ingestion cannot import the gateway, which is also why the sync LOOP is a gateway lifespan task and not a job in `ingestion/scheduler.py`). Do not import it from anywhere else, and do not add a second write client beside it — the whole path retires with WS-26e.
  - **Receivers** (both, same shape): verify the credential → log → best-effort `queue.enqueue` to their own `ingestion:*` stream (a Redis failure warns and continues — a provider webhook must never 5xx) → `BackgroundTasks`-schedule `emit_event(source, event_type, payload)`. **Never `await` the emit inline** — an emit inside the ack window turns a slow DB into provider retries. Gmail and Zoho both write an `acb_audit` row in `receive`. *(The ClickUp receiver, which audited only from a background task, was deleted 2026-08-24 — D52.)*
  - **Fail closed:** with `zoho_webhook_secret` / `gmail_pubsub_token` empty (the default, and the state of every environment) each push 401s and nothing is enqueued or emitted. Provisioning them and pointing the provider at the route is an OWNER action.
  - ⚠️ **The emit is flag-conditional** (BO-20a): each receiver calls `consumer.consumer_enabled()` per request; with `INGESTION_CONSUMER` set it **skips the inline emit entirely** and enqueues only, so the consumer is the sole caller of `emit_event` and an event fans out once, never twice (§BO-20 Q1). Flag unset (the default everywhere) = **dispatch-identical** to before, not byte-identical (one extra function-body import + one `os.environ` read per request). A failed `enqueue` while the flag is on is a **dropped event** — the accepted Q1 regression, logged at warning on `<source>.queue.dropped`. Never "fix" it by falling back to an inline emit.
  - **`(source, event_type)` is a user-visible vocabulary** (workflow event triggers match on it), prescribed in §BO-20 — do not invent strings in a PR, and coerce the provider's value to `str` before `xadd`. Zoho does; Gmail uses a constant. *(The known exception was the ClickUp receiver's bare `payload.get("event", "unknown")`; it was deleted with the receiver on 2026-08-24 — D52 — so the rule now holds everywhere.)*
  - **Never pass `event=` to a logger** — it is structlog's own message parameter and raises `TypeError` at call time. Use `zoho_event=` / `gmail_event=`. ⚠️ **The AST guard that pinned this lived in `tests/unit/test_clickup_normalise_dlq.py` and was DELETED with the ClickUp receiver (D52, 2026-08-24) — this rule is now advisory (R7) until someone re-homes the guard.**
  - **`consumer.py` — the drain side** (BO-20a, §BO-20.0 Option A): `XGROUP CREATE … cc-ingest $ MKSTREAM` per stream (`$` = tail, so the buffered backlog is skipped, never replayed) + a supervised `XREADGROUP` loop that decodes each entry, hands `(source, event_type, dict)` to `event_hooks`, then `XACK`s. Started/stopped from the gateway lifespan, gated OFF behind `INGESTION_CONSUMER`, and owns its own long-lived pooled `redis.asyncio` client (the producer's per-call sync `queue._client` is BO-9's — untouched). The dispatch is bounded by `asyncio.timeout(_DISPATCH_TIMEOUT_SECS=30.0)`: **one serial loop drains all three streams**, so an unbounded await turns one hung sink into a silent bus-wide stall. It acks **regardless of outcome** on purpose — honest ack + retry + DLQ is BO-20b, and so is the reclaim pass that recovers the batch remainder stranded in the PEL when an `XACK` raises mid-batch (the loop only ever reads `">"`).
  - **`event_hooks.py` — the sink registry** (the `post_sync.py` hook pattern): the gateway subscribes its workflow event dispatcher here, so **ingestion never imports upward**. `emit_event` takes a **keyword-only** `raise_on_error: bool = False` (BO-20b slice 1). Default = swallow the sink exception, log `event_hooks.sink_failed`, run the next sink — every receiver depends on it, because a webhook must never 5xx over a workflow sink. `raise_on_error=True` propagates the **first** sink exception and skips the rest, the only way a drain loop can observe a failed dispatch and honestly withhold the `XACK`. **Never flip the default, and keep it keyword-only:** the receivers schedule `add_task(emit_event, source, event_type, payload)` with three positional args, so keyword-only is what stops a future fourth positional from switching provider-facing behaviour on by accident.
    - ⚠️ **`raise_on_error=True` is a no-op against the only sink registered in production.** `gateway/main.py:1074` registers `workflows.triggers.dispatch_event`, whose body is entirely inside a `try/except Exception` that logs `workflows.event_dispatch_failed` and returns `[]` — nothing reaches `emit_event` to re-raise. **BO-20b slice 2 owns the matching strict path in `dispatch_event`** (propagate the DB/query failure and `RunRejected`; never the fire-and-forget per-run execution failures). Until it lands, do not build anything that assumes a strict emit can fail in production.
    - **Sinks must be idempotent per `(source, event_type, payload)`.** Strict mode stops at the first failure, so a retry re-runs every sink that already succeeded and still never runs the ones after it. Free today (one sink); it breaks silently the day a second is registered.
- customer_console/ -- **WS-31, the operator-side subscription/seat/AI-metering engine** (spec `project-docs/specs/customer_console.md`). ⚠️ **A different plane and a different database from every other service here**: it is *cross-tenant by design* (`saas_multitenancy.md` §0.9.2), so it uses its OWN engine (`customer_console/db.py`, declared in `test_db_engine_seam.py::_ALLOWED_SYNC` with its reason, R5(b)) and its OWN migration ladder `infra/customer_console/` — **never** `infra/postgres/`, which `apply_migrations.sh` replays into the *tenant* database and `gen_tenant_migration.py` scans to demand RLS. Its DSN (`CUSTOMER_CONSOLE_DATABASE_URL`) has no default, so it cannot silently reach the tenant DB. **Four** auth schemes, and which one an endpoint takes is a design statement: operator (staff, cross-org writes) / internal (the Router writes the meter) / organization key `cc_live_…` (the customer, **read-only**) / **deployment key `cc_depl_…` (one per *deployment*) — and what THAT one reaches is decided per door by its CAPABILITY SET, never by the scheme: `resolve` opens `POST /registry/resolve` (CP-2b), `provision` opens the second arm of `POST /orgs/provision` (CP-2c slice 1, 2026-08-19), `seat_admin` opens the two customer-authenticated seat WRITES `POST /registry/seats` (assign) + `POST /registry/seats/release` (§6 item (h), 2026-08-21) **and their matching READ `POST /registry/seats/overview` (CP-2h slice 1, D-SEAT-4, 2026-08-24)** — one capability, one door per plane: the read returns `SeatsView`'s grid and `MembersView`'s roster COMPOSED, never a third shape, so the deployment door and the org-key doors cannot report two answers about one org's seats (D32.5). It exists because the org-key reads `GET /me/seats` + `/me/members` cannot serve a SHARED box — a `cc_live_` key IS one organization, so N tenants have no single correct key and the customer Seats tab failed closed to "not configured for this deployment", a STRUCTURAL dark rather than a missing flag. It is a POST so the actor travels in the body exactly as the two writes send it (one R11 derivation for all three doors, `_admin_scheme_context`), and it takes the writes' `owner|admin` role gate because the Seats tab is an admin surface: "may read the roster" is the same question as "may move a seat". Fence: `tests/unit/test_customer_console_seat_overview.py` (R8). And **`member_admin` opens the member-add door `POST /registry/members` (CP-2f, D50.2, 2026-08-24)** — the ONLY membership writer besides `provision`'s founder INSERT, and therefore the reason an invited colleague reaches the registry at all (without it they are invisible to `GET /me/members`, 404 at `_seat_admin_target`, and resolve `console-empty` into the self-serve signup funnel that creates them an org of their own) — the only customer credential from which the Console can itself authorise "admin, not any member", because it resolves a MEMBER (via `store.deployment_visible_orgs`) whose `org_membership.role` it then reads; a `cc_live_` org key is *the org* with no member and reaches no seat write. All four doors are built from the one `deployment_or_operator(capability)` factory and **each closure must be registered in `AUTHENTICATING_DEPENDENCIES` separately** — the factory returns a new function per call, so a door left out of that set makes its route read as authenticating nobody. `{resolve}` is the column default and the only set anything mints by accident; a key holding it is refused at provision (or a seat write) with a **403** and the refusal is logged (`deployment_key.capability_refused`, capability + key prefix, **never the secret**). The whole route table is parametrised by `test_customer_console_resolve.py`.** The metered party never reports its own usage — that shipped once and became a credit-minting endpoint. ⚠️ **Two endpoints are opened by two schemes each — `/registry/resolve` and `POST /orgs/provision` — and in both the credential, never the body, decides**: an operator names its subject (`org_slug`, `deployment_label`) because that credential has no tenant and no deployment of its own; a deployment key naming one is **400, never ignored**, because that caller *does* have an identity from which the answer must be derived (R11). Never add a second endpoint to separate the arms — one endpoint with two schemes is the shipped decision, and a parallel route is root `CLAUDE.md` §5's defect by name. What a deployment key may see is bounded by `org_placement`, not by the organization — *placement is the boundary* — and the answer never carries `role` (registry/billing vocabulary must not cross into the tenant's permission ladder, D12). **Issuing a real `cc_depl_` key into a live deployment is OWNER-GATE** (customer_console.md §8 gate 7); there is deliberately no HTTP route that mints one. **Since CP-6 the Router rates each completion against `model_rate_card` and draws it from `credit_ledger`; the two refusals (balance gate 402, per-run circuit breaker 403) sit behind `CUSTOMER_CONSOLE_SPEND_GATE`, default OFF — flipping it for a real customer is OWNER-GATE.** Balance is `SUM(credit_ledger.delta)` and there is no balance column: `test_customer_console_credits.py::TestNoCodePathUpdatesABalanceColumn` greps the tree and fails if one is written (R7, proved by mutation). ⚠️ **`POST /orgs/provision` PLACES the organization, and it has TWO ARMS — the CREDENTIAL says which deployment, never a default and never a guess** (WS-29 MT-1j slice 4 + WS-31 CP-2c slice 1, D46.6, 2026-08-19). Until slice 4 landed nothing in the tree wrote `org_placement` while `store.deployment_visible_orgs` inner-joins it, so an org created here could never be resolved by any deployment key — fail-closed sign-in that reads as "the Console is down". The rules each have a fence in `test_customer_console_lifecycle.py` (`TestProvisioningPlacesTheOrganization` and `TestTheDeploymentKeyProvisionArm`). **Operator arm:** the operator NAMES the box (`deployment.label`, UNIQUE) because that credential is cross-org and carries no deployment identity — a missing `deployment_label` is **400** and an unknown one **404**. **Deployment-key arm** (capability `provision`): the key IS the deployment, so the box is `caller.deployment_id` and **presenting a `deployment_label` is 400, never ignored** (R11, the same rule the resolve arm applies to `org_slug`), refused on shape before the value is read so naming its own box and naming a nonexistent one are one refusal. **Nothing infers the box in either arm — a `count(deployment)=1` fallback is forbidden by name** and mutation-proved dead both ways (a fallback in `deployment_by_label`, and a working guess in the handler). ⚠️ `deployment_label` is `str | None` at the MODEL and both arms' rules live in the HANDLER — a required field cannot express "refused for this caller", which is why the operator's missing-label answer is 400 rather than pydantic's 422; do not "restore" the required field. The placement write is `ON CONFLICT (organization_id) DO NOTHING`, so **provisioning places but never MOVES** (a re-run onto the same box no-ops with `moved_at` untouched, a different target is 409 — a move is a separate operator act with its own ticket), and `database_target` is left NULL, day one every row resolving to the same target being the point of the indirection. `control_audit.actor` tells the arms apart (`deployment` vs `operator`). **Issuing or widening a REAL `cc_depl_` key is still OWNER-GATE** (§8 gate 7) — the arm is built, the act is the owner's, and there is deliberately no HTTP route that mints one. Test fixtures seed their `deployment` row through the one shared helper `tests/unit/_customer_console_ladder.py::ensure_deployment`. **CP-2f's member door (2026-08-24) needs NO migration** — `001_customer_console.sql:121-131` already CHECKs `org_membership.status IN ('invited','active','suspended','removed')`, so it took no ladder number (008 is D49's flat-plan repricing, a value change). Its write is **create-only** (`store.add_invited_member`: an existing `active` member is not demoted, a `removed` one is not resurrected) and mints **no role** — `org_membership.role` stays at the column default `member`, because mapping the tenant's `org_role` slugs onto the registry's is the second grant vocabulary D12 forbids. Its door gate is `status = 'active'`, **any role** — deliberately wider than the seat door's `owner|admin`, because a tenant's second admin is a Console `member` and an `owner|admin` gate would silently 403 their invites and re-open the funnel. Beside it, **D50.3's `invited → active` promotion** fires in the DEPLOYMENT arm of `POST /registry/resolve` only, guarded by the `AND status = 'invited'` in `store.activate_invited_member`'s own `WHERE` — never an `if`, because the natural implementation silently un-suspends people. Fences: `tests/unit/test_customer_console_member_write.py` (R8) and `tests/unit/test_invite_console_mirror.py` (DB-free).
  - ⚠️ **`customer_console/payments.py` is the ONLY path from money to entitlement (WS-31 CP-9, substrate half built 2026-08-18; migration `007_payments.sql`).** Four things about it bind anything you add nearby. **(1) Money is integer PAISE everywhere past `payments.paise()`**, the one named conversion, which *refuses a float argument* — `plan_catalog.price_inr` stays NUMERIC rupees and nothing else re-converts; a structural fence reads `information_schema` and fails on a NUMERIC/REAL money column in the payment tables. **(2) `payments.fulfil()` is the ONE writer of entitlements on the checkout path and has exactly TWO call sites** — the signature-verified webhook and SC-4g's ₹0 redemption — fenced structurally, because two implementations of "grant what was bought" is how the free path and the paid path drift into two products (D42). The ₹0 path is not a second implementation; it is this one with a different `reference`, and `test_the_free_path_and_the_paid_path_write_identical_records` allows exactly two differences (the `seat_grant.reason` prefix and `org_subscription`'s three provider columns). **(3) Duplicate-safety is TWO guards that are not the same guard**: `payment_event.provider_event_id` (PK) is *transport* dedup — the same delivery twice — while the *money* guard is the terminal-state rule on `payment_order.status`, because Razorpay sends **different event ids for one capture** (`payment.captured` and `order.paid`) and the key never sees them as duplicates. ⚠️ **Two rules ride on that guard and both were shipped wrong once (P0, repaired 2026-08-19).** *A failed payment ATTEMPT is not a failed ORDER*: one provider order accepts many attempts until one captures, so `payment.failed` is **recorded and logged and transitions nothing** — the order stays open for the retry, order-level failure is `abandoned` written by the clock, and **nothing in the tree writes `failed`** (the state stays on the graph for a surface-half customer cancel; `test_no_code_path_drives_an_order_to_failed` is the fence). Reads may precede the confirmation and do; a WRITE never may, which `tests/unit/test_crm_agent_write.py` asserts per tool. **The card must NAME the record being written to** — that is what those pre-reads buy, and it is not decoration: `log_activity` shipped a card carrying only the type, subject and body, all from the same turn of conversation, so a wrong `record_id` produced a card byte-identical to the correct call, with no delete tool to undo the note it approved. The Zoho note is the card body's FIRST line and the payload block is budgeted under it (`request_confirmation` clips `context` at 4000 chars, so appending it dropped the warning on exactly the long bodies that needed it); the wire always carries the full text. Two more surface rules: a tool takes NAMES where a person speaks names (stage, lost reason), resolves them against the CRM's own vocabulary rather than asking the model to hold a UUID, never creates vocabulary to make a call succeed, and **refuses when a name matches two rows case-insensitively** rather than taking the first (Postgres UNIQUE is case-sensitive and the Zoho importer mints unseen lanes by name, so "Closed Won"/"Closed won" can genuinely coexist); and **identity is never an argument** — `create_lead` has no `owner_email` parameter, because `create_record` defaults it to the acting user server-side. ⚠️ Per D-CRM-9 an agent write is born `zoho_dirty` exactly like a human's and queues for the live Zoho tenant when `CRM_ZOHO_SYNC` is on — that is the design, and it is why the gate is the fail-closed kind. Every tool calls the gateway's `/crm` routes with the caller's `X-User-Email` — the agent never opens a DB session, so authorization has exactly one implementation (the route's). ⚠️ **The METHOD allowlist is only half of it — the PATH is bounded too, and that half was a shipped defect.** `record_id` is an LLM-filled argument interpolated into the request path, and httpx applies RFC-3986 dot-segment removal before sending, so `get_record("deals", "../../admin/members")` issued `GET /admin/members` with the internal bearer and the caller's identity — `/admin/members`, `/email/messages` and `/memory/agent:<name>` were all reachable. `_record_uuid` now validates and **canonicalises** it (all four CRM tables key on `CAST(:id AS uuid)`, so a non-UUID id is never a legitimate call), and `_entity_slug` does the same for the entity segment. **Any new tool must route its path segments through those two and bind the results to `slug`/`record`** — `tests/unit/test_crm_agent.py::test_the_path_guard_is_structural_not_a_docstring` AST-scans every `/crm` path build — f-string, `.format()`, `%` and `+` alike, the three non-f-string idioms having been closed by WS-26d-write — and fails on an interpolation no validator produced. ## Conventions
- Each service / agent / skill has its own pyproject.toml and is a uv workspace member (`apps/services/*`, `apps/agents/*`, `apps/skills/*` — see root `pyproject.toml`)
- Moving a dir between groups means updating its `local_path` (registry + gateway `_AGENT_REGISTRY`) — Python imports are by package name and are unaffected
- Services communicate via Redis Streams (event bus)
- Gateway is the only internet-facing service
- All agents go through the unified `/agent/run/stream` endpoint (including orchestrator)
- The `/copilot/chat` endpoint in main.py is retained for backward compatibility but the workbench frontend no longer routes to it
