# Apps

## Purpose
Three distinct kinds of unit, grouped by lifecycle into subfolders. The split
is load-bearing: **services** are deployed processes; **agents** and **skills**
are *loaded by* a service at runtime and are never deployed on their own.

## `services/` — deployed FastAPI processes
- gateway/ -- FastAPI entry point, AG-UI chat, agent routes, OAuth, integration credential management (DB-backed, encrypted at rest), MCP server registry, plugin registry
- orchestrator/ -- Agent execution engine, mutation layer, MAF integration
- ingestion/ -- ClickUp/Zoho/Gmail webhook receivers, MCP servers, the Redis-Streams producer (`queue.py`), the drain loop (`consumer.py`), and the sink registry (`event_hooks.py`). Rules below; the design record is `FOUNDATION_BUILDOUT_CHECKLIST.md` §BO-20.
  - ⚠️ **`sources/zoho/writer.py` is the only outward-WRITE client in this package, and the only Zoho write surface in the repo** (WS-26b, spec `crm_app.md` §7.1/D-CRM-7). Its sibling `client.py` stays read-only — **ten reads**: the six module readers (Accounts, Contacts, Leads, Deals, Notes, Tasks), `list_deleted`, `list_users`, and the two WS-26f settings readers (`list_deal_layouts` / `list_deal_pipelines`). The one POST is the OAuth refresh. ⚠️ **The two settings readers are the one place this module does NOT use `/crm/v2`**: `settings/pipeline` does not exist on v2, so `SETTINGS_API_VERSION` names the version ONCE and a tenant that refuses it raises `ZohoApiVersionError` — a reported outcome, never a retry ladder down the version list, because the endpoint that answers on an older version is a different endpoint with different fields. `ZohoScopeError` carries the exact scope string (`ZohoCRM.settings.{layouts,pipeline}.READ`) an owner would have to re-mint the token with; "no scope" and "no data" are different sentences and the caller prints them as such. The writer has **exactly one caller**, `gateway/routes/crm/sync_zoho.py::execute_push`, grep-asserted in `tests/unit/test_crm_zoho_sync.py`; it is deliberately dumb about authority because the Action-Broker gate lives gateway-side (ingestion cannot import the gateway, which is also why the sync LOOP is a gateway lifespan task and not a job in `ingestion/scheduler.py`). Do not import it from anywhere else, and do not add a second write client beside it — the whole path retires with WS-26e.
  - **Receivers** (all three, same shape): verify the credential → log → best-effort `queue.enqueue` to their own `ingestion:*` stream (a Redis failure warns and continues — a provider webhook must never 5xx) → `BackgroundTasks`-schedule `emit_event(source, event_type, payload)`. **Never `await` the emit inline** — an emit inside the ack window turns a slow DB into provider retries. Gmail and Zoho also write an `acb_audit` row in `receive`; ClickUp audits only from its `_normalise_task` background task.
  - **Fail closed:** with `clickup_webhook_secret` / `zoho_webhook_secret` / `gmail_pubsub_token` empty (the default, and the state of every environment) each push 401s and nothing is enqueued or emitted. Provisioning them and pointing the provider at the route is an OWNER action.
  - ⚠️ **The emit is flag-conditional** (BO-20a): each receiver calls `consumer.consumer_enabled()` per request; with `INGESTION_CONSUMER` set it **skips the inline emit entirely** and enqueues only, so the consumer is the sole caller of `emit_event` and an event fans out once, never twice (§BO-20 Q1). Flag unset (the default everywhere) = **dispatch-identical** to before, not byte-identical (one extra function-body import + one `os.environ` read per request). A failed `enqueue` while the flag is on is a **dropped event** — the accepted Q1 regression, logged at warning on `<source>.queue.dropped`. Never "fix" it by falling back to an inline emit.
  - **`(source, event_type)` is a user-visible vocabulary** (workflow event triggers match on it), prescribed in §BO-20 — do not invent strings in a PR, and coerce the provider's value to `str` before `xadd`. Zoho does; Gmail uses a constant; **ClickUp is the known exception** (`clickup/webhook.py:95`, a bare `payload.get("event", "unknown")` annotated `: str`) — pre-existing; fix it in the next PR that touches that receiver, not as a drive-by.
  - **Never pass `event=` to a logger** — it is structlog's own message parameter and raises `TypeError` at call time. Use `clickup_event=` / `zoho_event=`; pinned by an AST guard in `tests/unit/test_clickup_normalise_dlq.py`.
  - **`consumer.py` — the drain side** (BO-20a, §BO-20.0 Option A): `XGROUP CREATE … cc-ingest $ MKSTREAM` per stream (`$` = tail, so the buffered backlog is skipped, never replayed) + a supervised `XREADGROUP` loop that decodes each entry, hands `(source, event_type, dict)` to `event_hooks`, then `XACK`s. Started/stopped from the gateway lifespan, gated OFF behind `INGESTION_CONSUMER`, and owns its own long-lived pooled `redis.asyncio` client (the producer's per-call sync `queue._client` is BO-9's — untouched). The dispatch is bounded by `asyncio.timeout(_DISPATCH_TIMEOUT_SECS=30.0)`: **one serial loop drains all three streams**, so an unbounded await turns one hung sink into a silent bus-wide stall. It acks **regardless of outcome** on purpose — honest ack + retry + DLQ is BO-20b, and so is the reclaim pass that recovers the batch remainder stranded in the PEL when an `XACK` raises mid-batch (the loop only ever reads `">"`).
  - **`event_hooks.py` — the sink registry** (the `post_sync.py` hook pattern): the gateway subscribes its workflow event dispatcher here, so **ingestion never imports upward**. `emit_event` takes a **keyword-only** `raise_on_error: bool = False` (BO-20b slice 1). Default = swallow the sink exception, log `event_hooks.sink_failed`, run the next sink — every receiver depends on it, because a webhook must never 5xx over a workflow sink. `raise_on_error=True` propagates the **first** sink exception and skips the rest, the only way a drain loop can observe a failed dispatch and honestly withhold the `XACK`. **Never flip the default, and keep it keyword-only:** the receivers schedule `add_task(emit_event, source, event_type, payload)` with three positional args, so keyword-only is what stops a future fourth positional from switching provider-facing behaviour on by accident.
    - ⚠️ **`raise_on_error=True` is a no-op against the only sink registered in production.** `gateway/main.py:1074` registers `workflows.triggers.dispatch_event`, whose body is entirely inside a `try/except Exception` that logs `workflows.event_dispatch_failed` and returns `[]` — nothing reaches `emit_event` to re-raise. **BO-20b slice 2 owns the matching strict path in `dispatch_event`** (propagate the DB/query failure and `RunRejected`; never the fire-and-forget per-run execution failures). Until it lands, do not build anything that assumes a strict emit can fail in production.
    - **Sinks must be idempotent per `(source, event_type, payload)`.** Strict mode stops at the first failure, so a retry re-runs every sink that already succeeded and still never runs the ones after it. Free today (one sink); it breaks silently the day a second is registered.
- customer_console/ -- **WS-31, the operator-side subscription/seat/AI-metering engine** (spec `project-docs/specs/customer_console.md`). ⚠️ **A different plane and a different database from every other service here**: it is *cross-tenant by design* (`saas_multitenancy.md` §0.9.2), so it uses its OWN engine (`customer_console/db.py`, declared in `test_db_engine_seam.py::_ALLOWED_SYNC` with its reason, R5(b)) and its OWN migration ladder `infra/customer_console/` — **never** `infra/postgres/`, which `apply_migrations.sh` replays into the *tenant* database and `gen_tenant_migration.py` scans to demand RLS. Its DSN (`CUSTOMER_CONSOLE_DATABASE_URL`) has no default, so it cannot silently reach the tenant DB. **Four** auth schemes, and which one an endpoint takes is a design statement: operator (staff, cross-org writes) / internal (the Router writes the meter) / organization key `cc_live_…` (the customer, **read-only**) / **deployment key `cc_depl_…` (CP-2b — one per *deployment*, capability set exactly `{resolve}`, reaching `POST /registry/resolve` and nothing else, parametrised over the live route table by `test_customer_console_resolve.py`)**. The metered party never reports its own usage — that shipped once and became a credit-minting endpoint. ⚠️ **`/registry/resolve` is the one endpoint two schemes open, and the credential — never the body — picks the response shape**: an operator names its customer in `org_slug` (a staff act on a named org, legal because that credential has no tenant of its own); a deployment key naming one is **400, never ignored**, because that caller *does* have an identity from which the answer must be derived (R11). What a deployment key may see is bounded by `org_placement`, not by the organization — *placement is the boundary* — and the answer never carries `role` (registry/billing vocabulary must not cross into the tenant's permission ladder, D12). **Issuing a real `cc_depl_` key into a live deployment is OWNER-GATE** (customer_console.md §8 gate 7); there is deliberately no HTTP route that mints one. **Since CP-6 the Router rates each completion against `model_rate_card` and draws it from `credit_ledger`; the two refusals (balance gate 402, per-run circuit breaker 403) sit behind `CUSTOMER_CONSOLE_SPEND_GATE`, default OFF — flipping it for a real customer is OWNER-GATE.** Balance is `SUM(credit_ledger.delta)` and there is no balance column: `test_customer_console_credits.py::TestNoCodePathUpdatesABalanceColumn` greps the tree and fails if one is written (R7, proved by mutation).
  - ⚠️ **`customer_console/payments.py` is the ONLY path from money to entitlement (WS-31 CP-9, substrate half built 2026-08-18; migration `007_payments.sql`).** Four things about it bind anything you add nearby. **(1) Money is integer PAISE everywhere past `payments.paise()`**, the one named conversion, which *refuses a float argument* — `plan_catalog.price_inr` stays NUMERIC rupees and nothing else re-converts; a structural fence reads `information_schema` and fails on a NUMERIC/REAL money column in the payment tables. **(2) `payments.fulfil()` is the ONE writer of entitlements on the checkout path and has exactly TWO call sites** — the signature-verified webhook and SC-4g's ₹0 redemption — fenced structurally, because two implementations of "grant what was bought" is how the free path and the paid path drift into two products (D42). The ₹0 path is not a second implementation; it is this one with a different `reference`, and `test_the_free_path_and_the_paid_path_write_identical_records` allows exactly two differences (the `seat_grant.reason` prefix and `org_subscription`'s three provider columns). **(3) Duplicate-safety is TWO guards that are not the same guard**: `payment_event.provider_event_id` (PK) is *transport* dedup — the same delivery twice — while the *money* guard is the terminal-state rule on `payment_order.status`, because Razorpay sends **different event ids for one capture** (`payment.captured` and `order.paid`) and the key never sees them as duplicates. ⚠️ **Two rules ride on that guard and both were shipped wrong once (P0, repaired 2026-08-19).** *A failed payment ATTEMPT is not a failed ORDER*: one provider order accepts many attempts until one captures, so `payment.failed` is **recorded and logged and transitions nothing** — the order stays open for the retry, order-level failure is `abandoned` written by the clock, and **nothing in the tree writes `failed`** (the state stays on the graph for a surface-half customer cancel; `test_no_code_path_drives_an_order_to_failed` is the fence). And *the benign no-op is scoped to `captured`*: a `TransitionRefused` from any **other** terminal state means a verified payment of the right amount arrived and nothing was granted — `payments.capture_after_terminal` at **ERROR** with the amount and both provider identifiers, never the `already_fulfilled` info line. **(4) The org key gained exactly TWO writes and neither can move value by itself** (create an intent; *present* an operator-issued code), gated on `lifecycle.can_pay` — **not** `can_use_ai`, which is false for exactly the `suspended` customer who needs to pay. `test_no_org_key_route_writes_an_entitlement_or_ledger_row` is transitive over the call graph with **one** allow-listed `(route, callee)` pair, plus **one declared, separately-fenced exemption** for CP-6's pre-existing metering draw on `/v1/chat/completions` (the exemption is a *declared deviation* awaiting owner ratification — customer_console.md §9 item 6 — not a rule an agent may extend). ⚠️ **An allow-listed pair licenses the whole SUBTREE under the callee it names** (the walk stops descending there), so `payments.fulfil`'s own reachable writer set is contents-pinned to `{activate_subscription, add_credit, grant_seats}` by `test_fulfil_reaches_exactly_the_three_named_writers`; and the walk's *depth* has its own two fences, because narrowing it to one hop once left all 105 tests green (2026-08-19 verification, F5/F7). **(5) A capture whose `order_id` matches no row here is money received with nothing granted** — not a stray row. Replacing or detaching a provider order does **not** retract it at Razorpay, so a stale payment link is payable; the `payment_event` receipt is kept with `order_id` NULL as the only record the money arrived, the webhook alerts at **ERROR** with the amount and both provider identifiers, and **CP-8's reconciliation owns those rows**. Never downgrade that line to a warning and never delete an unattributed receipt. **The shape has a twin** (2026-08-19): a capture landing on an order already `abandoned` by the TTL *does* name an order, so a query written for NULL-`order_id` rows misses it — CP-8 owns both under one description, *`payment_event` rows that fulfilled nothing*. **(6) The org key also gained one READ on the same `can_pay` door, and it mints nothing** — `GET /billing/catalog` (customer_console.md §6 item (f), built 2026-08-19; done-when 18). It answers the **active** `plan_catalog` rows as `slug · name · kind · price_paise · sort_order` and nothing else: no per-org price, no entitlement state, one denomination. The route binds its caller to `_`, so there is no organization in scope from which a per-org answer could be computed, and `active` lives in `store.active_plans`'s WHERE clause rather than in a caller — `rnd`/`support` are seeded INACTIVE because their Centers do not exist yet, and a read that leaves the filter to its caller eventually sells R&D Center. Fenced by `test_the_catalog_read_never_boards_an_inactive_row` and `test_the_catalog_read_carries_no_per_org_state_and_paise_only`. 🔴 **Creating the Razorpay account is OWNER-GATE even in TEST mode**: the seam ships dark (absent credentials ⇒ 503 at both the order route and the webhook), `FakeProvider` carries the **real** HMAC-SHA256 signer so only the network is fake, and the test-mode capture rehearsal (SC-4g clause 2) is scripted and handed over, never claimed.
  - ⚠️ **`gateway/routes/signin.py` (`POST /signin/resolve`, WS-31 CP-2b) is the ONE site in the tree that holds `CUSTOMER_CONSOLE_DEPLOYMENT_KEY` and the one caller of `acb_auth.console_resolve`.** It is reached from the workbench's NextAuth `signIn` callback through `headersActingAs()`, and it answers 200 always — the refusal is the ANSWER, carried as a code the sign-in page renders, because a 4xx would make "the Console says no" indistinguishable from "the route is broken". ⚠️ **It is NOT inert when the gateway's Console env is missing — it refuses (`ConsoleUnavailable`, logged `signin.resolve_unwired` at error), even though the module under it fails open there.** Reaching the route means the BFF's `CUSTOMER_CONSOLE_RESOLVE_ENABLED` was flipped, i.e. somebody declared this box wired; the two switches sit in different containers with different env files, so "flag on, gateway env empty" is an ordinary provisioning slip and a box that admitted there would be the fail-open posture CP-0 removed (finding F5, 2026-08-18). Ship-dark is the BFF flag, never this route. Fence: `tests/unit/test_signin_resolve_route.py`. Never add it to `PUBLIC_ROUTES`, never hang the resolve off `_with_resolved_access` (per request) or `resolve_access` (six callers, one a fan-out) — it allocates a seat, and the cap is farmable the moment there are two call sites. 🔓 Named accepted risk: a holder of the internal token ALONE can drive it for arbitrary addresses using the box's own deployment key; the gate that narrows it is the `GATEWAY_INTERNAL_TOKEN`/`LITELLM_MASTER_KEY` split, not anything in this route.
- email_ingestion/ -- Multi-provider email sync engine (Gmail, Microsoft 365, IMAP/SMTP, aiosmtpd inbound, background scheduler)
- reconciler/ -- Nightly source-of-truth diff and escalation
- action_broker/ -- Approval-gated source-of-truth write executor: authority-tier disposition + fail-closed handler registry. **Live and wired since 2026-07-13** *(corrected 2026-08-09 — this line falsely said "zero handlers, not wired" for weeks)*: handlers register at six sites (ClickUp, WhatsApp, workflow, app-publish, `crm.zoho_*`); `ACTION_BROKER_ENFORCE` ships OFF — it is set in no environment at all — so the posture is audit-and-chokepoint. **BO-1a + BO-1b landed 2026-08-11**: every gated ClickUp action name has a handler (an AST-derived test over `routes/tasks/providers.py` fails if a new one does not), and a queued push writes `sync_state='awaiting_approval'` rather than a false `'synced'`. ⚠️ **That did NOT make the flip safe, and a corrected line here said it had.** Those two closed the *handler-routing* and *sync-state* blockers; **`ACTION_BROKER_ENFORCE` stays blocked on BO-1d** — four callers of a gated write still index the pending marker as a result, so `POST /tasks/accounts/{id}/projects` (`accounts.py:335`), `POST /tasks/accounts/{id}/folders` (`:403`) and `POST /tasks/plan/apply` with `target:"clickup"` (`planning.py:377`) hard-500 under enforcement, and `items.py:790` swallows a queued update silently. The flip is OWNER-GATE regardless, and it still does **not** reconcile an approved write back onto the `gtd_items` row — see `work_plan.md` WS-1 and `FOUNDATION_BUILDOUT_CHECKLIST.md` §BO-1/BO-1d

## `agents/` — agent definitions (dynamically loaded at runtime)
Identity + system prompt + tool set + integrations. Loaded via `build_agents()`
and a `local_path` entry in `agent_registry.json` / the gateway `_AGENT_REGISTRY`.
Run *inside* the orchestrator/gateway process — no server of their own.
- agent-orchestrator/ -- Wraps the built-in orchestrator Agent so it goes through the same `/agent/run/stream` path as all other agents. Eliminates the separate `/copilot/chat` code path in the frontend.
- agent-task-manager/ -- ClickUp task management
- agent-apis-config/ -- API discovery and configuration assistant
- agent-email-assistant/ -- Email AI assistant: read, search, summarize, draft replies across Gmail and Microsoft accounts
- agent-whatsapp-assistant/ -- WhatsApp inbox briefing, triage, and reply drafting (drafts only)
- agent-crm/ -- CRM assistant (`crm-assistant`): search, pipeline, record and timeline reads over the native CRM, plus the four WS-26d-write tools (`create_lead`, `update_deal_status`, `log_activity`, `convert_lead`). ⚠️ **The directory is `agent-crm`, the agent is `crm-assistant`** — nothing derives one from the other; the `local_path` in `_AGENT_REGISTRY` is the whole mapping. **Every write asks a human first and fails CLOSED:** each write tool `await`s `acb_skills.ask_tools.request_confirmation` **before it builds a mutating request** and none passes `non_interactive_default="approve"`, so a run with no channel to deliver the card writes nothing at all. `@_annotate_risk(destructive=True)` is the other half and is **not** enforcement — `permission_policy` returns `tool_destructive_defer` precisely so the tool's own card is what gates it; annotate *and* confirm. **The METHOD allowlist survived the write half rather than being deleted with it:** `_ALLOWED_METHODS` is `{"GET", "POST", "PATCH"}`, still checked inside the single `_request` helper every tool goes through, and the absence of `DELETE`/`PUT` (and of a `_delete`/`_put` helper) is load-bearing — no tool here removes or replaces a record, so one added later that reaches for either raises instead of destroying data. Reads may precede the confirmation and do; a WRITE never may, which `tests/unit/test_crm_agent_write.py` asserts per tool. **The card must NAME the record being written to** — that is what those pre-reads buy, and it is not decoration: `log_activity` shipped a card carrying only the type, subject and body, all from the same turn of conversation, so a wrong `record_id` produced a card byte-identical to the correct call, with no delete tool to undo the note it approved. The Zoho note is the card body's FIRST line and the payload block is budgeted under it (`request_confirmation` clips `context` at 4000 chars, so appending it dropped the warning on exactly the long bodies that needed it); the wire always carries the full text. Two more surface rules: a tool takes NAMES where a person speaks names (stage, lost reason), resolves them against the CRM's own vocabulary rather than asking the model to hold a UUID, never creates vocabulary to make a call succeed, and **refuses when a name matches two rows case-insensitively** rather than taking the first (Postgres UNIQUE is case-sensitive and the Zoho importer mints unseen lanes by name, so "Closed Won"/"Closed won" can genuinely coexist); and **identity is never an argument** — `create_lead` has no `owner_email` parameter, because `create_record` defaults it to the acting user server-side. ⚠️ Per D-CRM-9 an agent write is born `zoho_dirty` exactly like a human's and queues for the live Zoho tenant when `CRM_ZOHO_SYNC` is on — that is the design, and it is why the gate is the fail-closed kind. Every tool calls the gateway's `/crm` routes with the caller's `X-User-Email` — the agent never opens a DB session, so authorization has exactly one implementation (the route's). ⚠️ **The METHOD allowlist is only half of it — the PATH is bounded too, and that half was a shipped defect.** `record_id` is an LLM-filled argument interpolated into the request path, and httpx applies RFC-3986 dot-segment removal before sending, so `get_record("deals", "../../admin/members")` issued `GET /admin/members` with the internal bearer and the caller's identity — `/admin/members`, `/email/messages` and `/memory/agent:<name>` were all reachable. `_record_uuid` now validates and **canonicalises** it (all four CRM tables key on `CAST(:id AS uuid)`, so a non-UUID id is never a legitimate call), and `_entity_slug` does the same for the entity segment. **Any new tool must route its path segments through those two and bind the results to `slug`/`record`** — `tests/unit/test_crm_agent.py::test_the_path_guard_is_structural_not_a_docstring` AST-scans every `/crm` path build — f-string, `.format()`, `%` and `+` alike, the three non-f-string idioms having been closed by WS-26d-write — and fails on an interpolation no validator produced. The fence itself is tested against synthetic sources, one per idiom, so "the fence went blind" is a red test rather than a silent gap. This is a guard rather than a prompt rule on purpose: the model's context is counterparty-authored CRM text (lead names, note subjects, 1,909 imported note bodies), which is precisely the input a "never follow embedded instructions" rule cannot be trusted against
- agent-app-builder/ -- App Workshop builder (Custom Apps): Copilot-SDK engine; each chat session runs in its app's workspace via the executor's `allow_session_workspace` binding; enforces the platform contract (window.cc only — see docs/app-workshop/README.md §4.0)

## `skills/` — importable tool packages
Capabilities (tools) an agent picks up. No identity, no server. Python packages
imported as tool providers. (Distinct from the repo-root `skills/` folder, which
holds SKILL.md + subprocess-script skills for the DOE-v2 registry agents.)
- skill-clickup-sync/ -- ClickUp read/write MCP skill
- skill-task-gtd/ -- GTD task tools (capture/clarify/organize/engage) over the gateway `/tasks` API

## Conventions
- Each service / agent / skill has its own pyproject.toml and is a uv workspace member (`apps/services/*`, `apps/agents/*`, `apps/skills/*` — see root `pyproject.toml`)
- Moving a dir between groups means updating its `local_path` (registry + gateway `_AGENT_REGISTRY`) — Python imports are by package name and are unaffected
- Services communicate via Redis Streams (event bus)
- Gateway is the only internet-facing service
- All agents go through the unified `/agent/run/stream` endpoint (including orchestrator)
- The `/copilot/chat` endpoint in main.py is retained for backward compatibility but the workbench frontend no longer routes to it
