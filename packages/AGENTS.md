# Shared Packages

## Purpose
Reusable Python packages shared across all Metorite services.

## Packages
- acb_skills/ -- Agent loading, skill management, tool injection. Org access control: `integrations.build_integrations(..., is_authorized=)` filters services the ACTING MEMBER may not use (agents declare a want, not an entitlement), and `memory_tools` gates org-scoped memory writes on `memory:write_org` via a run-scoped predicate ContextVar. Both default to unfiltered when no member is attached, so background runs are unchanged (agent_tools, web_tools, memory_tools, write_artifact, todo_tools, ask_tools, error_tools, note_tools, history_tools, github_tools, integrations, loader, registry)
- acb_llm/ -- LiteLLM integration, unified credential store (LLM + integration keys), model routing. **`key_store._resolve_org(None)` and `model_config._resolve_org(cur, None)` answer *the sole organization* and only while `count(*) FROM organization = 1`** — at org #2 every untenanted read returns nothing and every untenanted write raises. That is MT-0d's deliberate fail-closed contract and `work_plan.md` §3 (D33 finding 3) records it as one that **must NOT be "fixed"**: a default-org fallback keeps answering after tenant #2 and serves the operator's keys to a customer. The remedy is always passing `organization_id` at the CALL SITE, from the bound tenant (`acb_common.db.current_tenant`), never from request input. WS-29 MT-1j slice 5 ratchets that down; `tests/unit/test_credential_tenant_threading.py` counts the untenanted calls (parsed, not grepped), pins converted files at zero, pins the H4 leftovers at their exact count and refuses the `slug = 'default'` softening by name. ⚠️ **Only tenant-scoped methods resolve an org** (`get`/`put`/`delete`/`get_all`/`get_by_type`/`get_by_service`); `encrypt`/`decrypt` are plain Fernet over the deployment's single `ACB_MASTER_KEY` and 33 of the 48 store calls in the tree are those — reading the raw `get_key_store()` grep as the fail-closed blast radius over-states it ~3.5x. ⚠️ **`client.py` is `H4` and stays untenanted**: `_init_tier_models` runs at import and `_ensure_keys_loaded` is a once-per-process latch writing `litellm.<provider>_api_key` + `os.environ`, so per-org calls would not scope anything — and its caller, the gateway's `/v1/chat/completions`, binds no tenant. Per-tenant live credentials need a tenant-scoped API key, which is an owner gate, not a refactor
- acb_memory/ -- Mem0 and Graphiti memory providers. `compartments.py` owns the scope vocabulary (`scope_key`/`scope_kind`: a bare email, `prefs:<email>`, `room:<thread_id>`, `agent:<name>`, `org:global`) and `resolve_clearance` — WHICH compartments a run may read and the ONE it may write (spec: docs/multiplayer/memory-clearance.md §3). Solo resolves to exactly the three scopes and the write target it always had; a shared run swaps the actor's private compartment for the room's and keeps their prefs. The point is that an excluded compartment's scope key is never passed to `search()` — a boundary, not a request in a system prompt. Dependency-free on purpose: the CALLER decides `shared` (the gateway has `resolve_room_access`), which keeps acb_memory below acb_auth and the gateway in the import graph. `session_cache` keys on the clearance fingerprint as well as the thread — without it a thread cached while solo keeps serving the owner's private block after it is shared.
- acb_graph/ -- Postgres entity graph (SQLAlchemy sessions). ⚠️ **`db.py` is a SEPARATE, SYNC engine** (the async pool lives in `acb_common.db`; this one is `test_db_engine_seam.py`'s single `_ALLOWED_SYNC` entry, §0.1 connection path 4, carrying tenant data). It exposes TWO context managers: `get_session()` — **unbound, binds NO `app.tenant_id`**, kept for RLS-exempt/discovery reads and the best-effort `acb_audit` write until specific callers convert; and `tenant_session(organization_id)` (WS-29, added dark 2026-08-23) — the **sync twin of `acb_common.db.tenant_session`**: identical GUC name, the IDENTICAL `SELECT set_config('app.tenant_id', :tenant, true)` (bound param) inside an explicit `session.begin()`, and the SHARED `TenantUnbound` (imported from `acb_common.db`, never re-declared — one exception type across both engines). It is **explicit-tenant-only — NO ambient ContextVar fallback** (unlike the async seam): the sync engine serves background/service paths that must not inherit an upstream tenant (the H4 rule), so a caller passes the tenant it resolved or it refuses. `tenant_bind_enabled()` here is the **ONE reader** of `ACB_GRAPH_TENANT_BIND` (default OFF = byte-identical; flipping it on a live box is OWNER-GATE — it presumes phase-4 promotion) — later slices convert more paths behind it, so do NOT add a second reader. **First call sites converted (slice 3, dark): the orchestrator executor's four `chat_session` writes/reads** (`_store_session_id`/`_clear_stored_session_id`/`_get_stored_session_id`/`_session_workspace_override`) — flag OFF → `get_session`, flag ON + tenant → `tenant_session`, flag ON + no tenant → fail-closed skip/fallback. Fences: `tests/unit/test_acb_graph_tenant_seam.py` (R8, real non-priv `acb_app` role on the phase-4 catalog — bound write lands + is org-isolated, unbound read is 0-rows / write refused, no-org RAISES; plus a cross-engine bind-drift grep), `tests/unit/test_acb_graph_chatsession_bind.py` (R8, the executor's converted `chat_session` paths on the same catalog) and `tests/unit/test_db_engine_seam.py`
- acb_common/ -- Shared settings, logging, activity/cost feed, utilities. **`db.py` is the ONE async engine and pool for a process (BO-10)** — `get_db()` / `get_session_factory()` / `get_engine()`, cached at module level, SQLAlchemy's async stack imported INSIDE the functions so importing `acb_common` costs a process that never opens a connection nothing (`acb_common/__init__.py` deliberately does not import it). It lives here rather than in the gateway because `acb_auth.access` resolves permissions from Postgres on the request path *inside* the gateway process and cannot import `gateway` — a gateway-owned seam could never get that process below two pools. Every gateway route package re-exports from it under whatever `get_db`/`_get_db` name it has always used; `gateway/db.py` is a re-export too. The engine is **never disposed**: the pool's lifetime is the process's, and a dispose seam is a way to close connections other handlers are still using. Sized by `db_pool_size`/`db_max_overflow` (10+20), a deployment-wide number — stock Postgres allows 100 and Langfuse/LiteLLM/ingestion share the server. Adding a second `create_async_engine` anywhere under `apps/` or `packages/` fails `tests/unit/test_db_engine_seam.py`; the allowlist there is `acb_graph`'s sync engine and `email_ingestion`'s per-run engines, each with its reason. `_log.py` owns the run-correlation stamp: `_RUN_CONTEXT_KEYS` = `(run_id, thread_id, agent, user, source, instance)` — decision D1's attribution four-tuple plus the thread. Binds are **additive and non-empty-only**, so a caller may top up one field later (the executor resolves `instance` only after the agent config loads) and the shared partition `''` binds nothing rather than an empty value. `activity.py::_INHERIT` copies the same keys onto any event whose emitter omits them — which is why a model call inside a run is attributed with no change at its call site. Extend those two tuples together or attribution silently half-lands (`tests/unit/test_observability.py::test_inherit_and_run_context_keys_match` drift-fails if you don't). `instance` names the partition of the run that RESOLVED it — inheritance means a delegated sub-run carries its caller's key while writing blobs under the shared partition, so the stamp is not a join key onto `agent_blob` without knowing which run emitted it. The presence key (`cc:activity:live:{run_id}`) is written once from the `phase="start"` body, so a field resolved after start reaches `/observability/active` only via `activity.refresh_run_presence`. Spec: project-docs/specs/observability_e2.md §7. ⚠️ **`provisioning.py` (WS-29 MT-1j slice 4b) is the ONE caller-side wrapper over migration 179's `provision_organization`** — `provision_local_organization(slug, display_name=None, owner_email=None, …)`, one statement, every argument CAST, idempotent on the slug; a route that invoked the SQL directly would be a second seam. It sits beside `placement.py`, which READS the `tenant_placement` row it writes and refuses rather than guessing when it is missing. **It acquires through `get_session_factory()`, deliberately NOT `tenant_session()` and NOT `get_db()`**: it *creates* the tenant, so there is nothing to bind until after the statement (the same argument `acb_auth.console_resolve` makes for sign-in, and the same idiom), while a new `get_db()` site is red against `test_db_engine_seam.py`'s frozen H2 baseline. **Nothing calls it in production yet** — its first caller is `customer_console.md` CP-2c's signup route — and that is a stated state, not an oversight. Fences: `tests/unit/test_org_provisioning.py::TestSliceFourTheSeamCaller` (R8, through this function's own call path) and `test_deployment_resolve_cache.py`'s provisioned-slug case. ⚠️ **H6 slice 4 (D48) repair 2026-08-22: after the authoritative commit `provision_local_organization` calls `acb_auth.access.mirror_identity_membership` for the owner** (best-effort, own session, guarded by `if owner_email`), so a freshly-provisioned owner gets a `user_identity` AND their RBAC rows' `user_identity_id` bridged — else, once `IDENTITY_CUTOVER` flips the role leg onto that column, the owner resolves to NO roles (locked out; the sixth RBAC INSERT `provision_org_owner` never dual-wrote it). This is a **deliberate lazy `acb_common → acb_auth` call at the call site** (imported inside the function, never at module top): provisioning creates the tenant (`acb_common`'s job) while the identity shadow is `acb_auth`'s, and reusing the ONE identity seam is required over forking `provision_org_owner` in SQL. Fence: `tests/unit/test_h6_rbac_rekey.py` (`TestTheProvisionOwnerBridgeMechanism`, `TestTheProvisionOwnerIsBridged`). ⚠️ **Two additive CP-2e mirror-marker writes join it (WS-31)**: `persist_org_billing_profile(slug, *, gstin, billing_state)` (the signup step-1.5 GST-profile UPDATE) and `mark_console_mirrored(slug)` (the step-2.5 marker, `console_mirrored_at IS NULL` in the WHERE so it stamps once and is the SAME writer `acb_auth.console_resolve.reconcile` calls). Both go through `get_session_factory` (no new engine site) and are **best-effort — they never raise**, exactly like `console_resolve`'s projection writes: a failed marker leaves the org for the next idempotent sweep, a failed profile degrades to NULL the sweep tolerates. Columns are on the already-exempt `organization` (migration 181), so R5's source gate needs no new exemption. Fence: `tests/unit/test_signup_reconciler.py`
- acb_audit/ -- Audit event recording. `record()` logs always and DB-writes best-effort (`_persist`, which swallows its own errors — `routes/admin/members.py::purge_member` reasons explicitly about what that does and does not guarantee). The write goes through `acb_graph.get_session()`, a **sync** engine, so on an event loop `record()` hands it to `asyncio.to_thread` and returns immediately (BO-10); called from sync code, with no running loop, it still writes inline, which is what the orchestrator's agents expect. The cost is that an async caller's row is not written by the time the call returns — `await drain()` if you need it now, and the gateway lifespan awaits `drain()` last on shutdown so exiting cannot cancel an in-flight row. Pinned by `tests/unit/test_audit_non_blocking.py`. ⚠️ **`audit_event` is tenant-SCOPED (WS-29 acb_graph slice 5, dark behind `ACB_GRAPH_TENANT_BIND`, default OFF = byte-identical)**: flag ON, `_persist` opens `acb_graph.tenant_session(org)` where `org = event.organization_id OR the operator/DEFAULT org`. **The org rides ON THE `AuditEvent` object** (`organization_id: str | None`), stamped by the caller ON ITS OWN FRAME (the executor's five core-path `record` sites read `_RUN_ORG.get(thread_id)`) — NEVER read from a ContextVar inside `_persist`, which runs on the `to_thread` worker where contextvars are not reliably carried. **Owner-ratified Option-A**: unlike slices 3/4 which SKIP on no-org, a tenant-less system/cron event FALLS BACK to the operator/DEFAULT org so it is RETAINED, never RLS-dropped — `_resolve_operator_org_id()` reads the RLS-EXEMPT `organization` table for `slug = 'default'` (or the `OPERATOR_ORG_ID` env), cached module-level; a `slug = 'default'` fallback is CORRECT here (audit retention, not key service — contrast acb_llm's fail-closed rule). It skips + logs (`audit.persist_skipped_no_org`) ONLY if BOTH are unavailable (near-impossible — `default` is seeded by migration 130). The ORM INSERT names no `organization_id` (the GUC DEFAULT stamps it). The ORM `AuditEvent` model (`acb_graph.models`) is UNCHANGED — do not add the column there or SQLAlchemy would send an explicit NULL and defeat the DEFAULT. Fence: `tests/unit/test_acb_graph_audit_bind.py` (R8, reused two-org phase-4 catalog; asserts the ROW LANDED since the swallow would hide an RLS refusal; RED-on-removal demonstrated by mutation 2026-08-23).
- acb_auth/ -- Authentication, roles, and org access control. Two guard styles coexist: the original coarse `require_role(UserRole.EXECUTIVE)` (unchanged) and `require_permission("feature:whatsapp")`, backed by DB roles + per-user allow/deny overrides (`permissions.py` is pure and testable; `access.py` does the I/O with a 60s cache). `require_authenticated(public=...)` is the app-wide default-deny guard (BO-2 #1) — authentication, not authorization. **`permissions.FEATURES` is the feature vocabulary, not `feature_catalog`**: `allowed_features()` iterates that tuple and `/auth/me` returns exactly it, so a slug seeded in SQL but absent from the tuple is unreachable for every principal *including an owner holding `*`* (the wildcard is only matched against those literals). Seeding a feature_catalog row therefore always means editing `FEATURES` too — the Centers case is pinned by `tests/unit/test_org_access_control.py::test_every_center_has_a_feature_slug` (anchored on a literal, not derived from another tuple, so shortening a source cannot make it vacuous) and `::test_centers_registry_matches_the_feature_vocabulary` (parses `workbench/control_plane/src/lib/centers.ts`, the registry the UI actually renders, and pins it to `FEATURES` in both directions). Full registration checklist: `project-docs/specs/department_centers.md` §2. Two DISTINCT secrets: `GATEWAY_INTERNAL_TOKEN` is service identity (grants everything, never handed to agents) and `LITELLM_MASTER_KEY` is the /v1 API key agents hold, checked only by `require_llm_api_auth`. **The separation only exists once `GATEWAY_INTERNAL_TOKEN` is provisioned** — unset, `_get_internal_token()` falls back to the LLM key (that precedence ladder lives in exactly one place, `_resolve_internal_token() -> (token, is_fallback)`; `_get_internal_token` and `_internal_token_is_llm_fallback` are both readers of it, because a second copy that drifted would start refusing a legitimately provisioned token), and while that holds a Bearer proves nothing more than "holds the key every agent holds", so it can assert any colleague's `X-User-Email` (branch 1a) or act as the platform (1b). `GATEWAY_REFUSE_LLM_KEY_IDENTITY=1` refuses the fallback **for identity only** (`get_current_user`; the two Bearer guards keep accepting it, so a mis-provisioned box degrades to "nobody is anybody" rather than to "Bearer auth disabled"). It defaults OFF and flipping it is OWNER-GATE: the Next.js BFF mirrors the same fallback, so flipping before the token is set in BOTH `.env` and the workbench `.env.local` 401s every member. `X-User-Email`/`X-User-Role` are internal-only headers that nothing in this package can distinguish from forged ones — the boundary is the reverse proxy stripping them at the public vhost. `resolve_access(..., record_request=False)` files an unprovisioned email into `access_request` (migration 143, spec colleague_onboarding.md §6) so the owner can see who is locked out instead of the refusal dying in journald. ⚠️ **The default must stay False and `deps._with_resolved_access` must stay its only caller passing True**: `resolve_access` is NOT sign-in-only — `routes/rooms.py`, `resolve_session_access`, `routes/chat.py` and `orchestrator/executor.py` all call it over emails that are not somebody knocking, and filing those would queue people who never tried to sign in. **Do not read that list as the safety argument** — it is illustrative and has already been wrong twice. The property is "the default is `False`", enforced by `tests/unit/test_signin_requests.py`, which reads the tree and fails if a second `record_request=True` appears anywhere; a fifth caller needs no edit here. The write is best-effort (a failure changes neither the refusal nor the log line) and its volume is bounded by the same 60s cache, not the request rate. `allowed_email_domain()` / `is_company_email()` are the one **live** reader of `ALLOWED_EMAIL_DOMAIN` (`acb_common/settings.py` declares an `allowed_email_domain` field too, with the same default and zero consumers — collapse them if anything ever reads it) — a **label, not a boundary**: branch 1a only LOGS an off-domain identity, and the Entra tenant pin does not exclude these addresses either (a B2B guest IS a directory member), so the sign-in queue marks such a row `is_external` for the admin rather than pretending it cannot happen. **`console_resolve.py` (WS-31 CP-2b) is a SECOND, separate cache on a different axis and must stay one**: `access._cache` answers *what may this person do inside a tenant*, `console_resolve` answers *which tenant, and what did the registry last say about it* — D12's two axes, and one dict for both would be the second scoping doctrine root `AGENTS.md` §11 forbids (a second value type in `access._cache` would also break `_cache_get`). Three rules bind anything added beside it. **(1) It acquires through `get_session_factory()` — UNBOUND, and that is a decision, not an omission**: `auth_email_otp_token` (migration 186) is **RLS-EXEMPT** because the row is minted PRE-SESSION for an address that may belong to no organization at all (the zero-org `console-empty` signup funnel), so `tenant_session()` could only ever raise `TenantUnbound` and a tenant-scoped policy would have BRICKED email OTP the day it armed — phase-4 RLS is live in production. Its `_FACTORY_OPEN_ALLOW` entry says so, and unlike `provisioning.py`'s it is **not** a known-open brick: `test_h3_rls_promotion_rehearsal.py::TestTheEmailOtpTokenIsReachableUnbound` proves the row readable AND writable unbound as the non-privileged role on a phase-4-promoted catalog. **(2) Both limits are transactional, on the token ROW, under `pg_advisory_xact_lock` keyed on the identifier — never Redis** (the tenant Redis seam deliberately has no unbound fallback, and this row exists before any tenant does): **5 verification attempts per identifier per 10 minutes** (the budget is read BEFORE the submitted hash, so the 6th is refused *even when correct*; exhaustion invalidates the outstanding token and 429s the rest of the window) and **3 code-sends per hour**. **(3) The send count excludes the send in flight (`expires <> :expires`), but what BOUNDS mail is the atomic slot CLAIM.** The exclusion exists only so the two legs agree: `@auth/core`'s `send-token.js` starts `sendVerificationRequest` and `createVerificationToken` concurrently and hands the hash only to the second, so both call in and both must reach the same answer whichever lands first — count the row itself and the limit is nondeterministically 2 or 3. ⚠️ **Reading the exclusion as the bound was review finding P1b (2026-08-23) and it was a real bypass**: `expires` is `Date.now() + maxAge`, so two *different* sends started in the same millisecond share it, excluded each other, both passed a budget of three, and both mailed — repeatable per millisecond. `reserve_send` now CLAIMS the row (`ON CONFLICT … DO UPDATE SET reserved_at = now() WHERE reserved_at IS NULL`, migration 186's nullable `reserved_at`) and raises `SEND_DUPLICATE` when the claim finds it taken, so N simultaneous sends yield exactly ONE email. `record_token` **must not** claim — landing first is legitimate and a claim there would refuse every send whose token leg won the race. ⚠️ **The CLAIM also WRITES the hash, and `record_token` is FIRST-WRITER-WINS** (review finding P2, round 2, 2026-08-23): refusing the loser's *mail* did not stop its token leg (`send-token.js` starts both in one `Promise.all`, so a rejection cancels nothing), it landed on the shared `(identifier, expires)` row, and `_UPSERT_SQL`'s `COALESCE(EXCLUDED.token, …)` — whose docstring claimed the opposite — replaced the winner's hash, so the ONE email delivered carried a code that could never verify. `reserve_send(identifier, token, expires)` therefore takes the winner's hash (recomputed browser-side by `emailOtp.ts::otpWireHash`, because `@auth/core` hands the send leg the RAW code) and writes it **inside the statement that decides who won**, while `_UPSERT_SQL` is now `COALESCE(auth_email_otp_token.token, EXCLUDED.token)`. The property is whole-system, not per-statement: under EVERY interleaving of two same-`expires` sends the row's hash at mail time is the SLOT WINNER's — a "`record_token` must not overwrite a CLAIMED row" fix alone is NOT sufficient, because the loser's write can land before any claim exists. The two gates count different things on purpose: the send leg counts CLAIMED rows (mails), the token leg counts ROWS (so `/signin/otp/token` driven alone by an internal-token holder stays bounded). **(4) The consume takes exactly ONE row** — `UPDATE … WHERE id = (SELECT … ORDER BY created_at DESC, id DESC LIMIT 1)`. `(identifier, token)` is deliberately not unique, and the bare form matched two rows on a 6-digit collision, which `.one_or_none()` turned into `MultipleResultsFound`: a 500 on sign-in for a correct code (finding P2). ⚠️ The stored `token` is `@auth/core`'s SHA-256 of the code salted with `AUTH_SECRET`, never the six digits, so the rate limit is the WHOLE defence; and the log lines carry the address's **domain only** (this is a pre-auth path any internal-token holder can drive for an address of their choosing). Fences: `tests/unit/test_email_otp_token.py` (R8, real Postgres; the key mutations shown red 2026-08-23, including the removed slot claim, the restored bare consume, and — round 2 — `TestTheBurstsOneMailCarriesAWorkingCode`, three interleavings each asserting the WINNER's code consumes and the loser's does not, red on both the restored `COALESCE(EXCLUDED.token, …)` and the dropped claim-side `token` write) + the H3 rehearsal class above. As of the slice-4 repair (2026-08-22) it does THREE things once it ensures a human's identity: upsert `user_identity`, create-only `org_membership`, and backfill that human's existing RBAC rows' `user_identity_id` (`_bridge_rbac_to_identity` — scoped UPDATE per RBAC table via the lower(email) bridge, sets ONLY the still-NULL shadow, idempotent, moves no grant). That third step closes the RBAC-FIRST order migration 184's in-INSERT dual-write cannot reach (the provisioned/bootstrap owner, whose `user_role` is written before the identity exists).
