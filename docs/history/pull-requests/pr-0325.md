## Description

Follow-up to the first successful connected call, where nothing was audible.

## Why nothing was audible

Two separate gaps, both expected but poorly signposted:

1. **No outbound mic path** — the far end hears silence.
2. **Inbound audio goes to a WAV on the server**, not to your browser — so you hear silence too.

Neither was a failure. But there was no way to tell that apart from a genuinely broken media path, which is the real problem this fixes.

## Changes

**Prove audio arrived.** The sink now counts frames, so every call reports `audio_seconds` — how much peer audio actually landed. A call that ends with zero is logged as a warning naming the condition:

```
call <id>: ended (hangup) after 18.3s with NO audio received —
  signalling connected but no media arrived
```

A connected call that captured nothing is otherwise indistinguishable from one that worked: same phase, same recording path, no error.

**Play it back.** Ended calls with audio get an inline player in **Recent**. Ended calls without one say the recording is empty rather than offering a file that plays silence. Audio resolves through the bridge's own call registry — never a request-supplied path — so it can't be walked into an arbitrary file read.

**A dedicated Next route** (`/api/whatsapp/calls/[callId]/recording`), because the WhatsApp catch-all proxy parses every reply as JSON and would silently turn a WAV into `{}`. A more specific route wins over the catch-all.

**Say it up front.** The page now states calls are listen-only *before* the first call instead of leaving it to be discovered.
