## Description

Closes §11.2's second ClickUp-parity gap. Its complaint was one sentence: *"assignment is silent. A tool nobody hears from is a tool nobody opens."*

Migration `152_projects_notifications.sql`, `routes/projects/notifications.py`, a bell in the Projects header, and a mention picker in the comment box.

## Three rules decide who hears

Each is the whole reason for a rule:

1. **Never the actor.** A bell that pings you about your own click is a bell people mute, and a muted bell notifies nobody about anything.
2. **Never an agent.** Agents are handed work by the WS-27f dispatch sink, which starts a run; a row addressed to `agent:<name>` would sit unread forever inflating a badge nobody could clear. Enforced in Python **and** by a CHECK, because a row that reached the table another way would still be wrong.
3. **Never somebody who cannot open it.** This is the security property. The notification carries the task's **title**, so delivering one outside the project's grant closure leaks that title and lands the recipient on a 404. The comment still posts and the response names who was skipped — silently dropping a mention leaves the author believing a colleague was pulled in.

## Rule 3 needed new machinery, and the machinery is the point

`resolve_visibility` reads a `UserContext`, and the recipient of a mention has no request in flight. `resolve_visibility_for` answers for a third party by reading the same tables `/auth/me` reads and handing them to the **real** `build_access` — so wildcards (`*`, `data:*`) and allow/deny overrides resolve identically on both paths. Re-deriving that precedence in SQL is how two answers to "may they see this" start disagreeing.

## Other decisions worth reviewing

- **Written inside the transaction, not emitted on the bus.** `core.emit` swallows failures by construction so a broken workflow can never fail a task edit — right for agent dispatch, where a missed run is recoverable, and wrong here.
- **A mention is an address, not a name.** Migration 148 dropped `UNIQUE(name)` because two real people share one, so `@Priya` has no answer and guessing pings the wrong person. The picker inserts the address so nobody types it, and the browser's pattern is deliberately the gateway's — a composer that highlighted names the server ignores would promise notifications nobody receives.
- **Audience is derived (assignees + author), not subscribed.** A `pm_task_watchers` table is the fuller answer and is not this ticket — this is the set one would be seeded from, so nothing here has to be undone when it arrives.
- **Opening the bell marks nothing read.** Marking on open is how a tool loses a notification somebody glanced past.

## Also fixed

`/projects?task=<id>` did nothing. The People Center's "Open work" list has linked there since WS-28b and landed on an unchanged board, because the page never read the parameter. The bell needed the same entry point, so it is now wired.
