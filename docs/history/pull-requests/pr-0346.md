## Description

## Three live access defects, fixed

Found by a forensic audit of the multi-tenancy substrate. All three are live **at one organisation** — independent of any tenancy question.

### 1. 🔴 Notes: readable, deletable, and sendable-as by any colleague

`_LIST_SQL` had **no owner filter**, and its `query` searches `m.transcript` — so the meeting library was a **full-text search over every recorded conversation in the company**. `_load_meeting` had no predicate either, so `GET`, `PATCH`, `PUT`-scratch, attendees, speakers and the **hard DELETE** all worked on any id you could name.

**And the first attempt at the fix didn't close the worst part.** It used a sentinel actor `"auto"` so background generation could dispatch without a human in the request. That sentinel was **request-triggerable**:

> Bob holds `feature:notes` and knows the id of Alice's meeting. He `POST`s `/summarize` or `/retranscribe`. Generation **deletes Alice's existing action items**, re-creates them, then calls `auto_dispatch` — which sails past the ownership check on the strength of the string `"auto"` — and **sends an LLM-drafted email from Alice's mailbox** to a real external recipient, audited under Alice's name.

Neither gate stops it: `MIN_AUTO_CONFIDENCE` is an LLM score, not authorization, and `auto_dispatch_emails` **defaults to True** when the owner has no config row.

**The sentinel is gone.** `triggered_by` is now a **required, no-default** parameter threaded from the endpoint through `auto_dispatch` → `generate_notes` → `enqueue_summary` → `run_transcription`. A dropped argument is a `TypeError`, not a silent return to acting as anybody.

**Seven request paths reach `_dispatch`** — the review found two, the repair found five more:

| # | Path | actor | Owner-scoped at the endpoint? |
|---|---|---|---|
| 1 | `POST /notes/actions/{id}/dispatch` | `user.email` | yes (404) |
| 2 | `POST …/actions/approve-all` | `user.email` | seam only |
| 3 | `POST …/summarize` | `user.email` | **yes, new** |
| 4 | `POST …/upload` → pipeline | `user.email` | seam only |
| 5 | `POST …/recordings/{rid}/complete` | `user.email` | seam only |
| 6 | `POST …/retranscribe` | `user.email` | **yes, new** |
| 7 | `POST …/bot-join` → poller → ingest | `meeting_bot.requested_by` | seam only |

Path 7 carries **`requested_by`, not the meeting's owner** — using the owner would have laundered the requester's authority into the owner's and left the hole half-open.

`summarize` and `retranscribe` are *also* owner-scoped at the endpoint, independently of the seam, because `summaries.py:295` lets any member **destroy a colleague's action-item triage queue** whether or not anything is ever dispatched. That's data loss, not just send-as.

### 2. Identity trust — narrower than the audit claimed

**The gateway is not anonymously spoofable.** The original audit overstated this, and the correction matters: with either secret provisioned, a bare `X-User-Email` with no Bearer resolves to `NO_ACCESS`, and `require_authenticated` 401s on an empty email. There is exactly one place in the gateway or `packages/` that reads that header.

The real exposure is narrower: **`GATEWAY_INTERNAL_TOKEN` falls back to `LITELLM_MASTER_KEY`** — a key every agent holds — and that key can then assert any identity. Now refusable behind `GATEWAY_REFUSE_LLM_KEY_IDENTITY`, which **defaults to today's behaviour exactly** and is **inert** once a distinct token is provisioned (both pinned by tests that pass before *and* after).

`require_internal_auth` / `require_llm_api_auth` deliberately **still** accept the fallback. They fail open on an empty expected token, so wiring the flag through them would have turned a mis-provisioned box from *"the LLM key authenticates"* into *"everything authenticates"* — the opposite of the intent.

### 3. `resolve_room_access` failed open

One code path served both *"no session row yet"* and *"any DB error"*, returning **full owner access**. Only the error path flips. The genuinely-new-conversation case keeps its own named constructor and its own test, because every new chat passes through it. All 15 call sites were enumerated first — **none caches a denial or treats it as permanent**, and the frontend already falls back to a solo room on a failed fetch. The refusal names the outage rather than accusing the member.

### Also fixed, from review

- **The owner predicate was case-sensitive** while the dispatch check casefolded. An IdP that changes UPN casing between sessions (Entra does) would have **emptied a member's own library** and 404'd them out of their own meetings — the exact "locked out of my own work" shape this repo has been burned by. Now `lower(…) = lower(…)`, defined once in a shared predicate.
- **Four guard docstrings in `agent.py`** asserted the *opposite* of the shipped behaviour ("any DB error resolves to True", "allow on a DB hiccup so legitimate cancels never get stuck"). Those are what the next engineer reads when a ticket says "cancel 403'd during the outage" — they pointed at reverting the fix.
- **The token-fallback check re-implemented its own precedence ladder.** If the two drifted, the flag would start refusing a *legitimately provisioned* token — on a flagged box, a total member lockout. Now one resolver returning `(token, is_fallback)`.

### 🔴 Owner action — the edge protection does not exist yet

Everything here is defence in depth **behind a boundary that isn't applied**. Editing `deploy/` was correctly blocked as owner-gated. In the `api.commandcenter.fracktal.in` `reverse_proxy` block, after `header_up X-Real-IP`:

```
header_up -X-User-Email
header_up -X-User-Role
```

Strip **both** — a forged role alone still upgrades `_coerce_role`. **Apply to the API vhost only**; the UI vhost sets identity headers *after* the `extra` spread and never forwards inbound ones.

**Precondition, worth one grep before `systemctl reload caddy`:** every on-box caller must reach the gateway over loopback. Verified in-repo — `GATEWAY_URL` defaults to `127.0.0.1:8000`, browser traffic is same-origin and proxied server-side, and `GATEWAY_PUBLIC_URL` is used only for OAuth redirects and webhook URLs, never for an outbound call carrying identity headers. If one *were* pointed at the public URL, stripping would land it in `SERVICE_ACCESS` — a widening, not a lockout.

To flip `GATEWAY_REFUSE_LLM_KEY_IDENTITY` later: set `GATEWAY_INTERNAL_TOKEN` in **both** `/opt/acb/app/.env` and `workbench/control_plane/.env.local` first (the BFF mirrors the same fallback), deploy, confirm sign-in, *then* flip — at which point it is already inert, which is the proof it's safe.

### Lockout risk in these changes

- Auto-dispatch now refuses on an empty or non-owner `triggered_by` — **fails safe**: notes still generate, the item stays a draft with a retryable error.
- `summarize`/`retranscribe` now 404 for non-owners. Both are browser-only; no machine caller exists (verified).
- **Legacy `owner_email IS NULL` rows stay visible to everyone.** They predate the owner column, both insert paths sit behind `require_feature_router` so the set **cannot grow**, and excluding them would make members' own old meetings vanish.
- No new env var changes behaviour by default.
