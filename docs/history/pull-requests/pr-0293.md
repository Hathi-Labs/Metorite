## Description

BO‑2 residuals **#3** and **#4**. Fourth in the series, stacked on #291 → #290 → #286.

Both of these let a caller act as the platform, and both sit directly under the access-control work: the model in #286–#291 assumes a caller's identity means something. These two made that assumption false.

---

## 1. The LLM key *was* the identity token

`_get_internal_token()` fell back to `LITELLM_MASTER_KEY`, and the orchestrator handed agents whichever value it resolved to — **preferring `gateway_internal_token` when set**. So every agent held a credential granting `SERVICE_ACCESS`. An agent could `PUT /admin/members/{itself}/overrides` and grant itself anything, defeating the entire model the previous three PRs built.

Now two secrets with different jobs:

| Secret | Role | Checked by | Handed to agents |
|---|---|---|---|
| `GATEWAY_INTERNAL_TOKEN` | service identity → `SERVICE_ACCESS` | `require_internal_auth`, `get_current_user`'s Bearer branch | **never** |
| `LITELLM_MASTER_KEY` | the `/v1` API key | `require_llm_api_auth` (new) | yes — that is its purpose |

`/v1` accepts either, because the Next.js server and internal jobs route completions too. Everything else accepts identity only.

Every `/v1` client now reads `settings.llm_api_key`: `agents.py`, `_model_resolution.py`, `code_session.py`, `mutation.py` — which ships the value into a container as an env var, the worst possible place for a full-authority credential — and the executor's BYOK provider config. **A test asserts none of them resolves `gateway_internal_token`**, so the escalation can't come back by accident.

Callers that hit gateway *business* APIs (`skill-task-gtd`, the email/whatsapp agent repos, workspace upload) still use the identity token and are unchanged. Moving those to on-behalf-of auth is separate work.

**Upgrade path:** with `GATEWAY_INTERNAL_TOKEN` unset, identity still falls back to the LLM key so nothing 401s on deploy — but it warns on every resolution, because a silent fallback here is the vulnerability wearing a fix's clothes.

### What this does *not* fix

Agents run in-process (BO‑7), so one that reads `get_settings()` can still obtain the identity token. What's closed is the **shared-secret** exposure: the value most likely to leak outside the process — an API key, by design present in BYOK configs, provider settings and logs — is no longer an identity credential. The in-process path needs the sandbox.

---

## 2. `/agent/webhook/{source}` was unauthenticated

It dispatches an agent run with no auth and no `assert_can_run_agent` — a **fourth run path**, internet-reachable through Caddy, bypassing every gate added in #290.

Now HMAC‑SHA256 over the raw body in `X-CC-Signature`, with per-source secrets (`AGENT_WEBHOOK_SECRET_<SOURCE>`) overriding a global one, so one leaked integration can't trigger every agent. A valid signature *is* the authorization: it proves the platform's own secret produced the request, the same trust level as the internal token. There's no member to resolve — which is exactly why the signature is mandatory.

**It fails closed when unconfigured** (503, naming the variable to set), unlike the bridge and bot-token checks elsewhere that allow when unset. Those receive data; this one starts an agent run.

Safe to make strict: the audit report records that **nothing calls this path** — the provider receivers live in `ingestion/sources/*/webhook.py` and dispatch no agents — so there's no working sender to break.
