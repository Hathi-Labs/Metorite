## Description

Before answering *"will this work for the demo"*, I ran the importer against a **real Postgres**: the whole migration set applied to a scratch database, a seeded ClickUp mirror, and the actual route function. The hermetic suite was green throughout. Postgres was not.

## 1. `pm_projects` has no `clickup_snapshot` column

Only `pm_tasks` does. The insert named it, so the first real **Bring it all in** would have answered

```
UndefinedColumnError: column "clickup_snapshot" of relation "pm_projects" does not exist
```

and rolled back. **This shipped in #393.** A fake DB accepts any column — precisely the class of defect it cannot see.

## 2. `gtd_projects.space_id` is LOCAL-only

Migration 60 says so in its own header: synced projects mirror the provider's hierarchy via the account's schema cache and leave the column NULL. So *"each project remembers which Space it came from"* — in the docstring, the commit message, the PR body and what I told the owner — **was never true**. It would have written `{"space_id": null}` every time.

The Space and Folder live in `task_accounts.schema_cache->'hierarchy'`. The importer now reads them and rebuilds the real shape: **Space → Folder → List**, each a project with its own `clickup_id` and `clickup_kind`. Same flattening `import_clickup` performs, so both paths produce one shape — and the tree itself records the placement, which is better than a JSON blob and makes promoting a Space node genuinely how the department split happens.

## 3. The preview under-counted

It reported **4** projects where the run then created **7**, because Space and Folder nodes were only tallied on the write path. A number somebody would have read out loud during a demo.
