### 🔴 The finding that justifies the whole ticket

**Any colleague on the default `member` role can read your entire HR directory, and write
to it.**

`routes/tasks/people.py:22` imports the **feature-gated** `/tasks` router
(`tasks/core.py:27-30`) and adds no scoping of its own:

| Route | Line | Scoping |
|---|---|---|
| `GET /people` | `:80-84` | takes `_user` and **never uses it**; `SELECT * FROM gtd_people` at `:98` |
| `POST /people` | `:190` | `user` only for `_uid()` attribution |
| `PATCH /people/{person_id}` | `:241` | same |
| `POST /people/{person_id}/resume` | `:303` | same |
| `POST /people/embed` | `capability.py:225` | same |

`member` holds `feature:tasks` (`130:235`). So every colleague could read every person's
name, email, title, department, manager, skills **including résumé-extracted ones**,
capacity and ClickUp id — and add a person, edit anybody's record, or upload a résumé onto
it.

This is HR data, and it is exactly the surface D12's department privacy exists to protect.
`tasks/accounts.py` **is** scoped (`_assert_account_owner` at `:190, 259, 285, 325, 406`),
so the gap is specific to the people layer, not a blanket one.

Filed as blocking item **N4**. **Not fixed here** — this ticket is the gate; N4 is work it
schedules.

It hid behind the same feature flag as the task list, which is why every prior summary of
"what can a member see" answered for `gtd_items` and stopped. Mine included.

and its own remediation said *"restart the gateway and the workbench"*, not *"redeploy"*.

### Three designs that change meaning with a second person

Confirmed directly, all deliberate, none a bug — but all consequential now:

1. **Any `member` can read *and write* every agent's memory compartment.**
   `routes/memory.py::_authorize_agent` (`:103-109`) gates on `can_run_agent`;
   `_authorize_scope` (`:128-167`) calls it without passing `write`; `member` holds
   `agents:run:*`. The docstring says shared-by-design — coherent for one user, a shared
   space for a team.
2. **4 of 6 first-party agents declare `instancing: "shared"`** (orchestrator, task-manager,
   app-builder, apis-config) → `instance_key()` returns `''` (`manifest.py:235-246`) → one
   common artifact workspace, not per-user.
3. **`data:org:read` has zero consumers.** Declared (`permissions.py:132`), granted
   (`130:205,221,258`), listed (`access.py:148`), read by nothing. **So my earlier warning
   that `manager` "sees org-wide data" was wrong.** Manager's real breadth is
   `admin:members:read` — the auth floor for the *entire* `/admin` package
   (`admin/_common.py:77-91`) — plus approvals, observability, WhatsApp and
   `memory:write_org`. Minted as **D14** (`agent-proposed, owner may overrule`).
