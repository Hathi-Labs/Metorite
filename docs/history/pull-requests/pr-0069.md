## 1. The real output ceiling was 4096

`/v1` is the choke point every agent runtime POSTs through, so its `max_tokens` default **is** the platform's output cap whenever the caller omits the field — and the Copilot SDK **always** omits it: its wire protocol has no `max_tokens` field at all, so `COPILOT_MAX_OUTPUT_TOKENS` and the SessionConfig `max_tokens` never reach us. (Both are dead knobs; the one in prod `.env` is a no-op and should be removed.)

So every Copilot agent was capped at **4096 output tokens**. That's what truncated long tool-call arguments mid-JSON: the model emits a large file's content as a tool argument, gets cut at 4096, and the malformed JSON fails the call — `Unterminated string in JSON at position 16340` (÷4 ≈ 4096 tokens, exactly).

Measured on the live gateway (deepseek-v4-pro):

| request | result |
|---|---|
| no `max_tokens` | `completion_tokens=4096`, `finish_reason="length"` — **cut off** |
| `max_tokens=32000` | `completion_tokens=10940`, `finish_reason="stop"` — **finished** |

`max_tokens` is a *ceiling*, not a target — the model stops when it's done (the `stop` above proves it), so a generous default costs nothing and only removes an artificial cut. Verified accepted by the whole active fleet.

## 2. The clamp — but only against a cap we vouch for

The generous default cuts both ways: a model that caps below 32000 answers an over-large `max_tokens` with a **400** — a total failure, worse than the truncation the default exists to prevent. Nothing in the fleet does that today (all deepseek), which is exactly why the ceiling could be raised safely. `_clamp_max_tokens` keeps it true when a smaller model is added: **gpt-4o now gets 16384 instead of a 400**.

Only a limit we **vouch for** may lower the ceiling — a curated entry or an explicit env override. litellm's registry is excluded **on purpose**: it claims deepseek-v4-pro caps at 8192 while the live model emits 10940, so clamping to it would re-create the exact bug this default was raised to fix. Believing a guess is what broke this in the first place; an unvetted model keeps the generous ceiling. A resolver failure never blocks a call — the lookup is an optimisation, not a gate on inference.

## 3. Infinite-sessions policy survived nothing

The `_apply_copilot_infinite_sessions` wrap was installed at `_inject_agent_tools` and then **thrown away** by `executor.py:2361` rebinding `_create_session`. So BYOK compaction ran against the wrong (~90K) window on the streaming path. The old tests passed because they exercised the wrap in isolation — never through the rebind.

The policy is now extracted to `effective_infinite_sessions` and applied inside `CommandCenterCopilotAgent._create_session` / `._resume_session`, so it survives the rebind by construction. The new tests fail against the old code; all 14 original tests still pass.
