## Description

Closes the open item WS-18 recorded when Waiting-For shipped.

## The diagnosis

`gtd_waiting.expected_by` was a **derived copy**. Four insert sites snapshotted a due date into it and nothing ever updated it, so a renegotiated deadline left the Overdue badge judging against a dead date — wrong in both directions.

The recorded options were "add an updater" or "make it editable". Neither is the real fix: **the copy itself was the bug.** It isn't really *the date I asked them for* — nobody was asked, it was inferred — and storing an inference that then rots is the worst of both worlds.

## The semantics

| value | meaning |
|---|---|
| `NULL` | No explicit promise. The overdue line is the item's own `due_at`, read **live**. Nothing is copied, so nothing can go stale. |
| non-`NULL` | Someone actually promised this date. It stands on its own, deliberately independent of `due_at`. |

This keeps the two-facts distinction `lib/waiting.ts` documents, while making the common case self-correcting — no updater, no trigger, no sync logic to maintain.

## What changed

- **All four insert sites stop writing it** (delegate, clarify-delegate, email capture ×2, ClickUp sync). Each was verified individually: every one was writing *the item's own due date under another name* — the same variable stored to `gtd_items.due_at` in the same transaction. None was a distinct fact. The sync case is the clearest — the provider field **is** the task's due date, and the copy could never follow an upstream reschedule.
- **One writer remains:** `PATCH /tasks/items/{id}` carrying `expected_by` (ISO sets, empty string clears), updating the open `gtd_waiting` row under a re-stated ownership `EXISTS`. This fit the existing item-PATCH seam — same auth, same `_parse_ts` convention, no new endpoint invented.
- **Read-time fallback:** the client judges `expectedBy ?? dueAt`. A new pure `waitingLine()` lets the row say *which* fact it is showing — a bare date previously meant two different things.
- **UI:** `ItemDetail` gains a "Promised by" field in the Waiting-on section, same input+clear pattern as Due. Empty reads `not promised — judged on due <date>`.

## Migration and existing data

**No migration and no backfill.** Rows delegated between the last deploy and this change carry a snapshot `expected_by`; they keep it and stay judged on it, which is exactly what the new rule says a stored value means. Clearing one is a normal edit.
