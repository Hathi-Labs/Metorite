## Description

docs(D28 fix): "silo" is placement, not architecture — we are multi-tenant from customer #1

The doctrine's ring paragraph said "during the silo phase (customers 1-5)"
without qualifying it, which reads as though multi-tenancy is deferred until the
pooled cutover. It is not. §5.1 condition 2 requires every silo to run the pooled
schema with organization_id populated and RLS enabled from day one — a silo is a
pooled deployment with N=1, and cutover is a data move rather than a migration.
Skipping that is precisely what turns the bridge into a rewrite. D15 demoted the
deployment from "the tenant boundary" to "a placement, a priced tier", and R5
binds every PR regardless of customer count. There is no phase in which
single-tenant code is acceptable; what changes at the 8-12 cutover is only N.

Consequence made explicit in §8: promoting the RLS set is a HARD GATE for
customer #1, not a nice-to-have — "the policies are still un-promoted" and "we
have a paying customer" cannot both be true.

Caught by the owner reading the doctrine, which is the review the doc wanted.
