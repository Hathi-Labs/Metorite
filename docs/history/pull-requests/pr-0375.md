## Description

**Found by watching the first live sync cycles**, minutes after `CRM_ZOHO_SYNC` was enabled on prod. Every module converged to pulling 1–2 changed records per cycle. `Deals` pulled all 551, every cycle, and would have done so forever.

## Root cause

Zoho returns **no `Modified_Time` for any module on this tenant**. Leads, Accounts, Contacts and Notes survive on `modified_time()`'s `Created_Time` fallback. `Deals` has neither — 0 of 551 parse, and naming the fields in `fields=` returns them empty, so it is a per-module field permission on the tenant, not our query.

That left `advance_cursor` unable to distinguish two very different situations, because both produce `newest_applied is None`:

- nothing landed (must stand still, or a failed record is never offered again), and
- **everything landed, but Zoho gave us no timestamp to cursor on**.

It correctly chose the conservative reading, so the `Deals` watermark stayed NULL, `If-Modified-Since` stayed empty, and the pull never converged — ~79k redundant record-applies a day against the API and the DB.

## The fix

`advance_cursor` now takes the applied count. Everything applied + zero failures + no readable timestamp → adopt the cycle's start. The safety argument is the existing "nothing fetched" branch's, verbatim: every record Zoho returned for this window applied cleanly, so everything up to the cycle's start *is* reconciled — the missing timestamps are Zoho's, not evidence of unfinished work. **Any failure still stands still**, because a failure we cannot place in time must be re-read.

## What is deliberately NOT fixed

**LWW for deals stays one-sided.** With no Zoho timestamp, `_zoho_changed_since_agreement` reads "changed" and `_later` reads "not later", so a dirty deal always resolves **native-wins**. That is the recoverable direction the helper's own docstring argues for — the other silently discards a colleague's typing. `Last_Activity_Time` and `Stage_Modified_Time` *are* returned for deals, but neither means "last modified", and substituting a semantically-wrong field would flip conflicts toward the unrecoverable side. Documented in spec §7.1 rather than papered over.
