## Description

Mints **WS-27** — native org-level project management in the People Center, sliced into every other Center — and builds its first two tickets.

## What this is for

The company's work lives in ClickUp; CommandCenter's `/tasks` is a *personal* GTD lens over it. This adds the missing middle: departments → projects → subprojects → tasks → subtasks, owned natively, with each Center seeing its own slice and every member's assigned work still reaching their personal inbox.

## The decisions, and what changed after owner review

Three questions were opened for the owner and answered as **D-PM-8/9/10**; two changed the build:

- **D-PM-8** — no portfolio/program layer. Grants are the only grouping axis; a cross-department project simply carries several.
- **D-PM-9** — agent edits to ClickUp-linked tasks are treated **exactly like human edits** (*the agent proposed queueing agent-originated pushes for approval and was overruled*). The accepted cost is stated once in the spec: while `ACTION_BROKER_ENFORCE` is off, a mistaken agent edit reaches the live workspace with no human in between. The three properties that bound it — attribution, timeline-reversibility, and the enforce flip — are labelled as **not** being a gate, so a later reader can't quote them as if the risk were handled.
- **D-PM-10** — ClickUp Spaces map to Centers **explicitly**, from agent-proposed suggestions, owner-confirmed, applied as `group:<slug>` grants. This one grew a whole endpoint (below).

## WS-27a — schema and the grant read model

**Migration `146_projects.sql`**, eleven tables. The whole hierarchy is two self-referencing foreign keys (`pm_projects.parent_project_id`, `pm_tasks.parent_task_id`) with types-as-data — no table per level, no depth column. Statuses are per-project rows with a semantic `category`, so the importer can represent ClickUp's real status names. **No rank column on tasks**: ordering lives in `pm_view_task_positions` as fractional indexes, which is what lets the People Center board and a Center slice order the same task differently.

**`routes/projects/`** — behind `feature:projects`, consuming the shared `gateway/db.py` seam rather than adding engine thirteen (BO-10), asserted by grep in the suite.

Two rules that had to live in code rather than schema:

- **A task assigned to you is visible even when its project is not.** Delegation across a Center boundary is normal work; without it the task 404s for the person expected to do it.
- **One status transition, three effects** — status, `completed_at` stamped *or cleared* on the done boundary, and a timeline entry. A PATCH that writes only the column looks correct in the UI while silently emptying the timeline.

### Visibility is a data boundary here, not a nav one

Unlike `/crm` (D-CRM-3, org-visible by decision), a project is visible only when a grant on it *or an ancestor* matches the caller. `pm_project_grants` speaks exactly the shipped `email | group:<slug> | org` vocabulary — a second one would mean two answers to "who can see this". Non-visible is **404, never 403**.

The full-portfolio read requires **`data:org:read`**, which D14 measured at **zero consumers**; this is deliberately its first, which is why granting it is now registered as an owner gate.

## WS-27b — the ClickUp importer, and a mapping the owner confirms

Two endpoints, because D-PM-10 makes the mapping the owner's act. `POST /projects/import/clickup/plan` proposes a Center per Space and **writes nothing**; `POST /projects/import/clickup` applies only what came back in `mappings`. **An agent may propose a mapping and must never apply one** — a wrong auto-map grants one Center visibility of another department's work. The plan's claim is asserted against the session (no INSERT reaches it, nothing commits), not against the response, because a plan that quietly created projects would look identical from the outside.

Three signals, cheapest first: **assignee overlap** against `org_group` membership (deterministic, no LLM, and the strongest signal the platform already holds — who does the work is what a department is); a **name match** where a whole word beats a substring accident; and an **EVAL-LOCKED** title classification. Every signal that fired returns as evidence, because a confidence with nothing behind it is a number the owner cannot check. Below a floor it proposes nothing — a weak guess presented as a suggestion means reviewing our noise instead of deciding — and still returns the scores, so a blank suggestion is distinguishable from a signal failure. The classifier degrades to no-signal on any failure and the plan still arrives.

**An unmapped Space still imports in full** with no group grant, staying reachable for `data:org:read` holders and its assignees; refusing would make the mapping a precondition of seeing the data needed to decide it. Unmapped Spaces are **named**, not counted.

ClickUp's Space/Folder/List zoo flattens onto the one `pm_projects` self-FK, with `clickup_kind` remembering which was which. Re-import is keyed on `clickup_id`. Reuses the Tasks app's `ClickUpProvider` rather than adding a second ClickUp client — one less thing to retire at WS-27g — and makes two API calls regardless of Space count. Floor is `admin:access:manage`, **not** `integrations:use:clickup` (migration 131 grants `member` `integrations:use:*`, so that slug gates nothing — the WS-26b finding, applying unchanged).
