## Description

## The problem

"How big is this model?" had **five answers**. For `deepseek/deepseek-v4-pro` alone the codebase held five context-window values (`0 / 262144 / 840000 / 1000000`) and four max-output values (`0 / 8192 / 32768 / 384000`). Which one you got depended on which file happened to ask.

The worst part: the **curated table with the accurate numbers was only ever read by the Settings UI**. The runtime that actually budgets prompts couldn't reach it, so it asked litellm — which is provably stale for this fleet.

Everything now resolves through **`acb_llm.model_limits.get_limits`**, returning `{context_window, max_output}` plus the provenance of each number.

## Opposite rules for opposite failures

The two fields fail in opposite directions, so they resolve by opposite rules. This is deliberate, not an inconsistency:

| field | rule | why |
|---|---|---|
| `context_window` | **conservative** — lowest positive value any trusted source reports | Over-claiming is unrecoverable: the provider hard-rejects, and `acompletion_with_fallback` answers by switching *model* rather than re-fitting — and agent runs never touch that path. Under-claiming just trims sooner. |
| `max_output` | **trust order, curated first** | litellm claims v4-pro maxes at 8192 output tokens. The live model emits **10940**. Believing litellm is what truncated a tool call's JSON args mid-string and produced *"the agent produced no text output"*. |

## Also fixed

- **A guess, laundered into a fact.** `ensure_model_registered` invented `max_input_tokens: 262144` for any model litellm didn't know, wrote it into `model_cost`, and then `context_window_for` read it straight back *as though litellm had said it* — outranking the real fallback table. Routing stays; `STUB_MARKER` means the numbers are no longer believed. (`client.py` already did exactly this for the stub `$0` price via `_DYNAMIC_STUB_PRICED_MODELS` — the token counts just never got the same treatment.)
- **A pin that overwrote the truth.** `settings.py` hardcoded tier windows "matching config.yaml". They drifted — `tier_overrides.yaml` re-pointed `tier-balanced` at `deepseek-chat` (131K) while the table still said 1M — and the pin ran *after* the dynamic resolution and clobbered it. The endpoint computed the right window, then replaced it with the stale one. The UI's context ring under-reported usage by ~7.6×.
- **A 4× over-claim.** A model id litellm didn't know matched on its **bare suffix**, so `openrouter/deepseek/deepseek-v4-pro` inherited the *direct* provider's 1M window when OpenRouter serves it at 262K.
- **Default window 32768 → 128000.** The old default silently starved every unknown model to a quarter of a current model's real window.
- **`ACB_LIMITS__<MODEL>__{CONTEXT_WINDOW,MAX_OUTPUT}`** overrides — a provider raising a limit becomes an env var, not a deploy.

## Tradeoff, stated plainly

A curated entry that is **stale-low now binds**, where litellm's larger number used to win. That's the intended direction of error given the asymmetry above, and the remedy is cheap in a way it wasn't before: one table to correct, or an env var.

13 curated windows shrink — all are corrections of the bare-suffix over-claim, or of the 32K default exceeding a model's real window (Llama-3 is genuinely 8K). None are in the active fleet.
