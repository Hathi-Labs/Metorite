## Description

## The outage

`GET https://api.commandcenter.fracktal.in/email/oauth/microsoft/authorize?…` → `{"detail":"Authentication required"}`, **for every user, since 2026-07-29**.

Surfaced when a colleague tried to connect his mailbox. It is not about him: the owner's account was connected before that date, which is the only reason six days passed without anyone noticing.

### Why

1. Both **Connect** buttons do `window.location.href = ${gatewayUrl}/email/oauth/${provider}/authorize?…` — a top-level browser navigation **straight at the gateway host**, deliberately skipping the BFF, because the response has to be a 302 onward to Microsoft/Google.
2. That request carries no Bearer and no `X-User-Email`: session cookies live on the workbench origin, not `api.*`, and a browser navigation cannot add headers.
3. `57ec82d9` ("Make authentication default-deny app-wide") attached `require_authenticated` at the app level. The OAuth **callback** legs were exempted; the **authorize** legs were not — `main.py` says they "stay gated".
4. So the route 401s before its handler runs. The handler's own `user_email` query parameter — added precisely so "the workbench can pass the authenticated user's email when the browser navigates directly to the gateway" — has been unreachable the whole time.

`git log -S` confirms the authorize leg was **never** in `PUBLIC_ROUTES`. A route was made default-deny and the one entry point that structurally cannot carry credentials was never re-checked.

### 🔴 Why the obvious fix is worse than the bug

Adding the authorize leg to `PUBLIC_ROUTES` makes the button work. It also hands over accounts: the handler stored `"user_id": user_email or user.email`, so an anonymous authorize leg taking identity from a **query parameter** lets anyone bind a mailbox to somebody else's account.

**This PR does not do that, and pins that it stays that way** (`test_the_authorize_leg_is_not_public_and_must_not_become_public`).

## The fix

A BFF route the browser navigates to instead — `src/app/api/email/oauth/[provider]/authorize/route.ts`. It runs server-side, so it has the session; it calls the still-gated gateway route with `gatewayHeaders()` + `redirect: "manual"`, reads `Location`, and re-issues its own 302. **No gateway route change, no new public surface.**

Plus the half without which the first half is a hole: `user_id` was `user_email or user.email` and is now `user.email or user_email` — the authenticated identity outranks the query parameter.

### Verification found why both halves were needed

Probing for a route-precedence bypass:

```
GET /api/email/oauth/microsoft/%61uthorize?user_email=victim@fracktal.in
```

Next decodes the segment, so it falls through to the `[...path]` catch-all, which forwards every query parameter verbatim. **With only the BFF route and the old precedence, that URL is a live mailbox hijack.** The one-line precedence change is what closes it.

Residual, pinned deliberately: a caller holding the internal bearer with no identity header can still name `user_email`. That requires total platform compromise, and was reachable by *anonymous* callers before 29 July.

## Proven live, not by inspection

Stub gateway on `:8099` reproducing default-deny, `next dev` on `:3099`:

```
the outage   : curl :8099/email/oauth/microsoft/authorize  -> 401 "Authentication required"
the fix      : GET :3099/api/email/oauth/microsoft/authorize -> 302
               location: …/fake-consent?bound_user_id=dev%40fracktal.in&saw_user_email_param=<none>
               stub log: auth=yes  x-user-email=dev@fracktal.in
the contrast : same shape via the [...path] catch-all -> 200 text/html "PROVIDER CONSENT PAGE HTML"
```

That last line is the point: the existing catch-all **follows the redirect server-side** and returns the consent page as HTML instead of navigating the browser to it. A `fetch` through the normal proxy could never have worked.

## 🔴 The test written to stop false passes had one

`_code_only()` strips comments so a comment explaining why `user_email` is no longer sent doesn't read, to a substring check, exactly like sending it. It was **line-based**, so it only dropped comments that *began* a line. Verification found:

```ts
redirect: "follow", // was redirect: "manual"
```

passing **all 11 tests** — the trailing comment left the banned string in the assertion input. It also deleted real code: on a line where a block comment *ended*, everything after `*/` went with it, which can make a `not in` assertion green by removing the very token it looks for.

Replaced with a character scanner that tracks string state, so `//` inside a string survives and `{/* … */}` in JSX does not. **`_code_only` now has its own test** covering every position the line filter got wrong plus the two converse cases where it must not eat code. Regex literals are not modelled and the docstring says so rather than implying total coverage.

That mutant now fails. This is the seventh test in this repo to assert less than its docstring claimed — the first was caught during the build (an assertion satisfied by the route's own comment naming `manual`), which is why the helper existed at all.

## Recorded, not fixed

- **`_oauth_states` is a module-level in-process dict.** Any deploy landing mid-flow loses the state and the callback fails validation; not shared across workers; entries never expire. Written up on the dict, in `AGENTS.md`, and in the spec.
- **The catch-all re-sends the internal bearer when it follows a redirect.** No evidence of a real leak — undici strips `Authorization` across origins — but the catch-all stays reachable for gateway routes that answer 3xx, and `%61uthorize` proves it. Pre-existing.
- A signed-out navigation to the BFF route returns a JSON 401 in the address bar rather than redirecting to `/signin`. Deliberate: it must stay a refusal.

**No migration.** Spec: `email_app_master_plan.md` §7 Tier 1 item 1 is now 🟡 partially closed, and records what that item got wrong — it ranked this "not an active incident" because the owner had a working mailbox, while it was a total outage for everyone else.
