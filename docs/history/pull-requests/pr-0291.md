## The gap

Until now an agent run received **every configured credential regardless of who invoked it**. An agent's `config.json` was effectively an entitlement: picking an agent that declares Zoho was enough to reach Zoho, whatever the caller's access said.

## Two new permission families

Both usable immediately from the existing member access editor, with the same Inherit / Allow / Deny control and provenance as features and agents:

| Permission | Means |
|---|---|
| `integrations:use:<service>` | Which third-party services an agent may use **on this member's behalf**. Distinct from `integrations:manage`, which is the right to add and rotate the credentials themselves. |
| `memory:write_org` | Writing organisation-wide memory. |

Personal and agent-scoped memory stay **ungated** — they are already keyed to the acting user and the running agent, so there is nothing to authorise. Org memory is the shared one, which is why writing to it is the act that needs a permission. Reads stay open to `member`: a recall that silently returns nothing is worse than one that works.

*(Correcting something I said earlier in this series: memory scoping was not missing. Personal / agent / org scopes already existed via contextvars. What was missing was the permission on the shared scope.)*

## How it works

`build_integrations()` takes an optional authorization predicate; the executor supplies it from the member's resolved access, reusing the same lookup that arms the memory gate so there is exactly one access resolution per run.

Two properties worth checking in review:

- **An agent cannot widen its own access.** Declaring more integrations produces more entries in `unavailable`, not more credentials. There's a test named for exactly this.
- **Filtering runs before the env injection.** At the streaming call site credentials are injected into the run's environment (B6 Tier 0, restored by token afterwards). Filtering first means an unauthorized credential never enters that environment — not merely absent from `state["integrations"]`.

Unauthorized services are reported through the existing `unavailable` map rather than raising, so a member missing one integration still gets a working agent that can explain what it cannot do.

## Two deliberate asymmetries

**Background runs are unfiltered.** The predicate is `None` unless the run is attributable to an *active* member — so cron, the reconciler, webhook-triggered runs, and any address without an `app_user` row behave exactly as before. This is the important one: starving those runs would fail *silently*, with no 403 and no error, just work that quietly stops happening. Who may start a run at all is already enforced upstream by `assert_can_run_agent`, so an unidentifiable address here means "platform-initiated", not "attacker".

**Migration 129 grants `integrations:use:*` to every seeded role except `guest`**, so nobody loses access on deploy — that preserves precisely the behaviour already in effect. The restriction only takes hold once an admin sets a per-user deny.

## What this is *not*

**Authorization, not isolation** — and the spec now says so out loud (§8a). During a run, resolved credentials still live in the process environment; an agent reading `os.environ` directly rather than `state["integrations"]` can still see what's there. Per-run scoping narrows the window, but the boundary is cooperative.

Real isolation needs the sandbox work (**BO-7**). The honest claim today is: *the platform will not hand a member credentials they are not authorized for* — **not** *a hostile agent cannot obtain them*. Those are different sentences and only the first is true.
