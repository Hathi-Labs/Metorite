## 1. Priority & Engage show only tasks assigned to me on ClickUp

- **Engage** was already `NEXT & isMine` ✅.
- **Priority** also showed `WAITING` tasks — but those are tasks delegated to **others** (`is_mine=false`), i.e. *not* assigned to me. They now drop out. Priority = `isMine & (NEXT | WAITING)`. `viewCounts` updated to match exactly.

### The "assigned to me" mechanism is sound (and now locked)

`isMine` = my ClickUp user id ∈ the task's assignee ids, computed in `sync.map_pulled_task`. My id comes from `verify()` → `GET /user` (the authoritative owner of the connected token). New tests lock the parts that could silently break it:
- **Type-robust match** — a numeric assignee id (`42`) matches my string id (`"42"`); both sides are stringified. This was the real risk: ClickUp returns numeric ids in some payloads, so a strict `==` would silently drop *every* one of my tasks out of Priority/Engage.
- **No false positives** — a blank/missing id never matches (unassigned tasks don't look "mine").
- **Authoritative source** — the "me" id is ClickUp's own user id.

## 2. @context pills on Next Actions (Engage-style)

New `ContextPills` row in the Next Actions header — **All** + one pill per @context that has tasks (+ the **@no context** bucket), each with a count. Selecting a pill sets `selectedContext` — the exact signal the left-sidebar drill-down already uses — so pills and sidebar stay in lock-step. This replaces reaching for a dropdown, matching how Engage surfaces its energy pills. The sidebar drill-down stays as-is (per your choice). Energy stays on Engage; Next Actions only gains context pills.
