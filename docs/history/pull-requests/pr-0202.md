## Description

## Why

`main` is red on **two** independent, recently-merged issues, and because CI tests every PR *merged onto `main`*, this blocks **every open PR** — not just the ones that introduced them.

1. **Migration `97` collision** — `97_gtd_pending_plan.sql` (#201-era) vs `97_gtd_planning_prefs.sql` (from #197). The 2-digit numbering space (`00`–`99`) was already **full**: `main` occupies `95/96/97/97/98`, so there was *no free number left* to resolve the clash with.
2. **Stale eval** — #201 changed `skill_task_gtd` to delimit untrusted data with guillemets `«»` (a good anti-injection convention, `core.py:_untrusted`), but `evals/trajectories/test_gtd_quality_trajectory.py::test_synced_text_is_delimited_as_data` still asserted straight quotes.

## What

**Migration numbering is now length-agnostic (the real fix for the exhaustion):**
- `scripts/apply_migrations.sh` matches 2-**or-more**-digit prefixes and applies in **numeric** order via `sort -V`. This matters: plain lexical `sort` orders `100_` **before** `99_`, which would run a later migration first. Numeric sort keeps `…98, 99, 100, 101`.
- `tests/unit/test_migration_prefixes.py` matches the same set and keys prefixes as **ints**, so a zero-padded `097` and a bare `97` are still flagged as the same number.

**Resolve the `97` collision using the reopened space:**
- `97_gtd_pending_plan.sql` → `100_gtd_pending_plan.sql` (the newer collider moves; #197's `97_gtd_planning_prefs` keeps its number).

**Fix the stale eval:**
- `test_synced_text_is_delimited_as_data` now asserts the `«…»` delimiter.

## Why the renumber is safe against production

`apply_migrations.sh` has **no tracking table** — it re-applies every `NN_*.sql` on each deploy, idempotently, in order. A migration's number is *only* its relative apply-order, not an identity the DB recorded. The moved file is an idempotent `ALTER TABLE gtd_day_state ADD COLUMN IF NOT EXISTS pending_plan` that depends only on `92_gtd_day_state.sql` (far earlier) with no downstream dependents, so applying it later is a no-op.

## Note for maintainers
This reopens headroom above the exhausted 2-digit space, but it does **not** prevent two concurrent PRs from picking the same next number again — that's a coordination issue inherent to file-numbered migrations. Worth considering a longer-term scheme (timestamp prefixes or a sequence) if the collision rate stays high.
