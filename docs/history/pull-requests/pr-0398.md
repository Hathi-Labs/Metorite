# WS-27k — filters, grouping and saved views

*"My open bugs in Ops, grouped by assignee"* is the sentence §11.2 used to name this gap. It is now typeable.

`routes/projects/filters.py` and `lib/grouping.ts` (status / assignee / project / priority / tag / none), with `components/FilterBar.tsx` and saved-view chips.

**One filter builder serves the list endpoint AND saved views** — two implementations would drift, and a *saved* view showing a different set than the same filters typed by hand is the one thing it may not do. **Every filter is a WHERE clause**, because paging happens in SQL and a Python post-filter after `LIMIT` returns short pages. **`overdue` means past due AND still open** — permanent red is how a board teaches people to ignore red. **An unknown category is a 422 naming the five real ones.** **An unknown config *key* is dropped while a bad *value* falls back**, so a deploy never becomes a migration of everybody's saved views.

**A task with two assignees appears in BOTH columns.** **Empty status lanes are kept**; every other grouping drops empties. **Dragging is offered only when the columns are statuses.** **The project's order-bearing board is withheld from the chips** — it owns every `pm_view_task_positions` row, so its ✕ would delete every hand-arranged position.

### The `due_before` 500

`CAST(:due_before AS timestamptz)` with a raw query-string value: asyncpg infers the parameter's type **from that cast** and refuses to encode a `str`, so the query never reached the database. `parse_when` now binds a real `datetime`. Two tests — one on the bound value's *type*, one refusing any `CAST(:param AS timestamp…)` anywhere in the builder.

**No schema change.**

# WS-27l — custom fields

Migration `155`, `routes/projects/custom_fields.py`, `lib/customFields.ts`, a field block in the panel and a manager behind **Fields**. Seven types.

**Definitions in a table, values denormalised onto the task as JSONB keyed by `field_key`.** Not a row per (task, field) — that is the textbook EAV answer and costs a join per field on every board paint.

**The cost is stated rather than discovered:** the database cannot stop a key no definition owns from being written, so that guarantee moves into Python. **An unknown key is a 422**, not a silent drop. **A patch MERGES.** **An explicit `null` CLEARS the key.** **`true` is not the number 1** — `isinstance(True, int)` is True in Python, so the coercers are one-per-type in a dispatch dict specifically so that ordering cannot be undone by accident.

**The deliberate departure from Paca:** deleting a definition strips its values, because an orphaned key is invisible until somebody recreates the name and every old value resurfaces carrying the new meaning.

**`field_key` is never editable; `field_type` is a 409 naming the count** while values exist. **Custom fields are revertible**, folded into the existing `field_change` activity rather than a new activity type — `record_activity` refuses a type the CHECK does not list, the trap that made every attachment upload answer 422.

**A bug this ticket's own tests caught:** `changedValues` compared a checkbox against a `null` baseline, so an unanswered checkbox posted a phantom edit on *every* save.

**A fence that was quietly a subset check:** `test_projects_routes` now reads the package directory and asserts every module declaring a `@router` route is imported by `__init__.py`. Verified by deleting the import and watching it fail.

# WS-27m — the tag registry

Migration `156`, `routes/projects/tags.py`, `lib/tags.ts`, a picker, a filter row, a `tag` board axis and a manager behind **Tags**.

The row the research notes left open **on purpose**: row 13 REFUSED Paca's bare array — *"no registry, no colors, no rename/merge — the weakest part of Paca's model"*.

**The array stays** — a join table would add a row per tag per task and a join to every board paint. **One spelling per tag**: identity case-insensitive via a unique index over `lower(name)`, display case-preserving, and the task's array stores the **registry's** form.

**Applying an unregistered tag registers it** — refusing makes tagging a two-step errand, which is how tagging gets abandoned. **The cost, stated: every typo becomes a tag**, which is why merge is not optional and why the picker *shows* the moment of creation. **A rename onto an existing name is a 409, not a silent merge.** **A task carrying BOTH tags ends a merge with the target once.** **Two tag filters**: `tags` is ANY (`&&`), `tags_all` is ALL (`@>`).

### The migration backfills — and rewrites data, deliberately and narrowly

The winning display form is **the spelling people actually use**; `min()` alone would canonicalise 400 "Bug" to a single stray "BUG". Task arrays are then made to agree, bounded strictly to casing, with the count in a NOTICE.

**A bug the live run caught:** the implicit-comma `FROM pm_tasks t, unnest(t.tags) … LEFT JOIN` form leaves `t` out of scope for the join's `ON` clause. Rewritten as `CROSS JOIN LATERAL … WITH ORDINALITY`, which also fixed a second problem the first version would have shipped: `array_agg(DISTINCT ...)` sorts by its own expression, so every tag list would have come back alphabetised.

# WS-27n — bulk edit

`POST /projects/tasks/bulk`, `lib/selection.ts`, `components/BulkBar.tsx`, checkboxes on board and list. **No migration.**

**It reuses `automation.apply_task_patch` rather than growing a second writer.** That service exists because WS-27f needed an edit indistinguishable in validation from a human PATCH; a bulk endpoint with its own field handling would be a third opinion about what a task edit is. Tags go through the same registry the panel uses, because the registry cannot be true if bulk is a second door into the array.

**Status is named, never keyed — load-bearing here rather than stylistic.** A selection spans projects and a status id belongs to one root, so `status_id` across three projects would put two thirds of the selection in a lane that is not theirs. It is refused with its own message, because it is the mistake somebody makes by copying a single-task PATCH body.

**Assignees and tags are ADD/REMOVE, never SET** — a replace wipes every individual assignment the selection already carried.

**Shape is validated once; outcomes are per task.** An unsettable field is the same mistake for all fifty (422 before any write); a status name present in one project and absent from another is a fact about *that task*, and failing the batch for it makes a mixed selection unusable — precisely the selection somebody makes after an import. **An invisible task is skipped, not an error** (R5). **One transaction**, because a re-triage that half-happened is harder to recover from than one that did not.

**Re-asserting a value is not a change.** **One notification per person per batch, not one per task** — fifty bells is a bell people turn off, which is WS-27j's own argument applied to the case that would have broken it.

In the browser the selection is **pruned whenever the filter changes**; a shift-click ranges over the board's on-screen order; a two-assignee card drawn in two columns counts once; and the outcome line names every category including the boring ones.

# A shipped WS-27j bug that WS-27n uncovered (spec §11.12)

`core.task_visibility_clause` carries **two** ways to see a task — a grant on its project, or being an assignee — and its docstring warns that a second implementation *"would drift the moment one is edited alone"*. `notifications.deliverable` had drifted exactly that way, probing only `project_clause('t.root_project_id')`. Two silent consequences:

1. **Anybody assigned work in a project they hold no grant on was judged undeliverable.** They could open the task; the assignment notified nobody; and the response told the assigner they could not see it. That is the silent assignment WS-27j exists to end, still open for the most common case in a grant-scoped app: delegating outward.
2. **`root_project_id` also missed a grant made on a SUBPROJECT.** The old test asserted that scoping on the argument that "probing `project_id` would miss a grant made on an ancestor" — backwards, as a real-Postgres run showed: the closure is recursive and expands *downward*.

Fixed to use the shared clause; the test that encoded the wrong reasoning now records why it was wrong.

**A fake collision the fix exposed:** `FakeDB` matched the rule-3 probe by substring, and the new clause embeds both `pm_task_assignees` and the closure's `UNION` — exactly the *audience* branch's fingerprint — so four tests failed for a reason unrelated to the code under test. A fake that dispatches on substrings needs fingerprints that are **specific**, not merely present.

## Deploy note

**Two new migrations, 155 and 156**, applied in order. WS-27n adds none.

- `155` adds `pm_custom_fields` and one column on `pm_tasks`; its CHECK is added `NOT VALID` then validated in a guarded block, so an unanticipated row leaves a NOTICE rather than stopping the deploy (the pattern migration 148 established).
- `156` adds `pm_tags`, backfills it from tags already on tasks, and canonicalises tag *casing* on task rows. That rewrite is bounded to case and reports its count; it was run against a seeded corpus with mixed spellings before being committed.
