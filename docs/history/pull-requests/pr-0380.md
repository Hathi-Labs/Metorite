## Description

Closes both agent-safe halves of the platform's only *unrecoverable* failure mode. One owner step is left, and it's ten minutes with a terminal.

## Nothing was scheduled

`acb-backup.service` / `.timer` were written out verbatim in the spec but never created — `plan-guard` blocked `deploy/` writes in the session that authored them. That gate isn't active here, so they now exist.

More importantly, `deploy.sh` now syncs **every** unit in `deploy/hostinger/` into `/etc/systemd/system` on each deploy, reloads when a file actually changed, and `enable --now`s the timers. A unit added to the repo arrives with the code instead of waiting for someone to remember — which is how the backup timer sat unscheduled for days while the tooling existed. It also picks up `acb-health-watchdog.timer`, which was in exactly the same position.

Service units are copied but never restarted: bouncing the gateway mid-deploy is the compose stack's job, not this loop's.

## No restore had ever been run

It *couldn't* be. Both scripts reached Postgres only through `docker exec acb-postgres`, which exists on precisely one machine — that coupling is why they'd never executed anywhere. They now go through a two-function `pg`/`pgi` seam with `PG_MODE=local` for a cluster reached over libpq. **The VPS path is byte-for-byte unchanged.**

With that seam, `scripts/rehearse_restore.sh` does the real round trip: seed 250 known rows, run `backup_db.sh --verify-restore` (the exact command the systemd unit runs), `DROP` the table, run `restore_db.sh`, and compare an **md5 of the restored rows against the originals**.

The comparison is the point — every other step in that sequence passes against an empty database, which is precisely the outcome a restore must never quietly produce. It also asserts the live DB is untouched by a default restore, and that a truncated dump is **rejected**: a verifier that passes on garbage is worse than no verifier, because it turns an unnoticed problem into a false assurance.

**Verified in both directions** on a real Postgres 16 — passes clean, and with `restore_db.sh` sabotaged to create the scratch database without restoring into it, exits 1 with `restored 0 rows, backed up 250`.

Wired into `pr-check.yml` against a real `postgres:16` service, because *"we tested it once in August"* decays: a refactor to either script, or a `pg_dump` format change on a Postgres upgrade, would otherwise break the restore path silently and nothing would notice until it mattered.

## A deploy bug found on the way

`uv sync` ran only `if [ ! -d .venv ]` — so a dependency added to any workspace package reached a box **exactly once**, the day it was provisioned. Every deploy after that ran new code against the old environment, surfacing as an `ImportError` at request time rather than at deploy time. It now runs every deploy (~1s no-op when the lockfile hasn't moved). BO-10's new `acb_common` deps needed this, which is how I noticed.

## Still owed — and no test can supply it

**One restore against a *production* dump.** The rehearsal proves the scripts are correct. It cannot prove this box's dump holds what you think, that `/opt/acb/backups` has room for fourteen of them, or that `BACKUP_REMOTE` points anywhere at all. Those are properties of the machine. §6 of `ai-company-brain/specs/backup_and_restore.md` has the three commands.
