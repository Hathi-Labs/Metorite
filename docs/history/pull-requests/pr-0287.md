## Description

Recording a meeting in-app and running the copilot both worked — but you couldn't tell.

The copilot's output lives in the console at `/notes/live/[id]`. The recording screen said nothing about it at all, not even whether one was running, and its copy still promised the copilot *"will appear"* — written before it existed.

That split is deliberate and stays: the console is the considered view, and recording survives navigation via the RecordingDock. What was missing is that the screen you actually sit on during your own meeting had no state and no control.

## What's added

`LiveCopilotStrip` on the recording screen: on/off with a toggle, a running suggestion count, and **the latest suggestion inline** with its grounding. Inline because during your own meeting you won't go looking for it — and a suggestion you never see is the same as no copilot. Depth stays in the console, and the link now says recording keeps running if you follow it.

Only subscribes to the copilot stream while it's on, so an off copilot costs nothing.

## Verified while tracing this path

The backend for in-app-recording + copilot was already complete, and I confirmed each link rather than assuming:

- `live_session.begin()` fires on the first recorded chunk, and auto-starts the copilot when the meeting was prepared with it on
- The browser recorder relays finals **with the speaker** (`recordingStore.ts` maps `speaker → S1/S2`) to the same bus the meeting bot feeds
- The copilot orchestrator subscribes to that bus **source-agnostically** — so the in-app path and the bot path are the same seam downstream
- `LiveSpeakerRegistry.resolve()` passes provider labels through when there's no embedding, so speakers work without `EMBED_CMD`
