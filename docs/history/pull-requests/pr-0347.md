## Description

## BO-23 — a backup path that can restore one table, not just the whole VPS

### The recovery position this replaces — measured, not inherited

Queried against the live VPS on 2026-08-03:

| | |
|---|---|
| Application-level backup | **none** — no dump, no cron, no script, anywhere |
| Hostinger VM images | **2 retained**: `2026-07-22`, `2026-07-29` |
| Age of the newest one | **5 days** |
| Worst-case RPO | **~7 days of data loss** |
| Restore time | `restore_time: 3457` ≈ **58 minutes** |
| Granularity | the **whole machine** — code, `.env`, every volume |
| VPS snapshot | **none** (`id: 0`, `created_at == expires_at`) |

So *"recover one dropped table"* was not an operation this system could
perform — the only lever reverted the entire box to a point up to a week
earlier. Meanwhile **140+ migrations replay forward-only on every release**
under `ON_ERROR_STOP=1` with no down-migrations.

The databases are **193 MB** (`acb`) and **11 MB** (`litellm_proxy`) with
**67 GB free**. There was never a cost reason for the gap.

### What ships

**`scripts/backup_db.sh`**

- **Every non-template database, enumerated not hardcoded.** `litellm_proxy`
  holds API keys and spend records — an `acb`-only backup would have silently
  missed it, and so would any database added later.
- **Cluster globals dumped separately.** Roles and passwords live in the
  cluster, not in any database. A per-database dump restored into a fresh
  cluster comes up with **no roles and every `GRANT` failing** — a bare-metal
  rebuild would have been impossible from database dumps alone.
- **`-Fc`, not plain SQL**, so `pg_restore --table gtd_task` can pull one table
  out. A plain dump only replays whole, which is useless for the case that
  motivated the ticket.
- **Integrity-checked on every run** with `pg_restore --list`. A truncated or
  half-written dump fails *then*, not at 3am during an incident. This is the
  difference between having a backup and believing you have one.
- **`--verify-restore` proves a different claim**: it restores into a scratch
  database and compares `public` table counts against live. The cheap check
  proves *readable*; this proves *restorable*. ~20s on 193 MB.
- Manifest with sha256, the migration high-water mark, the app commit, and
  anchor row counts — so "what was true when this was taken" is answerable
  without restoring it.

**`scripts/restore_db.sh`** — the default is deliberately the safe one. With no
flags it builds `acb_restored_<ts>` and touches nothing live, which is what you
actually want mid-incident. Overwriting live requires `--target acb --force`,
takes an **unconditional pre-restore dump first**, and stops the gateway so
users are not served half-restored state while it runs.

**Pre-migration hook (done-when 4)** — the migration runner now takes a dump
before replaying the ladder and **fails closed** if it cannot. Placed in the
script rather than the pipeline YAML so it also covers anyone running it by
hand, which is when it is most likely to matter. `SKIP_PRE_MIGRATION_BACKUP=1`
overrides, on purpose and in writing.

### One repo-specific trap this is designed around

Backups land in `/opt/acb/backups`, **outside `/opt/acb/app`**. The release
pipeline runs `git reset --hard`, which has already destroyed tracked runtime
state in this repo's history. Anything under the app dir is one release away
from being gone.

### 🔴 Not done — and the box stays unticked because of it

- **Nothing schedules this.** The `acb-backup.service` / `.timer` units are
  written **verbatim in §5 of the spec** but could not be created: `plan-guard`
  blocks agent writes under `deploy/`. That refusal is correct — it just means
  an owner applies them. Until then backups happen only on a release or by hand.
- **No restore has been executed.** By BO-23's own rule — *a backup nobody has
  restored is not a backup* — tooling alone does not close this.
- **`BACKUP_REMOTE` is unset**, so these sit on the same disk as the database
  they protect. That covers bad migrations and dropped tables; it does not
  cover losing the disk, the box, or the provider account. The script warns
  loudly on every run rather than implying otherwise.
- **PITR deliberately not attempted.** It needs `archive_mode`, a WAL
  destination with real capacity, and a **production Postgres restart** — a
  poor trade before anything is even scheduled. Nightly verified dumps take the
  RPO from ~7 days to ≤24h; PITR is the *next* step, not the first one.
