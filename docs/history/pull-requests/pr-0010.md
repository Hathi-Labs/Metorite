## Description

## Problem

The previous deploy (PR #9) added a migration runner that applies `infra/postgres` migrations `02+` on every deploy. It works — but it surfaced a **pre-existing bug in migration 13** that blocks the chain before reaching migration 18 (the email `importance`/`categories` columns), so the email app still 500s:

```
ERROR: new row for relation "mcp_servers" violates check constraint "mcp_servers_transport_check"
DETAIL: Failing row contains (filesystem, ..., http-sse, ..., null[url] ...)
```

The seed `INSERT` declared the `filesystem`/`postgres` rows as `transport='http-sse'` with a `NULL` url, which violates the table's CHECK constraint (`http-sse` requires a url). It went unnoticed because migrations were never replayed through a strict (`ON_ERROR_STOP`) runner before.

## Fix

Remove the `mcp_servers` seed `INSERT` entirely. We're not building out MCP-server functionality right now, so the example rows aren't needed. The `mcp_servers` table and all code paths that reference it (executor injection, integrations CRUD) are untouched — servers can still be registered via the API/UI later.

With the broken seed gone, the runner proceeds through migration 18, the `importance`/`categories` columns land in prod, and the email app 500 is resolved.
