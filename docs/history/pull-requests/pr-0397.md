## What

**WS-26g — Forecast & funnel reports** (D3 on the demo critical path, spec §9.0). A `?tab=reports` tab over four new read-only endpoints in `routes/crm/reports.py`: pipeline-by-stage (count / ₹ / weighted ₹ + grand totals), funnel (entered / conversion-forward % / median dwell), win/loss trailing 90d, owner leaderboard. No migration, no flags, no owner gates — reads only.

## The definitions that make it honest (spec, post-#396)

- **Entered** = the visited-set union (`from_status` ∪ `to_status` ∪ current stage) — the only reading that counts the 551 imported deals, which have zero transition rows.
- **Median dwell** groups by `from_status` (the stage being LEFT); NULL dwell excluded; labeled median-over-departures.
- **Renamed lanes** (the f2 settings grid can do this) orphan name-keyed history → tallied into a reported `unmatched` field, never dropped.
- **Imported lost deals** carry no lost reason (importer bypasses both gates) → named unattributed bucket. NULL `closed_at` (f4 backfill not yet run) falls outside the 90d window — zeros, never errors.
- **Weighted formula**: `WEIGHTED_SQL` lifted to `core.py` beside `WEIGHTED_TYPES` — one expression, no retyped copy — and pinned cross-language by a shared fixture (`tests/fixtures/crm_weighted_parity.json`) read by BOTH pytest and vitest.

## Fake-extension choice (the ticket asks it be stated)

Path (a): the reports SQL emits per-key queries in `get_pipeline`'s existing shape — no GROUP BY reader added to `_crm_fakes.py`, no aggregation answer hard-coded. N+1 accepted over 3.4k rows; rationale in `reports.py`'s docstring.
