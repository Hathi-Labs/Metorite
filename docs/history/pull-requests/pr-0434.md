## Description

## The bug

`ensure_owner_bootstrap()` used `ON CONFLICT (email)`. Migration 162 dropped
`app_user_email_key` and replaced it with `app_user_email_lower_key ON (lower(email))`.
There is no longer a unique constraint on the bare column, so the statement raises.

## Why nobody hit it

`_HAS_OWNER_SQL` short-circuits once an owner exists, so production never
reaches the broken path. It fires only on a database with no owner yet — a new
tenant, a restore to scratch, disaster recovery, or a laptop.

**The lockout-recovery path was itself locked out.** That is the whole severity
of this: it is fine until the day it is the only thing standing between you and
a database you cannot get into.

## Verification (R8 — against a real Postgres, not a fake)

Run inside a rolled-back transaction:

- provisions an owner on an empty database
- is idempotent — a second call creates no second row
- a mixed-case email does not create a duplicate (the `lower(email)` index is
  the one that must be honoured)

Fenced structurally so the mirror cannot rot again: the test asserts the
conflict target names the index that actually exists, rather than restating the
column name.
