## Description

Corrects #87, which was too broad.

> "so basically, any new rules, any new emails that come in, the drafting will be on. It's just that when I'm processing previous emails using the process past emails feature in ai setting, the drafting should be off by default unless turned on via the checkbox. The regular rules apply as is for new mails that come in."

The rule is about the **age of the thread**, not the act of drafting. A draft on mail that just arrived is the feature — it is waiting when you open the message. A draft on a months-old thread is spend on a conversation that already ended, and a backfill can produce hundreds in one run.

That distinction is enforced where it belongs: `RuleProcessPastRequest.draft_replies` defaults `False` and `_without_drafting` strips `REPLY` / `DRAFT_EMAIL` / `FORWARD` from every backfill match (#80).

## Where each switch lands

| switch | default | why |
|---|---|---|
| `RuleProcessPastRequest.draft_replies` (backfill) | **OFF** | opt-in per run via the "Also draft replies" checkbox |
| `email_assistant_settings.draft_replies` (live) | **ON** | restored — new mail still gets a draft |
| `email_assistant_settings.follow_up_auto_draft` | **OFF** | stays off, see below |

`follow_up_auto_draft` nudges threads **by age** — the hundreds-at-once case, not the just-arrived one. Its scan was also dead from the day it shipped until #84, so the first working run on a long-configured account releases a whole window at once.

`draft_replies` is restored in all three places: the API model, the GET fallback the toggle renders from, and the column default (migration 82).

## Test change worth noting

The column-default assertions no longer check one migration file. They replay every migration in order and assert the value each column **ends up** with — so a later flip cannot leave an earlier assertion passing and wrong. That is precisely the failure mode this PR is correcting.

Existing rows are still never rewritten, now pinned across both migrations.
