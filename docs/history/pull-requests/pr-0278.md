## Description

Item 01 of the UX redesign plan, and the structural half of it.

A meeting moves through three phases — before, during, after — and the app had surfaces for the last two. Agenda, briefing and copilot context lived only in `/notes/live/[id]`, which doesn't exist until a session is already running. So the only moment you could tell the copilot what the meeting was about was *while it was happening* — exactly when you can't type. In practice the copilot walked in cold every time.

## What's new

The meeting page renders a prep view when a meeting has no recording and no segments: title, when, attendees, meeting type, agenda, briefing, copilot toggle, and the three ways to start. Almost everything it needs already shipped as an API (`/agenda/chat`, `/brief`, `/context/deep`, `/settings`) — what was missing was somewhere to use it beforehand.

`New meeting` on the library opens prep; `Record` still starts capture immediately.

## Three decisions worth flagging

**`meeting.copilot_enabled` is nullable, not `NOT NULL DEFAULT FALSE`.** Three states are needed, not two: on, off, and "not decided — follow the account default". With only two, turning the copilot off for one sensitive meeting would be silently undone by the global setting, which is the opposite of what "off" means. `copilot_should_run()` is pure so the precedence is testable without a session.

**`scheduled_at` is separate from the existing `start_at`.** `start_at` is when capture actually began, and the pipeline and library sort on it. Overloading it would make an unstarted meeting look like one that ran the instant it was created.

**`bot-join` now accepts an existing `meeting_id`.** Without this the bot creates a fresh meeting and the agenda, briefing, attendees and copilot decision you just set up are stranded on a different row — which would have made prep pointless for the bot path entirely. This was the non-obvious gap.

## The seam that makes prep worth doing

`live_session.begin()` honours the prepared decision and starts the orchestrator, so the copilot is listening from the first word rather than needing you to find the console mid-conversation. Fail-safe: a copilot that can't start must not take the recording with it.

## Two smaller ideas

- **Context meter** — three layers (briefing / history / agents), so "why is the copilot being generic?" is answerable *before* the meeting rather than after.
- **The meeting-type card shows its lens** — the copilot guidance that type applies is visible during prep, so "why did it say that?" is answerable in advance, and it links to the override in Settings.
