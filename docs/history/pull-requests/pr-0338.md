## Description

Live audio couldn't work because **the control to start it was hidden.**

## Root cause

`Talk` rendered only when the tracked phase read exactly `"active"`. That phase comes from meowcaller's `OnStateChange` — and a call can carry media without ever emitting it. Recording worked the whole time, which *proves* media was flowing while the button stayed invisible.

So the reported symptom — "can't speak, can't hear live, but the recording is fine" — was exactly right, and it was a UI gate, not the audio path.

## Fix

- **Talk is offered for any live call**, except one still ringing inbound. Attaching early is harmless: a call with no browser attached sends silence anyway (that's what holds the relay bridge). Hiding the control is unrecoverable from the UI.
- **Readiness no longer rests on a phase string.** The bridge reports `media_ready` from `OnReady`, and treats any received frame as proof media is up in case that callback never fires — belt and braces, since we've now been bitten once by trusting a single signal.
- **The call card shows state**: `media up` plus the live audio state (`mic + speakers live`, `mic muted`, or `audio failed`). A socket that fails is now visibly different from a socket nobody opened — which is precisely the ambiguity that made this take two rounds to find.

## Verification

Go builds/vets/tests clean, `tsc` and `next build` clean, 326 WhatsApp tests pass.

## Note

This is the second bug in this feature whose signature was "everything looks fine and nothing happens." The first was a WebSocket dying at handshake with no close code; this was a button that never rendered. Both are now surfaced in the UI rather than being silent.
