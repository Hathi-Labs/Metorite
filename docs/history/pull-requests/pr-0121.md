## Description

## Phase 2 — 2.2: one match→resolve enforcement point (`classify_matches`)

A conversation has ONE classification, re-evaluated per message (#110). That invariant was enforced at only *some* call sites — the live runner and the Reply Zero backfill resolved the conversation, but **`/rules/run-message` skipped it**, a bypass that let an explicit re-run splinter a thread the runner would have kept whole (review §3.1/§2.2).

### Change
Put match → conversation-resolve in **one** reusable function, `engine.classify_matches`:
- matches (single or multi per `multi_rule`),
- unless `resolve` is off, re-evaluates the whole thread so it keeps its single status (resolver is cost-aware — no model call on bulk mail; degrades to per-message on failure),
- raises `LLMUnavailable` on a classifier outage (a real no-match still returns `[]`), so callers skip the watermark.

Routed through it:
- **`_run_rules_job`** (highest-volume new-mail path) — behaviour-preserving; the match+resolve it already did is now the shared call, so any future path inherits the invariant.
- **`/rules/run-message` apply** — now resolves (**bypass closed**); `resolve=True` for apply, skipped for the `is_test` dry-run.
- **Reply Zero backfill** — same shared path as the live runner.

`approved_includes_only` is already an explicit engine parameter (cleanup passes `True`), so no change needed there.

### Deferred (own risk/scope)
Routing "Process past emails" through the resolver (it interacts with `_project_thread_status_for_backfill` — needs its own verification) and the provisional-column marker from 1.4 (a schema migration).
