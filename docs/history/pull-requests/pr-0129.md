## Phase 3 · item 3.7

The Reply-Zero rebuild ran a **fixed 8 passes** (200 threads each), so on a real 3,500-thread mailbox it rebuilt only the newest ~1,600 and left the rest on the old classifier — a click that looked like "reclassify everything" but didn't.

### Now it drains
The job loops until nothing still needs a status (`_count_reply_zero_backlog` — the same "needs work" predicate the backfill selects on), with:
- **No-progress stop** — if a pass doesn't shrink the backlog (LLM down → the inbound remainder can't be classified), it stops instead of spinning to the safety cap. Those threads keep their gap, so re-triggering picks up where it left off — **resumable by construction**.
- **Progress tracking** via the shared token-guarded `JobTracker`, polled at the new `GET /email/reply-zero/reclassify/status` (total / remaining / processed).
- **Concurrency guard** — a second reclassify while one is draining is refused (`already_running`), not run in parallel doubling the LLM spend.
- **Synchronous running-row seed** before scheduling, so an immediate poll sees "running", not a gap.

Deterministic FYI-filing already handles the bulk of an old mailbox with no LLM call, so the drain is cheap where it can be and bounded where it can't.
