## Description

## BO-20a — the ingestion stream consumer, wired but switched off

**§BO-20.0 answered: Option A** — an in-process supervised asyncio loop started from the gateway lifespan. Option B (a separate `python -m ingestion.worker`) is recorded as **rejected, not deleted**: it needs a systemd unit an agent cannot install, and it would start with an empty module-level `event_hooks._SINKS`, so it would `XREADGROUP`, `XACK`, and dispatch to **nothing**.

The `ingestion:*` streams have been written and trimmed **unread** since they were built — `xreadgroup`, `xgroup` and `xack` appeared **nowhere in the repo**. This adds the reader.

### 🔴 Ships OFF. The flip is yours.

`INGESTION_CONSUMER` defaults **off** and is set **nowhere in the tree** (verified). Nothing in this PR runs until you flip it.

| Flag | Behaviour |
|---|---|
| **OFF** (today) | **Dispatch-identical** to before: receivers still emit inline, consumer never starts, **not one Redis verb is issued** |
| **ON** | All three receivers cut over to enqueue-only; the consumer becomes the dispatch path |

The cutover had to be **all three receivers at once**. Gating only ClickUp would have double-dispatched Gmail and Zoho, which gained the same inline emit in BO-20f.

Consumer group `cc-ingest` is created on all three streams at **`$`**, and that is load-bearing: `0` would replay up to **10,000 buffered entries per stream** into real `start_run` calls the moment you flip the flag. A test pins `id="$"` per stream — one that only asserted call count would not close this ticket.

### Two regressions this PR would otherwise have introduced itself

**1. A hung sink would have stalled the entire bus.** On `main`, a hang is confined to one request's `BackgroundTasks` and the other two sources keep flowing. After the cutover a single serial loop drains all three streams, so the same hang stops everything — *silently*, because `emit_event` swallows sink exceptions and it could not even surface as a failed cycle. Now bounded at `_DISPATCH_TIMEOUT_SECS = 30.0`, chosen against what the one registered sink actually costs: `start_run` inserts the run row and `create_task()`s the execution rather than awaiting it, so the timeout **cannot truncate a workflow run**.

**2. "Redis down ⇒ events dropped" was not the only lossy state.** An `XACK` failure mid-batch **strands the entries already returned by that read** — they sit in the PEL, and the loop only ever reads `">"`, so nothing redelivers them in this process. BO-20b's reclaim pass recovers them — **but only until `_MAXLEN = 10_000` trims them out of the stream.** All three states are now written down, and **BO-20b's done-when now requires the reclaim to run at startup**, so a previous process's PEL is drained before the flag can strand more.

Guarding the `XACK` was considered and rejected: swallowing that error would hot-loop against a dead Redis instead of reaching the backoff, and honest-ack semantics are BO-20b's.

### Two tests falsified during review rather than trusted

- **Cancellation.** The test asserted `task.done()` — which a loop that *catches* `CancelledError` and returns also satisfies. Changing it to `task.cancelled()` turned out to be **only half a fix**: it still passed a deliberately swallowing loop, because `stop()` ran before the task had ever been stepped, so asyncio's `_must_cancel` fast path throws in at the coroutine's first instruction, **above the `try`**. The assertion was pinning asyncio, not our code. It now waits for the loop to reach its blocking read first, and was re-verified red against the swallowing loop.
- **Ack ordering.** `sink_calls` and `xack_calls` were independent lists, so an **ack-before-dispatch** implementation passed — exactly the line BO-20b will be editing. Both now append to one shared timeline.

Every new pin was proven red against a deliberately broken source, then reverted.
