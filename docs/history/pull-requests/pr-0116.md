## Phase 2 — 2.9: one token-guarded JobTracker for both background jobs

The runner's "Process past emails" job and the cleaner's sweep each publish per-account progress that a background task mutates while a request polls it. Both share one hazard: a **superseded (older) run's late write landing on the newer run's row** — marking the newer job done, or overwriting its counts. The runner guarded this with a monotonic token; the cleaner's `_SWEEP_JOBS` did not, and `/cleanup/auto-categorize` had **no concurrency guard at all**, so a double-clicked sweep (or a sweep starting during a backfill's cleaning phase) clobbered the in-flight row.

### Change
- Extract the guard into one `JobTracker` (`automation/jobs.py`); back **both** trackers with it.
- Runner behaviour is unchanged — the token guard is now shared code, not a second copy.
- The cleaner **gains** the guard: `job_token` threads through `sweep_uncategorized -> _sweep_tick`; both sweep jobs write via the token-guarded `finish()`/`update()`.
- Both sweep endpoints seed the row + mint the token **synchronously before scheduling the task**, and auto-categorize gains the same `is_running()` refusal the backfill endpoint already had — closing the check-then-act race.

In-memory, ephemeral by design (a restart drops the state with the job).
