## Description

> "When processing rules on old emails, do not do auto drafting. Otherwise you will burn tokens. Autodrafting off by default if not already the case."

## Process past emails — already correct, verified

`RuleProcessPastRequest.draft_replies` defaults `False` and `_without_drafting` strips `REPLY` / `DRAFT_EMAIL` / `FORWARD` from every match (#80, pinned by `test_email_process_past_drafting.py`). No change needed.

## The account-level switches were still on — and the API default wasn't the real one

Both columns were created `NOT NULL DEFAULT true` (migrations 26 and 29). **The column default beats any API-side default on an INSERT that omits the column**, and one such INSERT exists: `derive_writing_style` writes `(account_id, writing_style, updated_at)` only. So an account could acquire auto-drafting from a background writing-style capture, having never opened AI Settings.

| switch | what it does |
|---|---|
| `draft_replies` | adds `DRAFT_EMAIL` to the Reply rule → every Reply-classified email costs a drafting-model call |
| `follow_up_auto_draft` | drafts a nudge on awaiting threads |

`follow_up_auto_draft` has the sharper edge: the follow-up scan was dead from the day it shipped until #84, so its first working run releases a whole window's backlog at once. On by default, that backlog arrives as AI drafts.

All three layers now start OFF — the Pydantic model, the GET fallback the UI renders the toggle from, and the column default (migration 81).

## Existing rows are not rewritten

A stored value may be a deliberate choice. Changing what new accounts inherit is the fix; silently flipping a switch a user set is not. Pinned by a test that fails if migration 81 ever grows an `UPDATE`.
