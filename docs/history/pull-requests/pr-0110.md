## Description

## The screenshot, explained

One `thread_id` wearing **Done + Receipt + FYI**, with the supplier's invoice message physically moved out of the conversation into the Receipt folder. The smoking gun from `email_executed_rules` — both rows, same message, same run:

```
FYI      APPLIED  thread_status  "Thread status: FYI"            [LABEL]
Receipt  APPLIED  ai             "invoice copy from a supplier"  [LABEL, MOVE_FOLDER]
```

The system judged the thread conversational and ripped a message out of it anyway.

## The model change

**The unit of classification is the conversation. A new message is new *evidence* about it, not a new thing to classify.**

| before | after |
|---|---|
| arbitration ran only if the *message* matched a conversation rule | runs whenever the *thread* is a conversation |
| `[determined, *non_conv]` — losing matches ran their actions | losers come back `suppressed`: logged SKIPPED, never applied |
| "ok noted" matched nothing → thread status stale forever | no-match messages still refresh the thread |
| damage stayed | stale cleanup chips shed; our own mid-conversation moves undone |

`_thread_is_conversation` is deterministic and cheap — an existing status row, else ≥2 messages with our side (owner or org domains) participating. **Bulk mail never pays for a determination**: a newsletter blast stays on the per-message path, and a cold-email drip (≥2 messages, all external) stays bulk — a salesperson can't earn conversation treatment by following up with themselves.

## Robustness decisions

- **The suppression guard lives in `_apply_and_log_match`** — the one choke point every apply path crosses (same shape as the pattern-write gate in `rules._teach`), so no future caller can run a suppressed match by accident. History gets a SKIPPED row answering *"why wasn't this filed as a Receipt?"*
- **Move-back undoes only our own work**: a message still sitting in the exact folder an APPLIED rule-move put it in. Proven read-only against prod: the invoice message qualifies; four messages an *Outlook-side* rule filed under "fracktal internal emails" carry no rule move-label and are left alone. No provider → no move (a local-only move would be re-broken by the next sync). Move re-keys are persisted — the #100 lesson.
- **LLM failure degrades to per-message classification**, never to unfiled mail.
- **Corrections taught via Fix now steer the status determiner too** (same contract as the classifier prompt); cleanup-rule guidance is deliberately excluded from that prompt as noise.
- The gate SQL and the `actions_taken @> '"MOVE_FOLDER"'` containment predicate were both exercised against the live database before landing.
