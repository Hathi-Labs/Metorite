## Description

## What this is

The **App Workshop / Custom Apps** feature: team members build small internal web apps by chatting with an LLM builder (live sandboxed preview beside the chat) and publish them inside CommandCenter for the whole team — filling the `/build/apps` &#34;Custom Apps&#34; nav slot that previously 404&#39;d.

## Contents

**Planning (docs/app-workshop/):** full RFC — architecture, `window.cc` capability bridge, data model, security/execution model (client-side sandboxing, dependency isolation, T3 forward path), testing model, 4-phase roadmap, prior-art survey.

**Phase 0 — the loop works:** migration `114_custom_apps.sql`; gateway `routes/apps/` (lifecycle, containment-guarded files, publish/rollback with immutable versions, App Runtime API); `agent-app-builder` + executor `allow_session_workspace` binding; `/build/apps` gallery, Workshop, and run pages with the `window.cc` bridge. **Platform contract (RFC §4.0, binding):** CommandCenter is the app&#39;s only backbone, enforced by builder refuse-and-redirect instructions, sandbox physics, a publish-time conformance scan, and runtime scope checks.

**Phase 1 — durability &amp; workshop UX:** migration `115_app_files.sql` mirrors draft workspaces into Postgres with lazy rehydration; git checkpoint on every sync with additive restore; console drawer with &#34;✦ Fix with AI&#34;; &#34;Make live&#34; rollback UI.

**Phase 2a — platform integrations:** migration `116_app_tool_grants.sql`; `cc.tools.call()` — a scope-checked, human-confirmed, fully-audited proxy to platform integrations (ClickUp first), reusing the existing Action Broker end-to-end — the Approvals inbox needed zero UI changes. Windmill-style frozen-param scopes; per-use confirm or remembered grant; org-wide write-scope publishes get an always-on admin-review gate keyed to the scope set. Broker actions namespaced `app._` to avoid colliding with each product surface&#39;s own actions.

**Phase 2b — testing &amp; evaluation:** test scenarios (`tests.json`, a workspace file — no new backend route) run against an **ephemeral, in-memory `cc` store**, never the real backend — a test run never creates a real ClickUp task, spends real AI budget, or touches real app data, which is what makes it safe to auto-run after every builder turn. A hidden offscreen iframe + small in-frame `click`/`type`/`select` helpers (zero new capability — the app already owns its own DOM) drive real interaction, so a scenario catches UI-wiring bugs, not just backend logic. Scenarios are authored conversationally by the builder (mirroring the platform&#39;s own `evals/` &#34;one golden case per behaviour&#34; convention) and reviewed as a plain-English checklist in a new Workshop Tests tab, with a pass/fail badge near Publish, &#34;✦ Fix with AI&#34; on regression, and a publish-modal status banner.

**Phase 3a — sharing &amp; consent:** `app_grants` CRUD (`GET/POST /{slug}/grants`, `DELETE /{slug}/grants/{subject}`, edit-gated upsert) behind a new &#34;Specific people…&#34; publish-visibility option — an email-chip picker, prefilled from existing grants. A blocking first-open consent interstitial on the run page lists the app&#39;s LIVE (published+reviewed) scopes in plain language before the bundle is even fetched; `GET /{slug}` computes `needs_consent` server-side (always false for owners/editors), and `POST /{slug}/consent` re-verifies the client&#39;s claimed scope-set hash against the real LIVE version, 409ing `scope_set_changed` on a stale view rather than silently recording consent to outdated scopes.

**Phase 3b — apps as agent tools:** a new manifest `actions` block (`storage.list`/`storage.get`/`storage.set`/`tool.call`, `gateway/routes/apps/actions.py`) is the reverse direction from `cc.tools` — named, typed capabilities that let callers OTHER than the app itself (the REST API, and now platform agents) invoke into an app&#39;s data and logic. `readonly` is derived, never manifest-trusted. Granting an app to `agents:*` or `agent:<name>` (the same `app_grants` row Phase 3a introduced) makes its actions callable as ordinary tools on every orchestrator run (`orchestrator/app_tools.py`, dynamically-built per-action tools with a real per-action JSON schema) — routed through `_inject_agent_tools()`&#39;s existing risk-gated pipeline (`_gate_injected_tool` → `permission_policy.decide()`), deliberately **not** the `_load_specialist_agents_as_tools()` whole-agent-as-delegate path, which bypasses that permission gate entirely. Storage actions and readonly reads auto-apply for any caller; a non-readonly `tool.call` auto-applies only for a person who can also edit the app, else always queues for human approval — no bypass for an unattended agent caller.
