## Description

P0 from the context/output-budgeting review. Two defects, both proven against the live gateway.

## 1. The real output cap was 4096 — and the knob we'd been tuning is dead

`/v1` is THE choke point every agent runtime POSTs through, so its `max_tokens` default IS the platform's output cap whenever a caller omits the field — and **the Copilot SDK always omits it**: its create/resume-session wire protocol has no `max_tokens` field, so neither `COPILOT_MAX_OUTPUT_TOKENS` nor the SessionConfig `max_tokens` we set ever reached the model.

So every Copilot agent was capped at **4096**, which cut the model off *mid tool-call*: it emits a large file's content as a tool argument, gets truncated, and the malformed JSON fails the call — `"Unterminated string in JSON at position N"` (seen on `technical-project-planner` at 12997 and 16340 ≈ 4096 tokens).

**Measured on the live gateway (deepseek-v4-pro):**

| request | completion_tokens | finish_reason |
|---|---|---|
| no `max_tokens` (what the CLI sends) | **4096** | `length` ← truncated |
| `max_tokens=32000` | **10940** | `stop` ← finished naturally |

Default is now `GATEWAY_DEFAULT_MAX_OUTPUT_TOKENS` (32000, env-tunable).

**Why not clamp to the model's registry max_output?** litellm's bundled registry claims this model caps at 8192, yet it demonstrably emits 10940 — clamping to that stale value would reintroduce the truncation. `max_tokens` is a *ceiling* (the model stops when done, per `finish_reason="stop"`), so a generous default only removes an artificial cut. Verified accepted by the whole active fleet (deepseek-v4-pro / tier-powerful / tier-fast / auto all 200 at 32000). A per-model resolver is the follow-up once limit data is trustworthy enough to clamp on.

`.env.example` previously told operators to raise `COPILOT_MAX_OUTPUT_TOKENS` when *"the agent stops mid-response with no text"* — exactly this symptom, exactly the knob that does nothing. Now documented as a no-op.

## 2. The BYOK compaction mitigation was dead on the streaming path

`_inject_agent_tools` installs the `_apply_copilot_infinite_sessions` wrap, then `run_agent_stream` **rebinds** `agent._create_session` (executor.py:2361) — discarding the wrap before `agent.run()` calls it. So the Copilot backend kept running its default 0.80/0.95 compaction against its wrong ~90K BYOK window guess: the exact false "context length exceeded" the mechanism exists to prevent.

The policy now lives in one place (`effective_infinite_sessions`) and is applied by the CommandCenter session methods directly, on **both create and resume** (a resumed session rebuilds config from scratch). Independent of binding order; the wrap is kept for shapes that are never rebound and shares the same policy so they can't drift.

**Why the tests missed it:** they exercise the wrap in *isolation* and never simulate the rebind — all 14 stayed green while production bypassed the fix.
