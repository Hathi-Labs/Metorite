## Description

An audit of "do schedules survive a restart?" found something worse than a durability gap: **the schedule trigger did not work at all.** This fixes that and three related defects, all on the path a first real automation takes.

## The bootstrap trap (the big one)

`compute_due_fire()` only looks forward. With `last_fired_at IS NULL` it asked *"is the NEXT tick already in the past?"* — false at every instant except an exact tick boundary. So a new schedule produced no tick, never got a `last_fired_at`, and therefore produced no tick. Forever.

Simulated over a week of 30-second scans:

```
before:  new daily 09:00 schedule -> 0 runs in 7 days
after:   same schedule            -> 7 runs   (weekdays-only correctly gives 5)
```

The scanner now **arms** an unseen trigger (`_claim_baseline`, guarded on `last_fired_at IS NULL`) instead of firing it — a cron says *when*, not *how far back to catch up*.

Second half of the same bug: `update_workflow` rewrites trigger rows wholesale, so **every canvas save reset `last_fired_at` to NULL**, dropping the already-fired-this-tick guarantee and parking the schedule back in the dead state. Fire state now carries across for unchanged schedules (`_trigger_identity` = kind + cron@timezone); editing the cron or zone deliberately re-arms, so moving a 9am job to 10am can't fire a surprise catch-up.

## Timezones

Cron was UTC-only, so "weekdays 9am" meant 9am in London and 2:30pm in Bangalore — and drifted an hour twice a year anywhere with DST. Schedules now carry an IANA zone (`config.timezone`, default UTC) validated at save time alongside the expression: an unknown zone is a 422 the maker can act on, not a schedule that silently never runs. The zone is a wall clock, so 9am stays 9am across a DST change.

## No silently dropped ticks

The CAS claim commits *before* `start_run`, so a tick refused afterwards — concurrency cap reached, published version missing — was consumed with only a log line, leaving an unexplained gap in run history. Every path out of a claimed tick now writes a terminal run row with the reason. Recorded as `cancelled`, not `failed`: the workflow didn't break, the platform declined to start it, and being busy must never feed the auto-disable policy.

## Webhook URLs that the sender can actually call

The editor built the URL from `window.location` — the control plane, whose `/api` proxy does `JSON.stringify(await req.json())`. That changes the bytes, so an HMAC the sender computed **can never verify**, and non-JSON bodies (plenty of providers post form-encoded) arrived as `{}`. The UI was offering a secret field that was guaranteed to 401.

The gateway now names its own public URL (`PUBLIC_API_BASE_URL` → `hook_url`/`hook_path`), and shows the path with an explanation when that origin is unset rather than inventing one that 404s in production. A raw-passthrough Next route is the safety net for a control-plane URL someone already copied: byte-exact body, caller's headers, no internal bearer attached — the token in the path is the whole credential.

## Durability, now documented

Spec §3.3a is a full matrix of what survives what (restart while idle / mid-run / mid-wait / mid-approval, multi-worker CAS, downtime catch-up, clock skew). Short version: **the schedule is a database fact and the scanner is a stateless reader of it** — there is no OS cron and no scheduler daemon; APScheduler is a parser only.

## Testing

23 new tests: cron maths pinned across timezones and a DST boundary, arming and firing as separate tests, both dropped-tick paths asserting the recorded reason, the CAS pinned so a losing worker starts nothing, and save-preservation pinned in both directions. Full suite **3,062 passed**; frontend typecheck and lint clean.
