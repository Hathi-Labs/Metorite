## BO-6 — a migration ledger

Every deploy replayed **every** numbered migration — 152 files. That worked only because each is hand-written to be idempotent: a property of 152 authors' care rather than of the system, and one nobody had ever checked together.

The cost was not only time. `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` still takes ACCESS EXCLUSIVE when the column is already there, and on 2026-08-06 one such queued ALTER, behind a session left `idle in transaction`, froze every later reader of that table and took the app down. **Asking for 150 locks we do not need was the exposure.** A steady-state deploy now applies 0 files and takes 0 of them.

`schema_migrations` (migration 152) records filename + sha256 + duration. The runner skips what is recorded, and:

- a file whose checksum **changed** after it was applied is re-applied and named loudly, not refused — every file here is idempotent and the repo's workflow assumes an edit re-runs, so a hard failure the day the ledger arrived would break deploys for a legitimate fix. It is still a real bug class (a box that hasn't deployed since the edit runs the *original*), so it's reported;
- rows are written **after** success — a row for a failed migration would make the next deploy skip it and the schema silently diverge;
- `MIGRATION_REPLAY_ALL=1` restores the old behaviour for recovery.

**Verified on a real Postgres 16, not asserted:** fresh replay applies 150 files and creates 139 tables; the second and third runs apply 0. Change detection and the replay switch both exercised.

**Guarded by CI** — the ladder is replayed from empty on every PR and the repeat must be a no-op. "The 152 files are idempotent" was a claim about work nobody had verified as a whole; it's a build step now. It also catches a migration that only fails on a *fresh* database — the state a rebuilt stack or a restore lands in, previously undetectable until somebody hit it.

### A latent bug found while testing

With `shopt -s nullglob` a pattern matching nothing is **removed**, so `ls "$DIR"/[0-9][0-9]*_*.sql` collapsed to a bare `ls` — listing the current directory and handing psql whatever it found. First symptom: a syntax error in `AGENTS.md`. A mis-set `APP_DIR` would have done exactly that in production. It now fails with the directory it looked in.

Not Alembic yet — no autogenerate, no down-migrations, no auto-apply on `docker compose up`. The ledger is what Alembic needs anyway (`alembic_version` is the same idea) and the piece that pays for itself immediately.

## Two theming fixes (reported against the shipped engine)

**An accent override never brought its own ink.** `ACCENT_PROPERTIES` set `--primary`, `--ring` and `--sidebar-primary` but not `--primary-foreground` — the ink drawn *on* that fill. So the accent landed under whatever ink the theme chose for its **own** primary. On Graphite dark that's near-black (Graphite's primary is near-white), making the sidebar logo a near-black glyph on a red badge. Measured `rgb(20,20,20)`. It was never only the logo — every primary button, active pill and badge had it.

`accentInk()` picks black or white by relative luminance. The ink is computed **when the accent is stored** rather than recomputed in the pre-paint boot script — that script is a template string that can't import, so the alternative was a minified second copy of the luminance maths inside it, the kind of duplicate that drifts and that no test can reach.

**The collapsed rail had a native scrollbar.** `<nav>` scrolls but never opted into `.scrollbar-thin`, which `globals.css` has had all along — so it got the platform default: ~15px with stepper arrows, a quarter of the 56px collapsed rail, shoving every icon off-centre. Now 0px of layout width.

Regression tests added for both, including that the chosen ink *beats the alternative* on every Settings preset — a weaker test would pass by always answering black.
