## BO-20b Slice 1 — `emit_event` strict mode, and the blocker that **isn't** closed yet

**Stacked on #340** (BO-20a). Merge #340 first, or retarget with `gh pr edit --base main` **before** merging it — merging the base with `--delete-branch` auto-closes this PR.

### What shipped

Retry and DLQ logic needs to know a sink failed. `emit_event` swallows every sink exception, so today it cannot. This adds a **keyword-only** `raise_on_error: bool = False`:

- **`True`** — the first sink exception propagates; remaining sinks are skipped.
- **`False`** (default) — unchanged, and unchanged **deliberately**. All three webhook receivers schedule `emit_event` through `BackgroundTasks` with three *positional* args, so nothing they do can reach the new parameter, and a webhook must never 5xx because a workflow failed.

### 🔴 The finding three passes missed — and why this PR claims less than it looks like

**Making `emit_event` capable of raising does not make it raise.**

The only sink registered in production is `_wf_dispatch` → `dispatch_event` (`gateway/main.py:1074` — the sole `register_event_sink` call site in the repo). Its **entire body** sits inside `try:` / `except Exception`, with the docstring:

> *"Best-effort and **never raises** — event delivery must not break the webhook receivers that call it."*

Its return value carries no signal either: `started` is `[]` **both** when no workflow matched and when the DB threw.

So Slice 2 would have called `emit_event(..., raise_on_error=True)` against an unreachable Postgres, seen it return cleanly, `XACK`'d, and **dropped the event** — exactly the silent loss BO-20b exists to abolish, reproduced *through* BO-20b, with a full retry/DLQ suite green against a raising **fake** sink that does not exist in production.

The spec said *"blocker — SHIPPED in slice 1; do not rebuild."* It now says **necessary but not sufficient**, and Slice 2 grows to give `dispatch_event` a matching strict path.

Striking that non-goal **grows Slice 2 into the gateway package** (`triggers.py` joins its Files list). Marked `DECISION (agent-proposed, owner may overrule)` in three places, with the rejected alternative stated: *leave `dispatch_event` alone and accept that BO-20b cannot deliver its guarantee.*

| Propagate | Do not propagate |
|---|---|

### Also fixed in the spec — all the same class of defect: criteria that pass without the behaviour they name

- **The two prescribed constants contradicted each other.** `_backoff` yields `1,2,4,8,16 s` while `_RECLAIM_MIN_IDLE_MS = 60_000` floors re-delivery at 60 s — so under the section's own PEL-and-reclaim prose, the backoff function was **dead by construction**. Mechanism chosen and recorded: **PEL-and-reclaim**, `_backoff` struck, `_RECLAIM_EVERY_SECS` prescribed instead. The deciding argument is that the attempt counter becomes Redis's own `times_delivered`, which **survives a consumer restart** — an in-process dict resets, so a poison entry would loop forever and never reach the DLQ.
- **Nothing pinned `_backoff`'s call site.** Every criterion asserted its *shape*: define it, assert the algebra, never call it from the loop, all green. The replacement done-when is behavioural through the loop against a faked client.
- **`XAUTOCLAIM … JUSTID` is now forbidden in writing.** It suppresses the counter increment the whole design depends on — `times_delivered` freezes at 1, `MAX_ATTEMPTS` is never reached, no entry ever reaches the DLQ, **every prescribed test passes**. It also returns a bare id list that unpacks *silently* into a three-element destructure, so the trimmed-entry tripwire wouldn't catch it either.
- **The done-whens sourced `times_delivered` from `XAUTOCLAIM`, which doesn't carry it.** Only `XPENDING` does. Read order is now pinned, because before-vs-after the increment is the difference between a threshold of **5 and 6** — and the fake-based test passed either way.
- **"A reclaim can never steal an entry this process is still working on" was true by accident.** It holds because the loop is *serial*, not because `60_000 > 30_000`: entry *k* of a 24-entry batch idles (k−1)×30 s **while still queued in-process**, so the bound breaks the moment BO-20e adds concurrency or a second worker appears. Constraint recorded on BO-20e's ticket.
- **Three accepted costs were unstated:** per-stream **ordering** is given up (a stale payload can start a run after a fresher one); `times_delivered` counts *deliveries* not *failures*, so a crash-loop burns retry budget on a healthy event — and lands it in the DLQ during exactly the incident where you least want silent loss; and the counter does **not** survive a *Redis* restart — the group is re-created at `$`, and there is no `appendonly` anywhere in `infra/`.
- **A `ValueError` in a top-of-iteration reclaim wedges the whole drain loop**, not just the reclaim — the `try` spans both `_ensure_groups` and `_drain_once`, so the bus stops draining entirely at ~1 Hz. The reclaim must be wrapped to degrade to "no reclaim this cycle".
