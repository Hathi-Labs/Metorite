## Description

## WS-13 — Centers were unreachable by everyone, owner included

### The defect

`allowed_features()` (`packages/acb_auth/acb_auth/permissions.py:321-323` pre-fix) is
`tuple(f for f in FEATURES if self.can_use_feature(f))`. `FEATURES` was sixteen literal
slugs with **no `center.*` entry**, so:

- `GET /auth/me` (`routes/admin/me.py:84`) returned a `features` array containing no Center
  slug **for every principal**.
- `lib/nav.ts:229-232` filters items by `allowed.has(p.feature)`; `:233` then drops any
  section whose items emptied — removing the **section heading** too.
- `/centers/sales` hit `AccessGate`'s "You don't have access to this" — **for the owner**.

An owner holding `*` and an admin holding `feature:*` *do* match `feature:center.sales`
under `permissions.py:198-207`. But nothing ever asked, because the slug was never a
candidate. **`140_center_features.sql:5-7`'s own comment — "owners and admins see all
Centers via their `feature:*` baseline" — was false as written.**

`feature_catalog` is never read for nav or authorization. Its one runtime read
(`routes/admin/roles.py:345-356`) feeds the admin role editor only.

### The part that makes this worse than a missing entry

`validate_permission` is grammar-only (`permissions.py:167-193`) and **accepts**
`feature:center.sales`. So granting always worked — and
`routes/admin/groups.py:341-362` has been **writing `allow feature:center.<slug>`
overrides since 2026-08-01** whenever a member joins a Center group, pinned by
`tests/unit/test_admin_groups.py:338`.

**The system has been writing grants it could not display.**

⚠️ **Operational consequence of merging:** those existing override rows become effective
immediately. Centers will appear for those members with no admin action. Intended, but
this is not a "nobody gains until someone grants" change.

### The fix

Six slugs added to `FEATURES` in `140_center_features.sql:20-25` sort_order. Order is
load-bearing twice — `allowed_features()` emits in tuple order, and
`routes/admin/members.py:540-543` renders the member access editor in tuple order.

Plus two consistency edits the same defect had left behind: `types.ts:55`'s
`category` union was missing `"centers"` while the DB already emits it, and the roles
page rendered every chip under a hardcoded "Apps" heading.

### 🔴 The real fix is the invariant, and it took two rounds to get right

The root cause is not the tuple. **Three registries were kept in sync by comment only**
and drifted. The first attempt added an invariant test — and two reviewers, independently,
found it did not hold:

**Hole 1 — vacuous if its own source empties.** It derived the expected six from
`CENTER_GROUP_SLUGS` and then iterated *that*. The verifier emptied `CENTER_GROUP_SLUGS`
to `()` and re-ran: **`1 passed`**. It defended the regression that happened, not its
mirror image.

**Hole 2 — it pinned the wrong registry.** The UI reads `lib/centers.ts` (feeding
`nav.ts:113` and `access.ts:66`). The test pinned `groups.py`. Nothing connected them —
so following the documented recipe at `department_centers.md:178`, *"a `lib/centers.ts`
edit + one feature row"*, **reproduced this entire bug with a fully green suite**.

The documented recipe still produced the bug the branch exists to fix.

Both closed. `test_every_center_has_a_feature_slug` now asserts against a literal anchor
before iterating; `test_centers_registry_matches_the_feature_vocabulary` **parses
`centers.ts` from disk** and checks both directions — a Center whose feature is missing,
and a grantable `center.*` reaching nothing. A missing registry file **fails, it does not
skip** (a test that skips in CI protects nothing).

`department_centers.md` §2 now carries a five-place registration checklist naming what
each omission breaks and which test enforces which row.

### Corrections found along the way
