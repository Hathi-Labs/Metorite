## The spec — `people_center_app.md` rewritten to v2

- **§3 — the field inventory.** Every field states the question it answers, its read tier and its write class. **§3.6 lists what is refused**: date of birth (`birthday` is `MM-DD`), compensation, performance ratings, home address, a free-text HR-notes field — each with a reason, so their absence is a decision rather than an oversight.
- **§4 — the access model.** Three read tiers (directory · HR · private), three write classes (admin · self · derived), and one self predicate: `lower(caller.email) = lower(person.email)`. It is safe **only because migration 148 made that column partially unique** — before it, "edit yourself" could have edited somebody else.
- **§5 — the sub-app roster**, including §5.7 rewritten as the people-management dashboard (projects per person, tasks with deadlines, behind/at-risk/overloaded/idle/on-track as arithmetic over dates, department rollup, idle↔behind rebalancing).
- **§6.5–§6.8 — the AI contract.** What a server-side heuristic may read versus what may be rendered to a human; a suggester that ranks candidates and **never assigns**; follow-ups **drafted and queued**, because sending is the existing owner-gated outbound-nudge item and this row may not flip it.
- **§12 — D-PC-1…D-PC-18.**

## WS-28g — the person profile and self-service editing

- **Migration 171** — 20 nullable columns, expand-half only (R6). No CHECK over live data, so the two new vocabularies are validated in the route against one shared tuple, exactly as `status` has been since 148.
- **`routes/people/fields.py`** — the one field-class authority. The fence (R7) **discovers every `gtd_people` column from the migrations** and fails an unclassified one, so a column added next month cannot default into the permissive answer.
- `GET /people/me` with three distinct states, `PATCH /people/{id}` authorized by class and **refusing by name** (a save that succeeds and discards half the form is worse than a refusal), self-service CV upload through the existing parse pipeline.
- `/people/me` and the person page render the same panels, **from the server's `editable_fields`** — the client never carries its own class map.

**Three silent defects found while building:** `create_person` accepted every profile field and stored none of them; the self write door was about to return the *admin* projection of whoever was patched; and the Center's icon had no Fluent/Material mapping and would have rendered in the wrong style.

## WS-28g-2 — your own profile is not behind the directory's gate

`feature:people` is `is_default false` and routes match by prefix, so `/people/me` inherited the directory's gate: **an ordinary colleague could not open their own profile.** The one surface built for "every person maintains their own record" was reachable only by people granted the org roster.

The rule now (D-PC-15): the directory is gated, your own row is not — the same argument that made `/access` the one ungated pane. The build improved on the plan: the ungated paths carry **no person id at all** (`/people/me`, `/people/me/resume`), so there is nothing to address but yourself. That is structural where "check the id is yours" is a check a refactor can drop. Ungated is not unchecked — the field classes apply unchanged.

`UNGATED_ROUTERS` joins the enforcement registry beside `GATED_ROUTERS`: *"deliberately open"* and *"nobody checked"* must not look the same to the next reader.
