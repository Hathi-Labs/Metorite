## Description

Follow-up to #99, which found this on its first run.

## What was happening

**138 rule applications in 30 days returned 404 from Graph.** Every one logged `status='APPLIED'` with `actions_taken='[]'`. The rule matched, the mailbox was never touched, and no surface said so.

### Cause 1 — we invalidated our own message id

Outlook re-keys a message when it moves: `/move` returns a new id and the old one 404s. Inside a single rule, `_apply_rule_actions` already threads the new id forward. But the per-match loop calls it **once per matched rule from a row fetched before the loop**, so with `multi_rule_execution` on (it is) the second rule called Graph with the id the first rule's `MOVE_FOLDER` had just invalidated.

Traced end to end on one message:

| 03:57:43 | Cold Email | `MOVE_FOLDER` → succeeds, message re-keyed |
| 03:57:43 | Marketing | `LABEL` + `MOVE_FOLDER` → **404 on the stale id** |

46 of the 138 had a sibling rule that moved the message in the same run.

Fixed by re-reading the current `provider_message_id` before acting. `_apply_rule_actions` already persists it, so no signature threading is needed, and it also catches a re-key done by anything else.

### Cause 2 — the provider racing us (not fixable here)

The other ~92 are Outlook's own junk/delete filtering re-keying or removing a message between our sync and our call; 92 of the 138 ended in `trash`. Not preventable from this side — which is exactly why the status has to be honest about it.

### And `APPLIED` was load-bearing

- `_sender_consistent_for_rule` counts `APPLIED` rows as evidence → **three failed runs were three votes for pinning a sender to a rule forever**, off a mailbox that was never modified. This is a **fourth** defect in the gate audited in #97 (after dry runs counting, log rows counting as messages, and multi-rule ambiguity).
- Analytics counts `APPLIED` as "handled for you", overstating the assistant on the screen built to measure it.

## Changes

- `FAILED` when every action errored; `APPLIED` when any succeeded (errors ride along in `action_errors`); `PENDING` unchanged. Auto-learn is now gated on the computed status, not on `apply`.
- **Migration 86** backfills the 184 rows written under the old rule. The predicate is exact, not heuristic: nothing taken **and** at least one error. `actions_taken='[]'` with no errors is a rule with an empty action list — a no-op by configuration — and is left alone.
- History **shows** `FAILED` rows instead of filtering them out, in rose with "didn't apply" — distinct from the green of a real apply and from the red of "no match", because a rule that correctly decided to do nothing is not the same as one the mail server refused.

## Effect on the patterns awaiting review

Replaying the corrected gate over the 21: **one drops below the bar** — `anil.pradhan@haigcapital.com → Cold Email` had three votes, one of which was a run that failed entirely. The other 20 are unaffected.

11 new tests; 617 email tests green.
