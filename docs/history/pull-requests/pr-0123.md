## Phase 2 · item 2.4 (remainder)

The cc/bcc half of 2.4 shipped in #119; this finishes it by carrying **attachment content** on the draft, killing the last arm of the three-way native-vs-full-send branch in the composers.

### Before
Draft transport carried To/Cc/Bcc but not files. Any reply/compose with an uploaded file or an AI artifact fell back to a fresh full send — which starts an **unthreaded** message and discards the auto-saved draft.

### After
- `update_draft` gains an `attachments` param across `base`/`outlook`/`gmail`. Outlook POSTs the files to the draft's attachments collection (the same endpoint `create_draft` already used); Gmail rebuilds the draft as a MIME multipart.
- `DraftUpsertRequest` carries `attachments` (base64) + `artifacts` (workspace refs), resolved to provider bytes by `_resolve_draft_attachments` — reusing the exact resolution the `/send` path does (base64 decode + `load_artifact_attachments`).
- The local mirror sets `has_attachments` **sticky-true**, so a later attachment-less auto-save can't clear the flag.
- Both composers (`ComposePanel`, `EmailDetail`) now save-the-draft-with-attachments → native send whenever there's a draft **or** attachments; a plain no-attachment message still sends fresh.

### Why it can't duplicate
Attachments ride only on the **explicit pre-send save** — the debounced auto-save omits them — so `update_draft` uploads each file exactly once. `/drafts/send`'s body-only re-sign PATCH doesn't touch the attachments collection, so they survive to the native send.

### Tests
`tests/unit/test_email_draft_attachments.py` — Outlook update/create upload the bytes; a body-only autosave never touches `/attachments`; the resolver decodes base64 and rejects bad encoding. All green; blocking ruff + full `tsc` clean.
