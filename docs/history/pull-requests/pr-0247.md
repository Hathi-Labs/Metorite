## Description

Clicking a display name, avatar orb, or any To/Cc recipient in the mail app opens a people card — the Outlook affordance. Reading a card also files what it learned, so the mailbox accumulates a contacts directory as a side effect of being used.

## The card

`GET /email/contacts/card` (`transport/contacts.py`) → `ContactCard.tsx`:

- **Identity** — name, address, job title · company, each with a copy button
- **Actions** — *Email* (opens the composer to them), *All mail* (searches every folder for `from:`)
- **Contact details** — phones as `tel:` links, organisation, links; copy button on every field
- **Relationship** — `47 received · 31 sent · 2 unread · last 2d ago`, sender category, and an *Unsubscribed* / *Auto-archived* chip when the Cleaner is suppressing them
- **Recent mail** — last 3 messages as previews; clicking one opens it and closes the card

Wired into the reading pane's sender block, its To/Cc lines, and every message header in the conversation view. The popover portals to `<body>` so the scrolling pane can't clip it, flips above/left near a viewport edge, sizes to available room, and becomes a bottom sheet under 480px.

`ConversationView`'s message header changed from a `<button>` to a `div`: the trigger renders a real `<button>`, which a `<button>` row can't legally contain.

## Where the data comes from

There is no contacts table upstream and no directory to read from. Everything is derived from mail already in the caller's own accounts — every query goes through `core._account_scope`, and the caller's own drafts are excluded from "mail from them" (some providers echo the counterparty into `from_address`).

Phone / title / company are parsed from the sender's own signature block. That is the only place the card guesses, so it is deliberately conservative:

- cuts at the first quoted-reply banner, so a reply's "signature" is never the person being replied *to*
- requires a label or a country code before believing a digit run is a phone
- declines to guess a title without the display name to anchor on
- order numbers, invoice totals, dates and marketing plumbing yield nothing
- free-mail domains never become an organisation

## The directory (migration 119)

Each card open upserts into `email_contacts` — name, title, organisation, phones, links, with `source_message_id` + `parsed_at`. The card then renders the **merged** row, so a phone an older signature taught us survives today's one-line reply.

Invariants, each pinned by a test:

- **`manual_fields[]` is permanent** — names the columns a human edited; the parse skips them forever. Without it the next mail silently reverts a correction, which is the one failure that would make a contacts view untrustworthy.
- An empty parse never blanks a stored value.
- Derived facts (counts, first/last seen) are never stored — they are a live query and would be wrong the moment mail arrives.
- The domain→company guess is display-only, applied *after* the write, so the directory is never seeded with invented company names.
- The write is best-effort; a failure costs the caller the directory entry, never the card.

An optional `name` param means someone you only ever write *to* — no `from_address` to read a name from — is still filed under their name.

## Notes for the reviewer

- **`schema.generated.sql` is not regenerated.** It needs a live fully-migrated DB and this environment has no pgvector. It already lags (migration 118's table is missing too), so this matches current practice — but it is worth a regen on the VPS.
- **The message list is deliberately untouched.** Its rows have no avatar and the sender name sits inside the row `<button>` carrying selection, long-press and context-menu handlers; nesting a trigger there risked breaking list selection for little gain. Outlook's list doesn't open a card from the sender name either.
- **`ai-company-brain/specs/email_app_master_plan.md` §3.14** documents what the table already gives a future Contacts view and what still needs building. Two things want an owner call before that view ships: how two addresses for the same human merge (retrofitting identity onto a flat address table later is the expensive version), and photos (Gmail People / Graph need OAuth scope the app doesn't request).
