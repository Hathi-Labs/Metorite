## Description

Follow-up to the access-control series (#286, #290, #291, #293, #296). Merging it onto `main` surfaced two collisions with WhatsApp avatar work that landed independently. **Both were caught by tests, not by review.**

## 1. Migration number collision

`128_whatsapp_avatars.sql` reached `main` while `128_org_access_control.sql` was in flight. `test_migration_prefixes` asserts numeric prefixes are unique, and failed.

Renumbered **the access-control pair**, not the avatars migration, since that one reached `main` first: `128 → 130`, `129 → 131`.

**Both had to move**, not just the colliding one. `131` seeds roles that `130` creates, and `apply_migrations.sh` applies in lexical order — leaving the second at `129` would have run it *before* its dependency, silently seeding nothing.

Every reference updated: the SQL headers, the `migration:128` `assigned_by` marker, four Python modules, two frontend modules, four `AGENTS.md` files.

## 2. `/whatsapp/bridge/avatars` would have broken

The new bridge endpoint carries no `UserContext` — correctly, since the Go bridge authenticates with `X-Bridge-Secret` via `bridge_secret_ok`. But both the feature gate (#290) and the app-wide default-deny guard (#296) would have **401'd it**.

That wouldn't have restricted access. It would have **silently stopped avatar sync**, with no error attached to it — exactly the machine-entrypoint failure mode the enforcement test was written for. It fired on the first real collision.

Added to the whatsapp router's exempt list, to `gateway.main.PUBLIC_ROUTES`, and to the enforcement test's expected set.

## Verification

- The renumbered migrations applied in lexical order against a fresh Postgres 16 — `130 → 131` dependency satisfied, role backfill correct (`admin,owner` and `member` as expected).
