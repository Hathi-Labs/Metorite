## Description

## Why

`main` currently has **two** pairs of migrations sharing a numeric prefix, so `test_migration_prefixes::test_migration_numeric_prefixes_are_unique` fails. Because CI tests each PR *merged onto `main`*, this makes the **Unit tests** check red on **every open PR**, not just the ones that introduced the clash.

```
93: 93_gtd_planning_prefs.sql   +  93_rename_reply_to_needs_reply.sql (#170)
94: 94_gtd_day_templates.sql    +  94_email_voice_profile.sql (#176)
```

Both clashes came from the calendar work (`80722e1`, `2ec1be5`) picking numbers that #170 and #176 had already merged.

## What

Renumber the **later-merged file in each pair** (the calendar ones) to the next free slots — 95/96 are already taken by note-taker + deep-work:

```
93_gtd_planning_prefs.sql  →  97_gtd_planning_prefs.sql
94_gtd_day_templates.sql   →  98_gtd_day_templates.sql
```

Pure `git mv` + a one-line note in each file's header. No SQL body changes.

## Why this is safe against production

`scripts/apply_migrations.sh` has **no tracking table** — it re-applies every `NN_*.sql` on each deploy, idempotently, in `ls | sort` order. So a migration's number is *only* its relative apply-order, not an identity the DB has recorded; renaming a file cannot make it "re-run" or "double-apply" (it already runs every deploy and no-ops via `IF NOT EXISTS`).

The only real constraint is ordering, and both moved files are safe to move later:
- Each is an additive `ALTER TABLE gtd_settings ADD COLUMN IF NOT EXISTS …`.
- Both depend only on `48_task_manager_gtd.sql` / `77_gtd_calendar_prefs.sql` — far earlier, still ordered before them.
- Neither has a downstream dependent: `96_gtd_item_deep_work.sql` touches `gtd_items` (a different table), and nothing else references `planning_prompt` / `day_templates`.
