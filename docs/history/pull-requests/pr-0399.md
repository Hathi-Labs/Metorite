## ⚠️ Read first — merged with `main` on 2026-08-09, and it found a defect there

`main` landed the SaaS multi-tenancy programme (#404, MT-0a…MT-1i) while this branch was open. It is merged in, not left to rot. Three things changed:

**1. Migrations renumbered.** Main's H1 applied *its* 157/158/159 on a full-ladder replica, so ours became **160** (`projects_recurrence`), **161** (`projects_tenancy`), **162** (`app_user_email_case`). Older commit messages here say 157/158/159 — they mean these.

**2. D-MT-2 is answered, and not by this branch.** **D15 — pooled, enforced by RLS** against an `app.tenant_id` GUC bound by `acb_common.db.tenant_session()`. `specs/saas_multitenancy.md` is canonical; `specs/multi_tenancy.md` here keeps its *measured* record and says so at the top. **WS-29c is struck** as superseded by MT-1b + MT-1c. Migration 161 stays, because the generated set is deliberately not replayed by `apply_migrations.sh` while `routes/projects/core.py` reads that column on every request — 161's header documents how the two compose.

**3. MT-1b would have failed in the maintenance window.** `gen_tenant_migration.py` scoped tables by column **name**. `crm_contacts`, `crm_deals` and `crm_activities` have an `organization_id` that `REFERENCES crm_organizations` — a *customer company*, not the tenant. So it emitted a no-op phase 1, then this, verbatim:

```sql
UPDATE crm_contacts SET organization_id = (SELECT id FROM organization WHERE slug = 'default')
 WHERE organization_id IS NULL;
```

Reproduced against a live Postgres 16:

```
ERROR:  insert or update on table "crm_contacts" violates foreign key constraint
        "crm_contacts_organization_id_fkey"
DETAIL:  Key (organization_id)=(52eb2a2d-…) is not present in table "crm_organizations".
```

On an **empty** table those same statements return `UPDATE 0` / `ALTER TABLE` and look healthy. It needs one real row — the condition production has and a fixture does not — and it fails *after* phase 1 has run.

Fixed at generation time instead of apply time: `discover_homonyms()` derives the conflicting tables from the migrations, `HOMONYM_BLOCKED` is the human sign-off, and the generator **refuses to emit and exits 1** when the two disagree. Blocked tables are named in every generated file's header, for whoever is holding the psql prompt.

> ### 🔴 Owner call this PR does **not** make
> Those three tables now carry **no tenant isolation at all**, and they hold customer CRM records. Blocking them makes the gap visible and stops it corrupting a business column; it does not close it. Closing it means renaming the CRM column across every CRM route and query. Deliberately **not** filed in `EXEMPT` — exempt means "needs no isolation", and that is where a hole would stop being reviewed. Written up in `multi_tenancy_leak_audit.md` §2.1.

## WS-29 — this branch's multi-tenancy half

Measured, not recalled: **143 app tables, 3 carried a real tenant key, 140 did not.**

- **Migration 161** — `organization_id NOT NULL` on all 17 `pm_*`, plus a parent-consistency **trigger** (a `CHECK` cannot read another table). That trigger is why 43 `INSERT` sites across 16 modules needed no tenant argument.
- **Migration 162** — `UNIQUE (lower(email))` on `app_user`, replacing a byte-exact constraint that let one human become two rows in two organizations.
- **S1-1 fixed** — the admin plane resolved its tenant from a hard-coded slug across 27 call sites: cross-tenant *write* into access control.
- **S1-4 fixed** — agents acted as whoever ran last (`ACB_AGENT_USER_EMAIL` process-global, never cleared). A live cross-**user** bug, not just a future multi-tenant one.
- **A 14-finding leak audit**, with a SAFE section and an honest could-not-determine section.

## Defects found in already-shipped code

1. **`_` and `%` were live LIKE wildcards** on every search — `task_id` also matched `taskXid`.
2. **WS-27j's `deliverable` probed only the project-grant closure** — assignees without a grant were judged undeliverable, so assignment notified nobody.
3. **`overdue`'s date half was never mirrored in the fake** — every `overdue` test since WS-27k was asserting only the status half.
4. **`/assigned-to-me` and `/my/inbox` had no visibility clause at all** — by design, since assignment *is* the claim. Under multi-tenancy, reachable by typing an address.
5. **The extracted deploy script was not shellcheckable** — no shebang, so shellcheck exited 1 having checked nothing.
6. **MT-1b's homonym**, above.
