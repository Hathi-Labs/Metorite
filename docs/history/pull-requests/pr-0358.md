## Description

## The defect

`MANIFEST.txt` states, in its own words:

> `# anchor row counts (a restore that does not reproduce these is wrong)`

and then lists `app_user`, **`email_message`**, **`gtd_task`**, `meeting`, `agent_run`.

Two of those are not tables. The real names are `email_messages` and `gtd_items`. So every backup this deployment has ever taken printed:

```
email_message:       n/a
gtd_task:            n/a
```

and `n/a` reads as benign.

## What was actually behind those two slots

Measured on the box:

```
email_messages:      7398
gtd_items:            717
```

**A restore could have lost the entire email mirror — the largest dataset in the system — without contradicting a single anchor.** The integrity check that exists to catch exactly that was pointed at nothing.

## The fix

Correct names, plus: an unresolvable name now reports `MISSING — anchor names a table that does not exist`, and a failed count reports `QUERY FAILED`. A wrong anchor is worse than no anchor, because it occupies the slot where the check should be and looks like it is doing the job.

## Verified against the live schema before committing

```
app_user:            3
email_messages:      7398
gtd_items:           717
meeting:             16
agent_run:           184
email_message:       MISSING — anchor names a table that does not exist
gtd_task:            MISSING — anchor names a table that does not exist
```

## Found while doing the first real restore test

`backup_db.sh --verify-restore` has now been run on the box for the first time:

```
==> Deep verify — restoring acb.dump into a scratch database
    public tables: live=228 restored=228
    restore verified
```

That is BO-23's hardest done-when — *a restore has actually been performed* — satisfied rather than asserted.

Two things it also surfaced, **not fixed here**:

- **`BACKUP_REMOTE` is unset**, and the script says so itself: *"this backup exists ONLY on this box. It protects against bad migrations and dropped tables, NOT against losing the VPS."*
- **`deploy/hostinger/acb-backup.{service,timer}` do not exist.** The runbook's §5 install step is `sudo install -m 0644 /opt/acb/app/deploy/hostinger/acb-backup.{service,timer} /etc/systemd/system/` — pointing at files that were documented inline and never committed. So the scheduled half of BO-23 cannot be installed as written. I have the unit contents ready but `deploy/` writes are owner-gated and the guard blocked me; they are in the handover.

Until a timer exists, backups happen only when a migration runs — which is why one exists today at all.

**Docs + one script.** No migration, no `deploy/` change.
