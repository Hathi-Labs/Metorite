## Description

A copilot watching only the transcript can tell *that* an objection was raised, but not who raised it or which deal it concerns — so its suggestions stay generic. This gives it the background that makes them specific.

## Three independent layers

| | Source | Needs |
|---|---|---|
| **1 BRIEF** | `meeting.copilot_brief` — a user-written briefing | nothing |
| **2 HISTORY** | past meetings sharing an attendee email, their summaries + still-open action items | nothing — it's our own database |
| **3 SYSTEMS** | `call_agent("agent-sales-assistant" \| "task-manager", …)`, fanned out in parallel | the agents registered |

Layer 1 is the highest-value source and deliberately first: no connector, no inference, and usually the only thing that knows what the meeting is *for*.

## Two load-bearing rules

**Assembled once, before the conversation.** An agent call takes seconds; a meeting moves faster. The pack is built at session start and cached, then rides along as compact `BACKGROUND` in both the decide and craft prompts — so context isn't re-paid per suggestion.

**Every layer degrades on its own.** No brief, no history, an unregistered agent, a timeout, Zoho not connected — each just omits its section. No combination breaks the copilot; it simply knows less. The console says so plainly when the pack is empty, rather than quietly being useless.

## Cost control

Layer 3 is **opt-in per session** (`live_session.deep_context`) because the fan-out spends tokens before a word is spoken — worth it for a customer call, not for a standup. Everything is capped on every axis, because the pack rides in *every* prompt and an uncapped history would quietly raise the price of every suggestion. Agents are instructed to answer `NONE` rather than narrate an empty result, so "I couldn't find anything" can't eat prompt budget every meeting.

## UI

A briefing box plus a **"what the copilot knows"** panel — so both *"why did it say that?"* and *"why is it being generic?"* are answerable.
