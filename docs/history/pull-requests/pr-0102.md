## Description

Three defects, all found by checking the live account after #99 / #100.

## 1. Classification was **not** behind — the panel was wrong

Analytics reported **142 uncategorized arrivals in 30 days** and advised running a backfill. Checked against the mailbox:

| where | count | state |
|---|---|---|
| junk / trash / drafts | 681 | already excluded from the figure |
| **inbox** | **125** | **all `rules_processed_at IS NOT NULL`** |
| user-created folders | 18 | genuinely never processed |

Then the decisive query — of those 125, how many have a thread status?

```
DONE 68 · AWAITING 32 · FYI 15 · NEEDS_REPLY 10   →  125 of 125
```

**Not one was unclassified.** Conversation mail is classified per-*thread*; the per-message `categories` array stays empty by design. The panel was counting correctly-filed conversations as outstanding work and telling you to spend model calls redoing it.

Now a message with no categories falls back to its thread's status, so `(uncategorized)` means what it says. The status enum is mapped to its display name — unmapped, the chart grew `Done 41` directly above `DONE 69`. Live 30-day result after the fix: **eleven categories, no uncategorized bucket at all.**

The real gap it still surfaces: **18 messages in user-created folders**, which the inbox-only rule run never touches.

> This is the third time in this workstream a number was shown under a label that didn't match what it measured, and the second one I shipped myself.

## 2. The scheduler passed a UUID where every signature said `str`

`asyncpg` returns `row.id` as a UUID object, and `_account_sync_loop` handed it straight into the shared new-mail pipeline. Anything that merely put it in a SQL parameter worked fine — so it stayed invisible for months, until the reply drafter did string work with it:

```
'asyncpg.pgproto.pgproto.UUID' object has no attribute 'strip'
```

The `LABEL` action on the same rule succeeded, so the rule looked healthy and just never produced a draft.

## 3. Failed runs had no way back

184 rows were stranded, and the only repair was re-running the rules — which re-classifies (model calls) and re-enters drafting.

`retry_failed_executions` replays the rule **already chosen**:

- no matcher → no model calls, no chance of a different decision
- `REPLY` / `DRAFT_EMAIL` / `FORWARD` / `SEND_EMAIL` / `CALL_WEBHOOK` refused outright — a retry re-runs a decision made weeks ago, and a label is idempotent where a reply is not
- each row re-read for its **current** `provider_message_id` — the stale id is what stranded them
- a row that fails again **stays FAILED**: ~92 of the live failures are the provider racing us and those messages are gone; flipping them to APPLIED would hide them exactly as the original bug did

`POST /email/rules/history/retry-failed`, plus a button on the trust panel labelled **"Re-apply them (no drafts or sends)"** — "retry" on a mail assistant could plausibly mean re-sending something, and a button whose blast radius is ambiguous doesn't get pressed.
