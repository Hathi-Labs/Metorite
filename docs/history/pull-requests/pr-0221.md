## Description

## What this adds

A second WhatsApp transport so you can link a **personal number by scanning a QR code** (the way WhatsApp Web works) — no Meta developer account, no Business API, no app review. It flows into the **same** normalized store and AI triage brain (Reply Zero, intent, drafting, search, pulse …) as an official Cloud API number. The Cloud API path is untouched; the two live side by side.

Built behind the existing provider abstraction, so the whole vertical is reused unchanged — only a new `provider` value (`whatsmeow`) and a new inbound seam were added.

## How it fits together

```
Your phone ──scan QR──▶ whatsapp_bridge (Go, holds the session)
                              │ normalized JSON        ▲ /send /media
                              ▼                         │
                    gateway POST /whatsapp/bridge/ingest│
                              │                         │
                  persist_sync_result + post-sync hooks │
                              ▼                         │
                    the SAME triage brain a Cloud API number gets
```

The gateway holds **no** WhatsApp session and never talks to WhatsApp; the bridge holds the session and speaks only normalized HTTP to the gateway. They authenticate with a shared secret in both directions.

## Changes

**Gateway seam (W15.1)**
- Migration `112`: `wa_accounts.provider` column (`cloud_api` default | `whatsmeow`) + index. No-op for existing rows; idempotent (verified on pg16).
- `BridgeProvider` registered in the provider factory; `_provider_for_account` honors the `provider` column.
- Routes: `POST /whatsapp/bridge/{connect,ingest,paired}` + `GET /whatsapp/bridge/status`. Inbound runs through the identical `persist_sync_result` + post-sync hooks as the Meta webhook. `parse_bridge_payload` / `bridge_secret_ok` are pure/tested.
- 18 unit tests.

**whatsmeow Go bridge (W15.2, `apps/services/whatsapp_bridge/`)**
- Pairs a personal number by QR, holds the session in sqlite (survives restarts), streams normalized messages to the gateway. HTTP API: `/session`, `/session/{id}`, `/send`, `/media`, `/read`, `/health`, all shared-secret guarded.
- Renders the pairing code to a data-URI PNG. Pure-Go / CGO-free → static binary + distroless Dockerfile. `send_template` intentionally unsupported (personal WhatsApp has no templates/24h window).
- README with architecture, run/Docker steps, and an explicit ToS/ban warning.

**Connect UI (W15.3)**
- `/whatsapp/connect` opens on a transport chooser — **Personal WhatsApp (Fastest)** vs **WhatsApp Business (Cloud API)**. Personal path shows the QR, polls status every 2.5s, refreshes the code, and advances to "connected" when the phone links. Graceful bridge-unreachable state; honest ToS note on-screen. Same entry serves the app and the Integrations page.
- `.env.example`: documents gateway `WHATSAPP_BRIDGE_URL` + `WHATSAPP_BRIDGE_SECRET`.

## Heads up — Terms of Service

Linking a **personal** number via an unofficial multi-device client is **outside WhatsApp's ToS** and the number can be banned. The gateway/app side is ToS-safe (it only ever receives normalized messages); the risk lives entirely in the external bridge running against your own line, which is why it's an isolated, opt-in service. Use it for a personal line at your own risk — use the Cloud API path for a business number.
