## Description

Fixes the deploy failure:

```
Error [NoIdentityError]: No signed-in member to act as
Error: Failed to collect page data for /api/settings/llm/enabled-models
```

## Cause

Two routes had this at **module scope**:

```ts
const HEADERS = await gatewayHeaders({ "Content-Type": "application/json" });
```

The originals were a static object literal in that position. The migration in #309 rewrote the literal in place, which turned a constant into a top-level `await`.

**Failing the build was the lucky outcome.** Module scope runs once per *process*, at import. Had a session been resolvable there, `HEADERS` would have named whichever member imported first, and every later request would have been served as them — a cross-user identity leak from a line that reads like a constant. The headers are now built inside each handler, where the acting member actually is.

## Also

Eight routes marked `force-dynamic`. A handler that resolves the signed-in member can never be statically evaluated; without the directive, page-data collection runs it with no request and no session. Six were gateway-forwarding; `chat/suggestions` and `sessions/compact` call LiteLLM rather than the gateway but still resolve an identity, so they qualify for the same reason.

## Two new invariants

The existing sweep had already seen this and could not say so — it printed `?()` for these two files, unable to name the enclosing function because there wasn't one. That was the signal, unread. Now it fails explicitly on:

- a module-scope `await gatewayHeaders(…)` / `headersActingAs(…)`
- a route that resolves an identity without being `force-dynamic`

Verified by reintroducing the pattern and watching the test fire, rather than trusting that it would.
