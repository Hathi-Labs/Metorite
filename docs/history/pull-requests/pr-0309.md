## Description

Multi-person chat rooms, per-room memory clearance, and a fix for a privilege-escalation pattern that had been fixed twice locally and kept coming back.

Specs: `docs/multiplayer/README.md`, `docs/multiplayer/memory-clearance.md`, `docs/multiplayer/bff-identity.md`, `ai-company-brain/specs/groups_sessions_authority.md`

## What's in it

**Rooms.** A room is a `chat_session` row plus participants — no new object, because every transport primitive is already thread-keyed. Membership replaces ownership everywhere (`gateway/rooms.py`, `SESSION_VISIBLE_SQL`, `resolve_room_access`), which is the same answer when a session has one participant. Messages carry authorship set-once, so three racing writers cannot rename an author and a human turn is always attributed to the authenticated caller. A shared run acts at the **intersection** of every participant's access, viewers included, and the room header reports the resulting capability cap — what the room cannot reach and who is the reason — because the intersection rule's failure mode is mystery.

**Memory compartments.** A run reads at the clearance of its least-cleared viewer. In a room, nobody's private compartment loads — not the owner's, not the typer's — while `prefs:` travels so the agent still writes the way you like. The boundary is that excluded scope keys are never passed to `search()`, so there is no retrieval to leak, rather than a retrieval we hope the model ignores. The session-memory cache key carries a clearance fingerprint; without it a thread cached while solo would keep serving the owner's private block for the rest of the TTL after someone was invited in.

**The identity boundary.** `acb_auth/deps.py` §1b reads a bearer-matched call with no identity headers as the platform acting as itself and grants `SERVICE_ACCESS` — `*`. The BFF holds that token, and ~70 route files each carried a copy of `if (session?.user?.email) h["X-User-Email"] = …; return h` — so no session did not degrade to anonymous, it escalated past every `require_permission`. 74 of 88 gateway-forwarding routes could do it; 38 sat under a `proxy.ts` public prefix and needed no session at all, including agent registration, code-mutation approval and the integration key inventory.

`lib/gateway.ts` is now the only module that reads `GATEWAY_INTERNAL_TOKEN`. `gatewayHeaders()` throws without a member; `serviceHeaders(reason)` is the only bearer-only path and takes a written reason. All 86 route files migrated — roughly 960 net lines of duplicated identity logic removed. The same omission existed in three Python agent tool clients and is fixed there too.

## Behaviour changes to know about

- **Routes now run as the actual member**, so gates that were being satisfied by `SERVICE_ACCESS` start enforcing. Writes to `/settings/llm/*` need `feature:models`; agent registration needs `agents:manage`. Migration 130 backfills `executive` → `admin`, whose bundle holds both, so admins are unaffected; the model picker's reads are ungated so members keep a working picker.
- **`proxy.ts`** no longer pretends to be the authorization boundary. Signed-out page navigations redirect; signed-out API calls get a 401 instead of a redirect to an HTML sign-in page.
- **Agent tool clients raise** when no acting user can be resolved, rather than calling the gateway as the platform. Every surface they reach is per-person, so a run with nobody attributed has nothing to do rather than everything — but a scheduled sweep that ran without `ACB_AGENT_USER_EMAIL` will now fail instead of silently working.
- **Migrations 136–139** are new and need applying on deploy.

Honest gaps, stated because they matter for a change this size:

- **`next build` has never run.** `@tiptap/*` and `@xyflow/react` are declared in `package.json` but absent from the sandbox's `node_modules`, both pre-existing. `tsc` and `eslint` are clean, but CI is the first real compile.
- **Verification of the identity hole was per-link, not end-to-end.** The proxy list, the missing `auth()` calls, and the gateway's response to a bearer-only request were each confirmed directly; no full Next-plus-gateway exploit was run.
- **The access tables are now load-bearing in a way they weren't.** `resolve_access` fails closed when they're absent. Previously that barely mattered for these routes because they forwarded as the service principal; now, if the production database lacks the org role rows migration 130 seeds, members resolve to no access. Worth confirming against the live database before or right after deploy.

Two adjacent findings recorded in `bff-identity.md` §6 rather than fixed here: `scripts/setup_secrets.sh` seeds `GATEWAY_INTERNAL_TOKEN=${LITELLM_KEY}`, so the two secrets `deps.py` calls deliberately distinct start life as one value; and `require_internal_auth` fails open when no token is configured, which means this invariant rests on the token actually being set.
