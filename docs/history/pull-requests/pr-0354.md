## N7 — off-boarding yourself

**WS-24 / N7** · owning spec `ai-company-brain/specs/colleague_onboarding.md` §2 Step 5.

Asked for directly: *"I should have the ability to delete users except myself. Ensure that I do not delete myself by mistake."*

### What was actually wrong — the opposite of the ask

Removal was **already** self-guarded (`members.py`, *"You cannot remove yourself."*). The problems were elsewhere:

1. **The UI had no removal control at all.** The `DELETE` route had no caller in the product.
2. **`PATCH {"status":"suspended"}` reaches the same `is_active=False` with no self-check** — its only invariant was `assert_owner_survives`.
3. **The page rendered Suspend on your own row**, because it never learned who the viewer was.

So the one off-boarding action available from the UI was the unguarded one, pointed at yourself.

`assert_owner_survives` has been standing in for a rule it is not. With exactly one owner it happens to refuse; **add a second owner — which §2 Step 2 exists to do — and either owner can suspend themselves out of admin in one click.** `admin:members:manage` is the floor for undoing it.

### Three doors, one rule

`assert_not_self_lockout` in `_common.py`, called by **both** status doors. One helper with two call sites, because a check written into only one of them is precisely how they came to disagree.

Shipped **wider than the ticket asked**: the rule is *"any status that is not `active`"*, never a list of destructive ones. `is_active` is `status == "active"` exactly, so `invited` is a lockout too — an enumeration would have had to remember that. Fenced: narrowing it to `("suspended","removed")` goes red.

**The third door was found in verification, and proved reachable rather than argued about.** `PUT /members/{email}/roles` never touches `status`, so the status guard cannot see it — but demoting yourself out of `admin:members:manage` is the same lockout, and the permission you just gave up is the floor for undoing it. In the two-owner world:

```
PUT /admin/members/owner@fracktal.in/roles {"roles":["member"]}
as owner@fracktal.in                        -> ACCEPTED
status stayed 'active'; admin:members:manage gone
```

Closed by `assert_not_self_demotion`, which decides on **the permissions the new roles grant**, not a slug allowlist — a custom role carrying the permission passes, and an owner holding `*` passes. It runs *before* `assert_owner_survives` so the caller hears the true reason instead of being told to assign another owner and then hitting the real wall.

**The guard is about the permission, not about self-editing.** Moving yourself to `admin` still leaves you able to undo it, and is allowed. A blanket "you may not touch your own roles" would have been simpler and wrong.

**A fourth door already holds** — `PUT /members/{email}/overrides` refuses self-denial of `admin:access:manage`. I nearly shipped a spec line claiming it was open; checked first, and it is not. Recorded honestly: it holds by a *fourth inline copy* of the rule, guarding a *different* permission, invisible to the enumeration test. One consolidating pass is worth doing before a second admin exists — not here, since it is a refactor of working code.

### The UI

The page now reads `access.email` (`GET /auth/me`), renders **This is you** in place of Suspend/Remove on your own row, and gains a **Remove** control on other rows with a confirmation that names the person and says every role assignment is dropped — pointing at Suspend for anyone who wanted the reversible act. Refusals surface and re-read the roster.

Hiding a control is a courtesy; all four servers-side guards are the boundary (`lib/access.ts:126-129`).

### Two fences the verifier caught, and the honesty note

- The row-wiring test asserted `index(flag) < index(call)` — which `void actions.canSuspend;` above a `{true && (` satisfies **while the control renders on your own row**. It now asserts the JSX condition itself.
- The door-enumeration test claimed to find new doors automatically. It looked at one path — which is exactly why the third door was invisible to it. Claim retracted rather than repaired.

That is the fourth test in this workstream to assert less than its docstring claimed. The pattern and its tell — a bare status-code assertion where two guards return the same code — are written into the spec and into `_admin_fakes.py`'s docstring.
