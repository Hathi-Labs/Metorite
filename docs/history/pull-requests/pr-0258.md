## Description

The meeting-bot worker existed but nothing put it on the VPS — join-by-link needed a manual `docker compose up` there. It now deploys with everything else.

## What changed

- **`infra/docker-compose.yml`** — a `meeting-bot` service under the **`meetingbot` profile**, deliberately *not* `core`: each in-call bot is a real Chrome (~1–3 GB RAM + up to 2 CPU), so it must never start just because someone brought the stack up. `shm_size: 1gb` (Docker's default 64 MB `/dev/shm` crashes Chrome on real pages), a named volume so recordings survive a restart, and host-gateway resolution so the worker can call back with live segments.
- **`deploy.yml`** — builds and starts it, generates `MEETING_BOT_TOKEN` once, points the gateway at it (`MEETING_BOT_URL`, `NOTES_BOT_PROVIDER=selfhosted`, `NOTES_LIVE_CALLBACK_BASE`) *before* the gateway restart, then health-checks. Opt out with `MEETING_BOT_ENABLED=0`. Modelled on the existing WhatsApp-bridge block.

## Two things that would only have failed on the box

1. **Port collision.** The worker publishes on host **8095**, not 8080 — the gateway owns 8080 on the VPS (`deploy/hostinger/acb-gateway.service`). The obvious choice would have taken down the whole app rather than just the bot. Bound to loopback only, so nothing off-box can dispatch a bot.
2. **Compose env resolution.** The compose command passes `--env-file "$ENV_FILE"` explicitly, because a bare `.env` resolves against the *project directory* (`infra/`), not the app root — the substitutions would have come out silently empty.

A build or start hiccup skips the bot and never fails the deploy.
