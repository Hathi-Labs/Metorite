## Description

`core.ACTIVITY_TYPES` is a hand-maintained copy of `pm_activities`'s CHECK, and `record_activity` refuses an unknown type **before** the insert. Migration 150 added `attachment` to the database's CHECK; this tuple was never updated. So the upload route did its work, called `record_activity(activity_type="attachment")`, and got

```
422 Unknown activity type 'attachment'
```

which rolled back the whole write. **Attaching a file to a project task has been impossible since WS-27i shipped.**

All 25 attachment tests passed throughout. They monkeypatch `record_activity` to record the call, so they assert the activity was *requested* and never that the vocabulary accepts it — the seam under test was mocked out.

## The fence, not the string

The one-string fix is `attachment` in the tuple. The real fix is two tests that read the migrations instead of restating them:

- **`test_the_activity_vocabulary_mirror_is_exact`** — assembles the CHECK from whichever migration last redefines it (146 creates it; later migrations replace it wholesale, so the newest wins a full replay) and requires set equality with the tuple. Either side gaining a value without the other fails here.
- **`test_every_activity_type_the_routes_write_is_in_the_vocabulary`** — greps every `activity_type=` call site in the package, so a new one is covered without anyone remembering to list it.

## Verification

Both mutants red: dropping `attachment` from the tuple (the bug exactly as it shipped) fails both tests; dropping a value from a migration's CHECK fails the first. 207 cases across the six projects suites; ruff clean.

No migration in this PR — it is code and tests only.
