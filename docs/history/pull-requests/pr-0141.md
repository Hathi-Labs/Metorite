## Description

## What

Tier-A item **2.1**, the **defect half**. Only `trigger_sync` (the manual route)
learned FROM-classification patterns from the label changes a user makes in their
mail client. The **scheduler** — which is what actually polls every ~300s —
never did; its `_sync_account` persist loop just upserted. So every manual
re-label in Outlook between the rare manual syncs was **silently dropped**, and
inbox-zero's LABEL_ADDED / LABEL_REMOVED learning was effectively dead in prod.

## Why a plain hook couldn't do it

The learner needs a message's categories **before** the upsert — the upsert
overwrites them on a categories-authoritative provider (Outlook) — so the
existing `(account_id) → None` post-sync hooks can't recover the "before".

## Wiring (layering preserved)

- **`post_sync.py`** — `PostSyncHooks.learn_label_changes`, a hook that carries
  the per-message `(message, old_categories)` pairs, + `run_label_learn_hook`.
  `email_ingestion` stays standalone: an unregistered hook is a no-op.
- **`_sync_account`** — captures `old_categories` in its persist loop (gated on a
  learner being registered **and** an incremental sync — a deep backfill would
  mislearn, the same gate the manual route uses) and calls the hook after commit.
- **`scheduler_hooks.learn_label_changes`** (gateway) runs the shared
  `sync.learn_from_label_change_events` orchestrator — the **same** learner the
  manual route uses — so both paths learn identically. `email_ingestion` only
  touches the registry; the gateway registers the impl.

Best-effort throughout: a learning failure logs and never fails the sync.

## Deferred (pure dedup)

Collapsing `trigger_sync` into a thin `_sync_account` wrapper + deleting its
duplicated persist/reconcile/watermark loop — that rewrites the **live
manual-sync response path**, so it waits until this learning revival is confirmed
on a live cycle. Tracked in the plan.
