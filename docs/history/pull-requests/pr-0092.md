## Description

> "it says 65 uncategorized emails match patterns you've already taught the assistant... I have already done it and it's showing up again."

## The button was fine; the background sweep was stuck

Verified first: the sweep **is** applying and the labels **do** stick — 121 labels written in two hours, 121/121 still present, zero provider write failures.

The problem is the automatic sweep. It capped the **scan** at 100 rows per cycle, the query is ordered newest-first, and every cycle restarts at offset 0. A block of no-evidence mail at the top was therefore re-read every five minutes and nothing behind it was ever reached:

```
16:17  scanned: 100, applied: 0, no_evidence: 100
16:22  scanned: 100, applied: 0, no_evidence: 100
```

…with 575 older messages waiting behind the wall. The number kept coming back because the backlog genuinely wasn't moving.

## The fix

Reading a page is one indexed query. Writing a label is a provider round-trip. They are not comparable costs and must not share a budget.

- `sweep_uncategorized` gains `max_apply` — bounds labels written
- the scheduler passes a 5000-row scan budget with `max_apply=100`
- the summary reports `apply_capped` separately from `exhausted`, so "stopped early" is never rendered as "the mailbox is clean"
- `max_apply` defaults to `None`, so the manual **Categorize** button still covers the whole mailbox

## The spacing

The preview line was assembled from JSX text nodes split across source lines around `{expressions}`, so the spacing between `email` / `s` / `match` depended on JSX whitespace collapsing — hard to verify by reading and invisible in review. It's now built from explicit strings that read as the sentence they render.

Bonus: the singular case now says *"1 uncategorized email **matches**"* instead of *"match"*.
