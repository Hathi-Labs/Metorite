## Description

The spec-audit held back three of WS-26d's items — not on engineering grounds, but because each stated a *property* where a dispatchable ticket needs a *mechanism*. "Caller-scoped", "confirmation-gated fail-closed" and "attaches to the email pipeline" are all satisfiable by building the wrong thing. This closes B3, B4, B5 and B7, so all three become dispatchable as separate tickets.

**Every anchor in this text was read off `origin/main` at `af3d3fc8`, not recalled** — the repo's standing rule after an earlier spec cited an inverted precedent. Three of my own assumptions were corrected in the process (the scope seam is at `core.py:424-435`, not `:421-427`; `schema.generated.sql` is stale for `email_messages`; and there is no `email_threads` table at all).

## B3 → WS-26d-email

The failure mode is specific: the CRM is **org-visible** to every `feature:crm` holder (D-CRM-3) while a mailbox is **owner-scoped**. An unscoped join publishes one member's inbox to the whole company. So the rule is now stated as non-negotiable — the join is **caller-scoped, never record-scoped**: two people opening the same lead may legitimately see different email, and a holder with no mailbox sees none.

It reuses the email app's own `_account_scope` (`routes/email/core.py:424-435`), **copied into `routes/crm/` rather than imported**. That's a real decision, not a shrug: cross-package imports are precedented (`notes/dispatch.py:280`), but `routes/crm` already declined exactly that once on D-CRM-4 grounds (`broker_handlers.py:61-64`). The rule for next time is written down — a third copy anywhere means promote it to a shared module.

Also settled: the unit is the **thread**, not the message (there is no `email_threads` table; `thread_id` is the grouping column and the conversation is already the app's unit of classification and snooze); inbound `from_address` only in v1; organizations do **not** join by domain (an `@fracktal.in` match would attach the entire mailbox to our own org record); and the join needs an address index that **does not exist today** — the two FTS GINs bury the address in a `to_tsvector` expression, usable only via `@@`.

## B4 → WS-26d-autolead

The hook is **`process_new_mail`** (`routes/email/scheduler_hooks.py:57`) — the one seam the background scheduler, the manual-sync route and the webhook all funnel through, with per-step try/except isolation a CRM step can copy so it can never break mail sync.

The tempting alternative is **recorded as rejected**, with reasons: the per-message rules loop already holds the parsed sender and the classification, but a classifier outage there `continue`s *without stamping the watermark* (so a hook double-fires on retry), and it only sees INBOX mail with `rules_processed_at IS NULL` (so history backfills never reach it).

"Unknown sender" mirrors `_maybe_block_cold` rather than being reinvented, and colleague suppression goes through `is_own_mail`/`sender_scope` — because a lead row for your own CFO, pushed into the live Zoho tenant under D-CRM-9, is exactly what this paragraph exists to prevent.

## B5 → WS-26d-write

The mechanism is **`request_confirmation`** (`acb_skills/ask_tools.py:345-348`), awaited at the top of each tool before the HTTP call — a plain async function, not a decorator, that blocks on a card and **fails closed with no delivery channel** (`:446-448`). No CRM write tool may pass the `non_interactive_default="approve"` opt-out.

`@_annotate_risk` is the risk half and is a **shared platform convention** (read by `permission_policy.py`), but **annotation is not enforcement** — the policy layer explicitly defers to the tool's own confirmation. Annotate *and* confirm.

The sharpest line, and the reason these were conflated: **confirmation and the Action Broker fail in opposite directions.** `request_confirmation` denies on error; `_broker_gate` proceeds on error, deliberately ("a broker-layer error never blocks a user-approved write"). They are not interchangeable. The PR includes the division-of-labour table: tool confirmation covers the native write, the broker covers the Zoho push, and for `CRM_AUTO_LEAD` — where no human is in the loop at all — the flag itself is the gate.
