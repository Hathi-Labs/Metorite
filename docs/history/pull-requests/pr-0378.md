## Description

## Why

The owner's first working session on the live CRM board (2026-08-07) found the deal lanes out of order and every imported stage sitting at 0% win probability.

**Root cause, verified in code:** the model was never the problem — `crm_deal_statuses` has carried `position` and `probability` since migration 144, stage probability already inherits into deals on entry, and `admin.py` exposes full CRUD over all of it. Two delivery gaps:

1. The importer appends unseen Zoho stages past the last position at probability 0 (`import_zoho.py::_ensure_status`) — and 144's seeds *renamed* Zoho's defaults ("Proposal" vs "Proposal/Price Quote"), so name-match missed the tenant's real stages and they landed at the end of the board.
2. The admin API is headless — there is no settings UI, so nobody can fix (1) without curl.

## What this PR adds (docs only, no code)

- **spec §5.1 — the pipeline blueprint**: probability semantics (stage default + per-deal override), weighted-pipeline math, the four systems (truth+settings, forecast+funnel, discipline, data management), and deliberate deferrals (multi-pipeline, sequences, AI scoring) written down so nobody builds them early.
- **D-CRM-10 / D-CRM-11**: probability informs, `type` decides; single pipeline until a second sales motion exists.
- **Tickets WS-26f–i**: f = stage-metadata pull from Zoho `settings/pipeline` (dry-run agent-safe, prod apply OWNER-GATE) + Pipeline Settings surface + weighted ₹ on the board; g = forecast & funnel reports off `crm_status_changes`; h = stage entry requirements + rot badges; i = merge/bulk/CSV/saved-views (spec-thin, audit first).
- **work_plan**: board row updated; a fourth WS-26 owner gate registered (applying the stage repair against prod).

Research: Zoho's `settings/pipeline` endpoint returns per-stage `sequence_number` + `forecast_type` (the tenant's real order); per-stage probability is probed from layout metadata with a no-scope vs no-data distinction, since the current token likely lacks `settings.*` scopes.
