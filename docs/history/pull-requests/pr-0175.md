## Description

## What

The "Uncategorized" pill is an **indicator** (the absence of any known label), not a category — and clicking it should either fix the email or tell you honestly why it couldn't.

**1. Pill click now branches on the outcome** (`EmailList.tsx`, `emailStore.ts`):
- Rule matched → applied, pill resolves in place (unchanged).
- **No rule matched** (classifier healthy) → the Fix dialog opens automatically — the miss becomes a learned pattern, an exclude, or a new rule.
- **Classifier unavailable / transport error** → error banner saying it's a backend fault; the Fix dialog does NOT open, so a plumbing outage is never misread as "your rules are wrong".

**2. "Uncategorized" is unwritable as a category** everywhere a category can be written:
- `apply_label` (the single writer used by rule LABEL actions and the sweep) refuses it — an AI-resolved `{{...}}` label could produce it.
- The manual label endpoint (`PATCH /messages/{id}`) drops it before the mirror and the provider write.
- Ingest canonicalisation (`persist._canon_categories`) strips it if it ever exists provider-side.
- The restore-provider-labels repair now runs the same canonicalisation — it wrote **raw** provider label sets, which would also have resurrected pre-rename "Reply"/"Actioned" names.

**3. Rename regression fix**: `CONVERSATION_LABELS_LOWER` never learned `"needs reply"` in #168, so mail whose only label was "Needs Reply" counted as *uncategorized* in every facet, filter and Cleaner tab. Legacy names stay in the set until the reconciler has replaced them provider-side.

Searchability is untouched: `is:uncategorized`, the QuickFilters chip, and `/messages?uncategorized=true` all still share `core.UNCATEGORIZED_SQL`.
