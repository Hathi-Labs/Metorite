## The slice

`GET /crm/export/{leads,deals,contacts,organizations}.csv`. No migration. Read-only. Four literal per-entity paths with `export/` first, because a `/crm/{entity}` template would shadow `PATCH /crm/activities/{id}`.

Filters come from the **same** `core.list_contract` the list endpoint uses, so the export is exactly the list you were looking at and its refusals are inherited rather than restated. Complete-or-refused, never truncated: a `count(*)` over the same WHERE runs before any row renders, and the render binds `cap + 1` so it refuses on the rendered set rather than trusting a count taken in a different snapshot.

Read-only is the load-bearing property, not a nicety — the Zoho sync loop is enabled, so a row this path dirtied would reach the real tenant within one 600s cycle. It's asserted three ways: an AST fence on the module's imports, a source scan for write verbs, and a behavioural check per entity that every statement begins with `SELECT`. The verifier defeated the two source fences with an obfuscated write (`"upd" + "ate crm_leads set zoho_dir" + "ty = true"`); the behavioural one still caught it, 4 red.

Two seams promoted rather than copied: `gateway/csv_export.py` server-side (a second copy of the formula-injection guard is a duplicated *security control*) and `src/lib/export.ts` client-side. Projects consumes both.

## The thing worth reading

**Every gate was green and the feature still didn't work.** 503 pytest, `tsc` silent, 1,813 vitest, theme suite clean — and the UTF-8 BOM never reached the user.

The gateway emitted it; the BFF proxy's `await res.text()` is a UTF-8 *decode*, which strips a leading BOM, and re-encoding never put it back. Measured, node v22: `[239,187,191,78,97,109]` upstream → `[78,97,109,101,44,69]` relayed. On the 3,993-row Zoho-India backfill that's every "Café", "Sørensen", "₹" and Devanagari name rendering as mojibake the moment someone double-clicks the file in Excel — exactly what the BOM exists to prevent, for the audience this feature is *for*.

Three fences were pointing the wrong way, which is why nothing caught it:

1. **A fence that pinned the defect.** `src/lib/export.test.ts` asserted the source *contained* `await res.text()`, commented "`res.text()` keeps the bytes" — it does not. The correct fix failed the test. It now runs both proxies end to end over a BOM'd body and compares bytes, and it survives the subtle mutant (`TextDecoder().decode(await res.arrayBuffer())` passes the static regexes; the behavioural half still goes red).
2. **A vacuous fence.** The done-when-1 parity test compared `route.dependant.query_params`, but both routes take filters via a class `Depends()` — it was asserting `set() == set()`. Proven: adding a `city` filter to `ListParams`, the exact drift it claimed to catch, left all 46 tests green. It now recurses sub-dependencies, goes red once per entity, and asserts its own precondition so it cannot silently go vacuous again.
3. **A no-op header.** `X-Export-Rows` was set "for anything reading this programmatically" and the proxy forwarded exactly two headers, neither of them that one.

**This also fixes the same bug in Projects.** The broken arm was copied *from* `api/projects/[...path]`, so `/projects/export/tasks.csv` has been serving BOM-less CSV since WS-27ae. Fixing only CRM would have left the new shared rule documenting the broken shape as correct. Recorded in `project_management_app.md` and the WS-27 row so it isn't read as scope creep.
