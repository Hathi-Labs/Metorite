## Description

Part 2 of the email debt-paydown stack. Fixes the layering inversion between `email_ingestion` and `gateway`, then uses the resulting seam to converge three divergent sync pipelines into one.

## C2 — invert the `email_ingestion` → `gateway` layering

The ingestion scheduler lazy-imported `gateway.routes.email` to run its post-sync jobs (rules / categorize / classify / auto-archive / digest / follow-up / subscription). The **lower** layer reached **up** into the higher one, so neither package could be built or tested independently.

Direction is now correct:

- **`email_ingestion/post_sync.py`** — a hook registry (7 optional callbacks).
- **`gateway/routes/email/scheduler_hooks.py`** — registers the gateway callbacks. `auto_run_rules_for_account` absorbs the settings-gating that had leaked into the scheduler (it's gateway-domain logic).
- **`main.py`** lifespan calls `register_email_post_sync_hooks()` before sync starts.
- **`scheduler.py` now has ZERO gateway imports** — it invokes hooks via `run_hook()`, preserving the exact same new-mail gating, ordering, `try`/`except` and log messages.

Behaviour-preserving: same jobs, same order. An unregistered hook is a no-op, so `email_ingestion` runs standalone (tests, gateway-less processes).

## H1 — converge the post-sync pipeline

One shared `process_new_mail(account_id)` — auto-run rules → categorize senders → classify threads (Reply Zero) → auto-archive, **each step failure-isolated** — now runs from **all** sync paths via the `on_new_mail` hook:

| Path | Before | After |
|---|---|---|
| Scheduler loop | 4 separate steps | one `hooks.on_new_mail` call |
| Manual sync (`trigger_sync`) | re-classified inline only — **mail showed up unlabeled until the next 20s poll** | enqueues `process_new_mail` as a FastAPI `BackgroundTask`; Sync stays fast *and* rules/labels/archive actually apply |
| Graph webhook (`_webhook_sync`) | rules + classify only | full pipeline |

Digest / follow-up / subscription stay every-cycle scheduler-only (time-gated). Registry simplified from 4 granular new-mail hooks to 1 `on_new_mail` orchestrator.

## C1 — collapse 5 message-upsert copies into one helper

The `email_messages` upsert SQL was copy-pasted across four received-message ingest paths — manual sync, the background scheduler, the on-demand history backfill, and the inbound SMTP/webhook handler. **The copies had drifted:**

- `unsubscribe_link` was bound in only two of them
- scheduler/webhook stored bodies **untruncated**
- the backfill **clobbered `snippet`** with an empty re-send

Unified behind **`email_ingestion.persist.upsert_message`** — which lives in the *lower* layer, so the gateway calls **down** into it (consistent with C2 above). One `INSERT ... ON CONFLICT` with a conflict-mode switch (`update` for sync/scheduler/backfill, `nothing` for inbound), consistent body truncation, and `COALESCE`-preserve for body/snippet/`unsubscribe_link` so a headers-only re-sync never clobbers a hydrated body or an already-parsed unsubscribe link. **Net −334 LOC.**

The parity guard is rewritten from *"keep the copies in sync"* to *"there is one helper and no ingest path re-grows its own INSERT"*, plus a DB-free unit test for conflict modes, truncation, unsubscribe binding and attachment persistence.

## Frontend — "processing" sync state

H1 made `/email/sync` return as soon as new mail is persisted, running the pipeline in the background. The old `triggerSync` fetched once — too early to see the labels/categories/auto-archive applied a moment later, so they only appeared on the 20s poll.

`triggerSync` now flips to a **`processing`** state after the response: it shows what's already persisted immediately, then runs two catch-up refetches (`softRefresh` + `fetchFolders` at 2.5s and 6s) so labels land and auto-archived mail drops out without a manual refresh — degrading gracefully into the 20s poll if the pipeline runs long. Catch-up timers are module-scoped and cancelled on re-sync, so they survive unmounts and account switches.

The sync controls (top-bar button, `MailboxActions`, `EmailList` pull-to-refresh) treat `processing` as busy so the spinner keeps turning, and `MailboxActions` shows a "Processing new mail…" hint.
