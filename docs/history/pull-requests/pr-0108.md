## Description

## The screen

From your screenshots: **21 rows in one flat list**, with rejected patterns interleaved among the ones awaiting review — told apart only by 60% opacity and a small grey word *rejected*.

That's not a styling difference. The three states decide whether a pattern does anything at all:

| state | classifier | Email Cleaner |
|---|---|---|
| **Needs review** | uses it | no |
| **In force** | uses it | uses it |
| **Rejected** | never | never |

So they're three groups now, each with its count in the heading and one line saying what that state *means*. Rejected collapses behind a disclosure — it's a record, not something to act on, and left expanded it padded the list with rows you'd already dismissed. Still reachable, because *"why isn't this sender being filed?"* is answered there.

Note the middle row of that table: a pattern awaiting review is **already shaping classification**. The old copy only said the Cleaner wouldn't use it, which reads as "this does nothing yet". The new header says both halves.

- **The amber banner and the amber rows said the same thing twice.** The explanation moved into the group header; the separate banner is gone.
- **A rejected row still showed a green "Always match" chip** — asserting a live effect the engine doesn't honour. Now drained of colour and struck through.

## The other half of the ask: is teaching actually wired?

It is — but my existing test for it was weak, and worth saying so. `test_both_matchers_pass_guidance_to_the_model` asserted on **source strings** via `inspect.getsource`. It would have stayed green if the prompt came out empty, or if guidance were rendered into a variable nobody sent anywhere.

Replaced with tests that drive the real matcher and read the prompt the model would receive:

- a correction reaches the model
- it renders **between its own rule and the next one** — position is the mechanism, not decoration
- it's labelled `correction from the user:`, so a preset blurb and a human instruction aren't equivalent
- account-wide corrections get their own override block
- every correction for a rule is sent, not just the newest
- blank guidance and no guidance leave the prompt untouched

Critically, two of them run through **`_match_email_to_rules_multi`** — `multi_rule_execution` is ON for this account, so that's the path a real correction has to survive. Proving it on the single-rule branch alone would have proved nothing about this mailbox.
