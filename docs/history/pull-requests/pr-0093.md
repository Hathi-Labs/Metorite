## Description

> "how come my email cleaner still has only 564 emails when my mailbox shows over 43,000?"

Because it had never seen them.

## The cause

`_sync_account` fetches `INITIAL_SYNC_DAYS = 365` on an account's **first** sync, and every sync after that is incremental. Even the *Full re-sync* button is pinned to the same one-year window — so there was **no path in the product** to mail older than a year.

Measured on the live account: **6,803 messages held**, and almost every folder starting within days of `2025-06-30` — exactly one year before the account was connected on `2026-06-20`.

## The feature

The deterministic counterpart of *Process past emails*, placed in the Cleaner where the problem is visible. One action, two phases behind one progress line:

| phase | what happens |
|---|---|
| `downloading` | deep provider sync from a chosen floor — 2y / 3y / 5y / **Everything** |
| `cleaning` | the ordinary sweep over everything now present |

The sweep spends **nothing** on models, so this phase doesn't get more expensive as the backlog grows. It actually gets *better* with history: sender and domain consensus finally have enough labelled mail to fire.

## The load-bearing detail

`_mark_history_rules_processed`.

The scheduled rule run selects `folder = 'inbox' AND rules_processed_at IS NULL`, 50 per cycle, **and classifies each one with a model**. Backfilled mail all arrives with that column NULL — so downloading 36,000 messages would have silently queued 36,000 model calls. Precisely the cost this feature exists to avoid.

Three details make it safe, each pinned by a test:

- **Stamped before the sweep starts.** The rule run fires on its own schedule; every cycle the stamp is late is a cycle it can bill for.
- **The floor is the oldest message held *before* the sync.** Mail arriving during the backfill is newer than that, so it stays eligible for the rules — stamping it would silently stop new mail being classified.
- **The sweep doesn't consult the watermark.** Held-back mail is still fully cleanable, just not by the model.

## Notes

- Storage is not a constraint: 4 KB/message measured → ~178 MB for a full 43,000-message mailbox, against 23 GB free.
- A second run is refused while one is in flight, rather than racing the provider and the shared progress row.
- Progress is reported per phase because downloading years of mail takes minutes, and a job that reports nothing until it finishes reads as stuck.
