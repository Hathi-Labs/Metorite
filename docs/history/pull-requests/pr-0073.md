## Description

When a synced (ClickUp) task is moved into a local Next-Actions stage — by kanban drag or the new card stage selector — the backend reverse-maps to a concrete upstream status via `_status_for_stage`, which returns the **first** of the task's project statuses that maps to the target stage.

That first-in-order = the *lowest* status feeding the stage (so a move lands the task at the stage's **earliest** ClickUp status). But it depended on ClickUp returning the list's `statuses` already sorted by `orderindex` — true in practice, **not enforced in code**.

This sorts `_list_statuses_raw` by `orderindex` explicitly (unknown/unparseable → last), making "lowest status wins" deterministic regardless of API ordering. Behaviour is otherwise unchanged; local tasks and the detail-panel status picker are untouched.

- `providers.py`: sort the list's statuses by `orderindex`.
- `items.py`: docstring only ("first in order" → "lowest by orderindex").
