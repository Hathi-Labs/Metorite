## Description

## The defect

`_backfill_and_clean_job` used `MIN(received_at)` over the whole account as the floor for "this is downloaded history, keep it away from the model". On the live account that value is **2019-06-28** — a single message in Trash. A full backfill would have stamped roughly zero rows, and the scheduled rule run would then have classified every backfilled inbox message at one model call each.

The test asserted the floor was *passed correctly*. It never asserted the floor was *meaningful*.

The floor is now the job itself: `created_at >= started` identifies exactly the rows this backfill inserted (`created_at` is never in the upsert's `DO UPDATE SET`, so a re-sync preserves it), and `received_at < started` keeps mail that arrives mid-backfill eligible.

## Held back ≠ processed

The hold-back wrote `rules_processed_at`. That is the one column meaning "the rules have decided about this", and **Process past emails skips it**. So once the floor worked, backfilled history would have been permanently invisible to AI categorization — and the UI would have reported it as *already processed*.

> Ensure this does not interfere with AI categorization of past emails.

Migration 84 gives the second state its own column:

| | automatic per-cycle run | Process past emails | deterministic sweep |
|---|---|---|---|
| `rules_processed_at` | skips | skips | ignores |
| `rules_held_back_at` | skips | **reaches** | ignores |

Plus a partial index matching the live run's predicate — without it a full backfill leaves ~36,000 held-back rows inside `idx_email_messages_unprocessed` for every 5-minute cycle to scan through to find 50 candidates.

## Cost guard

The dialog had a free date picker and a Process button with nothing between them.

- **`GET /rules/process-past/estimate`** — `will_process` is `eligible` clamped to the row limit. The job reads `LIMIT :limit` and the tracker reports *that* as the total, so a 4,000-email range read as "processed everything" when it processed the oldest 1,000.
- **366-day cap, enforced in the API** — a bound that lives only in the client is not a bound. Checked before any DB work, so the refusal is cheap. An open-ended range is refused too: now that a whole mailbox can be synced, no start date means every message ever received.
- **The dialog** shows the count on the button, warns above 500, names the truncation, and says how much of the range is freshly-fetched history.

> limit processing to a few months up to a year
