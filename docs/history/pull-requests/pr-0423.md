## Description

Owner asked whether shared-database is still ideal, given that Odoo — a large app with many sub-apps for one company — runs database-per-tenant. Reviewed Odoo, then Salesforce/ServiceNow/NetSuite, then SAP.

**Outcome: D15 stands. One genuine gap found.**

## The rule the comparison yields (`saas_multitenancy.md` §0.9.9, new)

> What forces a database per customer is not customization. It is **customization implemented as DDL**.

Odoo adds a custom field by issuing real DDL — a physical `x_…` column, registered in `ir.model.fields` — and keeps modules, views and record rules as rows in the tenant database. That is the forcing function, and it is a fact about Odoo rather than a verdict on row security: Odoo already ships row-level filtering (`ir.rule`) and trusts it to separate legal entities inside one database.

We are already on the other side of that rule and shipped it three weeks ago — `155_projects_custom_fields.sql`: definitions as rows, values as JSONB behind a GIN index, schema unmoved. Apps are rows too (migration 114).

Salesforce/ServiceNow/NetSuite run the deepest per-tenant extensibility in the industry **pooled**. SAP constrained *how* extension is expressed rather than siloing.

## Recorded against ourselves

SAP CAP ships §7 item 1c's schema-per-tenant in production at scale. That contrary evidence is written **into** §7 rather than argued away. It survives rejection for a reason that is ours: CAP automates schema deploy across containers on a quarterly cadence; we ship continuously against a 160+ file ladder applied before restart with **no rollback**. §7 item 1c now names itself the first rejection to re-open if our cadence changes.

Also recorded: SAP re-invented pooling (CAP's shared container for cross-tenant master data = our control plane, reached from the opposite direction), and SAP's own guidance says HANA MDC suits a *trusted* environment — so "SAP uses tenant databases" is not "SAP treats one as a hard customer boundary".

## The one finding — new §6.6: there is no per-tenant restore

BO-23 restores the **cluster**. Under one tenant that is right. From customer #2 it is a §6 cross-tenant defect in that section's own terms: the only way to answer *"restore us to 3pm yesterday"* is to roll every other customer back.

Fix and its order: filtered logical export driven by the **same** `discover_tables()` set the RLS policies use → staging-schema re-import + reviewed swap → rehearsed in CI the way `rehearse_restore.sh` already rehearses the cluster path.

Deliberately **not** added to `engineering_practice.md` §8 — it is not a pre-customer-#1 gate, since with one tenant the cluster restore *is* the per-tenant restore. It lives in §6 (which already means "before a second tenant") and on the WS-29 row, rather than minting a second home for tenancy gates.
