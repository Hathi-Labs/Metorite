## The defect: three guards, three different project rows

#437 gated automation on project run-state. Verifying that against a real database showed the three guards did not agree on *which* project they were asking about:

| Guard | Consulted |
|---|---|
| `run_lifecycle_sweep` | the **root** — too high |
| `recurrence` | the task's **immediate** project — too low |
| `agent_dispatch` | the task's **immediate** project — too low |

So a subtree between the root and the leaf was governed by nobody, and it failed in **both** directions: pausing a mid-tree project left its tasks still firing, while pausing only the root silenced descendants that were themselves active.

The fix puts one seam in `core.py` and points all three at it:

- `is_runnable(project)` — one row, knows nothing of ancestors
- `is_runnable_with_ancestors(db, project_id)` — `WITH RECURSIVE` walk reduced with `bool_and`, so a task runs only when its whole chain is runnable
- `_sweep_candidates` gained a `NOT EXISTS` chain predicate, so every task earns its own verdict rather than inheriting the root's

Recurrence deliberately does **not** stamp `recurrence_spawned_at` on the skip path — doing so would kill the series permanently at the moment of pause, rather than resuming it.

## The fence was dead, twice over

Worth calling out, because it nearly shipped as coverage that wasn't. The four new ancestor checks passed **with the recursion deleted** — the fixture tasks sat directly in the root, so pausing the root paused their own immediate project and the recursive walk was never exercised. Moving them into a grandchild and re-arming `recurrence_spawned_at` made re-mutation turn both checks red, as it should.

This is the second dead fence in this workstream. Both were found by deleting the code and watching the test stay green.

`tests/live/live_ws27bg.py` grew to 31 checks against real Postgres (R8), driving the real endpoint functions rather than fakes. Every automation check runs **twice** — paused must not fire, active must. `_projects_fakes.py` had to be taught the recursive verdict query explicitly; falling through would have answered `None` → `False` → "nothing is ever runnable", silently disabling recurrence and dispatch across the whole unit suite.

## The R8 gate, measured (not assumed)

The ticket refused to let itself be built on an assumption about `timestamptz` precision. Measured on real Postgres 16 through asyncpg **and** `fastapi.encoders.jsonable_encoder`.

**Verdict: implementable.** Parse the token in Python, bind it as a `datetime`, let Postgres compare it as `timestamptz`. Exact for all three token shapes — ordinary microseconds, trailing-zero microseconds, and `microsecond == 0`.

Two fences the measurement moved, neither of which is visible from reading the code:

- 🔴 **A naive (offset-stripped) token silently compares `True`.** asyncpg reinterprets a tz-less `datetime` in the session zone, which on a UTC box happens to match. A client that drops the offset gets a precondition that *appears* to work and would start mis-comparing under any session-TZ change — exactly the "reports safety it does not have" failure this decision exists to prevent. Must be rejected with 400.
- 🔴 **`::text` and the JSON encoder disagree.** Postgres renders the trailing-zero case `.1`; the encoder renders `.100000`. Equal as `timestamptz`, different as strings. A string comparison passes every test written against ordinary microseconds and fails on a trailing zero.

## A finding for the board — `now()` can move backwards

Reproduced on a real database while measuring:

```
T1 txn now() = 09:22:18.560649      (starts first)
T2 txn now() = 09:22:18.762134      (starts 201ms later, writes, commits FIRST)
after T2 commit : 09:22:18.762134
after T1 commit : 09:22:18.560649   <-- WENT BACKWARDS by 201ms
```

`now()` is the **transaction-start** timestamp, so a transaction opening early and committing late stamps a time earlier than a row already written by a newer, faster-committing transaction.

**Harmless to the precondition** — an exact comparison still differs, so the client still gets its 412 and refetches. That is precisely why this does not expand WS-27bi's scope.

**It is a real gap in migration 168's keyset cursor**: a delta client whose cursor has advanced past the newer value will never be handed the row stamped behind it, and that change leaves the stream silently. Pre-existing and already merged, so per CLAUDE.md §5 it is recorded rather than refactored — the fix changes the delta feed's contract and owes its own row and its own decision.
