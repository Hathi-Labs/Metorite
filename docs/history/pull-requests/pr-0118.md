## Phase 2 — 2.6: dedupe Outlook re-keys by internet_message_id

Outlook changes a message's `provider_message_id` when it moves folders. The ingest upsert keys on `(account_id, provider_message_id)`, so a re-keyed message didn't conflict with its row — it was **inserted again as a duplicate "ghost"**, then classified twice and skewing per-thread heuristics (review §3.1).

### Change
- **Migration 89** — `internet_message_id TEXT` (the stable RFC 5322 Message-ID) + a partial index `(account_id, internet_message_id)`. Deliberately **not** unique: legacy rows are NULL until re-synced, and forwarded mail can repeat a Message-ID — a hard constraint would reject and lose it.
- **Provider** — `EmailMessage` gains the field; the Outlook `$select` fetches `internetMessageId`, `_parse_graph_message` populates it. (All `EmailMessage` constructions are keyword args — the mid-dataclass field is position-safe.)
- **Upsert reclaim** — `upsert_message` points an existing row at the new provider id before inserting, so the message keeps **one** row (categories + `rules_processed_at` watermark ride along; not re-classified). The reclaim is **collision-free**: renames only when exactly one row carries the id and nothing already holds the new id, so it can never collapse two rows onto one `(account_id, provider id)`.
- `ON CONFLICT` refreshes the id via `COALESCE` (a provider that omits it never wipes a stored id).

### Historical ghosts — deferred to a script (by design)
Existing ghosts have NULL id today; the id must backfill via a sync cycle first, so they can't be merged at deploy time. `scripts/merge_ghost_messages.py` does the one-off pass afterward (dry-run by default) — keeps the newest row, folds the losers' categories + watermark in, deletes them. Same pattern as the #112 repair.

### Verification
- `test_email_persist_upsert`: reclaim emitted before insert with collision guards; no reclaim without an id or on the insert-only inbound path; id carried + refreshed. Existing upsert/label tests unaffected. Blocking lint clean.
