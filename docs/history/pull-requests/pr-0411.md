## Description

docs(D28): the development doctrine — specs/engineering_practice.md, and R6/R7/R8 that bind it

Owner-requested: write down how we build now that the product is being sold with
live customers and most code is agent-authored.

Two premises, both argued from measured incidents in this repo rather than from
general advice:

  (i) Our failures are DELIVERY AND INTEGRATION failures, not coding failures.
      §0.1 tabulates seven from one fortnight — three migration-number
      collisions, two green-alone/red-together PR pairs, four deploys that
      reported success while shipping nothing, a statement that could not run
      sitting in the hand-applied production promotion script, a migration that
      broke three write routes predating it, and five SQL bugs invisible to
      hermetic fakes. Not one of them is a unit-test gap. Spend the effort on the
      seams between changes.

  (ii) A rule binds an agent only when a test refuses to break it. R5 already
      said this; R7 now generalises it.

Binding (work_plan.md §1, where every dispatch reads them):

  R6  expand/contract migrations. The deploy applies migrations BEFORE
      restarting services, so old code always meets new schema for a window —
      nullable-with-default, never rename in place, constraints NOT VALID then
      validated, tightening always a later migration. Plus the honest corollary:
      forward-only ladder and no blue/green means we CANNOT roll back, only roll
      forward or restore.
  R7  name the fence or label the rule advisory; prefer structural fences over
      example tests, because those are what defend against future agents.
  R8  SQL verified against a real Postgres; verified-red-first for every fence
      and bug fix; mutation testing for money, auth, tenancy, outward writes.

Doctrine, not enforced: deploy != release with a ring order (us -> one friendly
customer -> all; the silo phase makes rings free, and D25.2 already fixed per-org
flags as the only version-skew mechanism); seam-based work partition with short
branches and a 3-4 in-flight cap — long branches are the single root cause behind
the renumber trap, the cross-PR fences AND the duplicated tenancy design; the
verifier-is-not-the-implementer and adversarial-reviewer rules; and a definition
of done in which delivery is verified by evidence, never by a green job.

§8 names five things to close before customer #1, each pointed at an existing
board row rather than minting new ones: SHA-in-/health (WS-25), off-box backup
(BO-23, owner-deferred and now flagged for revisit), migration rehearsal against
a prod-shaped restore (WS-5, proposed), RLS promotion (MT-1b), lifecycle-sweep
tenant binding (MT-1d).

§9 states what the document is NOT: it binds new and changed work only, and is
explicitly not a licence to refactor the existing tree into conformance.

Registered in INDEX.md under CONTRACTS & DOCTRINE and in project-docs/AGENTS.md;
