## Description

Found during WS-26 activation: main was three merges ahead of what the box was actually running, and every signal said green.

**Defect 4a — `release` never moved.** `publish-release` uses the default depth-1 checkout, and `git push` proves fast-forward client-side — the runner doesn't have the commit `release` points at, so every publish after the ref-creating one was rejected with "fetch first". `release` sat at #360 while #361/#362/#365 merged. Fix: `fetch-depth: 0`.

**Defect 4b — the 900s SSH timeout is shorter than the backup.** The BO-23 pre-migration backup takes ~11 minutes on the 4GB box, so `timeout 900` killed the apply mid-flight: migrations never ran, services never restarted — and `verify()` then blessed the still-healthy OLD deployment. Fix: `timeout 1800`, matched to the pull unit's `TimeoutStartSec`.

**Defect 3 (recorded, not fixed here)** — the pull poller skips on `HEAD == origin/release`, but `git reset` moves HEAD before migrations run, so an interrupted push-path apply reads as "already current" to the pull path too. The durable fix (skip keyed on the end-of-apply `/var/lib/acb` marker) is written into the spec for WS-25's next slice.

Spec updated in the same PR (§8.3 Defects 3/4 + the corrections-exist-on-paper warning). Box-side remediation already done by hand today: corrected `User=acb` unit installed, `release` fast-forwarded, forced apply run.
