## The audit said no, and it was right

The ticket that started this was *"close the CREATE gap WS-26h recorded"*. The audit returned **NO-GO and refuted the premise.** Measured: `QuickCreateModal` sends no `status_id` and `ConvertDeal` has no such field, so **every deal the product creates lands in the default lane.** The recorded hole is reachable by direct API call only — not by any UI, and not by the CRM agent, which POSTs only `/crm/leads` and `/convert`.

Meanwhile gating the defaulted path would 422 quick-create and *every* lead conversion the moment an owner puts `required_fields` on the default lane, which `admin.py` permits unrestricted. Worse: `organization_id` is requirable and **neither surface can supply it** — `ConvertModal.tsx:126` renders "This lead names no company, so no organization is created" and offers no picker. A default lane requiring it would make those leads permanently unconvertible.

So the naive fix closes a hole nobody can reach and opens one every user hits.

## D-CRM-13

**Entry requirements gate the stage a caller CHOSE, never the stage the server DEFAULTED to.**

The principle, so this is a rule and not a workaround: *entry requirements exist to prove a deal earned its way into a stage, and a deal in the default lane has claimed nothing yet.* The default lane is where deals start, not somewhere they advance to; demanding proof of progress to enter it is a category error. Creating straight into a late stage by API **is** a claim worth checking, and that is what this gates.

This does not overturn `records._resolve_status`'s recorded doctrine — *"the gate belongs to the status, not to the verb that reached it."* That governs the **lost-reason** rule, a property of a TERMINAL status: a deal is lost or it is not, however it got there. Entry requirements are a property of an ENTRY lane. Same word, two questions.

Direction of travel is deliberate: this is the permissive reading and tightening later is one deleted condition. The strict reading is not cheaply reversible — it ships an organization picker, tells users conversion can be refused, and makes the ~1,516 imported leads a judgement call nobody can automate.

## The slice

Six lines of behaviour in `records._resolve_status`, beside the existing create-side lost-reason refusal: apply the gate **only when `values.get("status_id")` is truthy.** No migration, no UI, no SQL, no predicate. `_require_entry_fields` gained a `NO_EXISTING_RECORD` sentinel so "no row yet" is a stated case rather than `getattr(None, …)`.
