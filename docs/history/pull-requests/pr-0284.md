## Description

Live transcription arrived with no speaker separation. It looked like a model problem; it wasn't. **We never requested diarization at all.**

## The bug

AssemblyAI streaming does not diarize by default — it's opt-in per connection via `speaker_labels=true` on the WebSocket URL, exactly like Deepgram's `diarize`.

The Deepgram path has always sent `diarize: "true"`. The AssemblyAI path sent `sample_rate`, `encoding`, `format_turns` and the token — and nothing about speakers. Both producers had the same omission: the browser recorder (`lib/live.ts`) and the meeting-bot worker (`app/live.py`).

## Also fixed

Both parsers now read the speaker from **either the turn or its words**. Which field carries the label varies by streaming model, and reading only one presents as "diarization is broken" when the data is sitting right there. The worker maps AssemblyAI's `A`/`B` onto our `S1`/`S2` space so live labels agree with the batch path, the rename UI, and batch reconciliation against the voiceprint gallery.

## Two things that aren't bugs but will bite

- **Streaming diarization needs Universal-3 Pro Streaming** or a multilingual streaming model. **Universal-2 has no streaming diarization** — and it fails by returning captions without speakers, not by erroring, which is indistinguishable from the bug above.
- **The streaming model is chosen independently of the `tier-stt` batch model.** Picking universal-2 in Settings → Models does *not* make streaming use universal-2. `ASSEMBLYAI_LIVE_MODEL` governs that, and it's unset, so AssemblyAI's streaming default applies.

Batch diarization is unaffected and has always worked — `build_request` sets `speaker_labels: True`, including on universal-2. So post-meeting transcripts had speakers while live didn't, which is the confusing pattern that was reported.

## Docstring correction

`assemblyai_provider.py` claimed AssemblyAI "diarizes on both batch and streaming" — true only if you ask, and only on a model that can. That sentence is a large part of why this looked like plumbing rather than a missing parameter. Corrected with the precise rules and the model caveat.

## Testing

- 2549 backend tests, 94 frontend (9 new): that the socket URL carries `speaker_labels=true`, turn-level and word-level speaker extraction, A/B → S1/S2 mapping, and that an undiarized turn reports *no* speaker rather than a wrong one
- `tsc`, `next build`, blocking `ruff` all clean

Not verifiable from here: the actual streaming response shape against a live key — which is why both parsers accept either field position rather than betting on one.
