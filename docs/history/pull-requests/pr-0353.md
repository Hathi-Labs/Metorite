## N6a — the sign-in queue: 53 knocks, and the system told nobody

**WS-24 / N6a** · owning spec `ai-company-brain/specs/colleague_onboarding.md` §6 (new).

`/admin/members` was push-only: the only way an `app_user` row was ever created is
an admin typing an address into Invite (`members.py:168-183`). Somebody arriving at
the front door created nothing anyone could see. The refusal *was* logged
(`access.py` — `access_unprovisioned_signin`, with the email), but to journald,
where nothing reads it back and rotation eventually eats it.

**This is not hypothetical.** Measured on the box while writing the ticket:

    53 refusals   ishaanpilar@fracktal.in
    first  2026-08-03T16:21:15Z
    latest 2026-08-04T10:46:56Z   (still recurring)

One colleague spent eighteen hours telling the system he wanted in, fifty-three
times, and the owner had no way to find out except being told out of band.

**Approve provisions *and* activates in one action.** An approval already is the
decision to let somebody in, and they are demonstrably at the door — re-creating
the two-click trap inside a brand-new feature would have been perverse.

### 🔴 The write is on the auth path, and `resolve_access` is not sign-in-only

The single sharpest thing in this diff. `resolve_access` is called with **other
people's** emails — `routes/rooms.py:215` fans it out over room participants,
`access.py` folds it over session subjects, and there are two more callers. An
unconditional write in the `row is None` branch would have filled the queue with
people who never tried to sign in — precisely the harm the separate-table decision
exists to avoid.

Gated on a keyword-only `record_request: bool = False` with **exactly one** opt-in
call site (`deps.py`). A tree-scan test enforces that, so the safety property is
"the default is `False`", not "we enumerated the callers" — the enumeration was
wrong twice during review.

### 🔴 A P1 found in review, then two more instances of the same shape

Three rounds, and the third one is the interesting one because it explains the
other two.

**Round 1 — cross-gate escalation.** Approve is gated on `admin:members:invite`;
suspending and off-boarding are `admin:members:manage`. A decided `access_request`
row outlived its decision and `_load_request` had no `status` filter, so anyone
holding the *weaker* permission could re-approve an off-boarded member back to
`active` with roles re-granted — through a path the tab never renders. Worse, **the
test that claimed to fence it was a Python mirror of the same SQL**: mutating the
guard to `status <> 'active'` passed all 28 cases.

**Round 2 — the refusal was silent.** With the guard fixed, provisioning *declined*
— and approve returned **200** anyway, stamped `approved`, recorded an audit entry,
and re-granted roles. The person stayed locked out *and* left the queue forever,
since the tab renders only `pending` and the resolver's upsert deliberately never
rewrites `status`. **The 53-knock incident, recreated by its own fix.** Closed by
`APPROVE_MATRIX`, read before anything is written:

| existing `app_user` | approve |
|---|---|
| absent / `invited` | provision `active` with the chosen roles |
| `active` | leave their roles **alone**, resolve the request, say so in `detail` |
| `suspended` / `removed` | **409**, request stays `pending` |
| unrecognised | refuse — fail closed |

That row for `active` is its own fix: `provision_member` ends in `set_roles`, which
**replaces** assignments, so approving a stale request over a live `admin` with the
picker's default silently demoted them to `member` — on the weaker permission.

**Round 3 — approve predicted the write instead of verifying it.** The matrix is
read *before* the write, which closes both sequential holes and neither concurrent
one. `_PROVISION_MEMBER_SQL`'s `CASE` arms are re-evaluated by Postgres against the
latest **committed** row (`ON CONFLICT DO UPDATE` waits on a concurrent writer, then
re-reads), so a second admin off-boarding the same person mid-flight lands every arm
on `ELSE app_user.status`. Measured, SUT unpatched:

    RESULT         : HTTP 200  status='removed'  roles=['member']
    app_user.status: removed        can they sign in? NO
    request.status : approved       still in the queue? NO, GONE

**The structural cause of all three:** `_DECIDE_SQL` was made race-safe in round 2,
but that hardened the `access_request` row only — the `app_user` row stayed a
read-then-write with no write-side guard. Now the member must actually be `active`
before the decision is stamped, or the transaction is abandoned. Predicting is an
optimisation; the read-back is the authority.

### Fences, and three admissions about them

Every non-owner case was verified red-first with signatures already in place, so
each red is the security claim rather than a `TypeError`.

**Three tests in this ticket asserted less than their docstrings claimed** — and the
third one was mine, in the fix for the second. Recorded in the spec rather than
quietly corrected:

1. `test_approving_never_un_suspends_somebody` asserted against the fake's Python
   mirror of the SQL, not the SQL. Mutating the guard left 28/28 green.
2. A UI test asserted `"setNotice" in page`, which the `useState` declaration
   satisfies alone.
3. The fail-closed-default test asserted only `status_code == 409` — which passes
   while the matrix is wide open, because the new read-back check raises *its own*
   409. The discriminator is that a matrix refusal grants no role, since `set_roles`
   runs inside `provision_member`. **Treat a bare status-code assertion in this file
   as a smell.**

Eight mutants measured red and reverted sha256-identical, including both round-3
fences:

| Mutation | Result |
|---|---|
| terminal read-back check disabled | 1 failed — captured log is the trace above verbatim |
| `APPROVE_MATRIX.get(status, "refuse")` → `"provision"` | 1 failed (the weak first version of that test **survived** it) |
| matrix `removed`/`active`/`suspended` → `provision` | 2 / 3 / 2 failed |
| `_DECIDE_SQL` drops `AND status = ANY(:allowed)` | 1 failed — **structural test only**; the fake evaluates no predicates |

### Also closed on the way

  assignments first — so approving an address that is the last owner, with default

  and the gateway's own domain check is a log line, not a refusal. Marked with a chip
  and the DECISION block corrected.

### Corrections to the spec, made rather than worked around

* **N6b was written on a false premise** — "there is no `invited → active` transition
  anywhere" is **wrong**. `PATCH /admin/members/{email}` stamps `joined_at` and the
  roster already has an **Activate** button. The real defect was documentary: §2's
  runbook went Invite → Roles → Group → Verify and never said "activate", so it could
  be followed exactly and the colleague still be locked out. **Fixed as §2 Step 1b.
  No code.** Auto-promotion is now an open owner question, not a ticket.
* `invite_member` had **zero test coverage**; the characterisation test went in and
  passed *before* the extraction touched it.
* dw7's "approving twice is not an error" is **superseded** — a second approve is a
  409, marked inline. A 200 that did nothing was the escalation's vehicle.

### Not closed

* **N6b's owner question:** (a) leave activation at two clicks now that the runbook
  says so, (b) auto-promote on first sign-in, or (c) invite writes `active`. **The
  spec recommends (a)** — the measured failure was a missing sentence.
* `_record_signin_request` still swallows a failed write into a journald warning
  nobody reads. That is dw2's deliberate best-effort contract; the *user-visible*
  half of the same blindness is fixed.
* Migration 143 has **never been executed** — no local Postgres is reachable and the
  live DB is off-limits to an agent. Its first run is the deploy replay.
