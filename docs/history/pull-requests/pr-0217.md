## Description

The seek-player showed **"Error"** on iPhone. Root cause: **iOS Safari won't play `<audio>` unless the server honours HTTP Range** — it sends a `Range: bytes=0-1` probe and requires a `206 Partial Content` back. The Next proxy was buffering the whole file and returning a plain `200` with the range headers stripped, so iOS bailed. (The transcript loaded fine because that's JSON, not media.)

**Fix:**
- **Proxy** (`/api/notes/[...path]`): forward the browser's `Range`/`If-Range` upstream, and pass the response **status (206)** + `content-range` / `accept-ranges` / `content-length` / `cache-control` through. Streams `res.body` instead of buffering — lighter and preserves range semantics.
- **Backend** `get_audio`: serve **inline** (drop `filename` → no `Content-Disposition: attachment`) so the browser treats it as playable media. Starlette's `FileResponse` already answers Range with `206`; the proxy now relays it.

**Scope note:** iPhone recordings are mp4/AAC (the recorder picks `audio/mp4` on Safari), so they play once range works. webm/opus files recorded on **desktop Chrome** still won't play on iOS — that's an inherent iOS codec limitation, out of scope here.
