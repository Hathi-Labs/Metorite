### 🔒 The finding that justifies the exercise

The first draft told an implementer to compute the clearance cap *"the way `_capability_cap` (`rooms.py:191`) already computes the credential cap"*.

That function **drops `group:` and `org` participants on purpose** — `emails = [m for m in members if "@" in m]`, then `if len(emails) < 2: return {"capped": []}`. Its own comment says why: it is a **display** cap, safe to under-report, because the authority fold expands groups elsewhere. Promoted to an access decision it turns an intersection into a **union**:

> Room bound to `subject:falcon` (`restricted`); participants `[owner@x (a member), group:sales]`. Cap comes back empty → "no non-member participants" → the compartment enters `Clearance.read` → `search()` runs and its facts render into a transcript **all forty `group:sales` members can read**.

Built faithfully, the document would have shipped the disclosure it exists to prevent. And the old done-when said *"a **non-member** participant"* — which any implementer satisfies with two email addresses, so it would have passed while the group case leaked.

§7.1.4 now names the site and the helper, requires participant **expansion before** the intersection, **fails closed** on expansion failure, and forbids reusing `_capability_cap` in one bolded line with the reason. Done-when 4 is five parts asserting the `group:`, `org` and **partial-membership** cases specifically.
