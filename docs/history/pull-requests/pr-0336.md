## BO-20f — Gmail + Zoho receivers reach ClickUp's enqueue + emit parity

**Stacked on #335** (the §BO-20 doc remediation this builds against). Merge #335 first, or retarget this to `main` with `gh pr edit --base main` **before** merging #335 — merging the base with `--delete-branch` auto-closes this PR.

### The dead switch

`TriggerPanel.tsx:266-268` already offered **`gmail`** and **`zoho`** in the workflow event-trigger source dropdown. Nothing could ever fire them — both receivers verified their credential, wrote an audit row, and returned `{"status":"accepted"}` **without enqueueing or emitting anything**. A user could bind a workflow to a Gmail event and wait forever, with the only signal in Google's delivery dashboard.

Both receivers now do what ClickUp already did: a best-effort `enqueue(...)` to their own stream, plus a `BackgroundTasks`-scheduled `emit_event(...)` — so `event_hooks` → `dispatch_event` → `start_run` reaches them. Warn-and-continue on Redis failure; never 5xx a provider.

### 🐛 Two live production bugs, same root cause

These surfaced from writing the first tests that had ever driven these endpoints through a `TestClient`.

**1. Every authenticated Zoho push has been returning 500.**

```python
_log.info("zoho.webhook", event=event, module=module)   # TypeError, every time
```

structlog's bound logger takes `event` as its **own message parameter**. Verified by extracting the file at `HEAD` and driving it through `TestClient`: `status 500`, and at `LOG_LEVEL=WARNING` too — the filtered no-op method has the same signature, so raising the log level would not have masked it. The raise landed **before** `record()`, so the audit row was never written either. **Every Zoho notification has been silently dropped since the file was written.** Fixed to `zoho_event=`, mirroring `clickup/webhook.py:91`'s existing `clickup_event=`.

**2. Every successfully-normalised ClickUp task has been dead-lettered.**

Same collision in `_normalise_task`, but **inside a `try:` whose `except` calls `enqueue_dlq(...)`**. Observed order, verified end to end: `normalise_tasks` ran → session **committed** → audit row written → `_log.info(..., event=event_type)` raised → caught → `clickup.task.normalise_failed` → **DLQ write**. `audit rows = 1, DLQ writes = 1` for a task that persisted correctly. `clickup.task.normalised` has **never** appeared in the logs.

No test caught it because `test_clickup_ingestor.py` stubs `_normalise_task` wholesale (`:99`, `:121`).

### ⚠️ Scope call I made deliberately

The audited contract **forbade touching `clickup/webhook.py`**. I folded the one-token fix in anyway. The reviewer's argument, which I accept: that fence exists to protect BO-20a's premise that `test_clickup_ingestor.py` stays **exactly 10 passed and unmodified** — it is, byte-identical (`git diff` empty) — and that is a *behavioural* fence, not a file taboo. Shipping a PR whose entire subject is this bug class while knowingly leaving **the last remaining instance in the repo**, twenty-five lines below the line that demonstrates the fix, is the worse outcome. It also gets more expensive later: BO-20c prescribes a drainable DLQ with an admin view, whose first screen would be a queue of false failures with a "retry" button that re-normalises them for nothing.

A **repo-wide AST guard test** now asserts zero `event=` kwargs in logger calls, so instance #3 fails CI instead of dead-lettering in silence. `event=` was probed empirically and is the **only** structlog kwarg that raises — `level=`, `timestamp=`, `logger=`, `msg=`, `exc_info=`, `stack_info=`, `error=`, `source=`, `module=` all pass.
