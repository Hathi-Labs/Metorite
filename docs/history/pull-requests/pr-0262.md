## Description

Chasing "why don't I see the latest AssemblyAI model?" surfaced a worse problem than the missing query.

## 1. The catalogued model ids were wrong (would have broken every transcription)

I shipped `assemblyai/universal` and `assemblyai/nano`. AssemblyAI's own docs enumerate **`universal-3-pro`** and **`universal-2`**. Since whatever follows `assemblyai/` is passed straight through as the model, every transcription would have failed with a confusing provider error on first use.

Catalogue now carries the real ids — Universal-3 Pro as the accurate one, Universal-2 as the broader-language/cheaper option.

## 2. The model field name is uncertain, so it's now self-correcting

The current pre-recorded API appears to take **`speech_models` (a required list)**; older accounts take `speech_model` (a string). Guessing wrong fails *every* request, and AssemblyAI's docs 403 automated fetches so I could not confirm it from here.

`transcribe()` now sends the documented plural form and **retries once with the singular** if the API rejects the field — self-correcting rather than a hardcoded bet on a detail I can't verify.

## 3. Model discovery — the original question

`_fetch_live_models` had no `assemblyai` branch, so it fell through to `return []` and only the static list showed. That's exactly what you noticed.

The honest constraint: **AssemblyAI publishes no model-list endpoint**, unlike the OpenAI-compatible providers we enumerate. So "Refresh" genuinely cannot discover models. It now does the useful thing instead — probes a cheap authenticated endpoint to prove the **key** works:

| Result | Behaviour |
|---|---|
| 200 | return the curated list |
| 401/403 | return nothing, so a bad key can't look fine |
| 429/5xx | still show the models — a rate limit shouldn't blank the picker |
| network error | return nothing |

Deepgram has the same no-endpoint situation; noted in the fallback comment.
