## Description

> "when processing past emails, if emails in a particular time frame are already processed, there is no need for you to reprocess them. Only process emails that are unprocessed."

## The problem

The date picker is a **range**, not a cursor. Re-running "last 7 days", or nudging it out to 30, re-covered everything the previous run already did — one classification call per message, to rewrite labels those messages already carry. The job's own docstring admitted it: *"Reprocesses regardless of `rules_processed_at`"*.

The watermark that makes it idempotent already existed, and this job was already **stamping** it. Nothing was reading it.

## The change

`_date_range_clause` gains `unprocessed_only`, and `RuleProcessPastRequest.skip_processed` defaults `True`.

Reprocessing stays reachable — it's how you re-apply after editing a rule — as an explicit **Reprocess everything** toggle, with the cost stated next to it rather than discovered afterwards.

The watermark is only earned by a run that actually applied (live, with a working provider), so a dry-run preview or an auth failure still leaves mail eligible instead of silently consuming it. Pinned by a test that checks the stamp stays inside its guard.

## Reporting: "Processed 0 emails" is now distinguishable from failure

That is the **correct** outcome of a repeat run, and it reads exactly like the feature finding nothing. So the endpoint and the job tracker carry `already_processed`, and the banner says:

> Nothing new to process — 412 emails were already done.

It is counted separately from `skipped`, which means "processed this run, matched no rule" — merging them would report thousands of skips on a run that did nothing at all. The job re-measures the figure after the provider download, since the endpoint's count predates any mail that arrives during it.
