## Description

Stacked on #286 — review that first. Base is `claude/multi-tenant-user-management-1cb3ub`, so this diff shows only the enforcement work.

## The gap this closes

#286 shipped the permission mechanism but only applied it to `/admin` and the agent-run path. **Feature access was UI-deep.** Denying someone `feature:whatsapp` hid the nav item and blocked the route — while `GET /whatsapp/chats` still returned their data.

```
before →  whatsapp / email / tasks / notes / memory / apps: require_permission occurrences = 0
```

## Approach: gate at the router

Wherever a prefix has one audience, the gate goes on the `APIRouter` rather than each endpoint. The failure mode of per-route gating is the route someone forgets; router-level gating means an endpoint added next year is covered by default.

Router-gated: `whatsapp`, `email`, `tasks`, `notes`, `chat`, `actions`, `integrations`. `/memory` already required the internal token and is left alone.

## Mixed-audience surfaces, gated per route

A blanket gate would have broken each of these:

| Surface | Treatment | Why not blanket |
|---|---|---|
| `/settings` | writes need `feature:models`; reads stay open | The reads feed the chat model picker — gating them would break model selection for every ordinary member |
| `/integrations/oauth` | `authorize` + `refresh` gated, `callback` not | The callback is the provider's browser redirect |
| `/agent` | registry writes on `agents:manage`; runs stay per-agent; `/webhook/{source}` untouched | That webhook is deliberately unauthenticated for external callers |
| `/apps` | `require_app_author` (`feature:build.apps`) vs `require_app_viewer` (`apps:use:*`) | One prefix, two audiences: building an app ≠ using one the team shared |

Enforcing `apps:use:*` matters on its own — the permission was already offered in the admin UI and did nothing. A toggle that silently has no effect is worse than not offering it.

**Also fixes `/agent/run/async`**, which had no run gate at all. I missed it in #286 when gating the other two run endpoints.

## The exemptions are the load-bearing part

Six routes carry their own authentication and arrive with **no session and no internal token**:

| Exempt route | Its own auth |
|---|---|
| `/whatsapp/webhook` | Meta verify-token (GET), signature (POST) |
| `/whatsapp/bridge/{ingest,reclassify,labels,paired}` | `X-Bridge-Secret`, constant-time compare |
| `/email/oauth/{provider}/callback` | HMAC-signed `state` |
| `/email/webhook/microsoft` | `validationToken` echo + `clientState` |
| `/notes/meetings/{id}/live/segment` | `MEETING_BOT_TOKEN` |
| `/notes/stt/bot-live-token` | `MEETING_BOT_TOKEN` |

Gating any of these would not restrict access — it would **stop ingestion, silently**, until someone noticed missing data. The existing notes tests caught the meeting-bot case on the first run; a signature sweep across all gated routers found the other five before they shipped.

Exempting removes the *feature* check only. Each endpoint's own scheme still runs.

### Two properties keep the list honest

Both enforced by `tests/unit/test_org_access_enforcement.py`:

1. **Matching is on the route template, never the concrete URL** — so `/thing/items/webhook` cannot reach a gated route by spelling an exempt path in a parameter. There is a test for exactly that.
2. **Any route in a gated router taking no `UserContext` must be exempt or a declared UI read.** A new machine entrypoint added later fails the test instead of breaking production. The gateway DOX now carries this as an explicit warning for anyone adding a webhook.

## Audit trail

Admin writes now emit `acb_audit.record()` alongside their structlog line, per the gateway convention I skipped in #286. "Who could see what, and who changed it" is the first question after an incident and the first thing an access review needs. The override record captures the actual permissions and reasons, not just a count.

## Test change

`tests/unit/test_notes_live_http.py` stubbed `get_current_user` with a duck-typed object lacking `has_permission`. Replaced with a real `UserContext` carrying a resolvable permission set — more faithful to what the dependency actually returns.

## Verification

- 2612 unit tests pass (28 new: the gate's behaviour, exemption coverage, template-vs-URL matching, and a wiring check that fails if a router loses its dependency).
- Gateway boots with all 451 routes.
- Every exemption verified to match a real route template — a typo'd exemption is dead text that silently gates a machine callback, so that is asserted too.

## Deliberately unchanged
