## Description

Fixes the error hit when placing a call from **WhatsApp → Calls** on production.

## The defect

The gateway waited up to **30s** on the bridge, and the workbench proxy (`api/whatsapp/[...path]/route.ts`) aborts at **exactly 30s**. So a slow call tripped the proxy at the same moment the gateway timed out, and the user got the proxy's generic `gateway unreachable` — which names the wrong service and hides the real failure.

## The fix

The timeout budget is now a chain that shortens at every hop, so the innermost failure is always the one reported:

| Hop | Budget |
|---|---|
| workbench proxy → gateway | 30s (unchanged, not ours) |
| gateway → bridge, placing a call | **20s** |
| gateway → bridge, reads and actions | **8s** |
| bridge → WhatsApp, accepting an offer | **12s** |

A bridge that accepts the connection then goes quiet now returns its own **504** naming the service and the command to watch, instead of being indistinguishable from the gateway being down. An offer that times out no longer leaves a live call the caller never learns about. The dialer rewrites the two plumbing errors users actually hit into which service to check.

## Verification

24 call tests (3 new, covering the 504 path and asserting the budget stays under the proxy abort), 3288 Python tests, Go builds/vets/tests clean, `next build` clean.

## Note

This makes the failure *legible*; it may not make the call succeed. If the underlying cause is WhatsApp not acknowledging the call offer, the new error will say so directly — which is the diagnosis we currently can't get.
