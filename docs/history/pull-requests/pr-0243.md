## Description

## What

Pulls the labels/lists you created **inside WhatsApp** ("Clients", "Suppliers", "Follow up", …) into the app and mirrors them **read-only** into the triage inbox — distinct from `wa_categories`, which are our own policy carriers.

## Why

Those labels are the founder's existing organisation of who's who. They live in WhatsApp's app-state, and the whatsmeow (personal-number) bridge can see them — but nothing surfaced them yet. This brings them across so the inbox reflects the same tags you set up on your phone, and lets you filter the queue by a label.

## How

**Bridge (Go)**
- Enable `EmitAppStateEventsOnFullSync` and force a **one-time full sync** of the `regular` app-state collection on connect (guarded by a per-account meta flag), so an already-paired number **backfills its existing labels** — not just live edits.
- Handle `LabelEdit` / `LabelAssociationChat`: drop WhatsApp's built-in system lists (Unread, Groups, Favourites, Archived, …) by type, map the colour index to a hex swatch, and POST labels + chat associations to the gateway.

**Gateway**
- Migration `113`: widen `wa_labels` (colour, list_type, sort, active/deleted) and add `wa_chat_labels`, keyed by JID so an association can land before the chat's messages sync. Upsert key becomes the WhatsApp label id.
- `POST /whatsapp/bridge/labels` upserts labels + associations; `GET /whatsapp/labels` serves them with per-label chat counts; `/whatsapp/chats` now returns each chat's labels and accepts a `label` filter.

**Frontend**
- Colour label chips on chat rows; a **Labels** section in the desktop spine and the mobile triage drawer that filters the queue to a WhatsApp label.

## Scope / notes

- **Read-only mirror** — viewing/filtering by your labels, not editing them back to WhatsApp.
- Existing labels populate on the bridge's **next reconnect** (the forced full-sync re-imports them); live edits flow automatically after.
