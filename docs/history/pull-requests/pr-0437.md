Owner-directed 2026-08-13: coloured run-state indicators per project (green ongoing / red stopped / orange paused, plus queued), the ability to archive a project and its tasks, and a data audit of the task card against the Tasks app.

**Migration 171.** R1 re-checked at PR time: 170 is still the highest on `main`, `main` has not moved since branching.

## The finding that matters most

`run_lifecycle_sweep` walked every root project with a policy and had **no project-status predicate anywhere**. That was harmless only for as long as `status` meant nothing — which is exactly how long it had been. The moment `on_hold` became real, a project paused for a quarter under a three-month close policy would have had its **entire open backlog moved to the cancelled lane**, written by `system:workflow:<id>` through `apply_status_transition` — so `completed_at` stamped, the `status_change` activity written, recurrence fired. Indistinguishable from a person doing it, and nobody would have found it for months.

Recurrence and agent dispatch carried the same hole. All three now consult one `is_runnable` rather than three copies of the rule.

## Second finding: the feature was half-built and invisible

`pm_projects.status` has been CHECKed, defaulted, indexed, validated on create **and** patch, returned by the tree read and declared in the frontend type **since migration 146** — and `ProjectTree.tsx` contained the string `status` zero times. `archived_at` existed and was never written; there was no archive endpoint, and the only removal path was an unrecoverable `DELETE` cascade.

That is the **fourth instance of one failure**, after `pm_task_statuses.color`, `estimate_mins` and (in the card audit below) `pm_task_types`. Each was stored correctly and reachable by the API, so every test passed and the only symptom was a UI plainer than its data.

## What ships

### Slice 1 — the axis, the endpoints, the guards

- Migration 171 widens `pm_projects.status` to the **union** of old and new values (R6 expand — the deploy applies migrations before restarting services, so the pre-restart gateway must keep validating `archived`). Its removal is a **named later release**, not folklore.
- **`archived_root_id`** makes archive reversible: archiving stamps the subtree with the id of the project the user actually archived, unarchiving clears exactly those rows. A subproject archived on its own **survives** its parent's restore; restoring a swept-in child is refused with the ancestor named.
- The write path validates against `RUN_STATES`, not `PROJECT_STATUSES`, so no caller can PATCH `status='archived'` and recreate the two-facts-one-column defect.
- **No `pm_tasks` row is written by any of it** (D-PM-26). The read path derives instead, under the existing `include_archived` flag.

### Slice 2 — the indicator and the first project-editing control

- `PROJECT_STATES` in `src/lib/statusAccent.ts` as a **closed lookup** that never falls through `resolveHue` — the trap being that `keywordHue` maps the literal word `active` to blue and `done` to green, i.e. the exact opposite of the ruling on two of five states.
- `effectiveState` derives a node's state from its ancestors **on the way down the render**, writing nothing. Inherited states draw at half emphasis and say so.
- The indicator replaces the generic folder glyph — in a tree where every row is a project, "this is a project" carried no information.
- A right-click menu gives the run-state picker and Archive/Unarchive on the promise-bound toast. **This app had no project-editing control at all before it.**
