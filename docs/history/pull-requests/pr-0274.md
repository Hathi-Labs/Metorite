## Description

Sending a notetaker to a Google Meet failed with nothing to go on. The worker was running fine on the box (deploy 867: `meeting bot UP on 127.0.0.1:8095`), so this was never a config gap — the bot was dispatched and couldn't get into the call, silently.

## Why nothing was visible

**The failure erased itself.** `/notes/bots/active` filters to running statuses, so a bot that fails leaves the set instantly and the "Notetakers in meetings" strip just empties — "it didn't work" became indistinguishable from "nothing happened". Recent failures (30 min) now stay in the query.

**The error was fetched and discarded.** `ActiveBots.tsx` received `b.error` from the API and rendered only the status label. It now renders the explanation.

## Two real defects in the join path

- **`_click_first` passed its timeout to the visibility wait but not to `click()`.** Meet keeps "Ask to join" *disabled* until a guest types a name, so a visible-but-disabled button burned Playwright's 30s default per selector — five selectors could exceed the whole 150s join budget before reaching the last one.
- **Nothing dismissed Meet's device dialogs.** The container has a virtual mic but no camera, so Meet puts a modal over the green room. The join button sits behind it, which presents *exactly* as "no join button found".

Either alone reproduces the reported symptom.

## Timeout and refusal were the same status

`_await_admission` returned `not_admitted` both when Meet said "you can't join this call" and when it merely ran out the clock in the waiting room. Those need opposite responses from a human — click Admit, versus the link will never work for a signed-out guest. Now split into `refused` / `timeout` / `in_call`, each with an error that names the fix.

`classify_body()` is pure so the phrase lists are tested directly. The costly confusion — treating "asking to be let in" as terminal — is locked by a test.

## A missed selector now says what it saw

Meet's DOM is not a public API, so selectors drift; the useful question is what the page actually rendered. Failures capture url/title/body **plus the label of every visible button**, exposed at:

- `GET /bots/{id}/diagnostics` and `/bots/{id}/screenshot` (worker)
- `GET /notes/meetings/{id}/bot/diagnostics` (gateway)

Also: waits for a real control rather than a fixed 3s sleep (Meet hydrates well after `load`, slower on 2 vCPU), and retries the green room once after a settle.

## Testing

- 2510 unit tests pass (12 new, covering refusal-vs-waiting classification, error diagnostics, and failure visibility)
- `tsc --noEmit` and `next build` clean
- Not verifiable here: the join against a real Meet call — that needs the deployed box, which is the point of merging

## Known gap, not addressed here

`LIVE_ASR_URL` is unset on the VPS, so a bot that joins successfully still produces **no live captions** — only the post-meeting transcript. Wiring the worker to AssemblyAI's streaming endpoint is follow-up work.
