## Description

## What the deploy log revealed

After merging #380 I watched its deploy and grepped the job log for the unit sync it promised: **zero mentions of `acb-backup`**. The loop had been added to `deploy/hostinger/deploy.sh` — the manual runbook — while both automated delivery paths (the workflow's SSH step and the box's `acb-pull` poller) run `scripts/vps_apply.sh`. Green merge, green deploy, backup timer still unscheduled. Same failure family as `1b56465d` ("guards read a file the script had moved out of"), one file over.

## The fix

- The BO-23 unit-sync block now lives in `scripts/vps_apply.sh` (immediately after the watchdog step): install changed units from `deploy/hostinger/`, one `daemon-reload`, `enable --now` every repo timer, **never** restart services from the loop. Byte-for-byte the same semantics as #380's block, with `$APP_DIR`-absolute globs per this script's idiom.
- `tests/unit/test_backup_deploy_wiring.py` — five guards, all asserting on non-comment lines (the prose-guard lesson): live path globs+installs units · enables timers from the glob · no service restarts in the sync step · backup units exist with a real `OnCalendar` · both copies of the loop stay present, with the retirement order documented in the assertion message.
- **Mutation-checked**: 4 of 5 guards fail against the pre-fix script; all pass with it.

On merge, the next deploy finally schedules `acb-backup.timer` — the thing #380 set out to do.
