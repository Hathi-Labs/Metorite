## Description

`_maybe_send_follow_up_reminders` raised on **every** sync cycle:

```
asyncpg.AmbiguousParameterError: could not determine data type of parameter $2
[SQL: SELECT ts.thread_id, ts.status, ts.l…
```

A bare `:param IS NOT NULL` gives asyncpg no type to infer from. The exception was swallowed by a best-effort handler that logged a warning nobody reads — so the feature looked present in the UI and **did nothing at all, for its entire life**.

Reproduced and fixed against the production database: `PREPARE` on the old shape errors, on the new shape it succeeds.

## The fix

The NULL guards were **redundant**: `last_message_at < NULL` is NULL, not TRUE, so an unconfigured window already excludes its own branch. Verified live — passing the NEEDS_REPLY cutoff as NULL returns AWAITING rows only. Removed them, and cast both cutoffs explicitly so the types are unambiguous by construction rather than by inference.

## Staleness ceiling (`_FOLLOW_UP_MAX_AGE_DAYS = 30`)

Repairing a long-dead job releases everything it never processed:

| | |
|---|---|
| AWAITING threads due, no ceiling | **67**, oldest from Oct 2025 |
| ...with `auto_draft` on | one AI nudge **each** |
| AWAITING threads due, 30-day ceiling | **35**, all within the last month |

A reminder about last week is useful; one about last autumn is noise, and those threads are only queued because this job was broken long enough for them to pile up.

Stale threads are **excluded by the query, not stamped as reminded** — `_upsert_thread_status` re-arms `follow_up_reminded_at` when a thread changes hands, so one that comes back to life becomes eligible again on its own merits.

Also ordered newest-first, since the per-cycle `LIMIT` means order decides what gets attention while a backlog exists.
