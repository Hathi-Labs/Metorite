## Description

Asking for `speaker_labels` (#284) was necessary but not sufficient. Live diarization also needs a streaming model that supports it — and we were letting AssemblyAI pick.

## The model family confusion

AssemblyAI's **streaming models are a separate family from the batch ones**. Valid streaming ids are `universal-streaming-english`, `universal-streaming-multilingual`, and `u3-rt-pro` (Universal-3 Pro Streaming).

**`universal-2` is not a streaming model at all.** That's why selecting it in Settings → Models never affected live transcription — that setting only ever drove the batch pipeline. So the reported symptom had nothing to do with the model that was picked.

Of the streaming models, diarization needs **`u3-rt-pro`** or the multilingual one. That's now the default instead of whatever AssemblyAI would choose, overridable via `ASSEMBLYAI_LIVE_MODEL` if the cost tradeoff isn't worth it — captions still work on the others, just with every voice merged into one speaker.

## Second bug found while wiring this

The meeting-bot worker built its WebSocket URL **without `speech_model` at all**, so it silently discarded whatever model the gateway had chosen. A deployment could be correctly configured for `u3-rt-pro` and the bot would still connect on the default and return no speakers.

## Why both were expensive to find

They share a failure shape: a wrong streaming model returns a **working transcript with every voice merged into one**, not an error. That reads as "diarization is broken" rather than "misconfigured", which is what sent this hunting through the plumbing.
