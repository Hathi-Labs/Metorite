## The reviewer's P1 was refuted, and the method is the point

The adversarial reviewer argued that Enter on a now-focusable task title escapes the canvas keydown handler and performs a full-document GET, rebooting the SPA and discarding filters, selection and view mode. **The first half is exactly right** — `stepCursor` returns null at `cursor < 0`, and `TaskList.tsx:171` returns *before* `preventDefault` at line 172. The conclusion does not follow: the default action of Enter on an anchor is *to dispatch a click*, which `ControlLink` intercepts.

Reproduced in real Chromium with React-style **root delegation** (React 17+ delegates from the container, not the element — which is precisely where a late `preventDefault` would fail):

```
canvas keydown Enter -> stepCursor null -> return, NO preventDefault
root-delegated click: button=0 detail=0
INTERCEPTED -> onActivate(open panel)
NAVIGATIONS: []
```

Zero navigations, URL unchanged. A repair round for a non-bug was avoided by running it rather than reasoning about it.

## Findings that were real, and are fixed

- **`ControlLink` had no themed focus ring** — ~200 new focus stops on a long table drawing Chrome's default outline. Fixed by extending the **existing** `.cc-control:focus-visible` declaration with a `.cc-link` selector: one ring, two kinds of focusable thing. Deliberately **not** by applying `.cc-control`, which bundles the ring with control label weight, tracking, text-transform and a hover state layer, and would have restyled every task title.
- **The anchor was natively draggable**, stealing click-drag text selection from titles. `draggable={false}`.
- **`mywork.ts`/`mywork.test.ts` carried a retracted claim.** They said a finished task "rendered overdue in My Work". It did not — that export has **no in-app caller**; `MyWork.tsx` draws the chip through `cardChips` → the shared predicate. A latent divergence, not a visible bug. The spec was corrected earlier; the source comments were not, which is the same disappearance one level down.
- **The empty-`positions` write had no test.** The context menu's "Change status" sends `positions: []` on every use. Added `test_an_empty_position_list_is_a_no_op_and_never_wipes`, asserting `written == 0` **and that pre-existing rows survive** — the second half is the point, since `written == 0` alone passes a wipe-then-write-nothing. Mutation-measured: an authoritative DELETE turns it red on the survival assertion.
- **`LayoutBoundary`'s own rationale was wrong.** React unmounts the subtree below a boundary *before* rendering the fallback, so the key bump is belt-and-braces; the bump that earns its place is `page.tsx`'s `canvasKey`.
