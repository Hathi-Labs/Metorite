## What I found reviewing the learning patterns

**45 patterns on the live account. Every single one `source='AI'`.** Zero from Fix, zero from a label changed in the mail client, zero typed by hand.

So every pattern in the system was inferred by the machine from its own output. `_sender_consistent_for_rule` requires three matches to one rule and no other rule ever — which measures *consistency*, not *correctness*. If the classifier was wrong three times, the gate entrenches the error rather than catching it.

And a pattern is not a small thing: it short-circuits the classifier completely, and it is the **first and strongest** evidence `_decide` uses in the cleaner, which then offers archive / unsubscribe / delete on top. Top reach measured: 46 messages from one pattern.

**The review screen couldn't support review.** Settings → Learned patterns → Manage showed a sender, a rule, a source badge and a delete button. "Is this pattern right?" is unanswerable from that, which is why 45 of them accumulated untouched.

## The gate

Migration 85 adds `approved_at` / `rejected_at`. Two asymmetries, both deliberate:

**Includes vs excludes.** An include *asserts* a category; an exclude only ever *prevents* one. There is nothing to approve about "this sender is not Marketing" — gating it would make the cleaner label mail the user explicitly said it shouldn't. Only includes are gated.

**Cleaner vs classifier.** The classifier keeps using unreviewed patterns — its alternative is an LLM call, so a pattern there *saves* money and a mistake is one message the user can Fix. The cleaner's alternative is leaving mail uncategorized, and it applies one pattern across every matching message in the mailbox. Different blast radius, different bar.

Patterns the user authored (`FIX`/`USER`/`LABEL_ADDED`/`LABEL_REMOVED`) are approved on creation — that act *is* the confirmation.

## Rejection has to stick

Rejecting **keeps the row**. Deleting it would let the auto-learner re-infer the same pattern from the same sender within the hour, so rejection would be a gesture rather than a decision. `_upsert_rule_pattern` refuses to resurrect a rejected pattern — unless the *user* overturns it via Fix or a label change.

Resetting the rules now carries review state across the reseed. Without that, one reset silently un-approves everything.

## The screens

- **Learned patterns** — each row shows its reach ("about 46 emails"), with Approve / Reject per row and "Approve all N". Pending ones are visually separated; `SUBJECT` patterns no longer mislabel themselves as "From".
- **Email Cleaner** — "N patterns the assistant taught itself are waiting for your approval · would categorize about M more emails". A gate with no number and no route to the decision reads as the cleaner having got worse.

## Sequencing

This closes the loop the request describes: **AI-categorize a bounded window** (now cost-capped by #94) → **patterns populate** → **you approve them** → **the cleaner projects them across the whole mailbox for free**.

One honest note: on this account all 45 patterns are includes, so **all 45 go dark until reviewed**. That is the requested behaviour, and the Cleaner says so — but it is a real, visible change on first deploy.
