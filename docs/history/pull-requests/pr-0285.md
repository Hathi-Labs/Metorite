## Summary
This targets the apps end users *build* through the Workshop (T1/T2), not the Workshop's own UI (already made mobile-responsive in a prior PR). Three parts:

- **Desktop/phone-width preview toggle** in the Workshop editor's Preview tab (Monitor/Smartphone icons) — the same `srcDoc` rendered either full width or inside a 390px-wide frame, so an app can be checked at both sizes without leaving the Workshop. No changes needed inside `SandboxedHtml` itself; it already fills whatever container it's given.
- **Touch-target sizing bump** in `SandboxedHtml.tsx`'s injected design-token CSS (`min-height: 2.25rem` on buttons/inputs) — applies to every app automatically, published or draft, T1 or T2, since it's the same `buildSrcDoc` every app's frame goes through. Explicitly reset back to `0` on checkbox/radio/range inputs, which have their own well-established native sizing that a blanket `min-height` would otherwise distort (range in particular: `min-height` beats an explicit smaller `height`, so without the reset the 6px track would render 36px tall).
- **A new "Mobile & responsive layout" section** in `agent-app-builder/instructions.md`: keep the starter scaffold's viewport meta tag (called out explicitly not to drop it during the T1→T2 `index.html`-to-build-template conversion — the one place it's actually at risk), prefer the already-fluid block-kit classes and `flex-wrap`/`max-width` over fixed pixel widths, and check the new preview toggle before ending a round that touches layout.

The published run page needed no changes — it's a real full-page route, so it already renders at whatever width the viewer's actual device gives it. The platform-level gap was entirely in what the agent is told to build and how the Workshop lets it verify that, not in how apps are served.
