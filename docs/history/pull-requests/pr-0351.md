## Description

## N4 — the HR directory stops being org-wide read *and write*

**⚠️ Stacked: #348 ← #349 ← #350 ← this.** Retarget each child to `main` before merging its
base, bottom-up — merging a base with `--delete-branch` auto-closes its children.

Found while building the WS-24 readiness gate (#350). **This is the sharpest item that gate
turned up, and the only blocking one that did not need the owner.**

### What was open

`routes/tasks/people.py:22` mounts on the **feature-gated** `/tasks` router
(`tasks/core.py:27-30`, whose only dependency is `require_feature_router("tasks")`) and added
no scope of its own. `member` — the default role for a new employee — holds `feature:tasks`
(`130:235`).

So every colleague could read the whole roster (name, email, title, department, manager,
skills **including résumé-extracted ones**, `resume_summary`, `years_experience`, capacity,
current load, ClickUp id) and **add a person, edit anybody's record, or upload a résumé onto
it**. `GET /people` took `_user` — the underscore is the code stating the identity is unused.

It hid behind the same feature flag as the task list, which is why every prior summary of
"what a member can see" answered for `gtd_items` and stopped there.

### The decision — owner-answered 2026-08-04

**Directory open, HR fields restricted.** The roster stays visible to anyone holding
`feature:tasks`; the HR half is admin-only; writes are admin-only. Both rejected alternatives
(fully org-wide read; Center-scoped read, which needs D13's unbuilt grant shape and breaks
cross-team delegation) are recorded in the spec's DECISION block.

| | Non-admin member | Admin / owner |
|---|---|---|
| name, email, role, title, department, team, `reports_to`, `clickup_user_id` | ✅ | ✅ |
| `skills`, `skills_source`, `resume_summary`, `years_experience`, capacity / load / available | ❌ nulled | ✅ |
| `POST /people`, `PATCH /people/{id}`, `POST /people/{id}/resume`, `POST /people/embed` | ❌ 403 | ✅ |

### 🔴 Two things the brief did not ask for, and the fix is wrong without them

**1. The search box was an oracle for the column being hidden.** `GET /people?q=` appends
`EXISTS (… unnest(skills) …)`. Strip `skills` from the response but leave that clause and the
protection is cosmetic — you can binary-search a colleague's résumé skills through a query
parameter. The clause is now dropped for non-admins, and that is mutation-verified.

**2. The read fix alone would have destroyed data.** A non-admin now loads `skills: []`, and
`PersonEditor` **round-trips `skills` on save**. Without the write gate landing in the same
change, a member opening and saving a person would have **wiped that person's skills**. The
two halves are not independently shippable, and the PR says so rather than leaving the next
person to discover it.

### Implementation choices, each reusing an existing mechanism

- **Writes: `admin:members:manage`** — an existing `CAPABILITIES` entry, already the
  permission governing member records, bound the same way as `admin/members.py:145-146`.
  **No new slug**: a new slug is nobody's grant until an admin creates it, which would have
  broken HR features for the owner too.
- **HR reads: `admin:members:read`** — reused, not reinvented. It is `admin/_common.py:77-91`'s
  package floor and exactly what `admin/me.py:96` returns as `is_admin`. The owner's `*`
  matches both, verified by `permission_matches` and by test.
- **Projection at the serialization layer, not SQL.** `_row_to_person(row, *, include_hr)` is
  keyword-only with **no default**, so a missed call site is a `TypeError`, not a silent leak —
  the same discipline as the `triggered_by` fix in #346. Fresh containers per call; a
  module-level `[]`/`{}` would alias into every response.
- A shared seam in `tasks/core.py` (`can_read_hr_fields`, `require_people_write`) so the rule
  has one home. `can_read_hr_fields` **fails closed** on a non-`UserContext`.

### `fetch_people_for_clarify` is untouched — deliberately

`people.py:107-135` takes `db` only and feeds AI delegation/clarify. It has its own query, so
a serialization-layer projection leaves it structurally unaffected. Pinned by a test that
asserts full data **and** its signature is `["db"]` — because had the projection gone in at the
SQL layer, agent delegation would have silently degraded with nothing failing.

### Frontend — verified, not assumed

Only `PeopleView.tsx` and `PersonEditor.tsx` read `OrgPerson`, and `mapOrgPerson`
(`tasks/lib/api.ts:301-327`) already coerces null → `undefined`, null skills → `[]`,
null `skills_source` → `{}` — exactly the shape nulling produces. `PersonRow` degrades into its
existing **"No capacity set"** branch and hides skill chips behind `p.skills.length > 0`.
PeopleView's search is **client-side**, so the `q` change affects only the `gtd_people` agent
tool, not the UI.

**A wart, reported rather than hidden:** the "Add person" button and row-click editor still
render for a non-admin; Save now surfaces the 403 inline. That matches this repo's stated
doctrine (`lib/access.ts:126-129` — hiding a control is a courtesy, not a boundary), but
gating those affordances on `is_admin` is worth a follow-up slice.

Agent path: `skill-task-gtd`'s `gtd_people` tool calls `GET /tasks/people` **as the acting
member**, so an agent run for a non-admin now sees the restricted directory. Correct under the
intersection rule, and recorded in the DECISION block.
