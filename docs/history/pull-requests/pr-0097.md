## Description

You asked me to verify the learned patterns are actually working. They were not. **24 of the 45 patterns on your account — 53% — would not be learned under this commit.**

## What the gate claimed vs what it did

`_sender_consistent_for_rule` documented "at least 3 consistent matches, and no other rule ever matched this sender". It enforced neither.

**1. Dry runs taught.** The filter excluded `SKIPPED`/`REJECTED` but not `PENDING` — which is exactly what a *preview* logs.

```
arvind@exinous.com → Calendar
  7 log rows · 1 distinct message · 5 of them PENDING previews
```

Pressing "Test" on one email three times wrote a permanent pattern. A dry run is documented as changing nothing.

**2. It counted log rows, not messages.** `COUNT(*)` over a table that gets a row per rule per run.

```
donotreply@gst.gov.in       10 rows → 1 message
ar.zstoreind@zohocorp.com    9 rows → 1 message
almashines@mails.org.in     10 rows → 1 message
```

Re-running a backfill over the same mail manufactured its own evidence. Now `COUNT(DISTINCT message_id)`, and the 616 live rows with a NULL `message_id` no longer count — nothing can corroborate them.

**3. The "no other rule" invariant was unenforceable.** `multi_rule_execution` is **ON** for your account, so one message legitimately matches several rules — and `_apply_and_log_match` is called once per match *in a loop*, so the first rule's check reads a log that doesn't yet contain its own siblings.

```
Info@yourstory.com → pinned to Marketing
  but every message matches  Marketing + Newsletter
                          or Marketing + Cold Email
```

The pattern then short-circuits the classifier down to the single pinned rule, silently discarding the other half of a multi-rule outcome. Fixed with `sole_match`: an ambiguous classification teaches nothing, because pinning a sender only means something when the answer was unambiguous.

**4. People were pinned to cleanup categories.** The existing guard refuses to pin a sender to a conversation-status *rule*, but nothing stopped pinning a *human* to Receipt or Calendar.

```
midhun.vm@link-innovations.com → Calendar   (has Awaiting Reply, Done)
debesh@metafora.sg             → Receipt    (has Awaiting Reply)
```

Both send documents *and* ask questions. Pinned, their next real request is filed as a receipt. `_sender_is_a_correspondent` uses the conversation-status labels as evidence — they're assigned per-thread from the whole conversation, so their presence proves a real exchange — and **fails closed** on error.
