## Purpose
Control Plane (Next.js browser UI) and local development tools.

## Structure
- control_plane/ -- Next.js app (chat, email, agents, integrations, settings)
- control_plane/src/app/email/ -- Email AI Assistant: 4-panel email client (accounts sidebar, email list, email detail, AI chat) with multi-account Gmail/Microsoft support
- control_plane/src/app/email/components/ContactCard.tsx -- People card (Outlook parity). `ContactTrigger` wraps any avatar/name/recipient to open it; `RecipientList` renders a clickable To:/Cc: line; every field carries a `CopyButton`. Backed by GET /email/contacts/card, which also files what it learns into the server-side contacts directory — pass the display name you already have so recipients you only ever write TO are filed under a name, not a bare address. The trigger renders a real <button> and stops propagation, so a row that contains one must be a div (see ConversationView's message header), never a <button>
- control_plane/src/components/EmptyState.tsx -- THE empty-state box (icon · message · hint · one action), shared so a surface with nothing on it looks the same in every app. **Three states, never one**: a filtered-to-nothing surface says so and offers the control that undoes it; a genuinely empty one does not mention filters; and (WS-27am) a surface the reader may not write to draws its CTA **disabled rather than hidden** — `EmptyStateAction.disabled` + `disabledReason`, so they learn the action exists AND that it is not theirs. The reason is rendered as text, not only as `title`: a disabled button is not focusable, so a tooltip is unreachable from a keyboard and absent on touch. WHICH state a surface is in, and its wording, stays the app's own pure module (`app/projects/lib/emptyState.ts`, unit-tested — vitest here is node-env, so a component test cannot run); its precedence is filtered → no-permission → status-axis → empty, and the middle step is deliberate (never tell a viewer to "add a status"). Every prop of the third arm is optional and **no call site is wired yet** — the per-project write grant is not on the client's row shapes. Icon names must be mapped in `lib/theme/icon-data/registry.json` for every pack or the glyph silently falls back to Lucide. ⚠️ `/tasks`' `ItemList.tsx` still holds the local `NoMatchState`/`EmptyState` pair this was promoted from, and `projects/page.tsx`'s `renderState()` seam is still inline — both are owed
- control_plane/src/components/LayoutBoundary.tsx -- THE error boundary (WS-27am), and until it landed **the tree had none at all** — no `componentDidCatch`, no `error.tsx` — so one malformed group shape took React's root down and left a white document. Mounted per **layout**, around the untrusted part (the canvases that walk server-shaped data), so the tree, toolbar and task panel stay alive and switching view or project is still a way out. ⚠️ **Retry re-mounts by bumping a key** (`state.attempt`, handed to React as the guarded subtree's `key`) — clearing an error flag re-renders the same subtree and re-crashes. The arithmetic lives in `src/lib/layoutBoundary.ts` because vitest here is node-env and `.tsx` tests are not collected, and `caught()` returns ONLY `error`: it is `getDerivedStateFromError`, whose result React merges, so an `attempt` in it would silently reset the key. `src/lib/layoutBoundary.test.ts` fences the arithmetic plus a source scan that the boundary is the canvas region's only child. **What no test in this tree can prove** is that a throwing child is actually contained — that needs a DOM runner, which this repo deliberately does not have; it is a review check. `/projects` is the only consumer today

- control_plane/src/app/crm/ -- The native CRM (spec: `project-docs/specs/crm_app.md` §5; WS-26c, extended by WS-26f). Deals kanban landing tab + a list per entity on one shared list contract, a record sheet that opens OVER the list from `?deal=`/`?lead=`/`?contact=`/`?organization=` (no `/[id]` routes — Back closes the sheet, and v1 has no saved-views table so view state IS the URL), timeline with a note/task/call composer, inline-edit fields panel, convert modal, quick-create. ⚠️ **Everything server-shaped is pure and lives in `lib/`, each file unit-tested**: `urlState.ts` (the URL grammar), `board.ts` (lane order/tone, the move plan, the optimistic re-tally, `needsLostReason`), `filters.ts` (the list contract — including *never* sending `?status_id` to contacts/organizations, which the gateway 422s by design), `convert.ts` (§3.7's match rules mirrored so the modal pre-selects what the server would do), `format.ts` (₹ in `en-IN` lakh/crore grouping), `api.ts` (the BFF client; refusals keep their status so a 409 is explained, not reported as a failure). `components/` is composition only. Proxy: `src/app/api/crm/[...path]/route.ts` (the tasks-proxy shape). Three rules here were learned by breaking them: **(1) every list filter — `sort`/`dir` included — lives in `CrmView` and therefore in the URL**, because the load effect keys on view fields and a filter held in component state is a control that changes its own appearance and issues no request (`sort` is also cleared by `selectTab`: the keys are a per-entity server allowlist and a carried-over one is a 422, not an odd order). **(2) A write re-reads what is on screen, whatever the response was** — `refreshCollection()` off the store's `lastView`. The refusal half is obvious (a stale row after a 409 reads as success); the success half is the same lie told backwards, and it shipped first as a created record invisible until manual refresh and a rename that left the row behind the sheet unchanged. **(3) A post-write re-read carries the filters the view was loaded with** — `moveDeal`'s re-read used to fetch the pipeline unscoped, silently widening an owner-filtered board the moment somebody dragged a card on it. **WS-26f adds a fourth tab, `?tab=settings`** (three grids over the EXISTING admin API — deal stages, lead statuses, lost reasons; `lib/settings.ts` owns what a drag-reorder renumbers, which rows that actually PATCHes, and the client half of D-CRM-10's won=100/lost=0 rule). ⚠️ **`settings` is a tab that is NOT a collection, and every unchecked `as EntitySlug` cast on this page was a place that assumed otherwise** — `isEntity()` from `urlState.ts` is the guard, and the load effect, `store.refreshCollection()`, `setCreating` and `PARAM_FOR` all go through it; `parseView`'s old `isEntity(tab) ? tab : "board"` *swallowed* `?tab=settings` and landed the deep link on the kanban. Weighted ₹ (`lane.weighted`) comes from the gateway per lane and is **never** recomputed from `lane.rows`, which is one page of it; `board.ts` keeps the same formula (`weightedDeal`/`weightedRows`, `WEIGHTED_TYPES` = open+ongoing, a NULL probability inheriting the stage default) for the header rollup and the record sheet. **WS-26g adds a fifth tab, `?tab=reports`** (`components/Reports.tsx` + pure `lib/reports.ts`, over `GET /crm/reports/*`): forecast by stage, funnel, win/loss, owner leaderboard. It is another entry in the SAME `NON_ENTITY_TABS` grammar rather than a route, so the record sheet stays open across it — `?tab=reports&deal=<id>` is a link somebody sends. ⚠️ **The reports surface computes nothing**: every figure is server-side and rendered verbatim, and `lib/reports.ts` holds bar widths and wording only. The one formula that legitimately lives on both sides is `board.ts`'s weighted ₹, and it is held to the gateway's SQL by a fixture BOTH runners read — `tests/fixtures/crm_weighted_parity.json`, from pytest through the emitted statement and from `board.test.ts` through `weightedDeal`/`weightedRows`. Adding a non-collection tab is never one edit: `NON_ENTITY_TABS`, the `page.tsx` branch chain AND the load effect all have to learn it, or the tab parses, the pill highlights, and the screen keeps showing whatever was there. ⚠️ **A new tab also has to be reachable from `refreshCollection()`, and every write has to GO through it** — `moveDeal` used to hard-code a board fetch, so the reports branch was unreachable from the one write its own comment named and a deal moved from `?tab=reports&deal=<id>` left all four blocks stale while the fetched pipeline landed in state that tab does not render. `store.test.ts` pins WHICH request each write issues, not the state it settles into: the store's job is deciding what to re-read, and a final-state assertion cannot see a decision that was never made

- control_plane/src/app/projects/ -- Projects (spec: `project-docs/specs/project_management_app.md`). The **canonical** task surface: `/tasks` derives from it, so where the two differ Projects is right by default (owner ruling 2026-08-10; D-PM-6). Everything server-shaped or rule-shaped is a pure module under `lib/`, unit-tested, and `components/` is composition. Four of those modules are single-source contracts and a second copy is a defect: **`lib/grouping.ts`** owns the saved-view config round trip (`toConfig`/`fromConfig`) **and** `viewDivergence` — the ONE answer to "has this board stopped being the view", read by `FilterBar`'s Update view · Save as new · Reset row; a comparison written anywhere else is a second opinion about what a view IS. **`lib/shownFields.ts`** is the field vocabulary, gating the table's columns, every card's chips **and** (WS-27ab) the list's Status/Assignees columns — the list's column set is `table.listColumns`, so the header and both `colSpan`s are one number. **`lib/commands.ts`** is THE palette action registry: the palette lists it, `page.tsx` runs its `g`/`v` key sequences through `stepSequence`, and `ShortcutsSheet` is *printed* from it, so `?` cannot drift from the keyboard — its Go section is derived from `src/lib/nav.ts` rather than copied, and `ViewMode`/`VIEW_MODES` live here so the toolbar and the palette cannot offer different canvases. **`lib/panelMode.ts`** owns peek → side → full (a per-user `localStorage` preference, read in an effect because SSR has no storage). **`lib/taskMenu.ts`** (WS-27bd) is the TASK-scoped action registry behind the right-click menu — Open · Copy link · Select · Change status, each declared with the context it is offered in — read by `TaskBoard` and `MyWork` and rendered through the shared `@/components/ContextMenu`. ⚠️ It is a **second registry at a different scope** from `lib/commands.ts`, deliberately: the palette registry holds no task-scoped action to resolve to, and a card menu made of "Widen the task panel / Custom fields" is a junk drawer. What is enforced is that the two stay **disjoint in both directions** (`taskMenu.test.ts`) — adding a task action to `commands.ts` is a ticket that also moves the `g`/`v` sequences and the printed shortcuts sheet, not a side effect. **`lib/rowState.ts`** is the per-row pending/error reducer (`pending: Set<id>`, `errors: Map<id, string>`): three concurrent operations are three spinners and one failure is attributed to one row. Two rules in it are easy to get backwards — a retry does NOT blank the previous error on entry (it clears on success), and `prune` drops state keyed to a row that has left the list, so a message cannot outlive what it was about. ⚠️ **Escape is two handlers with one rule between them**: opening a task leaves focus on the *card* (the canvas is `tabIndex={0}`), so the panel's own `onKeyDown` never sees the key — the page's window listener closes it from outside, the panel's own handler blurs a composer holding text first and calls `stopPropagation` so exactly one fires. The panel returns focus to the element captured at mount, guarded by `document.contains`. **`lib/pagedPicker.ts`** (WS-27bc) is a long-list picker's arithmetic **with no picker in it** — a 48px scroll-threshold predicate over three plain numbers (inclusive at the boundary; content shorter than its viewport counts as "at the end", which is the stall nobody sees), page accumulation that dedupes by id because `/projects/tasks` is ordered by `updated_at` and a row legitimately crosses a page boundary (first position wins so the list does not re-sort under the cursor, last payload wins so it does not render a title already known stale), and a terminal state **derived** from the raw page length — never a `hasMore` flag beside the rows, and never from how many rows the dedupe added, or a full page of duplicates ends the list. ⚠️ Its min-length gate and stale-response guard are **imported** from `lib/search.ts` (`MIN_QUERY`, `isCurrent`), held there by a source scan in `pagedPicker.test.ts`: no behavioural test can tell a shared constant from a second copy holding the same number today. **Nothing is wired to it** — the surface half is D-PM-15's `src/components/ui/` wrapper, sequenced behind WS-27ak, and what happens *below* the minimum is a blocked decision (`/projects/search` is capped-not-paged and has no unfiltered mode; `/projects/tasks` is paged and unranked), not an omission
- control_plane/src/components/ControlLink.tsx + control_plane/src/lib/controlLink.ts -- THE "a clickable thing that is also a real link" seam (WS-27al). A surface whose rows are bare `onClick` handlers is a surface where cmd/ctrl/shift/middle-click do nothing; `/projects` measured **zero** `<a href>` on a task before this. The component is a genuine anchor and gives the *plain* left-click back to the app; `shouldIntercept()` in `lib/controlLink.ts` is the only place that decides which clicks those are, kept pure because vitest here is node-env and a decision inside the component would have no fence. ⚠️ **It goes in the title CELL, not around the row** — rows are `<tr>` and an `<a>` cannot wrap one — and it **stops propagation unconditionally**, or a plain click opens the panel twice and a cmd-click opens a tab *and* the panel. Plain `<a>`, never `next/link`: the target is the route the reader is already on, so a `<Link>` would prefetch it once per row for a navigation that only ever happens in a new tab. `TaskCardShell` is deliberately NOT a consumer (it is a `role="button"` div by a recorded decision — nested interactive elements inside an anchor are invalid HTML). Fences: `src/lib/controlLink.test.ts`, whose middle-click case is asserted by name because the upstream reference misses exactly it, plus a "wired, not merely imported" source scan. **That a modified click really opens a tab is review-only in this tree** — no DOM, no browser, no e2e
- control_plane/src/components/ui/Modal.tsx -- THE dialog primitive (WS-27ak item 1), and the **only** file in the tree allowed to `import … from "@base-ui/react"` — D-PM-15 picked Base UI as the one headless substrate and conformance **rule 8** is the fence, both for the import and for a *second* substrate arriving in `package.json` via a vendored shadcn/`cva` registry. Before it, **70 files** carried a `fixed inset-0` overlay and **zero** trapped focus: that is not seventy bugs, it is a primitive nobody had written. It gives every dialog focus-in / focus-return-to-the-opener, a real Tab trap at both ends, `aria-hidden` on the background, scroll lock with scrollbar-gutter compensation, `role`/`aria-modal`/`aria-labelledby`, and outside-press dismissal only when the press starts **and** ends outside. ⚠️ **It is strictly CONTROLLED and holds no open state** — `/projects`' `overlayOpen` (`page.tsx:968-974`) is derived from the page's own state and `:1039`'s window listener suppresses `g`/`v` sequences off it, so a wrapper that owned its open state would silently let `g` navigate out from under a half-filled import form. `e2e/modal.spec.ts` presses `g t` under an open dialog and asserts it does not. ⚠️ **`outsidePressEvent` is NOT a prop** in `@base-ui/react@1.7.0` — the `intentional` behaviour comes from rendering `Dialog.Backdrop` (removing it alone does **not** degrade to `sloppy`; the portal's `InternalBackdrop` covers for it, so the red mutation is backdrop-removed **and** `modal="trap-focus"`); and the library **never sets a real `inert` attribute**, so find-in-page can still reach the background (recorded in `project_management_app.md` §11.31, not fixed here). ⚠️ **Focus return past the opener is the WRAPPER's, not the substrate's** — Base UI drops a disconnected opener and then focuses *nothing*, leaving `<body>`, which is reachable whenever a dialog outlives the control that raised it (`ImportClickUp`). The documented order is explicit `finalFocus` → the opener captured at open → the page's `<main>` landmark with a borrowed `tabIndex={-1}` → nothing, and the docstring says so rather than promising a guarantee. A `max-h-*` passed in `className` **wins** over the wrapper's `max-h-full`; `closeLabel` names the close button. Six `/projects` dialogs consume it, and `conformance.test.ts` fails any of the six that grows a `fixed inset-0` back by hand. ⚠️ `app/email/components/automation/ui.tsx:15` is a **second** `Modal` with five consumers and none of the above — retirement owed, an email ticket, do not add a sixth consumer
- control_plane/src/lib/outsideClick.ts -- THE outside-click walker (WS-27al). ⚠️ **Modal does NOT consume it** and that is deliberate (WS-27ak): Base UI brings its own outside-press handling with the start-and-end rule this walker does not express. It stays the answer for a popover not built on the substrate. `shouldDismiss(target, walk)` climbs from the clicked node and refuses to dismiss on the surface itself, on any ancestor carrying `data-prevent-outside-click`, or on a null target; `domClickWalk()` is the one DOM adapter. Fence: `src/lib/outsideClick.test.ts`. A new popover consumes this rather than hand-rolling `contains()`
- control_plane/src/app/settings/billing/ -- Settings → Billing (spec: `project-docs/specs/subscription_console.md` SC-1b/SC-5, and SC-4a for the checkout). `page.tsx` is the credit monitor and bill archive; `Checkout.tsx` is SC-4a's LAUNCH slice — the ₹0 / discount purchase flow — and it is mounted from **exactly one place**, inside `page.tsx`'s `data.purchaseEnabled` arm, so the whole thing ships dark until the owner flips that flag on the Console. Everything server-shaped is pure in `lib/` (`billing.ts`, `checkout.ts`), unit-tested; the component is composition. **Four rules here, three of them learned from money bugs elsewhere.** ⚠️ **(1) The BFF is the ONLY gate these routes will ever have.** `src/app/api/billing/**` does *not* go to the gateway — it calls the Customer Console directly with this deployment's `cc_live_` organization key, so nothing re-authorizes downstream. `_console.ts::requirePurchaser()` resolves the caller's `billing:purchase` capability server-side through the gateway's `/auth/me` and refuses **before** the Console is touched; a 403 issued after the money route was hit is a different and worse bug, and `checkout.test.ts` asserts *zero calls to the Console*, not merely the status. The capability check runs **before** the 503 config check on purpose, and an *unresolvable* capability is a 403, never a pass. ⚠️ **(2) The browser never names a price and never sums one.** Prices are integer paise from `GET /billing/catalog` and are formatted once by `formatPaise`; there is no basket total anywhere on the client, and `POST /billing/orders`' proxy **rebuilds** the body as slug+quantity rather than forwarding it, so a page field cannot become a wire field. Fenced by a source scan for every D23/D24 figure in both denominations. ⚠️ **(3) Re-read the order before every act and after every one** (SC-4a done-when 5a) — `captured`/`abandoned` are terminal, a past `expires_at` is terminal even while `status` reads open, and nothing writes `failed` at order level, so a page branching on a third terminal state is branching on a state that cannot occur. The re-read runs after a *refusal* too: a stale row after a 409 reads as success. ⚠️ **(4) The refusal partition is the server's and this tree must not summarise it** — three distinct reasons for `expired`/`revoked`/`exhausted`, ONE byte-identical shape for {unknown, wrong-org}, because telling those apart is a membership test over other tenants' data. The proxies relay 400/404/409 bodies verbatim (and deliberately NOT 503, which names this deployment's own missing variables). 🔎 **Known-open board finding, NOT fixed here:** `GET /api/billing/summary` is reachable by any signed-in member and returns credit balance, burn and BYOK status while its own header claims otherwise; it is excluded from the gate fence **by name**, with a case that runs it and would go red the day it is fixed

Approve provisions AND activates in one action; the roster's `invited` rows are labelled **"invited — never signed in"** (`STATUS_LABELS`) rather than rendered as though they were live, because `is_active` is `status === "active"` exactly and an invited colleague sees the identical dead-end screen as a stranger — that ambiguity was the 2026-08-04 incident. ⚠️ **Two rules for this tab, both about not rendering a lie as calm.** (1) A failed `/members/requests` fetch is NEVER swallowed into `[]` — `queueError` is kept apart from `error` so the roster stays up while a non-dismissible warning says the queue is unavailable, and the empty-state copy ("Nobody is waiting.") is reachable only when the queue actually answered; the fallback-to-empty version rendered a deployment with an unapplied migration 143 as "nobody is locked out", which is the exact silence the tab exists to end. (2) A request whose address is outside the company domain renders an `is_external` marker — the gateway resolves the flag (the domain is server policy; the browser must never re-derive it) because approve provisions `active` immediately and an Entra directory guest would otherwise be indistinguishable from a colleague. (3) **`decide()` has NO early return, and a 200 can still carry news.** The gateway's approve matrix means a decision is refused (409) whenever the address is already a suspended or off-boarded member, or the row was decided by another admin — and a refusal is *about the row that was clicked*, so `load()` runs on every response, not just the successful ones, or the tab keeps rendering a state the server has already corrected. Approving over someone who is already an active member deliberately leaves their roles alone and returns a `detail`; that is rendered as a dismissible `notice` (distinct from `error`, since nothing went wrong), because a 200 that ignored the role picker must not look identical to one that honoured it. (4) **The roster knows who is reading it** (`colleague_onboarding.md` §2 Step 5 / N7): the page reads `access.email` from `useAccess()` and `./selfGuard.ts` — `isSelf` / `rowActions`, the ONE place that decides what a row may offer — renders **This is you** where Suspend and Remove would be. It used to draw Suspend on the viewer's own row like any other, which is the single click that takes an owner out of the surface they would need to undo it. `Remove` (the shipped `DELETE` route, which had no caller in the product at all) goes through `RemoveDialog`, which names the person and says the role grants are dropped — it is not the loud version of Suspend, and the way back is a fresh invite plus an activation. ⚠️ `selfGuard.ts` is presentation only: `_common.assert_not_self_lockout` in the gateway is the boundary, and `removeMember` surfaces its `detail` and re-reads the roster on EVERY response, refusals included. Unit-tested by `selfGuard.test.ts` (vitest); the page's wiring is fenced from `tests/unit/test_admin_member_offboarding.py`. (5) **Delete permanently** (`colleague_onboarding.md` §2 Step 5 / N8) is the hard delete — `DELETE /admin/members/{email}/purge`, gated by `rowActions().canPurge` (never on your own row; *offered* on an already-removed one, since "remove, then delete once you are sure" is the ordinary sequence) and confirmed through `PurgeDialog`, which names **both** halves — what is destroyed and what survives — because a deleted-only list reads as though the whole database goes and the audit trail surviving is the reassurance that makes the rest clickable. ⚠️ **The type-to-confirm rule lives in `./confirmPurge.ts`, never inline.** Written inline it was fenced only by a grep for the surrounding copy, and replacing the comparison with `const confirmed = true;` left every pytest and vitest case green — the last barrier in front of the one irreversible action on the screen, with nothing behind it. `purgeConfirmed` is case-insensitive and whitespace-tolerant (it makes the admin re-read the address, it is not a shift-key test) and an **empty** address confirms nothing rather than everything; unit-tested by `confirmPurge.test.ts`, wiring fenced from `tests/unit/test_admin_member_purge.py`. It is not a boundary and has no server-side twin by design: the gateway cannot tell a typed confirmation from an untyped one, and the authorization is `admin:members:manage`. The response's per-table counts are rendered through `PURGE_LABELS` — an unlabelled key falls back to its own name so a table added on the gateway shows up badly worded rather than invisibly, and `synced_*` vs `local` wording is deliberate: a connected task workspace cascades the SYNCED half of the GTD store away, so "2 synced tasks removed; 3 local tasks kept" has to read as one sentence

## Conventions
- Next.js App Router pattern
- SSE streaming for real-time chat
- AG-UI protocol translation in route.ts
- Microsoft Entra ID SSO (NextAuth v5) restricted to org domain
- Route protection via proxy.ts (auth-gated when Entra ID credentials are set)
- Identity chain: NextAuth session → X-User-Email / X-User-Role headers → gateway UserContext
- Role resolution: DB-backed org roles + per-user overrides, resolved server-side per request by the gateway (spec: project-docs/specs/org_access_control.md). EXECUTIVE_EMAILS remains only as the bootstrap path for a deployment whose access tables have not been migrated yet. Permissions are deliberately NOT put in the NextAuth JWT — a JWT outlives an access change, and access revoked an hour ago must not still work
- All API routes that proxy to gateway forward user identity headers alongside Bearer token
- ⚠️ **A proxy that stamps a fixed `Content-Type` on the way back can only serve JSON routes.**
  `api/projects/[...path]` did, and it relabelled WS-27ae's `GET /projects/export/tasks.csv`
  (`text/csv` + `Content-Disposition`) as `application/json`, turning a download into a
  document. It now forwards the gateway's own content type and its `Content-Disposition` —
  so the **filename is the server's single choice**, read back in the browser rather than
  composed a second time — while a refusal from the same endpoint still arrives as the JSON
  it actually is. Any other `[...path]` proxy that grows a non-JSON route needs the same
  change; the others are JSON-only today and correct as they stand.
  ⚠️ **The content type was only half of it.** Both the Projects and CRM proxies then
  did `await res.text()` and rebuilt the response — and `Response.text()` is a UTF-8
  decode, which **strips the leading BOM** the gateway emits so Excel on Windows does not
  read the file as the system code page. Measured on node v22: upstream `EF BB BF 4E 61
  6D` relayed as `4E 61 6D 65`. Both now read `res.arrayBuffer()` and pass the bytes, and
  both forward `X-Export-Rows` (this proxy is the only route to it). Fence:
  `src/lib/export.test.ts` runs each proxy end to end over a BOM'd body.
  Spec: `project-docs/specs/project_management_app.md` §11.26 and
  `project-docs/specs/crm_app.md` §9 (WS-26i-export)
- Agent-generated files (artefacts) are proxied via /api/agent/workspace/{sessionId}/file?path=
- Image URLs in markdown are rewritten through the workspace file proxy automatically
- Agents SHOULD write generated files to .tmp/ or outputs/ for discoverability
- **Design System**: ALL UI must follow `control_plane/DESIGN_SYSTEM.md`. Use shared
  components from `src/components/` (Tabs, FilterPills, etc.) — never inline ad-hoc
  tab bars, filter pills, or page headers. Use semantic color tokens from
  `globals.css` — never arbitrary hex values.

## Responsive / mobile layout
- AppShell picks the layout from useViewMode(): mobile by default on narrow screens (≤767px), desktop otherwise.
- "Request desktop" (via the "..." overflow menu on mobile, or the "Monitor" icon in the drawer) sets a persisted
  preference and widens the viewport meta to width=1280, so the full desktop layout renders.
- A floating "Mobile view" pill appears in forced-desktop mode to return to the mobile layout.
- **Mobile top bar**: slim (h-11), hamburger (opens unified drawer) + centered "Metorite" title + "…" overflow menu.
  The overflow menu contains Desktop toggle and Sign out — no toolbar-style "Desktop" button cluttering the header.
- **Unified drawer**: useMobileDrawer() context lets child pages inject arbitrary content (conversations list,
  file browser, filters, etc.) into the hamburger drawer. The drawer includes default nav links and user section.
  ⚠️ **The drawer holds a SNAPSHOT.** AppShell keeps injected content in its own state, so a sheet handed over
  once keeps rendering the props it was built with — a page whose sheet reads local state (rather than a store,
  as `ListsSidebar` does) must re-inject whenever that state changes, and must keep every callback inside it a
  `useState` setter or the re-injection loops through the drawer's own context. The other half: **dismissing the
  drawer from the outside has to clear whatever state says which sheet is open**, or the next data change reopens
  the sheet the user just closed. Both rules are written out in `src/app/projects/page.tsx` (WS-27ag).
- **Adding an app to the bottom bar** is two additive edits in `AppShell.tsx`: an `is<App>Page` const beside the
  existing ones, and a `<TaskTab>` block beside the existing tab sets — never an edit inside another app's branch.
  The page listens on the shared `cc-mobile-nav` CustomEvent; the detail strings agree at both ends **by
  convention only — nothing tests them**, so a typo is a dead tab. `/projects` uses `projects-tree`,
  `projects-views`, `projects-search`.
- **Chat page**: conversations and files are accessed via the drawer — no separate sidebar panels or "Chats/Files"
  sub-toolbar on mobile. Pills at the top of the chat area ("Chats" / "Files") open the drawer with the
  appropriate content. Desktop retains its collapsible side-panels.
- **AgentChat header**: compact on mobile — single runtime badge, GitHub link as icon-only, thread ID hidden.
  Toolbar wraps and uses smaller gaps on mobile.

## Identity — the BFF is not optional, it is where identity comes from

Contract: `project-docs/specs/user_management_contract.md` (**eleven** rules
since 2026-08-08). Two rules bind every page in this app — and a third arrives
with WS-29: **R11, never take the acting tenant from input.** The tenant rides
the authenticated session; a subdomain is a *lookup to be verified against the
session*, never an assertion to be trusted. See `saas_multitenancy.md` §1.5.

**Never point the browser at the gateway.** A top-level navigation to
`api.metorite.com` carries **no** Bearer and **no** `X-User-Email`
— session cookies live on the workbench origin and a navigation cannot add
headers. `/email/oauth/{provider}/authorize` was reached that way and answered
"Authentication required" to every user for six days.

So: if a flow needs a real navigation (OAuth consent, a provider redirect, a
download), add a route under `src/app/api/**` that authenticates, calls the
gateway with `gatewayHeaders()` from `src/lib/gateway.ts`, and re-issues the
redirect itself. Read that file's "THE RULE" comment first —
`gatewayHeaders()` needs a person and throws without one; `serviceHeaders()` is
bearer-only and takes a written reason.

⚠️ **A `fetch` through the `[...path]` catch-all cannot replace it** for a
redirecting route: the catch-all *follows* the redirect server-side and returns
the provider's consent page as HTML instead of navigating to it.

**Hiding a control is a courtesy, not a boundary** (`lib/access.ts` says so).
Ship the server-side refusal first; then hide the button. A refusal must surface
in the UI and re-read the list — a control that silently no-ops reads as broken,
and a stale row after a 409 reads as success.
