## What

🔨 **BUILT, dark (2026-11-13, task 3158).** **The store and the routes of a saved view.** Back end only, behind `STUDIO_ORGS`. **Migration:** `441_studio_saved_views.sql` (R1: check the number again at merge). It adds the table `studio_saved_views`, expand only (R6). **Columns:** `organization_id` (the DEFAULT of the bound tenant, FORCE RLS, and the one tenant policy in the guarded block of 438), `id`, `package_id`, `object_name`, `owner_email` (lower case), `name` (1 to 120 characters), `shared`, `spec` (JSONB, at most 8000 bytes), `position`, `created_at` and `updated_at`. `(organization_id, package_id)` is a foreign key to `apps`, with a cascade, so a package delete takes its views. One name is unique for each member, object and package, in any case. **The spec:** `{filter, sort, layout, columns}`, and each key is optional. `filter` and `sort` take the shape check of C2a (`studio_query.check_shape`). `layout` is `table` or `board`. `columns` is a list of at most 50 field keys. A key outside the four is 422. AF-3 adds the key `me`, and AF-4 adds `group` and `q`, each in its own slice. **The store:** `gateway/studio/views_store.py` is the one module that runs SQL on the table. Each statement names the bound org beside RLS. **The routes** (`routes/studio/views.py`): `GET /studio/packages/{id}/views?object=<name>`, `POST /studio/packages/{id}/views` (201), `PATCH /studio/packages/{id}/views/{view_id}` and `DELETE /studio/packages/{id}/views/{view_id}`. The order of each route: the switch (404, no session), the ids (404), the body with a cap of 16 KiB (413), the shape of the body and the spec (422), then one session. **Who reaches the app:** the member is `user.email`. The owner reads the package through `packages_store.get_package`, and each other member reads it through `package_host/viewer.installed_app`. These are the two reads of the door (`invoke._check`). A member with neither gets 404. **The rules (owner to confirm at preview).** (1) A private view reads, changes and deletes for its owner only. The private view of another member is 404. (2) A shared view reads for each member who reaches the app. Only the package owner shares, unshares, changes or deletes one. A viewer gets 403 `read_only`. An unshare makes the view a private view of the package owner. (3) A viewer of an install saves, changes and deletes their own private views. A viewer cannot share (403). (4) The caps: 50 private views of one member and 50 shared views on one object, and 200 of each on one app (409 `view_cap`). A taken name is 409 `view_name_taken`. A new view must name an object that the app holds: an object row, and for a viewer an object of the installed version too (422 `view_invalid`). So a made-up name cannot open a new cap. (5) **The hidden-field rule.** A view holds a query, never data. A viewer reads each view with each condition, the sort and each column dropped that names a key the viewer may not read. The roles of the viewer hide such a key (`objects_store.query_hidden_keys`), or the installed version does not declare it. `dropped` counts the parts, and no dropped value leaves. The read is an allowlist: it returns only the keys that it names, so a new key of a spec needs a rule of its own. The owner reads each view whole. ⚠️ The NAME of a shared view is free text that the owner types, and every viewer reads it. The rule protects the stored query, not prose. AF-10b warns the owner at share time. (6) A view of an object that the installed version lacks reads with each part dropped. A view stays when a later version drops its object, and it reads with each part dropped. **The write right of the app** is the package owner now. After C8b, a member whose role grants `write: all` on the object gets it too. That is not built here. **Audit:** one `app_audit` row for each write through `record_app_audit_in`, in the transaction of the write, kind `action`, with `{op, shared}` only. A failed row rolls the write back, because a share, an unshare and a delete change who reads a view. The op is `view_create`, `view_update`, `view_share`, `view_unshare` or `view_delete`. **The member purge:** the private views of the member go (`studio_private_views`). The shared views stay with the address (`studio_shared_views`, D63). **Chat parity:** AF-10a adds no UI call, so it adds no row. **Open points.** A view stores a flat filter list of C2a. It does not store the flat map of `lib/studio/pageState.ts`, so AF-10b maps one to the other. The clash of a rail name with a view name is a point of AF-2. The delete preview (`packages_store._preview`) does not count saved views. A package delete takes them by the cascade, the private views of viewers too. AF-10b or a slice of the delete preview can add the count. Fences: `test_studio_saved_views.py` and `test_studio_saved_views_r8.py` (R8, in both `--must-run` lists). Verify: `uv run pytest tests/unit/test_studio_saved_views.py tests/unit/test_studio_saved_views_r8.py -q -rs`, with the dev database and 0 skips
