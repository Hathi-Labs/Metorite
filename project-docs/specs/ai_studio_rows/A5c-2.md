## What

🔨 **BUILT (2026-11-11).** **The admin path and the chat tool** (task 1704). The admin path deletes a package whose owner left: the admin holds `admin:members:manage`, and the owner has no active `app_user` row in the org. An admin who targets the package of an active member gets 403 `owner_active`. The chat tool `studio_delete_package` always shows one card with the counts, and it deletes only after the card. **As built.** No migration and no UI. It is not dark. Both halves follow `STUDIO_ORGS` (the first line of each route) and `feature:studio`, and the chat tool rides the `studio` pack of `TOOL_PACKS`. No new flag and no new pack. **The routes** (`routes/studio/packages.py`): `_delete_mode` decides the path in one session, before the body parse. The owner read comes first, so an admin deletes their own package as its owner. Then a caller without `ADMIN_RIGHT` gets 404 with no other read. Then `packages_store.admin_may_delete` reads the package of any owner in the bound org: 404 for none, 403 `owner_active` for an active owner. The route sets `as_admin`, and no body key or query does. **The store** (`packages_store.py`): `delete_preview`, `delete_package` and `record_partial` take a keyword `as_admin` that is False by default. `_ADMIN_GET_SQL` reads the row of any owner, and `_OWNER_ACTIVE_SQL` reads `app_user` by `lower(email)` and `status = 'active'` in the bound org. Each step checks the owner under the `apps` row lock and before the org lock. An active owner raises `OwnerActive` on the preview and on the first step of a call. A later step ends the call with the partial row (reason `owner_active`) and 403 with `records_removed`. The counts, the purge and the `DELETE FROM apps` filter on the owner of the row, so the purge is the purge of A5c-1. Each audit row names the admin as `user_email`, with `by: "admin"`, `admin` and `owner`. **The chat tool** (`acb_skills/studio_tools.py`): it takes `package_id` only. It reads the preview, shows ONE card in every chat (the app, its first 10 tables, the records, the versions and the installs), and waits. Only `approved` deletes. Then it reads the preview again, and a token that differs deletes nothing. It sends the DELETE with that token and follows each 202 with its new token, at most `MAX_DELETE_CALLS` (12) calls. A 409, a 403, a 404 and a 503 end the loop with the records removed so far. The rules of the `studio` pack name the tool. `chat_parity.py` covers the two delete requests of BETA-1, so the debt of AI Studio goes from 3 to 1. **Not in this slice:** a list of the packages of a member who left, so an admin needs the package id. The card names no owner. The library does not read again after a chat delete (`assistantWrites.ts`)
