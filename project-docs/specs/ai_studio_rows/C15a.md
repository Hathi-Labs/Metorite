# C15a

Tier: HIGH

Gate: AGENT-SAFE. A migration at the next free number at build time (R1)

## What

🔨 **BUILT, dark (2026-11-14, task 2345).** It is the store half of C15. No screen draws the number yet (C15b). **The type.** `autonumber` is the 23rd type of `FIELD_TYPES`. The store fills it, and a caller never writes it. Its spec holds `prefix` (0 to 12 characters of `A-Z a-z 0-9 _ . / -`), `pad` (1 to 9, default 4) and `reset` (`never`, the default, or `day`). The type takes no `required`, no `many` and no `hot`. The stored value is the prefix and the number with zeros on the left, as `FV-0042`. A wider number keeps all its digits. **The counter.** Migration 444 (booked for this slice, so check it again at merge, R1) widens the two type CHECKs and adds `studio_object_counters`. Its key is `(organization_id, object_id, field_key, period)`. `period` is the empty text for `never` and `YYYY-MM-DD` for `day`. The table is tenant-scoped with FORCE RLS, and it takes its object by the pair `(organization_id, id)` with a cascade, so a deleted object takes its counters. `last_value` is 1 to 999,999,999,999,999. **The allocation.** `_apply_write` takes the next number for each autonumber field of a create, in step order, before `validate_record`. It runs ONE statement: `INSERT ... ON CONFLICT (...) DO UPDATE SET last_value = last_value + 1 RETURNING last_value`. It never reads then writes. It uses no SEQUENCE, because a sequence needs DDL for each object, `nextval` does not roll back, and RLS does not bind it. Every write of an org already runs under the exclusive org lock (`_lock_org`), and the one `INSERT` into `studio_records` is `_CREATE_RECORD_SQL`. So the number needs no lock of its own, and the key of the counter is the second fence. The apply_writes door, the batch door (B2c), the lines of C13 and the logic modules (B4a) all reach `_apply_write`, so each takes a number. **No gap from a refusal.** The counter is written inside the SAVEPOINT of the batch. A refused or rolled back write rolls the counter back too, so a refusal leaves no gap and no number is used twice. A DELETED record leaves a hole, and its number is never used again. A text sort puts `FV-10000` before `FV-9999` when a number outgrows the pad, so use a larger pad. This replaces the old text of this row, which said a rolled back write can leave a gap. **The day.** For `reset: day`, `_batch_day` reads the day ONCE for each batch, after the org lock, from `_wall_now()` (a function that a test patches), in the zone `default_timezone` of the work-schedule policy of the org (UTC when it has none or the name is bad). It never reads SQL `now()`, which is the start of the transaction. The period is part of the key, so two writers at midnight take two periods and cannot collide. A day token repeats on the next day by design, so no UNIQUE index on the value exists. **The rules for a caller.** A body that names the key is refused with 422 and a `FieldError` that names the field, on a create AND on an update, whatever the value. An update keeps the stored number. A copy is a create, so it gets a new number. A record that exists when the field is added stays blank, because there is no backfill. A manifest sync that changes `prefix`, `pad` or `reset` of a stored field is a `SyncProblem` (`field_changed`), because two records could then show the same number. A change of `prefix`, `pad` or `reset` of a stored field is refused with one sentence: make a new field. A second sync of an unchanged manifest is no change. A field that is dropped and added again continues its count, because the counter is keyed by the field key. PKG-13 refuses the type in a declaration of an extension field (`REFUSED_TYPES`). **The TypeScript twin.** `fieldCheck.ts` (the stored-form check and `autonumberText`), `manifest.ts`, `blocks.ts`, `draftEdit.ts` (label "Auto number") and the golden cases of `studio_field_cases.json`. Three places keep the key out of each write: `formFields` drops the type, `INLINE_TYPES` never held it, and `draftToValue` returns nothing for it. So no form, sheet or table cell sends the key. The Detail shows the value as plain text. **Accepted leak.** When a role shows the key, the number tells a viewer how many records the object holds, beyond the row rule. This is accepted for the first slice, to be confirmed by the owner. A viewer whose grants hide the key does not see the number in its own create answer, because `_run_steps` passes each answer through `view().shown()`. A create that names a hidden autonumber key gets the same refusal as any hidden key. **Not built.** Nothing draws the number as a column, a title or a read-only form row (C15b). No counter for each value of a select field (C15c). No hot autonumber
