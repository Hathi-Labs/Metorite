# C1b

Tier: HIGH

Gate: AGENT-SAFE. After C2a

## What

🔨 **BUILT, dark (2026-11-02).** Store level only: no route, no flag and no UI. B2b calls it later. **Multi-record writes and constraints.** One batch writes several records in one transaction, and a constraint runs on each write. **Migration:** `327_studio_object_constraints.sql` (R1: 325 and 326 are held by open pull requests, so check the number again at merge). Expand only: `studio_objects.constraints` is JSONB, NOT NULL DEFAULT `[]`, and a CHECK holds an array. No new table. **Ships:** `acb_common/studio_rules.py` holds the grammar and `RuleViolation`, with no SQL and no table name. `objects_store.py` gains `apply_writes`, `set_constraints` and the checks. `StudioObject` gains `constraints`. All SQL stays in `objects_store.py`. **Not shipped:** a manifest key (`rules` stays reserved, and C6 lifts it), state machines, formulas, constraints across objects or references, money fields, and a check of old data when a rule is declared. **The grammar.** `set_constraints(db, object_id, rules, *, package_id)` declares the rules of an object, and each call replaces the list. A rule has a `name` (`^[a-z][a-z0-9_]{0,47}$`, unique in the object), a `kind` and an optional `message` of at most 200 characters. An object holds at most 16 rules. Three kinds, and the list is closed. `range` is `{field, min?, max?}` on one number field of one record, and it needs one bound. Non-negative is `min` 0. A record with no value passes. A `range` field may be cold, because the check reads one record in Python. `unique` is `{fields: [<one hot field>]}`. An empty value never clashes. A text of 256 characters or more compares `data` too, because `v_text` holds 256. `group_sum_min` is `{field, group_by: [<1 or 2 hot fields>], min}`. It is the derived balance: the sum of a hot number field over the records with the same group values stays at least `min`. "Stock never below zero" is this kind over a ledger object. A record with no value in a group field joins no group. A key with no rows passes at any `min`, because a group that no longer exists holds nothing to break. So the last row of a group can leave. A key with rows and no amount sums to 0, and the floor judges it. A `unique` field and a group field have the type text, email, select, number, date or datetime. A checkbox has two states, and a money value has a currency, so neither is a key. Each named field must exist. A field of `unique` and of `group_sum_min` must be hot, and `set_constraints` refuses another and does not turn it hot. A field that a rule holds cannot turn cold while the rule stands, because a cold field has no hot rows to check. **A rule that the store cannot read fails closed.** A stored rule of an unknown kind, or a malformed one, does not stop a read. Each write of its object is refused until `set_constraints` replaces the list. Only raw SQL can store such a rule. **A declaration does not check old data.** A rule binds each write after it is declared. A `unique` key that clashes already is refused only when a later write touches that key. **On a floor of 0 or less, a write that does not lower a group never reads the group.** The store adds up the net change of the batch on each key of `group_sum_min`, in exact `Decimal`, from the values that it read under its locks. With a net change of zero or more, it skips the sum. The org lock makes that safe, and a group with no rows starts at a sum of 0, which meets the floor. So a receipt on a broken key passes and a repair is possible, and a write that lowers a broken key is refused. A floor above 0 always reads its group, because a new group starts below it. It holds from the first row: with `min` 1, a new group of 0.5 is refused, and a new group of 1 passes. **The batch.** `apply_writes(db, actor, *, package_id, writes)` answers one `Record` or `True` for each `Write`. A `Write` is a frozen dataclass: `op` (`create`, `update` or `delete`), `object_id`, `record_id` and `data`. A batch holds at most 50 writes, and a longer one is refused before any statement. **The lock order:** the org lock once, then the object rows FOR KEY SHARE in ascending object id, then the record rows FOR NO KEY UPDATE in ascending `(object_id, record_id)`. The store then applies the writes in list order. `set_constraints` takes the org lock, then the object row FOR UPDATE. **The wait.** `_lock_org` bounds each wait for the org lock at 1 s, for every caller, with a LOCAL `lock_timeout` in its own SAVEPOINT. A waiter past 1 s can try again, and the pool matters more. The old `lock_timeout` comes back as soon as the lock is held, so the bound covers the wait only. Past the bound the store raises `StoreBusy` (code `store_busy`): "This app is busy. Try again in a moment." It is retryable, the caller's transaction stays usable, and a route maps it to 503 with `Retry-After`. A deadlock that Postgres settles at this wait (SQLSTATE 40P01) raises the same `StoreBusy`. A deadlock on a later statement stays a database error. The one lock order is the `apps` row FOR UPDATE, then the org lock, and A5c-1 proves it on R8. Each waiter holds a pool connection for the whole wait, so the bound limits the delay of other tenants and does not end it. Measured on one PC, on a pool of 9 connections with one holder of the lock: a read of another org waits 1.1 s behind 12 writers, 3.2 s behind 30, 5.4 s behind 45 and 7.5 s behind 60. Behind 90 writers it fails with the pool `TimeoutError` at 10 s. **The check order:** apply all writes, then `range` on the last value of each written record, then `unique` and `group_sum_min` once for each touched key. So a stock move is judged on the net, and not on each row. A `group_sum_min` key is touched by the old and the new key of an update, by the key of a create and by the key of a delete. A `unique` key is touched by the new key only. A delete or an old key cannot add a clash, so a check there would only stop the repair of old duplicates. **Failure.** The whole batch runs in one SAVEPOINT. Any error rolls back the SAVEPOINT and raises `BatchError(index, cause)`, so the caller's transaction stays usable with its earlier work. A check reads hot rows only, through the query builders of C2a, in `_time_limit` (5 s). The one exception is a key of 256 characters or more. C2a has no hot candidates for it, so the check reads the records of the object, under the same deadline. A timeout refuses the batch with `query_timeout`. `create_record`, `update_record` and `delete_record` are a batch of one, with the same answers, so no single call skips a rule. C7b adds the member to `delete_record`, so a derived parent names who made the change. **The errors:** `ConstraintViolation(RuleViolation)` holds `.rule` and `.object`, and its message names the rule. It never echoes a value. `ConstraintError` refuses a declaration. `RecordNotFound` is a write that names no such object or record in the package. `StoreBusy` is the wait above, and a batch gives it as the `cause` of its `BatchError`. C6 and C7 reuse `RuleViolation` and `touched_keys`. **Concurrency.** Under READ COMMITTED, a check before a write is wrong unless the writers run one at a time. Every store write takes the exclusive org lock first, and each later statement gets a new snapshot. So all three kinds are correct against each other store writer. A database unique index is impossible, because no tenant gets DDL. ⚠️ **Known limit.** The org lock serializes all record writes of one org, and a finer lock is a later slice. A writer that skips the store is out of scope: raw SQL, and the cascade of a package hard delete. A write that lowers a group past about 500,000 rows can reach `query_timeout` (measured on one PC: 200,000 rows 1.5 s, 500,000 rows 4.2 s, 1,000,000 rows refused). The same limit binds each write on a floor above 0, because that floor always reads its group. A running balance table is a later slice.
