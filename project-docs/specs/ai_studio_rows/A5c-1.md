## What

🔨 **BUILT, dark (2026-11-05).** **Delete a package** (task 1532). Owner only. `GET /studio/packages/{id}/delete-preview` and `DELETE /studio/packages/{id}` with a confirm token, behind `STUDIO_ORGS` (the switch first, 404). The delete purges records in chunks of 500 under a 5 s statement timeout, in the one lock order: the `apps` row FOR UPDATE, then the org lock. Then it deletes the `apps` row, and the FK cascade removes the versions, objects, fields, hot rows, installs and contributions. `app_audit` stays, because it has no FK. The store writes the audit row (kind `action`, op `package.delete`) in the same transaction as the delete. No migration. **Not in this slice:** the admin path, the chat tool, any UI, and a cancel of pending MCP requests. **As built (2026-11-05).** `packages_store.delete_preview`, `delete_package` (one step), `confirm_token` and `CountsChanged`. `objects_store.lock_org`, `package_counts` and `purge_records`, under the 5 s deadline of `_time_limit` (a timeout is `StoreBusy`). The routes are in `routes/studio/packages.py`. The body of the DELETE holds at most 4 KiB (413). **The 202 answer carries a new `confirm`**, and the caller sends the DELETE again with it. A token holds no counts, so the server cannot test "not larger than the preview" with no state. A token that is not the token of now is 409 with the new preview. A `store_busy` on a later step answers 202, because the earlier steps hold. `other_member_installs` counts each install that is not archived and is not the private install of the owner. **Fix round 1 (2026-11-05).** A call ends at 8 s. Each purge stops at that end, and a step goes on only while one more step fits. The last step of a call that leaves records writes a partial audit row (op `package.delete.partial`, `records_this_call`) in the transaction of its purge, so each removed record has an audit row. The route logs `studio.packages.delete_partial`. Only one count runs past the budget, so a call ends before the client timeout of `studio_tools._send`. Each later step checks the object names of the confirmed preview, and a name that a publish added between two steps is 409 `counts_changed`. The final row names `records_this_call` and `records_total`. `other_member_installs` reads the one share rule of `package_host/sharing.py`. A preview of a package that a concurrent delete removed is 404. The live check found a purge that ran 21.5 s after a bulk load of 60,000 records, because stale statistics made the planner run the LIMIT once for each record. The purge now reads its chunk by key (`id = ANY(ARRAY(subselect))`), and an R8 fence bounds its buffers. **Fix round 2 (2026-11-05).** No end of a call loses the partial row of its earlier steps: a busy final count of a later step, a busy wait for the `apps` row (the route writes the row in a new session) and a package that another call deleted between two steps (404) each write it. The 409 of a later step names the records that the call removed, and each 409 body holds `records_removed`. A step waits at most 1 s for the `apps` row, so a held row gives 503 `store_busy` in about 1 s, and the step bound and the pin of the worst call count that wait. The catalog read `?app=` of a deleted id answers an empty list, as for each id that names no package. **The lock order, proved:** `test_r8_a_holder_of_the_apps_row_takes_the_org_lock_while_a_delete_waits` plays a publish between its two locks against a waiting delete, and `test_r8_two_deletes_and_a_publish_in_one_org_never_deadlock` races them. The `_lock_org` docstring now states the one order: the `apps` row, then the org lock. The refusal of the org cap of objects names the delete, not an admin.
