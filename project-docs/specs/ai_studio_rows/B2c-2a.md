# B2c-2a

Tier: HIGH

Gate: AGENT-SAFE. `APP_REQUESTS_ORGS` on a box is owner-only

## What

🔨 **BUILT, dark (2026-11-06).** **Delegated writes at the door** (§20.4, task 1336). B2c-2 elsewhere in this spec means the four rows B2c-2a to B2c-2d. A delegated write is a call of an object create, update or delete that is not direct. Mira, a workflow, a skill or an outside agent starts it. **B2c-2a calls the approval store of MCP-P1b-1 and builds no second one.** `DELEGATED_EXECUTORS` holds the three object writes. **Dark.** While `APP_REQUESTS_ORGS` leaves the org out (`app_requests.requests_allowed`), each delegated write gets 403 `approval_required`, as before. The slice adds no flag. **The door delegates only an explicit call (fix round 1).** A call with no proof opens a card only when its query holds the ask marker `ask=1` (`invoke.ASK_MARKER`). It runs a request only when its query names a `request_id`. Each other call that is not direct keeps 403 `approval_required`, also while the org flag is on. So an unsigned Save of the member's own screen never gets a 202. The marker is in no digest and no binding. The tools of B2c-2b send it, and the member's screen never does. **The ask.** A delegated call with `ask=1` reads the body, and checks its keys as B2c-1 does. In the session of the second check, it then calls `gateway.app_requests.open_request`. The source and the app are `studio`, and the subject is the package id. The op is the action id, and the class comes from `OBJECT_OP_CLASSES`. The client stamp is `studio:door`. The server writes the card title from the verb and the object name, and the app name is the package name. The call is `invoke._door_call`: POST, the template `/studio/apps/{app_id}/actions/{action}`, the path, the query `[["uses", USES]]`, the body, and no `if_match`. USES is the `uses` of the action. **The open request (fix round 2).** `app_requests.open_studio_request` takes the lock of `open_request` for the member and the app first. Then it reads ONCE: the newest open request (awaiting, or approved and not spent, and live) of the binding `session:MEMBER:studio:PACKAGE_ID` and the digest of the call. A found request is the answer, so a retry gives it. Else the door opens a new request with a fresh key (`invoke._ask_key`: the digest and a nonce). So an ask after a close opens ONE new request. Two asks at once meet on the lock, and the second one finds the request of the first. The cost is one lock and one read, whatever the history of the change, and no cap applies. The read is a bounded index scan: `pm_agent_runs_app_member` (org, member, `created_at` DESC, WHERE app IS NOT NULL), with the window `created_at > now() - OPEN_WINDOW_SECONDS` (the life of a request and one hour) in the index condition. The replay of `open_request` does not change for its MCP callers. **The answer** is 202 `{state, request_id, expires_at}`, and nothing runs. The audit row has the outcome `asked` and the `request_id`, and it commits with the request. A body with the wrong keys is 422 `bad_input`, and an object that the package does not hold is 404 `object_missing`. Neither opens a card. A call over 32 KiB of JSON is 413 `payload_too_large`. **The resend.** The caller sends the action again with `?request_id=ID`. The door reads no byte of that body. It takes a writer slot of B2c-1 before the session, so a full org gets 503 `store_busy` with `Retry-After: 1`. In ONE `_tenant_session`, `invoke._run_spend` runs five steps in this order. First `read_request` gives the stored call. Then the door computes the digest of `_door_call` with the stored body. Then it calls `acb_auth.app_requests.spend`, runs the stored write with `_do_object_write`, and writes the audit row with `record_app_audit_in`. The spend and the write are in one SAVEPOINT. A write that does not run (a refusal, a missing record, a busy store) rolls the spend back, so the request stays approved. A failed audit rolls back the whole transaction. **What a request spends on.** The query holds the `uses` of the action. So a request spends only on its own package, member and action, and only while the action names the same object and verb. **A refused spend** answers by the reason of `classify_refusal`, each as `{code, message}`: 404 `request_not_found`, 403 `request_declined`, or 409 `request_awaiting`, `request_spent`, `request_expired` or `request_mismatch`. Each refusal names a step that works: send the action again with `ask=1`, or with the `request_id` after the approval. `request_mismatch` never says `ask=1`, because an ask finds the same approved request. It says to change the input, and names the known limit of a value of 1e16 or more. While the org flag holds, `approval_required` for a write of an object says to send the action again with `ask=1`. A dark org, a source that is not an object and a run with the mark keep the plain text. A refused write answers 422 `{code, message, rule, fieldErrors}`, as B2c-1 does. **The workbench.** `realDoor.mapAnswer` reads a 202 as `ok: false` with the sentence "This change waits for an approval, so it is not saved yet." So no block shows a waiting change as saved. **No person present (AUTO-7a).** A call with the mark of `acb_common.no_person` and with `ask=1` or a `request_id` gets 403 `no_person_present` after the first check, before the body read. It opens no card and spends no request. A call with the mark and with neither gets 403 `approval_required` at the first check, as each call with no marker does. Neither text says to send `ask=1`. The mark is a ContextVar, so it holds for an in-process caller only. An HTTP call does not carry it. **A direct call** keeps B2c-1 with no card, and the door does not read its `request_id`. **Not in this slice:** the chat tools of Mira and their resend (B2c-2b), the card in the chat (B2c-2c), a workflow node (B2c-2d), the door op, an integration, and the run of a published workflow. That run stays 403 `approval_required`, and no row owns it yet. **Known limits.** A body with a key that holds `token`, `secret`, `password`, `credential` or `api_key` always gets 422 `secret_in_payload` on the delegated path (`_holds_secret_key` of the store). The direct path writes it. JSONB gives back a float of 1e16 or more as an integer, so the digest of the stored call differs, and the resend gets 409 `request_mismatch`.
