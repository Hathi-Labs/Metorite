# D24b

Tier: HIGH

Gate: AGENT-SAFE. After D24a and PR 2360. D145 preview. Not built

## What

**The capture upload on the file store of D13b** (task 3344). Wave 1 (D202). After D24a and after PR 2360 (D13b, task 1421). **D13b already owns the table.** `studio_record_files` (migration 442), `studio/files_store.py` (`put_file`, `read_file`), `studio/reach.py` and the serve route `GET .../records/{rid}/files/{fid}` come from D13b, and D24b adds none of them. The table is tenant-keyed with FORCE ROW LEVEL SECURITY, as the owner decided on 2026-11-14. D13b guards the org by a composite foreign key to `studio_records` and a policy with a check, not by a trigger. The owner said a trigger. The two give the same guard, and the row records the foreign key as the equal choice. **What D24b adds.** (1) The capture upload route `POST /studio/packages/{pid}/objects/{name}/records/{rid}/files?field=<key>` in `routes/studio/files.py`. Its order is: the flag `STUDIO_CAPTURE_ORGS` (default off), `studio_allowed`, `reach.py` as the owner (a viewer gets 403 `read_only`), the object, then `update_record(..., viewer=_row_viewer(member))`, which keeps the row rules and the hidden-key refusal. The route reads at most `MAX_CAPTURE_UPLOAD_BYTES`, runs `encode_capture` (D24a), and calls `put_file`. The type comes from the encoder output and never from the client. The name uses `_safe_name` with the extension of the output. The route sets the field to `{"id"}` in the same session. (2) A check in `objects_store._apply_write`, after `validate_record`. Each changed `file` value must name a row of `studio_record_files` of the same package, object, record and field, and RLS gives the org. A create with a non-null `file` value is refused with a sentence. `_file` in `studio_fields.py` stays pure. Today it checks only the id shape (line ~762), and no Studio code reads `attachments`. (3) The serve of D13b serves png and jpeg inline by the `_INLINE_MIMES` set of `routes/projects/attachments.py`. An SVG never stores, because the sniff of D24a refuses it. A replace deletes the old row of the same record and field. Purge follows the cascades of D13b. **The gate.** A member who can read the record gets the bytes. That member is the owner, or a J2a viewer through `installed_app`. A C8 row rule hides the file when it hides the record, and a field with `hide` hides the file too. **No migration** unless the owner wants the trigger. **Chat parity:** the upload is a byte route, so it has no `studio_*` tool. **Rows that say "After D24"** wait for D24b, and B13 waits for D24c and D24d too. **Non-goals:** the capture UI (lane-ui), offline capture (D26), the gallery (D19), a video (D24d), and a signature (D24c)
