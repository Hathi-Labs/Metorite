# C2c

Tier: HIGH

Gate: AGENT-SAFE for the build. The flag flip is `enforcement-flip`

## What

🔨 **BUILT, dark (2026-11-13, task 1349).** Flag `STUDIO_NUM_F8_ORGS`, default empty. **A number filter that the app role serves by index.** No `numeric` comparison is LEAKPROOF in Postgres 16, so under FORCE RLS the app role cannot use `studio_record_hot_num_idx`. A cast of `v_num` to float8 in an index does not help, because `float8(numeric)` is not leakproof either. The comparisons of `float8` are leakproof, so the store keeps a copy of the value in a plain float8 column and tests that column. **Built:** migration `433_studio_hot_num_f8.sql` (R1: found by content, checked again at merge) adds `v_num_f8 double precision` (expand only), a trigger that fills it, and the index `studio_record_hot_num_f8_idx` (CONCURRENTLY, no BEGIN, drops an invalid leftover first). `scripts/backfill_studio_num_f8.py` fills the old rows in small batches through the tenant seam, and reports the rows that remain. In `objects_store`, `_q_frag` adds the float8 test IN ADDITION to the exact test for `eq`, `in`, `lt`, `lte`, `gt` and `gte`. The float8 test uses the non-strict operator (`<=` for `lt`, `>=` for `gt`), and its bound is the same numeric cast to float8 with no column in it. A row with a NULL copy (a row from before the migration) would drop out of a float8 test. So the store honours the flag for an org only when the org has no row with a `v_num` and a NULL copy. `_warm_f8` asks once and keeps the answer for 10 minutes (30 seconds when not ready), through the small partial index `studio_record_hot_num_f8_todo_idx`. Until then the SQL is the SQL of C2a. A test `OR v_num_f8 IS NULL` made the planner skip the index, because the hot table holds a NULL copy for every row of another type. A value above 1e300 takes the float8 infinity of its sign, and a value with an absolute size below 1e-300 takes 0.0. Both maps are non-decreasing, so no row is lost. They guard direct SQL only, because the API caps the size below 1e15. Any other value casts without error. The exact test stays as the filter, so the records do not change. `ne`, `is_empty`, the sort, the group key and the sum read `v_num` as before. The filter of an aggregate goes through `_q_filtered`, so it gets the float8 test too. With the flag off, the SQL is the SQL of C2a. **Rollout:** (1) the deploy applies the migration. (2) Run the backfill until it reports `remaining=0`. The flag has no effect for an org until the backfill ends, and the records are right at every step. (3) The owner or the orchestrator turns the org flag on (`enforcement-flip`, a reload applies it). The guard runs inside the one deadline of 5 seconds of the call, takes at most 1 second of it, and fails closed to the exact SQL for 30 seconds. **Runbook:** after a restore or any trigger work (`DISABLE TRIGGER`, `session_replication_role = replica`, `pg_restore --disable-triggers`), restart the gateway before you trust the flag, because a ready answer is cached for up to 600 seconds.

On 50,000 records and the app role, `lte 500` with the flag on uses `studio_record_hot_num_f8_idx` and reads at most 1,000 hot rows (450 rows match, and the page and its total each read them).
