## What

Skill tests on a dry-run door

**Status: F4a built 2026-11-18. F4b built 2026-11-19, the server half: the run, the caps, the route and the flag. F4b is dark, and the UI is open.**

F4b is HIGH, because it spends credits and changes the agent loop. `STUDIO_SKILL_TESTS_ORGS` is empty. `STUDIO_SKILL_TESTS_CAP_CREDITS` has no value, so the runner refuses each run.

### The shape

A saved skill holds tests in the version body, as `body.tests`, at most 20:

```json
{"id": "t1", "input": "Add a task: Call Ravi",
 "expect": [{"action": "tool:create_task", "fields": {"title": "Call Ravi"}}]}
```

- `id` is a unique non-empty string of at most 64 characters. `input` is a non-empty string of at most 2000 characters.
- A test holds at most 5 `expect` entries. `expect: []` means that the turn writes nothing.
- Each `expect` entry names ONE catalog action: `tool:<name>`, `object:<name>.<verb>` or `workflow:<id>`. An object action names a write verb: `create`, `update` or `delete`.
- A generic tool takes a pin. `{"action": "tool:studio_record_create", "object": "lead"}` reads as `object:lead.create`. `{"action": "tool:run_workflow", "workflow": "<id>"}` reads as `workflow:<id>`. A record tool or `run_workflow` with no pin is `bad_test`.
- `package` pins the `package_id` of an object action. A pin on another action is `bad_test`.
- `fields` is an object of text, number, true, false or null, with at most 20 keys. A key may name one level down, such as `data.company`. A deeper key and a nested value are refused. `fields` may be absent.
- `fields` is a subset match. Each named key must equal the argument after a trim of a string. The match has no case folding, and a type that differs is no match. A key that `fields` leaves out is ignored.
- A test list of the wrong shape is reason `bad_test`. `skills_store.check_body` refuses it, in the store's own error style, after the hidden-character walk. The message names a path and never a value.

### The pass rule

The end state decides, never the words. `skill_tests.evaluate(test, calls, *, skill_actions)` reads only the calls that the dry-run door recorded. It has no text parameter. A test passes only when all three hold:

1. Each call is an action of the skill. A display tool (`DISPLAY_TOOLS`) is the one exception. A generic tool must name an object or a workflow that the skill holds. A call to `load_skill_tools` is an `other_action`, because the harness loads the forced skill. A read outside the skill's actions fails (owner decision). The reason is `other_action`.
2. Each held write passes the schema of its tool. The reason is `invalid_call`, and the detail names the bad keys.
3. The held writes match `expect` one to one, by action, pins and `fields`. The reasons are `missing_write`, `extra_write` and `field_mismatch`. A detail names the key, the tool or an action of the test, and never a value.

A held read is no write. A write is a call whose tool object has no read-only annotation, or a call from an MCP server. `egress._risk_of` is the one reader, and it fails closed.

`run_suite` adds three terms before the rule: no cap stopped the run, the door was armed (`hold_unarmed`), and the forced skill loaded (`skill_unloaded`).

### Reason codes

`passed`, `other_action`, `missing_write`, `extra_write`, `field_mismatch`, `invalid_call`, `cap_reached`, `cap_unset`, `call_cap`, `cost_read_failed`, `hold_unarmed`, `skill_unloaded`, `run_failed`, `bad_test`, `not_run`. `skill_tests.REASONS` holds the set, and TOF-3a uses the same one.

### Owner decisions

- A read outside the skill's actions fails the test. A display tool is excepted.
- Equality is exact after a trim. No case folding.
- The server carries `tests` forward. The route of a new version calls `skills_store.carry_tests`. A body with no `tests` key gets the `tests` of the newest version. The undo copies exactly and carries nothing. `"tests": []` clears them. A list replaces them. The editor form sends no `tests`, and the chat save and the undo copy the body whole.
- A change of `tests` alone returns a published skill to `draft`, as any new version does.
- The credit cap is a setting with NO default value (2026-11-18). With no value, the runner refuses every paid run with `cap_unset`. The owner sets the value later.
- The flag `STUDIO_SKILL_TESTS_ORGS` defaults empty. A flip spends credits, so only the owner flips it.

### F4b built

- **The frozen allowlist.** `skill_dry_run.REAL_READS` replaces `runs_for_real`. A tool runs for real only when four things hold. The door is armed and under its call cap. The tool is an action of the forced skill. `attach` captured the tool object from the run's own tool list. The identity of the object is on the list. The identity is `module.qualname` of the owner's function, never the bare name. An MCP tool never runs.
- **The list holds five GET reads of a first-party store:** `list_tasks`, `task_detail` and `my_work` of `skill_projects.reads`, and `read_page` and `list_spaces` of `acb_skills.knowledge_tools`. Each one speaks only GET to the gateway. A Projects read runs through its pack wrapper. That wrapper can write the sticky pack state and the focus item of the test thread. It writes no business data.
- **The list holds no other tool.** The display, member, extra-call, delegation and loader tools stay held. So do `analyze_image`, `search_company`, `crm_search_notes`, `remember`, `recall_*`, `query_history`, `get_errors` and `run_diagnostics`. `studio_record_list` stays held, because it reads through a POST to the action door. The `crm_*` reads and `org_facts` stay held, because no catalog action maps to them.
- **The fence of the list:** `tests/unit/test_skill_dry_run.py::REASONS` names a reason for each entry, and the test fails for an entry with no reason. Each held class has its own test.
- **The schema check.** `check_args` runs the input model of the tool, then the top-level checks of its JSON schema, as MAF does before a call. The record keeps `valid` and the bad key names. A tool with no schema fails closed.
- **The outermost hold.** `_tool_injection._apply_dry_run` calls `skill_dry_run.attach` beside `_apply_chat_hold`. `attach` puts `HoldAndRecord` and `CapGuard` at index 0 of the `middleware` list of a per-run view of each agent. MAF runs that list before each provider middleware and before `McpPermissionGate`. `attach` arms the record last. A Copilot agent, a plain object, or a chat client with its own middleware raises `DryRunRefused`, so the run fails closed.
- **The cap guard.** `CapGuard` is a chat middleware. Before each model call it reads the meter, and it raises `DryRunStopped` before `call_next`. The codes are `hold_unarmed`, `call_cap` (8 model calls a test), `cap_unset`, `cost_read_failed` (a fault, a read over 10 seconds, or no number) and `cap_reached`. A stop is sticky, so a retry starts no call. The meter lags one call under streaming, so the call cap is the cap that always holds.
- **Why no request hook.** The hook beside `acb_llm.attribution._stamp` was not used. The OpenAI client (openai 2.54.0, `_base_client.py`) catches each exception of a send, retries it, and raises `APIConnectionError`. So it does not let a refusal through unchanged.
- **The run ceiling.** `run_suite` binds `run_ceiling_scope` with the credits that the cap has left. The Router can then stop a test run too. `tests/unit/test_run_ceiling_header.py` names `run_suite` as the second binder.
- **The hooks.** `_turn_with_skills` returns the turn with the forced pack only, before the words check, and reads no store. `_apply_tool_packs` notes whether the forced pack loaded. With no dry run on the frame, each hook returns at once, and the run is as before.
- **The run.** `skill_tests.run_suite` gives each test a new run id and the thread `skilltest:<uuid>`. It runs the test as the member (`job_member_scope`), with no person present, under the run ceiling, and inside `dry_run_scope`. The runner and the meter are injected. `agent_runner` drains `run_agent_stream` of the orchestrator, and the route passes `headless_turn.console_meter`. At most 5 tests run in 300 seconds. The rest are `not_run`. A suite stops at `cap_reached`, `cost_read_failed`, `hold_unarmed` and `skill_unloaded`.
- **The runner runs in its own task.** The stream run clears the run context as it ends. On its own task, that clear stays inside the turn. So the meter read after the run still reads as the proven member, as `console_meter` needs.
- **The cap.** `STUDIO_SKILL_TESTS_CAP_CREDITS` has no default value. `flags.skill_tests_cap` is its one reader. Empty, text that is no number, `NaN`, `Infinity` and a value of 0 or less read as unset. A request cap can only lower it. The cap is no `*_ORGS` key, so a change needs a restart.
- **The route.** `POST /studio/skills/{id}/tests/run` takes `{version?, body?, inputs?, cap?}`. `inputs` holds at most 1 input, and `cap` is a decimal string. The order is fixed. First come `STUDIO_ORGS` and `STUDIO_SKILL_TESTS_ORGS`, with 404 before any other work. Then come the request checks and the body checks of an unsaved body. Then the owner check (404), and last the cap (409 `cap_unset`). The org and the member come from the session only.
- **The answer holds codes and names only.** `TestResult.writes` and `TestResult.calls` hold action names. A generic tool shows its catalog action only when the skill holds it. The recorded arguments stay in memory for `evaluate`.
- **The lock.** `carry_tests` takes the row lock first (`get_skill(..., for_update=True)`), as the undo route does. So a second save waits, and no save carries a list that another save replaced.
- **Fences:** `tests/unit/test_skill_dry_run.py`, `tests/unit/test_skill_tests.py`, `tests/unit/test_studio_skill_tests_route.py`, `tests/unit/test_studio_skill_tests_r8.py` (R8) and `evals/trajectories/test_skill_dry_run_trajectory.py`.

### What the cap does not cover

- The tier ask of the executor (`_ask_run_tier`) can make one model call before the agent runs. `CapGuard` does not see it. The check before each test and the meter read after it bound it.
- The runner needs the tool packs of the org. An org with no pack gives `skill_unloaded`, and the runner never routes around the pack gate.
- The cap holds for one run. Two runs at once each get the whole cap, because no slot holds one run for each member.
- The Console door `POST /registry/usage/run` needs `billing_read` on the deployment key, as the headless turn does. Without it, each run ends with `cost_read_failed`.
- The spend of a test run bills as the app `chat` and the agent `orchestrator`. The config of the agent replaces the app `studio`, and only the headless turn may bind the attribution scope.

### F4b leaves open

- The UI of a test run.
- An `object:` pin. The catalog check refuses an `object:` action in a saved skill (`catalog_rows` holds no package row). So only `tool:` and `workflow:` pins can match a saved skill today.
- The thread `skilltest:<uuid>`. The executor can index the live run and save a native session for it. Nothing tells the member that the thread is a test.
- A record of a failed run for TOF-3a (`studio_skill_runs`, a migration).

### The interface of TOF-3a

```
run_suite(*, org, member, skill_id, version=None, body=None, tests=None,
          inputs=(), cap=None, runner, meter) -> SuiteResult
```

`SuiteResult` holds `skill_id, version, content_hash, results, passed, credits, cap, stopped`. Each `TestResult` holds `test_id, passed, reason, detail, writes, calls, credits, model_calls, run_id`. `writes` and `calls` hold action names, never an argument.

`tests` replaces the tests of the body, so TOF-3a can pass the tests of an earlier version and a repair cannot weaken them. Each entry of `inputs` adds an input-only run: a `SkillTest` with `expect=None`. Only the action rule and the schema rule count for it. `expect: []` still means "writes nothing".

## Done when

A test fails when the turn calls another action. No write leaves the dry-run door. A test run stops at its credit cap
