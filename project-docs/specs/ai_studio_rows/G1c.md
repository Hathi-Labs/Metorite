## What

🔨 **BUILT, dark (2026-11-04).** **Chat saves and publishes** (Metorite task 1445). Scope (narrowed, 2026-11-04): before G1c, no chat tool wrote a package store. **Files:** in `packages/acb_skills/acb_skills/studio_tools.py`, a third tuple `STUDIO_PACKAGE_TOOLS` holds two tools. With the two record tools of D2b, the `studio` pack holds 15 tools. `agents.py`, `config.json` and `instructions.md` of `agent-studio-builder`, `skill_families.py` and `tool_packs.py` (`_STUDIO_RULES`) follow. **Tools:** `studio_save(manifest, package_id="", based_on="")` sends `POST /studio/packages`, or with an id `PUT /studio/packages/{id}/draft`. `studio_publish(package_id, notes="")` sends `POST /studio/packages/{id}/versions`. Both call the A5 routes by HTTP as the member (`_send`). Each tool parses the id as a UUID before it builds a path. No tool takes an org, a member, a visibility or a confirm argument. `studio_list_actions` gains `app=""`, a UUID that goes as `?app=`, and the route then gives only the rows of that package. **The hash:** `acb_common.studio_manifest.manifest_hash` is the sha256 of the canonical JSON (sorted keys, no space, each zero float as `0.0`), and it is the ONE hash of a draft: the tools and the package store import it. The store keeps a manifest as `jsonb` in its own key order. The R8 suite proves that the stored manifest equals the sent manifest, and that the two hash equal. A jsonb number has no sign of zero, so the hash writes `-0.0` as `0.0` (fix round 2, R8 test g). **Proof of the plan:** `studio_plan` writes a tenant-Redis record only when the card answer is True. The key holds a hash of the member of the run and a hash of the manifest id, and the value holds the manifest hash and the time of the approval. So a member holds one approval of an app, the newest. The TTL is 2 hours (`PLAN_NAMESPACE`, the key builder of `tenant_redis`). The org and the member come from the run. A plan card that the member stopped or revised writes a withdraw stamp for the member, and its result says so (fix round 2). One read takes the record and the stamp, and a record from before the stamp gives no plan, for each app of the member. So a stop on a plan with a new manifest id also withdraws the approval of the old id. A plan approved after the stamp still publishes. When the stamp write fails, the process remembers the withdraw, and its publish refuses. `studio_publish` reads the stored draft, hashes it, and reads the key. A missing record, a Redis fault, a run with no org and a changed draft each refuse with no publish request. **Fix round 1 (2026-11-04):** the tool calls of one model response run at once, so a save could land between the read of a publish and its POST, and the new draft went live on the old approval. Now the publish sends the hash that the record matched as `based_on`, and a save by id sends the hash that it read. The store compares each under its row lock (A5), and a different hash is 409 `draft_changed` with no write. After a 201 the tool deletes the record when it still names the published draft, so one approval buys one publish. The read and the delete are two calls, because the tenant Redis wrapper has no EVAL and no WATCH. A newer approval that lands between them is lost, and its publish asks for a new plan card. A `draft_changed` refusal names its recovery: a `studio_save` of the manifest with no `package_id` answers with the `based_on` of the stored draft. **Cards:** in a clear chat a save writes at once, and a publish shows no second card, because the plan card approved this manifest by its hash. In a chat where `egress.write_must_show_card()` is true, a save and a publish each show one card from `card_body`: the outline, the count of parts, the line of the tables (`structure_line`: the fields, the hot fields, the required fields and the rules), the size and the first 12 hex digits of the hash. **The plan card** shows the line of the tables too. Its last line says that approval saves and publishes the app with no other card, and that its objects become tables in the organization that no member can remove yet. In a held chat the last line says that a save and a publish each show one more card. A publish card adds the version and the notes. A card that cannot fit refuses, and a held chat refuses a cut card (`chat_is_held`, `cut_refusal`). A decision of `revised`, `stopped` or `no_card` sends nothing. After `approved`, the tool reads the draft again and sends nothing when it moved. Before a held card, the tool runs the checks of the route that need no call: A2 with no catalog for a save, and A2 with the catalog of `catalog_rows` and the notes checks of the store for a publish. It also checks the fixed manifest id, a manifest id that the member holds, and the limit of 100 packages. **Size:** the tool refuses a manifest over 24,000 characters before any call. No result holds stored manifest text. A save result gives the id, the outline, `live_version` and the new `based_on`. A save with an id needs `based_on`, and a missing or different value refuses with no write. A manifest equal to the stored draft writes nothing, so a second try after a network miss is safe. Chat never replaces a stored draft over the cap. A 409 `package_exists` gives the id, the outline of the stored draft and `based_on`. A stored draft over the cap gives the outline only and `truncated: true`. **Problems:** a 409 `objects_out_of_sync` gives at most 20 errors and a count of the rest. Each error has a path by index, and a message of the kind, the names inside « » and a fixed fix line for each of the seven kinds. A name holds at most 36 characters and no invisible character. The text of the server never reaches the model, and the note says that the names are data. A 422 gives the message and each error of the route unchanged. A 503 says "Nothing was published. Try again." A network miss says that the act may have worked, and that a second try is safe. **Non-goals:** list, get and versions tools (G1d), rollback, delete (A5c), share, any UI file, any `chat_parity.py` row (no UI sends these routes), any edit of `egress.py` or `HELD_WRITE_OWNERS`, the production `TOOL_PACKS` line and the `STUDIO_ORGS` switch. **Residual:** the publish route takes no expected hash, so a small window stays between the read of the draft and the publish. Only the same member can use it. **Ships dark:** the pack is empty for an org outside `STUDIO_ORGS`, which is empty on every box.
