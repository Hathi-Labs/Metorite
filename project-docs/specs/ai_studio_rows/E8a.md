## What

🔨 **BUILT, dark (2026-11-13, task 3095).** **The batch ledger, store level.** Parent: E8 (task 1422). **Audit (Opus, 2026-11-13):** E8 does not need E2 (loops). The node of E8b loops INSIDE one executor, so the graph stays a DAG. **Scope.** Two tables and one store. Migration 438 adds `studio_batches` (one frozen list of one package) and `studio_batch_items` (one item of that list). Both are tenant-scoped with FORCE RLS, and the generated tenant set names both. `gateway/studio/batch_store.py` is the one writer. `open_batch` freezes a list of at most 1,000 items (a literal). It refuses a duplicate key, an op other than create or update (no delete, also in a line), and an item of more than 50 writes. It stores the digest of each item and the digest of the list. `run_chunk` locks the batch row `FOR UPDATE`, takes whole pending items in place order while their writes fit in 50 (an item with `n` lines counts `1 + n`), and runs them as ONE `apply_writes` call. It sets each item `done` with its record id in the SAME transaction as the writes. The store never commits, so one call is one transaction of the caller, and the org lock is free between chunks. **A refusal fails ONE item.** On a refusal the store splits the chunk in halves until ONE item is refused, and only that item is marked `failed`, with a short code (never a message). So a refusal that the whole chunk causes, such as the roll-up caps of one call, fails no item that writes fine alone. Of two items with one unique key, the later fails at any chunk edge. `StoreBusy`, and a timeout of a single item, are retry signals and mark nothing. A cause that is not a `ValueError` is raised. `open_batch` also checks the line `parent` places of each item. **Where the list lives.** The store keeps a DIGEST of each item and NOT its writes. A copy of pay data outside the object store would skip the rules of C9 for a restricted field. So the caller passes the writes again to each chunk, and the store checks each against its digest BEFORE it writes. A difference raises `DigestMismatch` and writes nothing (fail closed). The item key is an id or a row number, never pay data. **Non-goals.** No route, no workflow node, no UI, no flag, no resume and no card. A driver opens one session for each chunk and never holds two.

## Done when

A crash in chunk 3 at item 120 of 300 leaves 100 records and 200 pending, and a second drive ends with exactly 300 records, one for each key. Two drivers write no item twice. A range refusal fails one item and the other 49 of the chunk are written. An item with lines counts `1 + n`. Org B reads and drives no batch of org A. A duplicate key and a delete are refused. A digest mismatch writes nothing
