## What

🔨 **I9a BUILT, dark (2026-11-14, task 3169).** I9b is open. **Built in I9a:** the declaration, the met-check and the approval gate. It reads no credential, and it adds no migration, table, route, UI or flag. **The manifest:** an item of `connections` is a name, or `{name, as, scopes}`. A plain name stays valid, and its hash does not change. `as` is `org` or `member`. With no `as`, `studio_manifest.connection_as` reads the `scope` of the row in the connector list (IN-11). Mail, WhatsApp, both calendars and Google Drive give `member`. Every other name, and an unknown name, gives `org`. `scopes` is a list of at most 16 words with no space, once each. Each refusal has a path and one sentence. The schema change is additive, so `CURRENT_VERSION` stays `1`. **The read:** `connections/store.met_providers` now returns `(org_met, member_met)`. The first set holds the `connected` org rows. The second holds the `connected` rows of the viewer only. **The rule:** `resolve.first_unmet_connection` is the one rule. A `member` need is met only by a row of the viewer, and never by an org row. An `org` need is met only by a `connected` org row AND an `approved` version of an ORG install (`resolve.org_install_approved`, J2b-1). A new version needs a new approval, so a widened scope asks again with no new code. **The door:** the 409 `needs_connection` now carries `provider` and `as` for the first unmet need. It carries no text about another member. The sidebar `needs_setup` follows the same rule. The flag is `STUDIO_CONNECTION_GATE_ORGS` from I1a, and a second flag does not exist. With the org off the list, nothing changes. ⚠️ **Known limit until I9b:** an `org` need fails closed in a private install, a group install, a draft run and a preview. The OWNER of an app always runs the draft, even when the org installed it. So the owner gets 409 `needs_connection` for an `org` need, and the sidebar shows `needs_setup` for the owner too (`resolve.owns`). The owner cannot use the org install as a viewer, because the door reads the owner's draft first. Another member of the org runs the approved install and sees it ready. The owner cannot test an `org` app until I9b. A `member` need works in all of them. ⚠️ **The `as` default is read at each read.** `connection_as` reads `connector_list.json` each time. It is not frozen at publish. A later edit of the `scope` of a connector silently changes whose account an existing plain-name app uses. A move from `member` to `org` still needs an approval. Track this in IN-11 or I9b. **Non-goals of I9a:** any use of a credential, IN-3, the J6 screen, the I8 connect step, the mailbox met-check, a match against the scopes of the connection row, an approval record for each install, and any flag flip. **I9b (open, needs a migration that nobody booked):** a record of the approved org account and its scopes. Book the number with `~/lanes/reserve_migration.sh` first. **Three open questions for I9b:** (1) Who is an admin who approves: the right `studio:publish`, as J2b-1 uses, or `admin:members:manage`? (2) What does an `org` need do in a private install, a group install and a draft? (3) What is the scope vocabulary of each provider, and do fewer scopes on the row count as met? Tests: `test_studio_manifest.py`, `test_studio_manifest_ts_parity.py`, `test_package_host_resolve.py` (the truth table) and `test_studio_connections_whose_r8.py`. **The scope of the whole row:** Whose account (task 3169). Rung 7 (D220.2). A connection need takes `as` (`org` or `member`) and `scopes`. With `member`, each viewer uses their own connection, and a viewer with none reads nothing. With `org`, the install screen (J6) names the account, and an admin approves it. Mail and calendar default to `member`. A version that widens the scopes asks again (§8.1 rules 3 and 4)
