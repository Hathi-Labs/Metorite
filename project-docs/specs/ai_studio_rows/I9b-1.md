## What

🔨 **BUILT, dark (2026-11-15, task 3169).** **The scope check of a connection need, its reasons and its texts.** No table, no migration, no new route, no new flag. **The read:** `connections/store.met_providers` now returns, for the org rows and for the member rows, a map from a provider to the granted scope set of EACH `connected` row (the `scopes` column of `integration_connections`, migration 245). It never reads the credentials blob. The rows are never merged. A need with scopes is met only when ONE row holds every scope, so no union of two accounts counts. `_MET_SQL` still keeps `member_email = :member` for the member rows. 

**The rule:** `resolve.need_reason` is the one rule of one need, and `resolve.first_unmet_need` gives `(provider, as, reason)` for the first unmet need. `first_unmet_connection` keeps its `(provider, as)` shape. The need scopes come from `studio_manifest.connection_scopes`. A subset test, with exact and case-sensitive strings, decides. A need with no scopes is met by any connected row. A need WITH scopes is never met by a row with empty scopes. The reasons: `missing` (no connected row of the right account), `reconnect` (a row exists, and no single row holds every scope), `org_approval` (an `org` need whose org row is fine, but the install is no approved ORG install: private, group, draft, preview, or a version with `auto` or `pending` review). 

**The door:** the 409 `needs_connection` keeps `provider` and `as`, and adds `reason` and a sentence for the reason. `missing` keeps the sentence of I1a. `reconnect`: \"Reconnect <provider>: your connection does not grant what this app needs.\" `org_approval`: \"An admin must approve this app before it can use the org account.\" The detail names no other member and no scope. The sidebar `needs_setup` follows the same rule. 

**The I8a Connect step:** each row gains `reason` (`ok`, `missing`, `reconnect`, `org_approval`). `met` is true only when the door would meet the need for the DRAFT of the owner, so an `org` need reads `org_approval` even with an org row. This closes the known limit of I9a. The IDE draws the three sentences (`lib/studio/connect.ts`). 

**Non-goals:** a table, a migration, an account pin, a new route, a change of the connect flow, and any read of a credential. **Demo (rung 7):** an app that needs a mail scope that the member did not grant says Reconnect, and an org need of a draft says that an admin must approve. 

**Known limits:** each owning app asks FIXED scopes in its connect flow, so a Reconnect cannot widen a grant until the lanes that own those flows change them. `can_connect` stays as it was. The GitHub App row writes empty scopes, so a need with scopes on it stays unmet. Zoho records the requested set, not the granted one. 

**Tests:** `test_package_host_resolve.py` (the truth table), `test_studio_action_door.py`, `test_studio_connect_in_place.py`, `test_studio_connections_whose_r8.py` and `test_studio_scope_match_r8.py` (R8).
