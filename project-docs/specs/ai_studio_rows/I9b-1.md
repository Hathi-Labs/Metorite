# I9b-1

Tier: HIGH

Gate: AGENT-SAFE. Dark behind `STUDIO_CONNECTION_GATE_ORGS`

## What

🔨 **BUILT, dark (2026-11-15, task 3169).** **The scope check of a connection need, its reasons and its texts.** No table, no migration, no new route, no new flag. **The read:** `connections/store.met_providers` now returns, for the org rows and for the member rows, a map from a provider to the granted scope set of EACH `connected` row (the `scopes` column of `integration_connections`, migration 245). It never reads the credentials blob. The rows are never merged. A need with scopes is met only when ONE row holds every scope, so no union of two accounts counts. `_MET_SQL` still keeps `member_email = :member` for the member rows. 

**The rule:** `resolve.need_reason` is the one rule of one need, and `resolve.first_unmet_need` gives `(provider, as, reason)` for the first unmet need. `first_unmet_connection` keeps its `(provider, as)` shape. The need scopes come from `studio_manifest.connection_scopes`. A subset test, with exact and case-sensitive strings, decides. A need with no scopes is met by any connected row. A need WITH scopes is never met by a row with empty scopes. The reasons: `missing` (no connected row of the right account), `reconnect` (a row exists, and no single row holds every scope), `org_approval` (an `org` need of an install that is no approved ORG install: private, group, draft, preview, or a version with `auto` or `pending` review). **Order of checks:** the approval test runs FIRST. An unapproved `org` need always says `org_approval`, whatever the org rows hold (none, fewer scopes, equal, more). So a non-admin cannot probe the scopes of an org account, and the answer matches decision 2. The scope test and `missing` apply only to an `org` need of an APPROVED install, and to each `member` need. 

**The door:** the 409 `needs_connection` keeps `provider` and `as`, and adds `reason` and a sentence for the reason. `missing` keeps the sentence of I1a. `reconnect` of a `member` need: \"Reconnect <provider>: your connection does not grant what this app needs.\" `reconnect` of an `org` need (an approved install, an org row that lacks scopes): \"Ask an admin to reconnect <provider> with the scopes this app needs.\" The IDE shows it as an `ask` line with no Connect. <provider> is the connector label. `org_approval`: \"An admin must approve this app before it can use the org account.\" The detail names no other member and no scope. The sidebar `needs_setup` follows the same rule. 

**The I8a Connect step:** each row gains `reason` (`ok`, `missing`, `reconnect`, `org_approval`). `met` is true only when the door would meet the need for the DRAFT of the owner, so an `org` need reads `org_approval` whatever the org rows hold. Each row also names its account (`as`). This closes the known limit of I9a. The IDE draws the three sentences (`lib/studio/connect.ts`). 

**With I8b-1a (merged on main):** the line and the ask read one rule, `_need_reason` in `routes/studio/connections.py`, which calls `resolve.need_reason`. So an `org` need of a draft is never `already_met`, and an ask answers the same with an org row and with none. A member need with too few scopes is not `already_met` either.

**Non-goals:** a table, a migration, an account pin, a new route, a change of the connect flow, and any read of a credential. **Demo (rung 7):** an app that needs a mail scope that the member did not grant says Reconnect, and an org need of a draft says that an admin must approve. 

**Known limits:** each owning app asks FIXED scopes in its connect flow, so a Reconnect cannot widen a grant until the lanes that own those flows change them. `can_connect` stays as it was. The GitHub App row writes empty scopes, so a need with scopes on it stays unmet. Zoho records the requested set, not the granted one. Provider stores differ in the form of a scope. Outlook calendar stores the raw `scope` of the token answer (`calendar_sync/outlook.py`), which can read `https://graph.microsoft.com/Calendars.ReadWrite` or `Calendars.ReadWrite`, and the owning app itself normalizes before it compares. Google Drive stores the full URL strings (`kb_sources/google_drive/auth.py`). The compare is literal (the owner chose it), so an author must write the stored form of the provider. An author who writes one form never meets a row that holds the other. The code does not change. A later slice may add a normalizer for each provider.

**Tests:** `test_package_host_resolve.py` (the truth table), `test_studio_action_door.py`, `test_studio_connect_in_place.py`, `test_studio_connection_ask.py`, `test_studio_connection_ask_r8.py` (R8), `test_studio_connections_whose_r8.py` and `test_studio_scope_match_r8.py` (R8).
