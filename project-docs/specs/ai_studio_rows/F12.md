### Non-goals

- **No live model call in a test.** Each test injects the runner and the meter, as F4b does. No test and no eval calls the production Router.
- **No widening.** A repair never adds an action, so it never adds a write action. It changes no key of the body other than `instructions` and `actions`.
- **No auto-publish.** A repair is a proposal. Only the approve of the member writes a version.
- **No start by itself.** A repair starts only when the member asks for it. A failed run writes a row and offers nothing.
- **No repair of the skill of another member.** Only the owner repairs a skill. D187 level (b) for a skill is a later slice.
- **No thumbs-down signal.** `POST /chat/feedback` writes an audit event that names no skill. F12 does not read it.
- **No feed to the failure store.** A skill run can fail because a platform tool fails. That failure can also reach TOF-2b, through the TOF-2b capture seam. That is TOF-2b work.
- **No retention job.** A later slice decides how long a row stays.
- **No Studio page control.** The chat is the one surface of F12.

### Not a second store

Nothing keeps the reason of a failed skill run, or its input, today. The TOF-2b store does not cover it (`tool_failure_log.md` on PR 2591):

- Its fingerprint is a hash of the platform tool name, a failure code, the exception type and the code site. It holds no message, argument, result or tenant (§0 item 2, §3.2).
- Only counts and code facts cross a tenant (§10.1).
- A Studio skill or action gets the value `studio`, because a skill name is tenant data (§3.2). So the built-in tool set never holds an F3 skill pack, and no row names a skill id or a version.
- `failure_events` (§5.1) holds no argument, no input and no skill outcome. Error text leaves a tenant only on a consent card (§8).

So `studio_skill_runs` is the ONE store of skill runs. It shares only the pointer `run_id` with `failure_events`. Its shape follows `user_tool_runs` of `agent_sandbox.md` §7.3 (`repair_of`, a closed failure code). That table is for code tools, and SBX-1 builds it. A skill is no package, so the two tables stay apart.

### The table `studio_skill_runs` (F12a)

One row for each run of a skill: a live turn, a test, or a repair proposal. A row never changes after its INSERT.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | Primary key, `gen_random_uuid()` |
| `organization_id` | `uuid` | Not null. `REFERENCES organization (id) ON DELETE CASCADE`, then `DEFAULT current_setting('app.tenant_id', true)::uuid`, as in 320. FORCE RLS, with one policy that has USING and WITH CHECK |
| `skill_id` | `uuid` | Not null. FK `(organization_id, skill_id)` to `studio_skills (organization_id, id)`, `ON DELETE CASCADE` |
| `version` | `int` | Not null, 1 or more. The version that ran. For a proposal, the base version that it changes |
| `kind` | `text` | Not null. `live`, `test` or `proposal` |
| `passed` | `boolean` | Not null |
| `reason` | `text` | Not null. A code that matches `^[a-z_]{1,32}$`. `skill_runs.REASONS` holds the closed set. **This column keeps the reason of each failure** |
| `detail` | `text` | Not null, default `''`, at most 300 characters. Names only: a tool, an action, a key or an error class. Never a value |
| `body_key` | `text` | Not null, `^[0-9a-f]{64}$`. The repair key of the body that ran |
| `input_hash` | `text` | Null, `^[0-9a-f]{64}$`. Set on a `live` row and a `proposal` row. Never the input |
| `writes` | `jsonb` | Not null, default `'[]'`. At most 10 items `{"action": ..., "keys": [...]}`, at most 4096 bytes. Action names and key names only |
| `repair_of` | `uuid` | Null. On a proposal, the `id` of the failed live row |
| `test_id` | `text` | Null. On a test row, the id of the F4 test |
| `run_id`, `thread_id` | `text` | Null. Pointers to the agent run and the chat thread |
| `credits` | `numeric` | Null. The spend of a test row or a proposal |
| `created_by` | `text` | Not null, lower case. The member of the run |
| `created_at` | `timestamptz` | Not null, default `now()` |

- **CHECKs.** `kind = 'proposal'` exactly when `repair_of` is not null. A `live` row has an `input_hash`. A `test` row has a `test_id`. `writes` is a JSON array.
- **Indexes.** `(organization_id, skill_id, created_at DESC)`. A unique partial index on `(organization_id, repair_of) WHERE kind = 'proposal'`. A unique partial index on `(organization_id, skill_id, run_id) WHERE kind = 'live' AND NOT passed`, so one run of a skill has at most one failed live row. A NULL `run_id` never collides in a unique index. So a `live` row always carries a `run_id`, and a CHECK (`kind <> 'live' OR run_id IS NOT NULL`) says so.
- **Immutable.** A trigger refuses each UPDATE for each role, as `studio_skill_versions_immutable` of 320 does. A DELETE stays legal for the cascade and the purge.
- **The member purge.** `routes/admin/members.py` gets one `_PersonRows` entry on `created_by` in the bound org, beside the `studio_skills` entry.
- **The migration.** Take its number at build time with `~/lanes/reserve_migration.sh <lane> 3418` on `metorite-home` (R1). `bash scripts/premerge.sh` checks it again at merge. It only expands (R6): one new table, its keys, one trigger and its RLS. The R8 test finds the file by its content, never by its number.

**The repair key.** `body_key` is the SHA-256 of the canonical JSON of a body, as `skills_store.content_hash` makes it. Before the hash, the key function changes each run of white space in each string to one space. It trims each string and sorts `actions`. So a change of white space alone gives the same key.

**The input hash.** `input_hash` is the SHA-256 of the org id, one NUL byte, and the input text after the same white-space rule. It is a link, not a secret. The row sits under FORCE RLS in the org whose `chat_message` rows already hold the text.

**The reason codes.** `skill_runs.REASONS` holds three sets:

1. All codes of `skill_tests.REASONS`, `passed` included, for a proposal row. A test row takes only the seven skill faults.
2. Three live codes: `tool_error`, `card_declined` and `member_said_wrong`.

A refusal of a proposal before its dry run writes no row, so it needs no code here.

### The writers (F12b)

**The live writer.** A chat run in which `_turn_with_skills` loaded a skill writes one `live` row for each loaded skill, at the end of the run.

- `passed` is true when no signal hit an action of that skill.
- `tool_error`: a tool of an action of the skill raised or answered an error. `detail` holds the tool name and the error class.
- `card_declined`: the member declined the card of an action of the skill. `detail` holds the tool name.
- When both hit, `tool_error` wins.
- `input_hash` hashes the words of the turn. `thread_id` and `run_id` point at the turn.
- `writes` names each write action that the run called, with its key names.
- The write is best effort. A fault logs the error class and never fails the run. The writer opens `tenant_session()` on the bound tenant, as `_turn_with_skills` does.
- The F12b audit names the exact hooks: the skill list of `_turn_with_skills`, the pack tool guard, and the card decision. It also confirms that the hashed words equal the `content` of the `chat_message` row of the member.

**The limit of the live writer.** The hook sees only the calls that go through `_pack_tool`. Some calls leave no signal, so the row reads `passed`:

- A call of a tool in the run base: a workflow action, `tool:crm_change_history`, `tool:crm_search_notes`, or a door-op tool that the member holds.
- A call that a pack refusal answers before the hook. These refusals are held in the turn, the batch write refusal, the pack write refusal and the shape refusal.

A run that ends in an error or a stop also writes `passed` rows. A RESUME run that keeps its `run_id` can write `passed` rows two times. F12c reads failed rows only, so a `passed` row never blocks a repair. When no tool of a loaded skill is a pack tool of the run, its `passed` row holds the code word `unobserved` in `detail`.

The write task has no time limit, and a shutdown does not wait for it. The write is best effort, so a row can be lost.

`agent_sandbox.md` §6.7 says that a refusal is not a signal. That rule starts the repair of a code tool by itself. A skill repair never starts by itself, so a declined card is a record here, not a start.

**The test writer.** The F4b route `POST /studio/skills/{id}/tests/run` writes one `test` row for each result that failed with a skill fault. The faults are `other_action`, `missing_write`, `extra_write`, `field_mismatch`, `invalid_call`, `run_failed` and `call_cap`. A cap code, `bad_test`, `not_run` and `suite_running` write no row, because the skill did not cause them.

A test of a body that is not saved writes no row. The row would name a version that did not run. A row names only the stored version that the suite ran.

Both writers write only for an org on `STUDIO_ORGS` and `STUDIO_SKILL_REPAIR_ORGS`.

### The data flow (F12c)

1. **A failure.** A live turn of the skill fails. F12b writes a `live` row with `passed` false and the reason.
2. **The ask.** The member asks Mira why it failed, or asks her to fix it.
3. **The history.** `studio_skill_list` reads the skill. For an org on the flag, its answer adds the failures of the skill.
4. **The proposal.** Mira calls `studio_skill_repair`. She sends the skill id, the id of the failed row, the new instructions and the actions to remove. She also sends `based_on` from her read.
5. **The checks.** The route checks the contract, the one-repair rule, the repeat rule, the input, the test count and the cap. A refusal spends nothing and writes no row.
6. **The dry run.** The route calls `run_suite` with the proposed body, the tests of the base version and the failed input. The door holds each write.
7. **The record.** The route writes one `proposal` row with the result.
8. **The end-state rule.** Version 2 goes to the member only when the suite passed.
9. **The card.** The tool shows the change on a card, and waits for the member.
10. **The approve.** On `approved`, the tool calls the approve route. The route writes the next immutable `studio_skill_versions` row through `skills_store.add_version`.
11. **The undo.** The member says undo. `studio_skill_undo` calls the F7 undo route, and the old body comes back as a new version.

### The history read

`GET /studio/skills/{id}/runs` gives the owner the failed rows of the skill, newest first. `studio_skill_list` calls it when the org is on the flag.

- At most 10 failed rows: the version, the kind, the reason, the detail, the date and the row id.
- The instructions of at most 3 earlier failed versions that differ from the newest version, each cut to 400 characters. They reach the model inside the untrusted frame (`acb_skills/untrusted.py`).
- A row of another member shows only as a count for each reason.
- No input text, no argument and no value.

### The contract of a repair

`skill_repair.check_contract(base, proposed)` is a pure function of two bodies. It returns a refusal code, or None.

- `proposed.actions` is a subset of `base.actions`. An added action gives `widened`.
- Each key other than `instructions` and `actions` is equal in both bodies. That covers `description`, `cards`, `knowledge`, `tests` and each other key. A change gives `widened`.
- The highest class of the proposed actions is not above the highest class of the base. One read of `catalog_rows` gives each class, as the undo route reads it. A subset cannot raise the class, and the fence keeps the check in place.
- A proposed body with the `body_key` of the base gives `no_change`.

The route passes the tests of the base version as `tests` to `run_suite`. So a repair cannot weaken a test.

### The checks before the dry run

The route keeps this order. A refusal spends nothing, writes no row, and leaves the one repair of the run unused.

1. `STUDIO_ORGS`, `STUDIO_SKILL_TESTS_ORGS` and `STUDIO_SKILL_REPAIR_ORGS`. An org outside one of them gets 404.
2. The request shape. A bad request gets 422.
3. The owner check. A member who is not the owner gets 404.
4. The failed row. It must be a `live` row of this skill, with `passed` false and `created_by` the caller. Else 404.
5. **One repair for each failed run.** A `proposal` row with this `repair_of` gives 409 `already_repaired`. Each proposal row counts, whatever its result, because each one spent credits.
6. The skill did not move. The `version` of the failed row must equal `current_version`. Else 409 `skill_changed`.
7. The contract. A refusal gives 422 with its code.
8. **No repeat.** A failed row of this skill with the proposed `body_key` gives 409 `repeat_change`. Only a failure of the skill counts here. That is a live code, or one of the seven skill faults of the test writer. Check 5 alone counts a stop for a cap or a meter fault. It also counts the time limit, an unloaded skill and an unarmed door.
   `run_failed` is not a skill fault for the repeat check until F4b gives a time limit its own code. F4b gives `run_failed` to a time limit and to a runner exception too (F12a, `skill_runs.REPEAT_REASONS`).
9. The input. The route reads the newest 50 messages of the member in `thread_id`. RLS and the member check of the session bind the read. It takes the message whose hash equals `input_hash`. No match gives 409 `input_gone`. A text over 2000 characters gives 409 `input_too_long`.
10. The tests. The base tests and one input must fit `MAX_RUN` (5). Else 409 `too_many_tests`.
11. The cap. When `flags.skill_tests_cap()` returns None, the route gives 409 `cap_unset`.

**"It was wrong".** The member can say that a run of the skill gave a wrong result when no failed row exists. Then the tool names the newest `live` row of the skill with `passed` true, by the caller, in the last 24 hours. The route runs checks 5 to 11 with the pointers of that run. When each check passes, it writes a new `live` row with `member_said_wrong` and the same pointers, just before the dry run. That row is the failed row of the repair.

The unique index on failed live rows allows one such row for each run. So this path cannot give one run a second repair.

### The end-state rule

The record of the dry-run door decides, never the words of the model. The route calls:

```
run_suite(org=<session>, member=<session>, skill_id=id, body=proposed,
          tests=<the tests of the base version>, inputs=(<the failed input>,),
          runner=agent_runner, meter=console_meter)
```

- Version 2 goes to the member only when `SuiteResult.passed` is true. Then each F4 test of the base passed, and the failed input passed the action rule and the schema rule.
- `passed` comes only from `skill_tests.evaluate`, which reads the record. No parameter of the rule holds text.
- The `proposal` row holds `passed`, the first reason that failed, its detail, the held write actions of the input run, the credits and the `body_key`.
- **A known limit.** The input-only run proves the two invariants. It cannot prove the fix of a fault that the dry run cannot show, such as a refusal by the real tool. When the held writes of version 2 name the same actions as the failed run, the card says so. The check reads action names only, and `skill_repair.write_name` gives each side its chat tool first.
- **A skill with no tests.** Only the failed input runs, and the card says so.
- **A crash.** The route writes the proposal row after the suite. A crash between the two leaves no row, and then a second repair of that run can spend again. The cap and the F4b slot of 360 seconds limit that spend.
- **The wait.** A suite can take 300 seconds. The tool waits on the route for at most 330 seconds. The F12c audit confirms that the chat run allows that wait. If it does not, the audit narrows the slice before the build.
- **A known risk of the wait (accepted).** The Tier 2 fallback shim stops a tool after 300 seconds (`COPILOT_TOOL_TIMEOUT_SECONDS`). Then the route can still spend the credits and write the proposal row. The one repair of the run is used, and no card shows. The audit item of the wait names this risk.

### The approve and the undo

**The card.** The tool builds the card with `_card` of `studio_tools.py`, THE one builder of a skill card. The card shows the removed actions in full, the new instructions as long text, and one line of results. It shows for each repair, also in an open chat, as the publish card of `_publish_after_card` does.

**The approve route.** `POST /studio/skills/{id}/repairs/{proposal_id}/approve` takes `{expected_version, instructions, remove_actions}`.

- It locks the skill `FOR UPDATE`, as the undo route does.
- It gives 409 when the proposal did not pass. It gives 409 when `current_version` is not `expected_version`, or is not the base of the proposal.
- It builds the body again from the base version. A `body_key` that is not the key of the proposal gives 409.
- It runs the body checks and the catalog check, as `POST .../versions` and the undo do.
- It writes the version through `skills_store.add_version`. `created_by` is the caller.
- The skill keeps its state, in the same transaction. A published skill stays published, and a draft stays a draft. `POST .../versions` moves a published skill to `draft`. Here the approve of the owner is the publish of that version (D180.2).
- On a shared skill, `shared_version` does not move. The other members keep the approved version until a holder of `studio:publish` approves the new one (J2c, migration 463).
- A second approve gets 409, because `current_version` moved.

**The decision of the card.** The tool calls the approve route only on `approved`. On `revised`, `stopped` and `no_card`, it calls nothing and writes nothing.

**The undo.** The chat tool `studio_skill_undo(skill_id, expected_version)` calls the F7 route `POST /studio/skills/{id}/undo`. It adds no undo rule. The F7 rules stand: version N+1 copies the body of N-1, and a published skill returns to `draft`. So after an undo, the member publishes again.

### The flag, the cap and the spend

- **`STUDIO_SKILL_REPAIR_ORGS`.** A comma list of org ids, and `*` lists every org. The default is empty. With it empty, no writer writes a row, and the history read and each repair route answer 404. Its one reader is `gateway.routes.studio.flags.skill_repair_allowed`. It is an `*_ORGS` key, so a SIGHUP reload applies a change (`docs/flag_reload.md`). The BUILD PR of F12b adds its paragraph to `docs/flag_reload.md`. This docs PR does not. A flip is OWNER-GATE (`enforcement-flip`). Only the owner flips it, because a repair spends credits.
- **The cap.** A repair uses the F4b cap `STUDIO_SKILL_TESTS_CAP_CREDITS` and its one reader `flags.skill_tests_cap`. With no value, each repair refuses with `cap_unset` before any model call. F12 adds no second cap.
- **One suite at a time.** The F4b slot of each member holds for a repair too. A second suite gets 429 `suite_running`.
- **No model call of its own.** Mira writes version 2 as the arguments of the tool, inside the chat turn. Only the dry run spends, under the cap.

### The words

**The result text of the tool.** The schema room of the chat tools is small (`SCHEMA_TOKEN_BUDGET = 30_000` in `evals/one_assistant_measure/checks.py`). So each new tool has a description of one sentence, and its guidance goes in the result text.

- The result text holds at most 1188 characters.
- Its first 400 characters hold the outcome and the next step of the member. A cut never reaches them.
- The rest holds the reason of each failed test, the removed actions and the results line.
- A cut takes the tail first and ends with "and N more".
- The figures 1188 and 400 come from the TOF-3a brief. The F12c build measures them again.

**The words of the member.** Plain English, with no internal name: no "dry run", "proposal", "F4", "body" or "suite". Each failure says what happened and what the member can do. The model may reword a line. The tool gives these lines as the base:

### Decisions (conservative defaults, for the owner to confirm)

- **D-F12-1, when a repair starts.** Only on the ask of the member. A failure offers nothing and starts nothing.
- **D-F12-2, who repairs and approves.** The owner of the skill, on a failed run of the owner. A failure of another member shows as a count.
- **D-F12-3, how far back the read goes.** 10 failed rows, and the instructions of 3 failed versions. The repeat check reads each row of the skill.
- **D-F12-4, the tests.** A repair keeps the tests of the base version and runs each one. It adds no test from the failed input.
- **D-F12-5, the keys a repair may change.** `instructions`, and the removal of an action. Not `description`, because the description decides when a skill loads (TOF-1c).
- **D-F12-6, approve and publish.** The approve keeps the state of the skill, so a published skill stays published. The F7 undo still returns a skill to draft.
- **D-F12-7, too many tests.** A skill whose tests and the failed input need more than 5 runs cannot get a repair. F12 does not raise `MAX_RUN`.
- **D-F12-8, no tests.** A skill with no tests can get a repair on the failed input alone. The card says so.
- **D-F12-9, the hash.** A SHA-256 with the org id and no secret key. A keyed hash needs a new secret, and a secret is an owner gate.
- **D-F12-10, a declined card.** It records `card_declined`, and it starts nothing.
- **D-F12-11, "it was wrong".** The words of the member in the chat are the signal. The thumbs-down is not wired.
- **D-F12-12, a refused proposal.** A refusal before the dry run does not use the one repair of the run. Only a proposal that spent credits uses it. F12c runs the load check of the skill pack (`skill_packs.build`) in check 7, before the dry run. So a proposal that the pack builder refuses gets 422 and writes no row. D-F12-12 and check 8 now agree: only a proposal that ran uses the one repair.
- **D-F12-13, a stop that is not a skill fault.** A proposal that stopped for a cap, a meter fault or the time limit still uses the one repair, because it spent. It does not count as a failed change for the repeat check.
