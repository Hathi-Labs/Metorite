# AF-10b-3

Tier: STD

Gate: AGENT-SAFE. After AF-10a. The owner turns the pack on

## What

🔨 **BUILT, dark (2026-11-14, task 3292).** **A chat tool for saved views.** One tool, `studio_view_manage(op, package_id, object, view_id, name, spec, shared, position, offset, limit)`, with the ops list, save, update (name, spec, position, share and unshare) and delete. It sends the four routes of AF-10a as the member over HTTP, with no identity argument and no SQL. The studio packs sit at `MAX_REQUEST_TOOLS`, so the tool is the one tool of the new pack `studio-views`. That pack is NOT in `tool_packs.FOLLOWS`, so it ships dark. The `TOOL_PACKS` line that turns it on is owner-only. **The card rule** (`_view_needs_card`): a share, an unshare, and a change or a delete of a shared view always show one card, because every member reads the name and the spec. That card shows each filter condition as `«field» op «value»`, the sort, the layout and the columns, from the body or else from the current spec. A value over 300 characters, or a hidden character in a held chat, gives no card. Conditions that together pass one card give no card. An unshare card says that only the owner reads the view after it, and each card row is a `key: value` line that the chat card draws as a row. A write of a private view shows a card only where `_must_ask()` says so (RX-1, D169). `list` needs `object`, pages with `paged`, frames each name and filter value in an `UntrustedFrame`, with each hidden character left out, and explains `dropped`. A viewer who shares gets the sentence "This app is shared with you to read, so only its owner shares a view." **Non-goals:** no UI, no route, no migration, no `studio_describe` part, no edit of `studio-more`, no production `TOOL_PACKS` edit, and no COVERED parity row (they land with AF-10b-2). Fences: `test_studio_view_tool.py`, `test_studio_view_tool_r8.py` (R8). Demo: with the pack on, the member says "share my Open orders view", sees one card, approves it, and a viewer reads the view
