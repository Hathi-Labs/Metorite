## What

The human step node: a task in `pm_tasks`, and a wait until it is done. 🔨 **BUILT, dark (2026-11-13), backend only.** The node type is `human_step`, with a literal `assignee` (a member email), a `title` and an optional `description`. The task goes into the personal project of the assignee, with `announce=False`, so it needs no project grant and starts no event. The assignee must be an active member of the org of the run. The task carries `origin.kind = workflow_run` with the run id, and the pause row (reason `task`, migration 427) carries the task id. `scheduler.scan_done_tasks` reads the task in the org of the run. A done stage resumes the run once, through the compare-and-set of `resume_run`. A cancelled task ends the run `failed`. The default personal tree has no cancelled lane, so a trash that stood for 60 seconds (My Tasks keeps a 7 second Undo), an archived or merged task, a deleted task, a cancelled lane and an assignee who left all count as cancelled. A done task wins over an archive, and a trash wins over a done lane. The assignee stays the creator of the task, so the assignee may move or delete it. The assignment and the "Captured" line name `system:workflow:<id>` as the actor. A refused hold reports `failed` to the feed and to the health streak. The node stays dark until the owner lists the org in `WORKFLOW_UNATTENDED_ORGS`. WFC-4a-1 adds its palette item and its form. Fence: `tests/unit/test_workflows_human_step.py` and `test_workflows_human_step_r8.py`. 🔨 **BUILT (2026-11-13, STU-E4b, task 3120): the steps of a run.** `GET /workflows/runs/{run_id}/steps` lists the human steps of one run in walk order, with `node_id`, `title`, `assignee`, `state` (`pending`, `done`, `cancelled` or `not_reached`) and `task_id`. The walk order comes from `acb_common.planning.analyze_plan`. A graph with a cycle gives the block-list order. A graph over 500 blocks gives the block-list order (`MAX_WALK_BLOCKS`). The title and the person come from the literal config of the graph that the run pinned. A test run of a draft that has no pause yet reads the published version, so its list can differ from the draft that ran. The state of a pending step reuses `read_task` and `task_outcome`, and the route reads the run, its pauses and each task in one tenant session. A rejected pause reads `cancelled` on a failed run and `done` on a run that `resume_run` cancelled after a done task. The route then reads no task, so a later change to the private task changes no answer. One answer holds at most 200 steps (`MAX_RUN_STEPS`), and `truncated` marks the rest. The access is the access of `GET /workflows/runs/{run_id}`. A run of another org, an unknown id and a bad id get the same 404. The route is live for each org with `feature:workflows`. It shows human steps only where `WORKFLOW_UNATTENDED_ORGS` lists the org, because only such an org runs a human step. **The privacy rule:** this route gives the task id only to the person of the step, and only while the task exists. Each other reader gets the state word and nothing else of the task. The chat read is the `run_id` mode of `studio_workflow_read` (STB-6a, the `studio` pack). It is not a tool of its own, because the pack is at its room limit of 23 tools. It calls the route as the member. It puts the list in one untrusted frame, because each title, node id and person is text that other members wrote. The Checklist block (D9) adds the parity row when the UI sends the request. Fence: `tests/unit/test_workflows_run_steps.py` and `test_workflows_run_steps_r8.py`. **Open:** an expiry for a task that stays open (no task seam holds a deadline, and `PARK_LIFE` is for decisions), a role as assignee, `{{ref}}` text in the title, and a due date. **A known gap, not fixed here:** `GET /workflows/runs/{id}` and the run stream also show the task id of a done step in `node_results` (`runner.py`), to each reader of the run

## Done when

The run resumes once when the task moves to done. A cancelled task fails the step
