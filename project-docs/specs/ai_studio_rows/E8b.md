# E8b

Tier: HIGH

Gate: AGENT-SAFE for code. After E8a. A new flag, and the owner flips it. STU-Q14

## What

**The `studio_batch` node and the run.** A new workflow node type that follows an approval DIRECTLY, as `studio_write` does (B2c-2d). The park freezes the list through E8a and binds the list digest to the one approval. `run_workflow_batch` sits beside `run_workflow_write` and reuses its steps. **One resume way, chosen here: a new run of the node over the SAME open batch.** A stop inside a chunk leaves the run `running`. `reconcile_orphaned_runs` fails a `running` run at boot, but only for an org on `WORKFLOW_UNATTENDED_ORGS`, and not at all when `WORKFLOW_SCHEDULER_ENABLED` is off. So no pause exists to resume, and the design adds none. The node runs its chunks one after the other, each in its own session. A stop leaves the run `failed` and the batch `open`, with its pending items. **Both gates.** The park and the scan need the E8b flag AND the org on `WORKFLOW_UNATTENDED_ORGS`, as the human step does. The park refuses an org that is not on that list, so no batch opens for it. **The scan must check the approval.** A batch `open` with a `failed` run is NOT enough, because the park opens the batch BEFORE the decision, and some paths set a parked run `failed` with no yes. Examples are `_fail_unresolved_write`, a hold that the system refuses, and a second read of the decision that refuses. The scan AND the new run both re-read the bound decision (`park.outcome_of` or the broker row), and both need a yes. A reject or an expiry sets the run `cancelled`, which is safe. **One resume at a time.** The scan rebinds `studio_batches.run_id` from the old run to the new run with a compare-and-set, `UPDATE ... WHERE run_id = :old`, as `resume_run` claims its pause. A pass that updates no row starts no run. So two passes cannot start two runs. The rebind is a nullable-column change, and so expand-only. **The source.** The new run reads the source list again and builds the writes. It refuses when the digest differs from the stored one (`DigestMismatch`). So E8b supports ONLY a source that stays the same for the life of the batch, such as an attachment or a frozen input. A source that the batch changes itself (set `status` to paid where `status` is due) would differ at the second read and fail for good. The park refuses such a source. E8b does not store the frozen list, because a copy outside the object store skips the C9 rules. **What the new run does.** It starts AT the batch node, finishes the chunks, and then runs the nodes AFTER it. The failed run never reached them. **The end of a stuck item.** `StoreBusy` and a timeout are retried a few times, with a bound on the number of resumes. After the bound, E8b records a code on the item that blocks. It does this through a store call that marks that item `failed` with `query_timeout`. A `StoreBusy` that came from `apply_writes` leaves the transaction usable, and the earlier groups keep their writes, so E8b may commit them first. The read view of E8c shows the reason. The batch then ends `failed` and no scan picks it up again. **E8b must test:** a kill at item 120 of 300, then a boot, then the scan, ends with 300 records, one for each key. A second scan of a `done` batch starts no run. A changed source refuses the resume and writes nothing. A run that failed with no yes is never resumed. Two scan passes start one run. An org off the unattended list gets no batch. An item that always times out ends `failed` after the bound. One approval card exists for the whole run. **Chunking is INSIDE the node.** The graph stays a DAG. **Rejected:** a graph loop over `studio_write`. It needs the iteration state of `workflows_app.md` §8.3c (E2) and one approval for each pass, so it breaks "one approval for one run".

## Done when

A run of 300 items stopped at item 120 resumes and repeats none. One approval covers the whole list. A change of the list after the approval refuses the run (the digest)
