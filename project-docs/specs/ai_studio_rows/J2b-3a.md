## What

🔨 **BUILT, dark (2026-11-13, task 3090).** **The chat twins of the approval routes.** Four tools in `acb_skills/studio_tools.py` send the four routes of J2b-1 as the member of the run: `studio_request_approval(package_id, version)`, `studio_list_approvals()`, `studio_approve(package_id, version)` and `studio_reject(package_id, version)`. No tool takes an org, a member or a confirm argument (R5). The route checks each right, and the tool checks none. Each tool checks the id (a UUID) and the version (a whole number from 1 to 2³¹−1, never a bool) before the call. The four tools are their own tool pack, `studio-approvals`. It follows the `studio` pack (`FOLLOWS`), with the same owner. The `studio` pack is at its room limit (23 tools, STB-6a), so the new pack loads by its own words only and never by the Studio surface. The list gives each pending row with the package id, the name, the version, the owner, the publisher, who asked and when, the manifest hash and the count of parts. So the approver can read what they approve, each row also holds the start of its manifest as JSON text. The rows share 12 000 characters. Each row shows at most 6 000 characters of its manifest, whatever the count of pending rows, so a manifest that the list cuts once is always cut. `manifest_cut` is true on a cut row, and a row that does not fit is skipped (`truncated`). A later row that fits is still shown, so a large row never hides the rest. The rows sit in an untrusted frame. **Review fix round 1:** `studio_approve` and `studio_reject` ALWAYS show one card, in a clear chat too, like the delete of an app. The list puts text of another member in the chat, and neither move can be undone: a rejected version stays rejected. Both tools are `destructive`. The rules say: call each only when the member asks, in this chat, to approve or to reject that version. **Defaults, owner to confirm at the preview:** (1) The card shows the name, the version, the owner, who asked and the manifest hash. (2) The ask and the list show no card. The ask is the owner's, and a second ask changes nothing. (3) A 404 of the approve and the reject names each cause in one sentence, because the route gives no message. (4) Default (a), owner to confirm at preview: approve refuses in chat when the manifest was cut, or when the list left the row out. Each refusal has its own sentence. The cut is the same with one pending row or many. Option (b): the card shows a summary built from the FULL manifest (actions, data classes, counts of parts)
