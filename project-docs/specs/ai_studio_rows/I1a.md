# I1a

Tier: STD

Gate: AGENT-SAFE. A flip of the flag is gate `enforcement-flip`, after the pre-check

## What

🔨 **BUILT, dark (2026-11-14), task 1197.** Backend only: no UI, no card, no migration, no table and no route. **The flag:** `STUDIO_CONNECTION_GATE_ORGS`, empty by default, `*` for every org. Its one reader is `acb_common.studio_flags.connection_gate_on`, and a SIGHUP reload applies a change (`docs/flag_reload.md`). With the org off the list, `connections` changes nothing: `needs_setup` and the door are as before I1a, and nothing reads the registry. The resolve takes the org from the bound tenant, and the door takes the org of the session. The validator below is not behind the flag. ⚠️ **Before a flip, an operator does a pre-check.** Count the rows of `apps` and of `app_versions` in production whose manifest holds a `connections` list that is not empty. Each such app loses all of its actions in a listed org until each of its names has a connected row. The registry cannot hold `mailbox`, `whatsapp` or `gmail`, so an app that names one of them stays `needs_setup` until IN-11 and I9 land. The owner must not flip the flag for an org that holds such an app. A flip is gate `enforcement-flip`. **The manifest:** `studio_manifest._check_connections` refuses a name that is not `mcp:<server>` or a provider id (`CONNECTION_NAME_RE`), a name used twice, and more than 32 names (`MAX_CONNECTIONS`). Each refusal has a path and one sentence. The validator also refuses a field whose key names a secret (`secret_shapes.is_secret_field_key`: a name of `SECRET_FIELD_NAMES` as whole segments, so `token_number`, `secretary` and `credential_expiry` pass), and the sentence points to `connections`. The schema export does not change. The sample of §3.6 and of `test_studio_manifest.py` now names `mcp:tally` and the door op `crm.log_activity` in place of `whatsapp` and `integration:whatsapp.send_template`, because §8.1 rule 10 holds until IN-3. **The read:** `connections/store.met_providers(db, org, member)` reads the providers of the `connected` rows: each org row, and each member row of that member. The row of another member, `needs_reconnect`, `needs_reset` and `disconnected` never count. It reads no blob. `package_host/resolve.met_connections` is its one caller: it reads the bound org of the session, never an org of the caller. A `mailbox` is not in the registry, so I9 adds it. **The resolve:** `connections_met` is the one rule, and `needs_met` calls it. `resolve_for` reads the set ONCE, and only when a kept install names a connection, so `/auth/me` pays nothing for an app with none. `needs_setup` stays computed and never stored (`package_host.md` §5.1 decision 1). `NEED_KINDS` does not change, so `connections` is the one place of a connection need. `connection_names` is the pure reader that IN-10 reuses. **The door:** `invoke._check` refuses each action with 409 `needs_connection`, before the declaration, next to `package_paused`. The draft decides for the owner, and the installed version for a viewer. A `preview=1` object action stays open, so the IDE works while the member connects. `run_as_read` refuses the same way with the set of the `run_as` member, never of a caller. The audit row holds the code. Until I8, `realDoor.ts` shows the 409 as the general `ACTION_FAILED`, so the member gets no next step. **Tests:** `test_studio_manifest.py` (the grammar, a duplicate, the cap and a secret field key, each with a path), `test_package_host_resolve.py` (the rule, and no statement for an install with no connection), `test_studio_action_door.py` (`TestTheConnections`), `test_studio_run_as.py` (section 3b), `test_flag_reload.py` (the reload of the flag), an `_off` test in each suite (the flag off changes nothing and reads nothing), and the R8 suites `test_package_host_resolve_r8.py` (section 12: two orgs, two members, `needs_reconnect`, one read of the registry), `test_studio_action_door_r8.py` (section I1a) and `test_studio_run_as_r8.py` (case p)

## Done when

In an org that `STUDIO_CONNECTION_GATE_ORGS` lists, an app with a missing connection installs with `needs_setup: true`, computed and never stored (`package_host.md` §5.1 decision 1), and runs no action. In an org off the list, nothing changes and nothing reads the registry. "Needs a connection" stays the text of the card (I8). R8: a row of org A meets no need of org B, and the row of member X meets no need of member Y
