# C10a

Tier: HIGH

Gate: AGENT-SAFE. The deploy applies the migration, not the builder

## What

🔨 **BUILT, dark (2026-11-13, task 3092).** **The org caps.** An org holds at most 1,000,000 records and 2 GiB of record JSON. **Migration:** `435_studio_org_usage.sql` (the number is taken at build time, so check it again at merge, R1). It adds the gauge table `studio_org_usage`: one row for each org, with `records`, `bytes` and `updated_at`, FORCE RLS and the bound tenant DEFAULT. Three AFTER statement triggers on `studio_records` (INSERT, UPDATE and DELETE, each with a transition table) keep it exact for each writer: the store, `purge_records`, `drop_object`, the cascade of `delete_package`, raw SQL and old code in the deploy window (R6). The INSERT trigger upserts. The UPDATE and DELETE triggers only update, so the cascade of an org delete never puts a row back. The migration fills the gauge from the records that exist, under `LOCK TABLE studio_records IN SHARE MODE`, and a second run changes nothing. **The check.** `_run_steps` reads the row under the org lock before the writes, and again after the writes and the roll-ups. It refuses the batch with `OrgCapReached` (a `BudgetExceeded`, code `org_cap_reached`) only when the org is past a cap and the batch raised that count (the D108.5 idiom). The SAVEPOINT writes nothing. The door answers 422 `org_cap_reached` with one sentence: "This organization holds 1,000,000 records, the most it can hold, so delete records that you do not use." or "This organization holds 2 GiB of records, the most it can hold, so delete records that you do not use." **Not in C10a:** a history row does not count (owner decision, C10b). No credit and no ledger, so D19.3 and D32.5 do not apply. Other callers of `apply_writes` (the chat tools and the workflow write) see the sentence through their generic error path.

## Done when

A create past a cap gets 422 `org_cap_reached` and writes nothing. At the cap a delete and a smaller update pass. The gauge equals `count(*)` and `sum(octet_length(data::text))` after each writer, and two orgs never share a row. An org delete works. Two writers at the cap on two connections give exactly one pass. The backfill is exact and idempotent.
